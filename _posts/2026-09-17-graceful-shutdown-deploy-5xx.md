배포는 성공으로 끝났는데 그 2~3분 구간에만 5xx가 몰려 찍힙니다.
롤백하면 사라지고, 다시 배포하면 또 생깁니다.

코드에 원인이 없으니 찾을 수가 없습니다. 실제로 코드의 문제가 아니기 때문입니다.
문제는 **프로세스가 죽는 순서**에 있습니다.

## 에러는 '살아 있는 요청'이 끊겨서 난다

롤링 배포에서 구버전 인스턴스가 빠질 때, 그 인스턴스를 향해 이미 출발했거나 처리 중이던 요청이 있습니다.
이 요청들이 어떻게 되느냐가 배포 중 에러율의 거의 전부입니다.

끊기는 경로는 세 가지입니다.

- **로드밸런서가 아직 모른다.** 프로세스는 종료 신호를 받고 리스닝을 닫았는데, LB는 그 대상을 여전히 정상으로 알고 새 요청을 보냅니다. 연결이 거부되고 502가 나갑니다.
- **처리 중이던 요청을 버린다.** 종료 신호를 받자마자 `process.exit()`을 부르면 응답을 절반쯤 쓰다 만 소켓이 그대로 닫힙니다.
- **keep-alive 커넥션을 서버가 먼저 닫는다.** LB가 재사용하려고 붙들고 있던 유휴 커넥션을 서버 쪽에서 끊으면, 그 커넥션에 실릴 다음 요청이 실패합니다. 이건 배포와 무관하게 상시로도 납니다.

셋 다 "종료 처리를 안 해서"가 아니라 **"종료 처리를 잘못된 순서로 해서"** 생깁니다.

## 지켜야 하는 것은 부등식 하나다

종료 절차를 아무리 길게 써도, 결국 만족해야 하는 조건은 하나로 줄어듭니다.

> LB가 이 인스턴스로 **새 요청을 보내지 않게 된 시점**이,
> 애플리케이션이 **리스닝 소켓을 닫는 시점**보다 앞서야 합니다.

이 순서가 뒤집히면 앞의 첫 번째 경로가 열립니다. 그리고 기본 설정만으로는 이게 보장되지 않습니다.

보장되지 않는 이유는 두 계층이 서로를 기다리지 않기 때문입니다.
오케스트레이터는 컨테이너에 종료 신호를 보내고, 로드밸런서는 헬스체크 실패나 등록 해제 요청을 자기 주기로 처리합니다.
헬스체크가 몇 초 간격으로 돌고 몇 번 연속 실패해야 대상을 빼주는 구조라면, 그 전파에 걸리는 시간만큼 창이 열립니다.

> 종료 신호와 등록 해제 중 **무엇이 먼저 일어나는지는 플랫폼마다 다릅니다.**
> Kubernetes는 엔드포인트 제거와 파드 종료가 병렬로 진행돼서 `preStop`에 대기를 넣는 관용구가 굳어졌고,
> ECS는 서비스 스케줄러가 대상 그룹에서 먼저 등록을 해제합니다.
> 다만 **어느 시점까지 기다린 뒤 신호를 보내는지**는 쓰는 플랫폼의 현행 공식 문서에서 직접 확인하세요. 이 값에 절차 전체가 걸립니다.

플랫폼 동작을 정확히 모르는 채로도 안전하게 만드는 방법이 있습니다.
**애플리케이션이 스스로 유예 구간을 만드는 것**입니다. 이러면 순서가 어느 쪽이든 부등식이 성립합니다.

## 죽기 전에 먼저 아파야 한다

그래서 종료 절차는 "즉시 종료"가 아니라 이 순서가 됩니다.

```text
종료 신호 수신
  │
  ├─ 1. 헬스체크를 실패로 전환한다 (리스닝은 유지)
  │      → LB가 이 대상을 빼기 시작한다. 이 동안에도 들어온 요청은 정상 처리한다.
  │
  ├─ 2. 전파에 걸리는 시간만큼 기다린다        ← 여기가 핵심
  │
  ├─ 3. 리스닝 소켓을 닫는다 (새 연결만 차단)
  │
  ├─ 4. 처리 중인 요청이 끝나기를 기다린다
  │
  └─ 5. DB 풀·브로커 연결을 닫고 종료한다
```

2번 구간을 흔히 lameduck이라고 부릅니다. 살아는 있지만 새 일감을 받지 않겠다고 광고하는 구간입니다.
이 구간이 없으면 1번과 3번이 사실상 동시에 일어나서, 헬스체크를 내린 의미가 없어집니다.

기다릴 시간은 **LB가 대상을 빼는 데 걸리는 최악의 시간**에서 옵니다.
헬스체크 주기 × 실패 판정 횟수에 여유를 더한 값이 출발점이고, 등록 해제를 먼저 하는 플랫폼이라면 그만큼 짧아도 됩니다.

## Node.js로 쓰면

핵심은 상태 플래그 하나와, 순서대로 진행되는 종료 함수입니다.

```typescript
import express from "express";

const app = express();
let accepting = true;

// LB가 보는 엔드포인트. 프로세스 생존이 아니라 '트래픽을 받을 의사'를 답한다.
app.get("/healthz", (_req, res) => {
  res.status(accepting ? 200 : 503).send(accepting ? "ok" : "draining");
});

const server = app.listen(3000);

// LB 유휴 타임아웃보다 길게 잡는다. 이유는 아래 절에서.
server.keepAliveTimeout = 65_000;
server.headersTimeout = 70_000;
```

`/healthz`가 프로세스 생존이 아니라 **트래픽을 받을 의사**를 답한다는 점이 중요합니다.
살아 있으면 무조건 200을 주는 헬스체크로는 이 절차를 만들 수 없습니다.

종료 핸들러입니다.

```typescript
const DRAIN_WAIT_MS = 15_000;   // LB가 대상을 빼는 데 걸리는 시간
const SHUTDOWN_MAX_MS = 25_000; // 이 안에 못 끝내면 강제 종료

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

let shuttingDown = false;

async function shutdown(signal: string) {
  if (shuttingDown) return;       // 신호가 두 번 와도 절차는 한 번만
  shuttingDown = true;
  console.log(JSON.stringify({ msg: "shutdown:start", signal }));

  // 1) 헬스체크만 내린다. 아직 리스닝은 살아 있다.
  accepting = false;

  // 2) LB가 우리를 뺄 때까지 기다린다
  await sleep(DRAIN_WAIT_MS);
  console.log(JSON.stringify({ msg: "shutdown:drained" }));

  // 3) 새 연결만 차단. 처리 중인 요청은 끝까지 간다.
  await new Promise<void>((resolve) => server.close(() => resolve()));

  // 4) 남은 자원 정리
  await pool.end();
  console.log(JSON.stringify({ msg: "shutdown:done" }));
  process.exit(0);
}

for (const sig of ["SIGTERM", "SIGINT"] as const) {
  process.on(sig, () => {
    // 절차가 걸려도 반드시 끝나도록 상한을 건다
    const killer = setTimeout(() => {
      console.error(JSON.stringify({ msg: "shutdown:forced" }));
      process.exit(1);
    }, SHUTDOWN_MAX_MS);
    killer.unref();

    void shutdown(sig);
  });
}
```

세 가지를 의도적으로 넣었습니다.

`shuttingDown` 가드가 있어야 신호가 두 번 들어와도 절차가 겹치지 않습니다.
배포 도구가 재촉하느라 신호를 반복해서 보내는 경우가 있습니다.

`SHUTDOWN_MAX_MS` 상한이 없으면, 끝나지 않는 요청 하나가 프로세스를 붙들고 있다가 결국 플랫폼에 강제 종료당합니다.
강제 종료는 로그를 남길 기회도 없이 끊기므로, **우리가 먼저 포기하고 기록을 남기는 편**이 낫습니다.

종료 각 단계에 로그를 남기는 것도 그래서입니다. 나중에 "드레이닝은 했는가, 그런데 몇 초 걸렸는가"를 이 타임스탬프로만 답할 수 있습니다.

### 살아있음 검사와 같은 엔드포인트를 쓰지 말 것

여기서 한 가지가 어긋나면 절차 전체가 거꾸로 돕니다.

플랫폼에는 대개 검사가 두 종류 있습니다. **트래픽을 보내도 되는지**를 묻는 것과, **컨테이너를 재시작해야 하는지**를 묻는 것입니다.
Kubernetes의 `readinessProbe`와 `livenessProbe`가 그렇고, ECS라면 대상 그룹 헬스체크와 컨테이너 헬스체크가 각각 그 역할에 가깝습니다.

우리가 위에서 503을 반환하게 만든 건 **앞의 것**입니다.
그런데 두 검사가 같은 `/healthz`를 보고 있으면, 드레이닝을 시작하는 순간 뒤의 검사도 같이 실패합니다.
플랫폼은 이걸 "죽은 컨테이너"로 읽고 재시작하거나 강제 종료하고, 정성껏 만든 드레이닝 구간은 그대로 날아갑니다.

그래서 엔드포인트를 나눕니다.

```typescript
// 트래픽을 받을 의사 — LB/대상 그룹이 본다. 드레이닝 중 503.
app.get("/healthz", (_req, res) => {
  res.status(accepting ? 200 : 503).send(accepting ? "ok" : "draining");
});

// 프로세스 생존 — 재시작 판단용. 종료 중에도 200을 유지한다.
app.get("/livez", (_req, res) => res.status(200).send("alive"));
```

`/livez`가 종료 중에도 200을 주는 게 핵심입니다. 지금은 스스로 내려가는 중이지 고장 난 게 아니기 때문입니다.

> `server.close()`는 새 연결을 막고 **진행 중이 아닌 커넥션**을 닫습니다.
> 유휴 keep-alive 커넥션까지 정리하는 `server.closeIdleConnections()`와 활성 커넥션까지 끊는 `server.closeAllConnections()`는 Node.js 18.2.0에서 추가됐고,
> Node.js 19.0.0부터는 `server.close()`와 함께 `closeIdleConnections()`를 부를 필요가 없습니다.
> 쓰는 런타임 버전에 따라 `close()`만으로 충분한지가 갈리니 확인하세요.

수명이 긴 연결이 섞여 있다면 4번 단계는 영영 끝나지 않습니다.
WebSocket이나 SSE 연결은 요청-응답이 아니라 계속 열려 있는 것이 정상이라, "처리 중인 요청이 끝나기"를 기다리는 방식으로는 정리되지 않습니다.
이쪽은 종료 시작 시점에 서버가 먼저 닫고, 클라이언트의 [재연결 로직](/blog/websocket-reconnect/)이 새 인스턴스를 잡게 하는 편이 낫습니다.

## keep-alive 경쟁

앞서 `keepAliveTimeout`을 설정한 이유가 남았습니다. 이건 배포와 무관하게 상시로 502를 만드는 원인이라 따로 봐야 합니다.

LB와 백엔드 사이 커넥션은 요청마다 새로 맺지 않고 재사용됩니다.
그런데 양쪽이 각자의 유휴 타임아웃을 들고 있고, **서버 쪽이 더 짧으면** 문제가 생깁니다.

```text
LB     : 이 커넥션 재사용해야지 → 요청 전송
서버   : (막 유휴 타임아웃이 지나서) 커넥션 닫는 중
결과   : LB는 응답을 못 받고 502
```

서버가 닫는 것과 LB가 요청을 보내는 것이 겹치는 순간이고, 재사용 빈도가 높을수록 자주 부딪힙니다.
그래서 규칙은 단순합니다.

> **서버의 keep-alive 타임아웃을 로드밸런서의 유휴 타임아웃보다 길게** 두세요.
> 먼저 닫는 쪽이 LB가 되면 이 경쟁 자체가 사라집니다.

Node.js는 `keepAliveTimeout` 기본값이 짧은 편이라 대부분의 LB 설정보다 작습니다. 그대로 두면 이 경쟁에 계속 집니다.
위 코드에서 65초를 쓴 건 LB 유휴 타임아웃이 60초일 때의 예시일 뿐이니, **실제 설정값을 확인하고 거기에 맞추세요.**

`headersTimeout`을 `keepAliveTimeout`보다 크게 두는 것도 같이 챙깁니다. 반대로 두면 헤더를 기다리다 먼저 끊는 경로가 생깁니다.

## 타임아웃들을 한 줄로 맞추기

지금까지 나온 값들이 서로 물려 있습니다. 하나만 어긋나도 앞의 노력이 무의미해집니다.

| 값 | 어디에 있나 | 하는 일 |
| --- | --- | --- |
| 헬스체크 주기 × 실패 임계 | 대상 그룹 | LB가 대상을 빼기까지 걸리는 시간 |
| 등록 해제 지연 | 대상 그룹 | 대상을 뺀 뒤 진행 중 요청을 기다려주는 시간 |
| 앱의 드레이닝 대기 | 애플리케이션 코드 | 헬스체크를 내린 뒤 리스닝을 닫기까지 |
| 종료 유예 시간 | 태스크 정의 · 파드 스펙 | 이 시간이 지나면 강제 종료 |

맞춰야 할 관계입니다.

```text
앱의 드레이닝 대기  ≥  LB가 대상을 빼는 데 걸리는 시간
앱의 전체 종료 시간  <  플랫폼의 종료 유예 시간
```

두 번째가 자주 깨집니다. 드레이닝 대기를 넉넉하게 늘려놓고 플랫폼의 유예 시간은 기본값으로 두면,
**앱이 아직 1번 단계에 있는데 강제 종료당합니다.** 헬스체크를 내리자마자 죽는 셈이라 설정을 추가하기 전보다 나빠집니다.

그래서 드레이닝 대기를 늘렸다면 종료 유예 시간도 같이 올려야 합니다.
ECS라면 컨테이너 정의의 `stopTimeout`, Kubernetes라면 `terminationGracePeriodSeconds`입니다.
둘 다 기본값과 상한이 정해져 있고 런치 타입에 따라 다르므로, 올리기 전에 해당 플랫폼 문서에서 허용 범위를 확인하세요.

반대 방향도 봅니다. 등록 해제 지연이 길면 배포 한 번이 그만큼 느려집니다.
요청이 짧은 API라면 이 값을 줄이는 게 배포 시간을 크게 줄이지만, **처리 중인 요청의 최대 소요 시간보다는 길어야** 합니다.
파일 업로드나 리포트 생성처럼 오래 걸리는 엔드포인트가 섞여 있다면 그쪽 기준으로 잡거나, 아예 다른 서비스로 분리하는 편이 낫습니다.

## 큐 컨슈머는 조건이 다르다

HTTP 서버만 이 절차가 필요한 게 아닙니다. 그리고 큐 컨슈머 쪽은 실패 양상이 더 조용합니다.

HTTP는 끊기면 5xx로 드러나지만, 컨슈머가 처리 도중 죽으면 **메시지가 다시 큐로 돌아갈 뿐** 지표에 아무것도 안 남습니다.
같은 메시지가 두 번 처리돼서 생기는 문제는 한참 뒤에 데이터로 발견됩니다.

컨슈머의 종료 절차는 더 단순합니다. LB가 없으니 lameduck 구간이 필요 없고, **지금 잡은 메시지를 끝내고 다음 걸 안 가져오면** 됩니다.

```typescript
let running = true;

process.on("SIGTERM", () => { running = false; });

while (running) {
  const messages = await queue.receive({ max: 10 });
  if (messages.length === 0) continue;

  for (const msg of messages) {
    if (!running) break;          // 남은 건 집지 않는다. ack 안 하면 다시 배달된다.
    await handle(msg);
    await queue.ack(msg);         // 처리가 끝난 뒤에 ack
  }
}

await queue.close();
```

`ack`를 처리 **뒤에** 두는 게 전부입니다. 앞에 두면 종료 중에 집어든 메시지가 처리되지 않은 채 사라집니다.
그리고 이 구조는 필연적으로 최소 한 번 전달이 되므로, 핸들러 쪽에 [멱등성](/blog/idempotency-key-payment-api/)이 있어야 합니다.

폴링 대기가 긴 롱 폴링이라면 `receive` 자체를 중단시킬 방법도 필요합니다.
`AbortController`를 받는 클라이언트라면 그걸 쓰고, 아니면 폴링 대기 시간이 종료 유예 시간보다 짧은지 확인하세요. 아니면 매번 강제 종료로 끝납니다.

## 고쳤는지 확인하는 법

이 작업은 **고쳤다고 믿기 쉽고 확인하지 않으면 모릅니다.** 배포 중 에러는 원래 간헐적이라, 한 번 조용히 넘어간 배포는 증거가 되지 않습니다.

부하를 주면서 배포를 돌리고 5xx가 0인지 보는 게 유일하게 확실한 방법입니다.

```bash
# 배포 직전에 띄워두고, 배포가 끝날 때까지 유지한다
hey -z 5m -c 50 https://api.example.com/healthz

# 배포 중 대상 그룹 상태 변화를 같이 관찰한다
watch -n 2 'aws elbv2 describe-target-health \
  --target-group-arn "$TG_ARN" \
  --query "TargetHealthDescriptions[].TargetHealth.State"'
```

대상이 `draining`으로 바뀌는 시점과 애플리케이션 로그의 `shutdown:start`가 **얼마나 떨어져 있는지**가 실제로 봐야 할 값입니다.
드레이닝 대기를 그 간격보다 짧게 잡았다면 아직 창이 열려 있는 것입니다.

확인할 것을 정리하면 이렇습니다.

- [ ] 헬스체크 엔드포인트가 종료 중에 실패를 반환하는가 (생존 여부만 답하고 있지 않은가)
- [ ] 헬스체크를 내린 뒤 리스닝을 닫기까지 대기 구간이 있는가
- [ ] 앱의 전체 종료 시간이 플랫폼 종료 유예 시간보다 짧은가
- [ ] 서버 keep-alive 타임아웃이 LB 유휴 타임아웃보다 긴가
- [ ] 종료 절차에 상한 타이머가 있는가 (안 끝나는 요청 하나에 붙들리지 않는가)
- [ ] 큐 컨슈머도 같은 처리가 돼 있는가 (여기는 에러로 안 드러난다)
- [ ] 부하를 준 상태로 배포해서 5xx가 0인 것을 **눈으로 확인**했는가
