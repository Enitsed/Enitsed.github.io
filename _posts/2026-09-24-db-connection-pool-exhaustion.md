응답 시간 p99가 튀는데 DB CPU는 한가하고, 느린 쿼리 로그도 평소와 비슷합니다.
그런데 느려진 API 목록을 보면 DB를 거의 안 쓰는 엔드포인트까지 섞여 있습니다.

쿼리가 느린 문제와, 쿼리를 시작도 못 하고 줄을 서는 문제는 원인이 다릅니다.
커넥션 풀은 후자가 생기는 자리이고, 기본 지표에서 가장 잘 숨는 구간이기도 합니다.

## 풀은 성능 장치가 아니라 제한 장치다

커넥션 풀을 두는 이유를 "접속 비용을 아끼려고"로만 기억하면 튜닝 방향이 어긋납니다.
TCP 핸드셰이크와 인증, TLS 협상을 매 요청마다 반복하지 않는 것도 맞지만, 더 중요한 역할은 **DB에 동시에 밀어 넣을 수 있는 작업 수의 상한**을 정하는 것입니다.

DB 쪽 병렬성은 공짜가 아닙니다. 커넥션 하나마다 서버 쪽 메모리 버퍼가 붙고, 동시에 도는 스레드가 늘면 CPU는 일보다 컨텍스트 스위칭과 락 경쟁에 시간을 더 씁니다.
그래서 풀은 애플리케이션이 DB를 밟아 죽이지 않게 막는 안전장치에 가깝습니다.

문제는 이 상한이 걸리는 순간의 증상이 **DB 지표에 나타나지 않는다**는 점입니다.
풀이 다 찼을 때 요청은 애플리케이션 프로세스 안의 큐에서 기다립니다. DB 입장에서는 그냥 요청이 안 들어온 것이고, 한가해 보입니다.

## 대기 시간은 쿼리 시간에 잡히지 않는다

대부분의 ORM과 드라이버 계측은 "쿼리를 보낸 시점부터 응답을 받은 시점까지"를 잽니다.
풀에서 커넥션을 얻으려고 기다린 시간은 그 앞에 있고, 그래서 어디에도 안 찍힙니다.

한 요청의 DB 구간은 사실 두 토막입니다.

```text
요청 ──▶ [ 풀 대기 ] ──▶ [ 쿼리 실행 ] ──▶ 응답
          ↑ 여기가 지표에 없다
```

계측을 붙일 자리는 커넥션을 얻는 함수 하나입니다. 애플리케이션 코드가 드라이버 풀을 직접 호출하지 않게 감싸두면 그 뒤로는 전부 따라옵니다.

```typescript
import type { Pool, PoolConnection } from 'mysql2/promise';

async function acquire(pool: Pool): Promise<PoolConnection> {
  const started = process.hrtime.bigint();
  try {
    return await pool.getConnection();
  } finally {
    const waitedMs = Number(process.hrtime.bigint() - started) / 1e6;
    dbPoolAcquireMs.observe(waitedMs);      // 히스토그램
    if (waitedMs > 100) {
      logger.warn({ waitedMs }, 'pool acquire slow');
    }
  }
}
```

여기에 풀 상태 자체를 주기적으로 찍어두면 원인 추적이 훨씬 빨라집니다.
드라이버마다 노출하는 속성 이름이 다르니 실제 값은 쓰는 라이브러리 문서에서 확인하고, 최소한 아래 세 가지는 뽑아두는 편이 좋습니다.

- **사용 중 커넥션 수** — 풀 크기에 붙어 있으면 그게 병목입니다.
- **대기 중인 요청 수** — 0이 아니면 이미 줄이 서 있습니다.
- **획득 대기 시간 분포** — 평균이 아니라 p99로 봅니다. 평균은 마지막까지 멀쩡해 보입니다.

이 세 개만 있어도 "DB가 느린 건가 풀이 좁은 건가"를 그래프 하나로 가릅니다.
사용 중 커넥션이 상한에 딱 붙어 평평한 선을 그리고 있으면, 그건 부하가 그만큼이라는 뜻이 아니라 **더 들어오고 싶은데 못 들어오고 있다**는 뜻입니다.

## 느린 쿼리 하나가 전체를 세우는 경로

풀 고갈이 고약한 이유는 장애가 번지기 때문입니다.

리포트 쿼리 하나가 평소 50ms에서 5초로 늘어났다고 해봅시다. 그 API만 느려지고 끝나야 할 것 같지만 그렇지 않습니다.
느려진 쿼리는 커넥션을 100배 오래 쥐고, 그 시간 동안 풀의 자리를 점유합니다. 자리가 부족해지면 로그인도, 목록 조회도, 헬스체크도 같은 큐에 섞여 기다립니다.

여기서 재시도가 끼어들면 더 빨라집니다. 타임아웃이 난 요청이 재시도로 다시 들어오면 큐는 두 배가 되고, 앞선 요청은 아직 커넥션을 놓지 않았습니다.
한 하류가 흔들릴 때 재시도가 부하를 곱하는 구조는 [타임아웃 예산과 재시도 증폭](/blog/retry-timeout-budget-circuit-breaker/)에서 다룬 것과 같고, 커넥션 풀은 그 증폭이 모이는 지점 중 하나입니다.

그래서 풀을 나누는 선택이 나옵니다. 성격이 다른 트래픽에 서로 다른 풀을 주는 방식입니다.

```typescript
// 사용자 요청용 — 짧은 쿼리만, 빨리 실패
const userPool = createPool({ connectionLimit: 20, queueLimit: 50 });

// 배치·리포트용 — 느려도 되지만 남의 자리를 뺏지 않는다
const batchPool = createPool({ connectionLimit: 4, queueLimit: 0 });
```

격벽(bulkhead)이라고 부르는 패턴입니다. 총 커넥션 수는 늘어나지만, 리포트가 아무리 느려져도 사용자 요청이 쓸 자리 20개는 남습니다.
같은 이유로 읽기 전용 조회를 리드 리플리카로 빼면 풀도 같이 분리됩니다. 부하 분산보다 **장애 격리** 쪽이 더 큰 이득인 경우가 많습니다.

## 풀 크기를 정하는 계산

"넉넉하게 100"이 가장 흔한 설정이고, 대개 틀린 설정입니다.

필요한 동시 커넥션 수는 대기 행렬의 기본식으로 어림잡을 수 있습니다.

```text
필요 커넥션 ≈ 초당 요청 수 × 요청 하나가 커넥션을 쥐는 시간(초)
```

초당 200건이 들어오고 커넥션 점유 시간이 10ms라면 필요한 건 2개 남짓입니다.
같은 처리량이라도 점유 시간이 200ms면 40개가 필요합니다. **풀 크기를 좌우하는 건 요청 수가 아니라 점유 시간**입니다.

그래서 풀을 늘리기 전에 점유 시간을 먼저 봐야 합니다. 점유 시간을 반으로 줄이면 필요한 커넥션도 반이 됩니다.

무턱대고 키우면 안 되는 이유는 세 가지입니다.

첫째, DB 쪽 상한이 있습니다. MySQL의 `max_connections`는 유한하고, 관리형 DB에서는 인스턴스 사양에 따라 계산된 값이 들어갑니다. 값은 직접 조회해서 확인하세요.

```sql
SELECT @@max_connections, @@wait_timeout;

SHOW STATUS WHERE Variable_name IN
  ('Threads_connected', 'Threads_running', 'Max_used_connections');
```

`Threads_connected`는 붙어 있는 수, `Threads_running`은 그중 실제로 일하고 있는 수입니다.
연결은 많은데 running이 적다면 커넥션이 놀고 있는 것이고, running이 계속 높다면 DB가 실제로 포화입니다. 처방이 정반대이니 둘을 같이 봐야 합니다.

둘째, 상한은 **애플리케이션 인스턴스 전체가 나눠 쓰는 값**입니다.

```text
총 커넥션 = 인스턴스 수 × 풀 크기 × (풀 종류 수)
```

오토스케일링으로 인스턴스가 4대에서 20대로 늘어나는 순간 총 커넥션도 5배가 됩니다. 평소에 여유로웠던 설정이 트래픽이 몰릴 때 정확히 터지는 이유입니다.
여기에 배치 워커, 마이그레이션 작업, BI 도구, 그리고 사람이 접속할 몫까지 더해야 합니다. **관리자가 붙을 자리를 남겨두지 않으면 장애 조사조차 못 합니다.**

> MySQL은 `SUPER` 권한을 가진 계정을 위해 커넥션 한 자리를 따로 남겨둡니다. 다만 관리형 DB의 마스터 계정은 이 권한 구성이 다를 수 있으니, 비상용 접속 경로는 미리 시험해두는 편이 안전합니다.

셋째, 커넥션이 늘어도 DB가 동시에 처리하는 양은 코어 수와 디스크가 정합니다.
풀을 100으로 늘리면 100개가 동시에 도는 게 아니라, 100개가 DB 안에서 서로 락과 CPU를 두고 경쟁합니다. 대기 장소를 애플리케이션 큐에서 DB 내부로 옮겼을 뿐이고, 대개 DB 안에서 기다리는 쪽이 더 비쌉니다.

풀 크기는 **줄여서 나빠지는지를 확인하며 내려가는 방향**으로 정하는 편이 맞습니다.
대기 시간 p99가 올라가지 않는 한 작은 풀이 낫습니다.

## 커넥션을 오래 쥐는 코드

풀이 마르는 원인의 대부분은 크기가 아니라 점유 시간입니다. 그리고 점유 시간을 늘리는 건 거의 언제나 코드입니다.

가장 흔한 세 가지입니다.

**트랜잭션 안에서 외부를 호출하는 경우.**

```typescript
await conn.beginTransaction();
await conn.query('UPDATE orders SET status = ? WHERE id = ?', ['paid', id]);
await paymentGateway.capture(id);   // 여기서 3초가 걸리면 커넥션도 3초 잡혀 있다
await conn.commit();
```

외부 API가 흔들리는 순간 커넥션 점유 시간이 그 응답 시간을 그대로 따라갑니다.
하류 장애가 DB 풀 고갈로 번역되는 가장 짧은 경로입니다. 외부 호출은 트랜잭션 밖으로 빼거나, 커밋 뒤에 내보내도록 아웃박스에 적어둡니다.

**결과를 다 받기 전에 다른 일을 하는 경우.** 커서를 열어 한 건씩 처리하면서 그 안에서 또 다른 쿼리를 날리면, 커넥션은 루프 전체 시간 동안 잡혀 있습니다.
배치는 페이지 단위로 끊어 읽고, 읽은 뒤에는 커넥션을 놓았다가 다시 얻는 편이 낫습니다.

**반납을 빠뜨리는 경우.** 예외 경로에서 `release()`가 빠지면 커넥션은 영영 돌아오지 않습니다.
이 누수는 조용히 쌓이다가 며칠 뒤에 터지고, 재시작하면 사라져서 원인을 찾기 어렵습니다.

```typescript
async function withConnection<T>(pool: Pool, fn: (c: PoolConnection) => Promise<T>): Promise<T> {
  const conn = await acquire(pool);
  try {
    return await fn(conn);
  } finally {
    conn.release();     // 어떤 경로로 빠져나가도 반납한다
  }
}
```

원칙은 하나입니다. **애플리케이션 코드가 `getConnection()`을 직접 부르지 않게 합니다.**
반납을 잊을 수 있는 API를 노출하지 않으면, 잊는 일도 안 생깁니다.

누수를 감시하는 장치도 걸어둘 수 있습니다. 커넥션을 빌려준 시각을 기록해두고, 임계값을 넘겨 반납되지 않은 것을 로그로 남기는 방식입니다.
HikariCP의 `leakDetectionThreshold`가 하는 일이 이것이고, 직접 구현해도 몇 줄이면 됩니다.

## 무한히 기다리지 않게 하기

풀이 비었을 때의 기본 동작이 "빌 때까지 기다림"인 드라이버가 많습니다.
이게 가장 나쁜 조합입니다. 요청은 쌓이고, 사용자는 이미 떠났고, 그 요청들은 여전히 자리를 기다립니다.

대기에는 상한이 있어야 하고, 그 상한은 **요청 전체의 타임아웃보다 짧아야** 합니다.

```typescript
function acquireWithTimeout(pool: Pool, ms: number): Promise<PoolConnection> {
  let timer: NodeJS.Timeout;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error('pool acquire timeout')), ms);
  });

  return Promise.race([pool.getConnection(), timeout]).finally(() => clearTimeout(timer)) as Promise<PoolConnection>;
}
```

> 위는 어떤 드라이버에서도 동작하는 최소 구현입니다. 경쟁에서 진 `getConnection()`이 나중에 성공하면 그 커넥션은 반납되지 않은 채 남으므로, 실제로는 `.then(c => c.release())`를 붙여 뒤처리를 해야 합니다.
> 드라이버가 획득 타임아웃 옵션을 직접 제공한다면 그쪽을 쓰는 편이 안전합니다. 옵션 이름과 적용 범위(신규 접속에만 적용되는지, 큐 대기까지 포함하는지)는 버전마다 다르니 문서에서 확인하세요.

큐 길이 자체에 상한을 두는 방법도 있습니다. mysql2의 `queueLimit`처럼 대기 인원이 넘치면 즉시 에러를 내는 설정입니다.
사용자 요청용 풀이라면 이쪽이 대체로 맞습니다. **10초 기다린 끝의 성공보다 50ms 만의 실패가 낫습니다.** 앞단에서 대체 응답을 주거나 캐시를 내보낼 수 있기 때문입니다.

정리하면 부등식 하나로 맞춥니다.

```text
풀 획득 타임아웃 + 쿼리 타임아웃 < 요청 타임아웃 < 클라이언트 타임아웃
```

이 순서가 어긋나면, 클라이언트가 이미 끊은 요청을 서버가 계속 붙들고 커넥션을 쓰는 구간이 생깁니다.

## 인스턴스가 늘어나는 환경

풀 크기를 아무리 잘 잡아도, 인스턴스 수가 통제되지 않으면 총 커넥션은 통제되지 않습니다.
서버리스 함수가 대표적입니다. 동시 실행이 200개로 튀면 각자 자기 풀을 들고 있고, 함수 하나가 커넥션 하나만 써도 200개가 붙습니다.

여기서 커넥션 프록시를 앞에 둡니다. RDS Proxy나 PgBouncer처럼 애플리케이션과 DB 사이에서 커넥션을 다중화하는 계층입니다.

```text
[함수 200개] ──▶ [프록시: 커넥션 20개 유지] ──▶ [DB]
```

프록시는 트랜잭션 단위로 실제 커넥션을 빌려주고 회수합니다. 그래서 애플리케이션 쪽 커넥션 수와 DB 쪽 커넥션 수를 끊어낼 수 있습니다.
얻는 게 있으면 내주는 것도 있습니다. 트랜잭션 풀링 모드에서는 **세션에 상태를 남기는 기능들이 깨집니다.**

- 세션 변수와 `SET`으로 바꾼 설정 — 다음 트랜잭션은 다른 물리 커넥션일 수 있습니다.
- 임시 테이블, `LAST_INSERT_ID()`처럼 세션에 묶인 값
- 세션 수준 어드바이저리 락
- 준비된 구문(prepared statement) — 지원 여부와 방식이 프록시·버전마다 다릅니다.

[InnoDB 락 읽는 법](/blog/innodb-deadlock-gap-lock/)에서 "세션 격리 수준을 바꿨다면 풀에 반납하기 전에 되돌리라"고 적은 것과 같은 함정이고, 프록시가 끼면 되돌릴 기회조차 없어집니다.
도입 전에 **세션 상태에 기대는 코드가 있는지** 먼저 훑어야 합니다. 대부분은 ORM이 내부적으로 쓰고 있어서 애플리케이션 코드만 봐서는 안 보입니다.

프록시가 만능은 아니라는 점도 적어둡니다. 홉이 하나 늘어나 지연이 조금 붙고, 프록시 자체가 장애 지점이 됩니다.
인스턴스 수가 예측 가능한 컨테이너 환경이라면 풀 크기를 제대로 잡는 쪽이 대개 더 단순합니다.

## 지금 무엇이 붙어 있는지 보기

풀이 말랐다는 의심이 들 때 DB 쪽에서 볼 것들입니다.

```sql
-- 누가 붙어 있고 무엇을 하고 있는가
SELECT id, user, host, db, command, time, state, LEFT(info, 80) AS query
FROM information_schema.processlist
ORDER BY time DESC
LIMIT 20;
```

`command`가 `Sleep`인데 `time`이 큰 커넥션이 잔뜩 보인다면, 애플리케이션이 커넥션을 잡아두고 아무 일도 안 하는 중입니다.
풀을 늘릴 게 아니라 점유 시간을 줄여야 하는 상태입니다.

```sql
-- 애플리케이션(계정·호스트)별로 몇 개씩 쓰고 있는가
SELECT user, SUBSTRING_INDEX(host, ':', 1) AS client, COUNT(*) AS conns
FROM information_schema.processlist
GROUP BY user, client
ORDER BY conns DESC;
```

인스턴스별 커넥션 수가 고르지 않다면 로드밸런싱이 기울었거나, 특정 인스턴스에만 누수가 있는 것입니다.

`Max_used_connections`는 기동 이후 최고치를 기억하고 있어서, 지나간 피크를 확인하는 데 유용합니다.
이 값이 `max_connections`에 근접한 적이 있다면 이미 한 번은 벼랑까지 갔다는 뜻입니다.

> 관리형 DB에서는 유휴 커넥션이 DB의 `wait_timeout`이나 중간 네트워크 장비에 의해 조용히 끊길 수 있습니다.
> 애플리케이션 풀의 유휴 커넥션 수명을 그보다 **짧게** 잡아, 이미 죽은 커넥션을 빌려주는 상황을 피하세요.

## 정리

- 풀 대기 시간은 쿼리 시간에 포함되지 않습니다. **획득 시점을 따로 계측**하지 않으면 이 병목은 지표에 없습니다.
- 필요한 풀 크기는 처리량이 아니라 **점유 시간**이 정합니다. 키우기 전에 점유 시간부터 줄이세요.
- 상한은 인스턴스 전체가 나눠 씁니다. `인스턴스 수 × 풀 크기`에 배치와 관리자 몫까지 더해 `max_connections` 안에 들어와야 합니다.
- 성격이 다른 트래픽은 풀을 나눕니다. 리포트 쿼리가 로그인을 세우지 않게 하는 값싼 방법입니다.
- 무한 대기를 없애고, 획득 타임아웃을 요청 타임아웃보다 짧게 둡니다.
- 인스턴스 수가 통제되지 않는 환경에서만 프록시를 고려하고, 세션 상태에 기대는 코드를 먼저 확인합니다.

풀 크기는 성능을 끌어올리는 손잡이가 아니라 **어디서 줄을 설지 고르는 손잡이**입니다.
작게 두면 애플리케이션 큐에서, 크게 두면 DB 내부에서 기다립니다. 어느 쪽이 나은지는 그 대기를 관측할 수 있는 곳이 어디냐로 갈립니다.
