"분당 60건"으로 제한을 걸어뒀는데 모니터링에는 1초 안에 120건이 찍힙니다.
설정이 잘못된 것도, 누가 우회한 것도 아닙니다. 카운터를 세는 방식이 그렇게 생겼을 뿐입니다.

레이트 리밋은 붙이는 건 한 줄이고, 어디서 새는지 아는 데 시간이 걸립니다.
계수 방식마다 새는 자리가 다르고, 그 차이가 그대로 장애 대응의 차이가 됩니다.

## 무엇을 막으려는 건지부터 정한다

같은 "레이트 리밋"이라는 이름 아래 목적이 최소 세 가지 섞여 있습니다. 목적이 다르면 고를 알고리즘도, 세는 키도 달라집니다.

- **남용 차단** — 로그인 무차별 대입, 크롤러. 개별 주체를 오래 기억해야 하고, 거절이 강경해도 됩니다.
- **과부하 보호** — 하류가 못 버티는 양이 들어오는 걸 막습니다. 주체가 누구인지보다 **총량**이 중요합니다.
- **비용 통제** — 외부 API 호출이나 LLM 토큰처럼 요청 하나가 돈인 경우. 요청 수보다 **요청의 무게**를 세야 합니다.

세 번째가 특히 자주 잘못 설정됩니다. 요청 수로 제한을 걸어두면, 짧은 요청 100건과 긴 요청 100건이 같은 한도를 먹습니다.
실제로 아픈 건 후자인데 제한은 둘을 구분하지 못합니다.

과부하 보호가 목적이라면 레이트 리밋만으로는 부족하다는 점도 같이 봐야 합니다.
초당 요청 수를 제한해도 요청 하나가 오래 걸리면 동시 처리량은 계속 올라갑니다. 이쪽은 [커넥션 풀](/blog/db-connection-pool-exhaustion/)이나 동시성 제한(세마포어)이 맡는 영역이고, 레이트 리밋과 역할이 다릅니다.

## 고정 윈도우 — 경계에서 두 배가 나오는 이유

가장 짧게 짜이는 구현입니다. 시간을 창으로 잘라 창마다 카운터를 두고, 넘치면 거절합니다.

```typescript
// 분 단위 고정 윈도우
const key = `rl:${userId}:${Math.floor(Date.now() / 60_000)}`;
const count = await redis.incr(key);
if (count === 1) await redis.expire(key, 60);
if (count > 60) throw new TooManyRequests();
```

문제는 창의 경계입니다. 12:00:59에 60건, 12:01:00에 60건을 보내면 두 요청 묶음은 서로 다른 카운터에 들어갑니다.
제한은 "분당 60"인데 **실제로는 2초 안에 120건**이 통과합니다. 한도의 두 배가 구조적으로 허용되는 셈입니다.

부수적인 결함도 하나 있습니다. 위 코드는 `INCR`과 `EXPIRE`가 두 번의 왕복이라, 그 사이에 프로세스가 죽으면 TTL 없는 키가 남습니다.
그 사용자는 그 뒤로 영원히 막힙니다. 이런 다단계 연산은 나중에 보게 될 Lua 스크립트로 묶거나, 최소한 `SET key 0 EX 60 NX` 뒤에 `INCR`을 쓰는 식으로 정리해야 합니다.

그렇다고 고정 윈도우가 못 쓸 물건은 아닙니다. 키 하나에 정수 하나라 가장 싸고, "대략 이 정도 위로는 못 오게" 수준의 방어에는 충분합니다.
한도의 두 배를 견딜 수 있는 자리면 그냥 쓰면 됩니다. 문제는 그 판단을 안 하고 쓰는 경우입니다.

## 슬라이딩 윈도우 로그 — 정확하지만 비싸다

경계 문제를 없애려면 창을 고정하지 말고 **지금부터 과거 60초**를 봐야 합니다.
요청 시각을 전부 기록해두고 매번 오래된 것을 버린 뒤 세는 방식입니다. Redis의 정렬 집합이 그대로 들어맞습니다.

```lua
-- KEYS[1]=키, ARGV[1]=현재시각(ms), ARGV[2]=윈도우(ms), ARGV[3]=한도, ARGV[4]=고유 멤버
local now    = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit  = tonumber(ARGV[3])

redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
local count = redis.call('ZCARD', KEYS[1])
if count >= limit then
  -- 가장 오래된 요청이 빠져나가는 시각까지 기다리면 된다
  local oldest = redis.call('ZRANGE', KEYS[1], 0, 0, 'WITHSCORES')
  return { 0, math.ceil((oldest[2] + window - now) / 1000) }
end

redis.call('ZADD', KEYS[1], now, ARGV[4])
redis.call('PEXPIRE', KEYS[1], window)
return { 1, 0 }
```

정확합니다. 어느 시점에 잘라 봐도 최근 60초 안의 요청은 한도를 넘지 않습니다.
게다가 거절할 때 **언제 다시 오면 되는지**를 정확히 계산해서 돌려줄 수 있습니다. 이 값이 뒤에서 `Retry-After`가 됩니다.

대신 키 하나가 최대 `limit`개의 원소를 들고 있습니다. 한도 60이면 별것 아니지만, 한도를 10000으로 잡고 사용자가 10만 명이면 메모리 계산을 해봐야 하는 규모가 됩니다.
**정확도를 메모리로 사는 방식**이라고 보면 됩니다. 한도가 작고 정확도가 중요한 곳(로그인 시도, 인증번호 발송)에 어울립니다.

> `EVAL`로 실행되는 Lua 스크립트는 Redis에서 원자적으로 실행됩니다. 읽고-판단하고-쓰는 과정이 중간에 끼어들지 않는다는 뜻이고, 레이트 리밋처럼 경쟁이 생기는 연산은 이 성질에 기대야 합니다.

## 슬라이딩 윈도우 카운터 — 둘 사이의 타협

로그를 다 들고 있지 않으면서 경계 문제를 줄이는 방법이 있습니다. 직전 창과 현재 창의 카운터 두 개만 두고, 겹치는 비율로 가중 평균을 내는 것입니다.

```typescript
const windowMs = 60_000;
const now = Date.now();
const curKey  = Math.floor(now / windowMs);
const elapsed = (now % windowMs) / windowMs;          // 현재 창의 진행률

const [prev, cur] = await redis.mget(
  `rl:${userId}:${curKey - 1}`,
  `rl:${userId}:${curKey}`,
);

// 직전 창의 값을 남은 비율만큼 끌어와서 더한다
const estimated = Number(prev ?? 0) * (1 - elapsed) + Number(cur ?? 0);
if (estimated >= limit) throw new TooManyRequests();
```

12:01:00 시점이면 직전 창이 100% 반영되고, 12:01:30이면 절반만 반영됩니다.
경계에서 카운터가 통째로 리셋되는 일이 없어지니 두 배 통과가 사라집니다.

정확한 값은 아닙니다. 직전 창 안에서 요청이 고르게 퍼져 있었다고 가정하는 근사이기 때문입니다.
실제로는 창 끝에 몰려 있었는데 고르게 퍼진 것으로 계산하면 실제보다 적게 잡히고, 반대면 멀쩡한 요청이 막힙니다.
대신 키 두 개에 정수 두 개뿐이라 비용은 고정 윈도우와 거의 같습니다. 대부분의 공개 API에는 이 정도가 합리적인 타협점입니다.

## 토큰 버킷 — 버스트를 의도적으로 허용하기

앞의 세 방식은 전부 "일정 시간 안에 몇 건"을 봅니다. 그런데 실제로 원하는 건 대개 이런 쪽입니다.

> 평소에는 초당 10건씩만 쓰되, 한동안 쉬었다면 한 번에 50건쯤은 몰아 써도 된다.

토큰 버킷이 이걸 그대로 모델링합니다. 버킷에 초당 `rate`개씩 토큰이 차고 최대 `burst`개까지 쌓입니다. 요청은 토큰을 하나(또는 무게만큼) 꺼내 쓰고, 없으면 거절됩니다.

핵심은 **토큰을 채우는 타이머를 돌리지 않는다**는 점입니다. 마지막 접근 시각만 들고 있다가, 요청이 올 때 그동안 흘렀어야 할 양을 계산해 채웁니다.

```lua
-- KEYS[1]=버킷 키
-- ARGV[1]=초당 충전량, ARGV[2]=버킷 용량, ARGV[3]=현재시각(ms), ARGV[4]=이번 요청의 무게
local rate     = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])
local now      = tonumber(ARGV[3])
local cost     = tonumber(ARGV[4])

local state  = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(state[1])
local ts     = tonumber(state[2])

if tokens == nil then            -- 첫 요청이면 가득 찬 버킷에서 시작
  tokens = capacity
  ts = now
end

-- 지난 시간만큼 채우되 용량을 넘지 않는다
tokens = math.min(capacity, tokens + (now - ts) * rate / 1000)

local allowed = 0
local retry_after = 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
else
  retry_after = math.ceil((cost - tokens) / rate * 1000)   -- ms
end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
-- 가득 차는 데 걸리는 시간이 지나면 어차피 초기 상태와 같다
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) + 1000)

return { allowed, math.floor(tokens), retry_after }
```

`cost`를 인자로 받는 게 이 구현의 쓸모입니다. 무거운 요청에 3을, 가벼운 조회에 1을 매기면 **요청 수가 아니라 부하를 기준으로** 제한이 걸립니다.
LLM API 앞단처럼 요청 하나의 비용 편차가 큰 곳에서는 이 구분이 있고 없고가 큽니다.

다만 무게를 미리 알 수 없는 경우가 있습니다. 응답 토큰 수는 응답이 끝나야 확정되니까요.
그럴 때는 예상치로 먼저 차감하고 끝난 뒤 정산(차이를 되돌려주거나 더 빼는)하는 방식을 씁니다. 완벽하진 않아도 사후에만 세는 것보다는 훨씬 낫습니다.

> 버킷 상태가 만료돼 사라지면 다음 요청은 "가득 찬 버킷"에서 다시 시작합니다. TTL을 버킷이 가득 차는 시간보다 짧게 잡으면 한도가 새는 통로가 되니, 위 코드처럼 충분히 길게 잡아야 합니다.

버킷 용량을 1로 두고 충전 속도만 남기면 버스트를 전혀 허용하지 않는 **리키 버킷**에 가까워집니다. 요청 간격을 일정하게 강제하고 싶을 때 이렇게 씁니다.

정리하면 이렇습니다.

| 방식 | 경계 정확도 | 저장 비용 | 버스트 | 어울리는 곳 |
| --- | --- | --- | --- | --- |
| 고정 윈도우 | 최대 2배 초과 | 정수 1개 | 통제 불가 | 대략적인 상한, 내부 API |
| 슬라이딩 로그 | 정확 | 한도 개수만큼 | 없음 | 로그인·인증번호 등 작은 한도 |
| 슬라이딩 카운터 | 근사 | 정수 2개 | 없음 | 일반적인 공개 API |
| 토큰 버킷 | 정확 | 필드 2개 | 용량만큼 허용 | 비용 가중, 버스트 허용 |

## 무엇을 키로 셀 것인가

알고리즘보다 여기서 더 자주 틀립니다.

**IP로 세는 건 기본값이지 정답이 아닙니다.** 회사나 학교, 모바일 캐리어 NAT 뒤에서는 수백 명이 같은 IP로 나옵니다. 한 명 때문에 나머지가 막힙니다.
반대로 공격자는 IP를 바꾸는 쪽이 훨씬 쉽습니다. IP 기반 제한은 **막고 싶은 쪽에는 약하고 막으면 안 되는 쪽에는 강한** 비대칭을 갖습니다.

그래서 식별 가능한 주체가 있으면 그쪽을 씁니다. 인증된 사용자 ID, API 키, 테넌트 ID 순으로 내려오고, 아무것도 없는 경로(로그인, 회원가입)에서만 IP로 떨어집니다.

프록시 뒤에 있다면 클라이언트 IP를 어디서 읽는지가 곧 보안 문제가 됩니다. `X-Forwarded-For`는 클라이언트가 얼마든지 위조할 수 있는 헤더라, **신뢰할 수 있는 프록시가 붙인 마지막 항목**을 써야 합니다. 그냥 맨 앞 값을 읽으면 헤더 한 줄로 제한이 무력화됩니다.

계층을 나눠 거는 것도 흔한 구성입니다. 하나로 다 막으려 하면 한도가 어중간해집니다.

```typescript
const rules = [
  { key: `ip:${ip}`,                limit: 100,  window: 60 },   // 넓게, 크게
  { key: `user:${userId}`,          limit: 600,  window: 60 },   // 주체별
  { key: `user:${userId}:${route}`, limit: 10,   window: 60 },   // 비싼 경로만 따로
  { key: `tenant:${tenantId}`,      limit: 5000, window: 60 },   // 계약 단위
];
```

여러 규칙을 검사할 때는 순서가 중요합니다. 싼 검사를 먼저 하고, **하나라도 걸리면 거기서 멈춥니다.**
전부 검사한 뒤 거절하면 거절된 요청도 모든 카운터를 소모해서, 막힌 사용자가 다른 한도까지 같이 태워버립니다.

## 거절하는 법 — 429를 제대로 돌려주기

제한에 걸린 요청을 어떻게 돌려주느냐가 실제 부하를 좌우합니다. 그냥 `429`만 던지면 클라이언트는 대개 즉시 재시도하고, 그 재시도가 다시 제한에 걸리면서 요청량은 줄지 않습니다.

최소한 이 세 가지는 담아야 합니다.

```typescript
res.status(429);
res.set('Retry-After', String(Math.ceil(retryAfterMs / 1000)));   // 초 단위
res.set('RateLimit-Limit', String(limit));
res.set('RateLimit-Remaining', '0');
res.set('RateLimit-Reset', String(Math.ceil(retryAfterMs / 1000)));
res.json({ error: 'rate_limited', retryAfterMs });
```

`Retry-After`는 표준 헤더이고, 많은 HTTP 클라이언트가 이 값을 보고 대기합니다. 앞서 슬라이딩 로그와 토큰 버킷 구현에서 굳이 대기 시간을 계산해 돌려준 이유가 이것입니다.

`RateLimit-*` 계열은 남은 한도를 미리 알려주는 용도인데, 이름과 형식이 아직 통일돼 있지 않습니다.
`X-RateLimit-*`를 쓰는 서비스도 많고 IETF 표준화 작업도 진행 중이니, 공개 API라면 현재 문서를 확인하고 한 가지를 골라 **문서에 명시**하는 편이 안전합니다. 클라이언트 입장에서는 이름이 뭐든 일관되기만 하면 됩니다.

한 가지 더. 전체 클라이언트에 같은 `Retry-After`를 주면 그 시각에 전부 다시 몰려옵니다.
서버가 값에 약간의 지터를 섞거나, 클라이언트 쪽에서 [재시도에 지터를 넣는](/blog/retry-timeout-budget-circuit-breaker/) 규약이 필요합니다. 제한을 걸어놓고 동기화된 재시도 폭풍을 만드는 건 흔한 자충수입니다.

## 인스턴스가 여러 대일 때, 그리고 Redis가 죽을 때

애플리케이션 인스턴스가 여러 대면 카운터는 공유돼야 합니다. 메모리 안에서 세면 10대에서는 한도가 10배가 됩니다.
그래서 Redis 같은 공용 저장소로 가는데, 대신 **모든 요청이 네트워크 왕복을 한 번 더 합니다.**

여기서 두 가지를 결정해야 합니다.

첫째, 레이트 리밋 조회의 타임아웃. 보호하려고 넣은 장치가 지연의 원인이 되면 안 되니, 이 호출의 타임아웃은 아주 짧아야 합니다. 수십 밀리초 수준입니다.

둘째, **Redis가 응답하지 않을 때 통과시킬 것인가 막을 것인가.**

```typescript
try {
  const { allowed, retryAfterMs } = await withTimeout(check(key), 50);
  if (!allowed) return reject(retryAfterMs);
} catch (err) {
  rateLimiterErrors.inc();
  // fail open: 제한 장치가 죽었다고 서비스까지 멈추지는 않는다
  logger.warn({ err }, 'rate limiter unavailable, allowing request');
}
```

정답은 목적에 달려 있습니다.

- **과부하 보호**가 목적이면 열어두는 쪽(fail open)이 대개 낫습니다. Redis 장애로 전체 서비스가 멈추는 건 과한 대가입니다.
- **남용 차단**이 목적이면 닫는 쪽(fail closed)을 고려합니다. 로그인 시도 제한이 꺼진 채로 열려 있는 상태는 그 자체로 사고입니다.

경로마다 다르게 가져가는 것도 충분히 합리적인 선택입니다. 중요한 건 이 동작을 **의식적으로 고르고 문서에 남기는 것**입니다. 기본값으로 굴러가다가 장애 때 발견하면 늦습니다.

열어두기로 했다면 인스턴스 로컬 폴백을 붙여두는 방법도 있습니다. Redis가 없을 때는 인스턴스별로 `한도 / 인스턴스 수` 만큼만 허용하는 식입니다. 정확하진 않지만 무제한보다는 낫습니다.

## 어디에 둘 것인가

같은 알고리즘이라도 어느 계층에 놓느냐에 따라 막아주는 범위가 달라집니다.

- **엣지(CDN·WAF)** — 애플리케이션에 트래픽이 닿기 전에 막습니다. 대량 공격에는 여기가 유일하게 의미 있는 자리입니다. 대신 사용자·테넌트 같은 도메인 정보를 모릅니다.
- **게이트웨이·리버스 프록시** — 애플리케이션 코드를 건드리지 않고 경로별로 걸 수 있습니다. Nginx의 `limit_req`처럼 대부분의 프록시가 기본 기능으로 제공합니다. 인증 정보는 제한적으로만 쓸 수 있습니다.
- **애플리케이션** — 사용자·플랜·요청 무게 같은 도메인 정보를 전부 쓸 수 있습니다. 대신 요청이 이미 서버까지 들어온 뒤이고, 제한 로직 자체가 리소스를 씁니다.

셋 중 하나를 고르는 문제가 아니라 **역할이 다른 층을 겹쳐 쌓는 쪽**에 가깝습니다.
엣지에서 대량 트래픽을 걷어내고, 애플리케이션에서 플랜별 한도를 정교하게 거는 구성이 흔합니다.

마지막으로, 어떤 방식을 쓰든 **거절된 요청을 지표로 남겨야** 합니다. 키 종류별 거절 건수와 상위 주체 목록 정도면 충분합니다.
이게 없으면 한도가 너무 빡빡해서 정상 사용자를 막고 있는 건지, 실제로 남용을 막고 있는 건지 구분할 방법이 없습니다.
레이트 리밋에서 가장 흔한 실패는 알고리즘을 잘못 고른 게 아니라, 잘못 고른 걸 아무도 모르는 상태로 몇 달이 지나는 쪽입니다.
