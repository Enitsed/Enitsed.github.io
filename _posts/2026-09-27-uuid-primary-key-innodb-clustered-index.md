행이 1000만 개를 넘어가면서 `INSERT` 지연이 슬금슬금 올라갑니다. 쿼리도 인덱스도 그대로고, 디스크 IOPS도 CPU도 한도에 닿지 않았습니다.
읽기는 여전히 빠른데 쓰기만 느립니다.

원인이 데이터 양이 아니라 **행이 들어가는 자리**인 경우가 있습니다. 기본키를 어떻게 정했는지가 여기서 드러납니다.

## InnoDB에서 기본키는 그냥 식별자가 아니다

다른 엔진을 쓰다 오면 기본키를 "행을 고유하게 만드는 제약"으로만 생각하기 쉽습니다. InnoDB에서는 그보다 훨씬 많은 것을 결정합니다.

InnoDB 테이블은 **클러스터드 인덱스**입니다. 기본키로 만든 B+트리의 리프 페이지 안에 행 데이터 전체가 들어 있습니다.
테이블과 기본키 인덱스가 따로 있는 게 아니라, 같은 것입니다.

기본키를 선언하지 않으면 InnoDB가 알아서 고릅니다. NOT NULL인 유니크 인덱스가 있으면 그걸 쓰고, 그것도 없으면 내부적으로 감춰진 행 ID를 만들어 씁니다.
어느 쪽이든 "클러스터드 인덱스가 없는 InnoDB 테이블"은 존재하지 않습니다.

여기서 두 가지 성질이 따라옵니다.

**첫째, 행은 기본키 순서로 물리적으로 배치됩니다.** 새 행이 어느 페이지에 들어갈지는 기본키 값이 정합니다. 값이 정해지는 순간 자리도 정해집니다.

**둘째, 모든 보조 인덱스가 기본키 값을 들고 있습니다.** 보조 인덱스의 리프에는 행의 물리 주소가 아니라 기본키 값이 저장됩니다.
보조 인덱스로 찾은 다음 그 기본키로 클러스터드 인덱스를 한 번 더 타는 구조입니다.

두 번째 성질의 결과가 생각보다 큽니다. 기본키가 넓으면 그 폭이 **보조 인덱스 개수만큼 곱해져서** 디스크와 메모리를 먹습니다.

## 랜덤 키가 만드는 비용

기본키가 증가하는 값이면 새 행은 항상 트리의 오른쪽 끝 페이지로 갑니다. 그 페이지 하나만 메모리에 있으면 되고, 가득 차면 새 페이지를 이어 붙입니다.

기본키가 랜덤이면 이야기가 달라집니다.

```text
순차 키                      랜덤 키
[p1][p2][p3][p4*]           [p1*][p2][p3*][p4][p5*][p6]
              ↑ 항상 여기      ↑    매번 다른 자리    ↑
```

### 페이지 분할과 단편화

새 행이 들어갈 페이지가 이미 꽉 차 있으면 InnoDB는 그 페이지를 쪼갭니다. 대략 절반씩 나눠 갖고, 양쪽 모두 절반쯤 빈 상태로 남습니다.

순차 삽입에서는 이 일이 거의 일어나지 않습니다. 삽입 지점이 페이지 끝이면 InnoDB가 반으로 쪼개는 대신 새 페이지를 붙이는 쪽으로 처리해서, 페이지가 꽉 채워집니다.
랜덤 삽입에서는 분할이 상시로 일어나고, 그 결과 **같은 행 수를 담는 데 더 많은 페이지**를 씁니다.

페이지가 늘어나면 트리 높이가 올라갈 수 있고, 무엇보다 버퍼 풀에 담아야 할 양이 늘어납니다. 읽기까지 같이 느려지는 경로가 여기서 생깁니다.

### 삽입할 페이지를 먼저 읽어야 한다

더 직접적인 비용은 이쪽입니다. 행을 쓰려면 대상 페이지가 버퍼 풀에 있어야 합니다. 없으면 **디스크에서 읽어온 다음에** 씁니다.

순차 키라면 대상 페이지는 방금 전 삽입에서 이미 메모리에 올라와 있습니다. 랜덤 키는 매번 다른 페이지를 찾아가므로, 테이블이 버퍼 풀보다 커지는 순간부터 삽입마다 읽기가 한 번씩 붙습니다.

> 보조 인덱스 쪽에는 변경을 모아뒀다가 나중에 반영하는 완충 장치가 있습니다(버전에 따라 동작과 기본값이 다르니 쓰는 버전의 문서를 확인하세요).
> 클러스터드 인덱스에는 해당하지 않습니다. 리프에 행 데이터가 있으니 미룰 수가 없습니다.

"테이블이 버퍼 풀보다 커지는 순간"이라는 조건 때문에, 이 문제는 **처음에는 안 보이다가 어느 시점부터 갑자기 나타납니다.**
개발 환경과 초기 운영에서는 데이터가 전부 메모리에 들어가니 랜덤 키의 대가가 0에 가깝습니다. 그래서 설계 단계에서 잡지 않으면 나중에 비싸게 갚습니다.

### 폭이 곱해진다

기본키 폭은 보조 인덱스마다 복제됩니다. 어림셈을 해보면 감이 옵니다.

1000만 행에 보조 인덱스가 3개인 테이블에서, 기본키를 36자 문자열로 두느냐 16바이트 이진값으로 두느냐의 차이는 행당 20바이트입니다.
클러스터드 인덱스와 보조 인덱스 3개에 각각 실리므로 대략 `20바이트 × 1000만 × 4 ≈ 800MB`. 인덱스 오버헤드와 내부 노드까지 더하면 더 커집니다.

문자셋까지 고려하면 격차가 벌어집니다. `utf8mb4`에서 `CHAR(36)`은 정의상 문자당 최대 4바이트라 **최대 144바이트**를 잡습니다.
UUID는 16진수와 하이픈뿐이라 아스키 계열 문자셋이나 `BINARY(16)`으로 저장하는 편이 맞습니다.

현재 상태는 바로 볼 수 있습니다.

```sql
SELECT TABLE_NAME,
       ROUND(DATA_LENGTH  / 1024 / 1024) AS data_mb,
       ROUND(INDEX_LENGTH / 1024 / 1024) AS index_mb,
       ROUND(DATA_FREE    / 1024 / 1024) AS free_mb
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE()
ORDER BY DATA_LENGTH DESC
LIMIT 10;
```

`INDEX_LENGTH`가 `DATA_LENGTH`에 육박하거나 넘는다면 기본키 폭을 의심할 만합니다. 값 자체는 추정치라 정확한 측정이 아니라 비율을 보는 용도로 씁니다.

버퍼 풀이 실제로 모자란지도 같이 봅니다.

```sql
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
-- 히트율 ≈ 1 - (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)
```

`Innodb_buffer_pool_reads`는 디스크까지 내려간 횟수입니다. 이 값이 꾸준히 오르고 있다면 워킹셋이 메모리를 넘어선 것이고, 랜덤 키의 비용이 실제로 청구되고 있는 상태입니다.

## 그럼 왜 UUID를 쓰는가

여기까지 읽으면 `BIGINT AUTO_INCREMENT`로 돌아가면 될 것 같지만, UUID를 고른 이유들도 대체로 정당합니다.

- **애플리케이션에서 미리 만들 수 있습니다.** DB에 다녀오기 전에 ID가 정해지므로, 연관 객체를 한 번에 조립하거나 [아웃박스 이벤트](/blog/transactional-outbox-pattern/)에 ID를 미리 실을 수 있습니다.
- **여러 곳에서 동시에 만들어도 충돌하지 않습니다.** 샤드나 서비스별로 번호 대역을 나눠 관리할 필요가 없습니다.
- **밖으로 내보내도 열거되지 않습니다.** `/orders/1024`는 옆 번호를 찍어보게 만들고, 순번은 그 자체로 누적 건수를 알려줍니다.
- **데이터를 합치기 쉽습니다.** 별도 환경의 데이터를 가져올 때 ID 재발급이 필요 없습니다.

문제는 UUID 자체가 아니라 **랜덤 UUID(버전 4)를 기본키로 쓰는 것**입니다. 위 장점 중 어느 것도 "값이 완전히 무작위여야 한다"를 요구하지 않습니다.

## 시간 순서를 앞에 둔 ID

UUIDv7은 이 지점을 겨냥한 형식입니다. 128비트 중 **앞 48비트를 유닉스 밀리초 타임스탬프**로 쓰고, 버전·변형 비트를 뺀 나머지를 난수로 채웁니다.

앞자리가 시간이라 값이 대체로 증가하고, 그래서 삽입이 트리 오른쪽에 모입니다. 뒤쪽 난수 덕분에 여전히 추측하거나 열거할 수는 없습니다.
UUID 형식과 파싱 방식은 기존 버전과 같아서, 쓰던 자료형과 라이브러리를 대부분 그대로 씁니다.

> UUIDv7은 RFC 9562에 정의돼 있습니다. **같은 밀리초 안에서의 단조 증가는 형식이 보장하지 않습니다.**
> 필요하면 구현이 카운터를 두는 방식으로 채웁니다. 순서에 기대는 로직을 짤 거라면 쓰는 구현이 그걸 하는지 확인해야 합니다.

직접 만들 일은 거의 없지만, 바이트가 어떻게 배치되는지 보면 성질이 명확해집니다.

```typescript
import { randomBytes } from "node:crypto";

export function uuidv7(): string {
  const bytes = randomBytes(16);

  // 상위 48비트(바이트 0~5)를 유닉스 밀리초 타임스탬프로 덮어쓴다
  let t = Date.now();
  for (let i = 5; i >= 0; i--) {
    bytes[i] = t % 256;
    t = Math.floor(t / 256);
  }

  bytes[6] = 0x70 | (bytes[6] & 0x0f);  // 버전 7
  bytes[8] = 0x80 | (bytes[8] & 0x3f);  // 변형 비트

  const hex = bytes.toString("hex");
  return [
    hex.slice(0, 8), hex.slice(8, 12), hex.slice(12, 16),
    hex.slice(16, 20), hex.slice(20),
  ].join("-");
}
```

타임스탬프가 맨 앞에 있으니 **문자열로 정렬해도 시간순**이 됩니다. 16진수 소문자는 `0`~`9`가 `a`~`f`보다 앞이라 사전순과 수치순이 어긋나지 않습니다.

ULID도 같은 발상입니다. 앞 48비트가 밀리초 타임스탬프이고 나머지 80비트가 난수인데, 표기를 26자 Base32로 합니다.
텍스트 상태로도 정렬되고 하이픈이 없어 짧지만, UUID 자료형이나 기존 도구와 바로 맞물리지는 않습니다. 이진으로 풀면 똑같이 16바이트입니다.

MySQL 내장 `UUID()`는 버전 1을 만듭니다. 버전 4나 7이 필요하면 애플리케이션에서 생성하는 것이 일반적이고, 데이터베이스·배포판에 따라 내장 함수를 제공하기도 하니 쓰는 쪽 문서를 확인하세요.

## 저장은 16바이트로

형식을 정했으면 저장 형식을 정합니다. 결론은 `BINARY(16)`입니다.

```sql
CREATE TABLE orders (
  id          BINARY(16)   NOT NULL,
  user_id     BINARY(16)   NOT NULL,
  status      VARCHAR(20)  NOT NULL,
  amount      DECIMAL(12,2) NOT NULL,
  created_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_user_created (user_id, created_at)
);
```

MySQL 8.0에는 변환 함수가 있습니다.

```sql
INSERT INTO orders (id, user_id, status, amount)
VALUES (UUID_TO_BIN(?), UUID_TO_BIN(?), 'pending', 10000);

SELECT BIN_TO_UUID(id) AS id, status
FROM orders
WHERE id = UUID_TO_BIN(?);
```

여기에 함정이 하나 있습니다. `UUID_TO_BIN`의 두 번째 인자 `swap_flag`는 **버전 1 UUID의 시간 필드 앞뒤를 바꿔** 순차성을 만들어주는 옵션입니다.
버전 7에는 이미 타임스탬프가 앞에 있으니 이걸 켜면 오히려 순서가 망가집니다.

> `swap_flag`는 `UUID_TO_BIN`과 `BIN_TO_UUID`에서 **같은 값**을 써야 합니다. 한쪽만 켜면 되돌린 문자열이 원본과 달라집니다.
> 버전 7이나 ULID를 쓴다면 양쪽 모두 끄는 쪽(기본값)으로 통일하세요.

조회할 때 변환을 빠뜨리면 이진 컬럼과 36자 문자열을 비교하게 되어 **오류 없이 빈 결과**가 돌아옵니다. 원인을 찾기 번거로운 종류의 버그라, 변환을 한 군데로 모아두는 편이 안전합니다.
사람이 눈으로 볼 일이 잦다면 생성 컬럼을 하나 붙여두는 방법도 있습니다.

```sql
ALTER TABLE orders
  ADD COLUMN id_text CHAR(36)
  GENERATED ALWAYS AS (BIN_TO_UUID(id)) VIRTUAL;
```

`VIRTUAL`이라 저장 공간을 쓰지 않고, 관리 쿼리나 대시보드에서 `id_text`로 읽으면 됩니다. 애플리케이션 경로에서는 여전히 `id`를 씁니다.

## 정렬 가능한 키가 덤으로 주는 것

기본키가 시간순이면 [커서 페이지네이션](/blog/cursor-pagination-keyset/)이 단순해집니다.

`created_at`으로 정렬하려면 동점을 깨기 위해 `(created_at, id)` 복합 커서를 써야 하는데, 기본키 자체가 시간순이면 대략의 최신순 정렬을 컬럼 하나로 처리할 수 있습니다.

```sql
SELECT * FROM orders
WHERE id < ?          -- 직전 페이지의 마지막 id
ORDER BY id DESC
LIMIT 20;
```

"대략"이라는 단서가 중요합니다. 같은 밀리초 안의 순서는 보장되지 않고, 서버 간 시계 차이만큼 어긋날 수 있습니다.
**목록을 빠짐없이 한 번씩 훑는 용도로는 충분하고, 정확한 시간순이 계약인 자리에는 쓰면 안 됩니다.** 정산 마감처럼 경계가 중요한 곳에는 명시적인 타임스탬프 컬럼을 그대로 두세요.

범위 삭제도 쉬워집니다. 보관 기간이 지난 데이터를 지울 때 대상이 트리 앞쪽에 모여 있어, 오래된 페이지가 통째로 비워집니다. 랜덤 키에서는 삭제가 온 페이지에 흩뿌려져 빈 공간만 남습니다.

## 내주는 것

정렬 가능한 ID가 공짜는 아닙니다. 두 가지를 내줍니다.

**생성 시각이 노출됩니다.** UUIDv7 문자열 앞자리를 밀리초 단위로 되돌릴 수 있습니다.
이미 API 응답에 `created_at`을 내보내고 있다면 새로 새는 정보가 없지만, 그렇지 않다면 판단이 필요합니다.
다만 랜덤 UUID를 고른 이유가 대개 "열거 불가능성"이라는 점은 짚어둘 만합니다. 그 성질은 뒤쪽 난수 비트가 계속 지켜줍니다. 잃는 건 시각 은닉이지 추측 불가능성이 아닙니다.

**삽입 지점이 한 곳에 몰립니다.** 동시 삽입이 많으면 트리 오른쪽 끝 페이지를 두고 경합이 생깁니다. 랜덤 키는 이걸 자연스럽게 분산시키고 있었던 셈입니다.
`AUTO_INCREMENT`가 예전부터 안고 있던 것과 같은 성질이라 대부분의 서비스에서는 문제가 되지 않지만, 쓰기가 극단적으로 몰리는 테이블이라면 "랜덤이 유리한 경우"가 실제로 존재한다는 점은 알아둘 만합니다.

정리하면 선택지는 이렇게 놓입니다.

| 방식 | 삽입 위치 | 키 폭 | 미리 생성 | 시각 노출 | 열거 가능 |
| --- | --- | --- | --- | --- | --- |
| `BIGINT AUTO_INCREMENT` | 끝에 추가 | 8B | 불가 | 순번으로 추정 | 가능 |
| UUIDv4 `BINARY(16)` | 무작위 | 16B | 가능 | 없음 | 불가 |
| UUIDv7 · ULID `BINARY(16)` | 대체로 끝 | 16B | 가능 | ms 단위 | 불가 |
| `BIGINT` 기본키 + 공개용 UUID 컬럼 | 끝에 추가 | 8B + 유니크 인덱스 | 공개 ID만 | 없음 | 불가 |

마지막 줄이 의외로 실용적인 선택입니다. 내부 조인과 외래 키는 좁은 정수로 돌리고, 밖으로 나가는 식별자만 UUID로 둡니다.
대신 공개 ID로 들어온 요청은 유니크 인덱스를 한 번 더 타야 하고, 애플리케이션 안에 식별자가 두 개 존재하는 부담이 생깁니다. 어느 쪽 복잡도를 감당할지의 문제입니다.

## 이미 v4로 굴러가고 있다면

새 테이블이면 지금 고르면 되지만, 대개는 이미 돌아가는 테이블이 문제입니다.

기본키를 바꾸는 건 가벼운 작업이 아닙니다. 클러스터드 인덱스를 다시 만드는 일이고, 보조 인덱스는 기본키 값을 들고 있으니 **전부 같이 재작성**됩니다.
큰 테이블에서는 [온라인 스키마 변경](/blog/mysql-online-schema-change/) 도구를 붙여야 하는 규모의 작업이고, 그 사이 외래 키와 애플리케이션 코드도 함께 움직여야 합니다.

그래서 순서를 이렇게 잡는 편이 현실적입니다.

1. **새로 만드는 테이블부터** 정렬 가능한 ID와 `BINARY(16)`으로 통일합니다. 여기는 비용이 0입니다.
2. **가장 큰 테이블 하나**를 골라 지금 상태를 측정합니다. 인덱스 크기, 버퍼 풀 히트율, 삽입 지연. 숫자가 없으면 바꿔야 할 이유도, 바꾼 뒤 좋아졌다는 근거도 없습니다.
3. 측정값이 실제로 나쁠 때만 교체를 계획합니다. 행이 수십만 개이고 워킹셋이 메모리에 다 들어간다면, 지금 바꿔서 얻을 게 거의 없습니다.

`CHAR(36)`으로 저장 중이라면 값 형식은 그대로 두고 **저장 형식만 이진으로 바꾸는 것**이 먼저 검토할 만합니다.
값이 랜덤이라 삽입 위치 문제는 남지만, 인덱스 폭이 절반 이하로 줄어드는 효과는 즉시 나옵니다.

무엇을 하든 순서는 같습니다. 측정하고, 하나 바꾸고, 다시 측정합니다.
기본키는 한 번 정하면 되돌리기 가장 비싼 결정 중 하나라서, 바꿀 때도 감이 아니라 숫자로 결정해야 합니다.
