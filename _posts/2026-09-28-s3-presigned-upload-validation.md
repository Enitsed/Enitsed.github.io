파일 업로드는 처음엔 서버가 받습니다. 그러다 용량이 커지면서 타임아웃이 늘고, 업로드 하나가 워커를 몇 십 초씩 붙잡습니다.

그래서 브라우저가 S3로 직접 올리게 바꿉니다. 부하는 정말로 사라집니다.
**같이 사라지는 게 있습니다.** 크기를 재고 확장자를 보고 저장 경로를 정하던 코드가 전부 요청 경로에서 빠집니다.

## 서버를 거치는 업로드가 먼저 막히는 곳

서버 경유 업로드의 비용은 대역폭이 아니라 **점유 시간**입니다.

100MB를 올리는 클라이언트가 느린 회선이라면 그 요청은 몇 분간 살아 있습니다. 그동안 워커 하나, 커넥션 하나, 임시 디스크 공간이 묶여 있습니다.
동시 업로드가 몇 개 겹치면 업로드와 무관한 API까지 같이 느려집니다. [커넥션 풀이 마르는 것](/blog/db-connection-pool-exhaustion/)과 같은 모양입니다.

앞단에 프록시나 게이트웨이가 있으면 여기에 요청 본문 크기 상한이 또 걸립니다. 서버리스 환경이라면 페이로드 한도가 더 낮고, 그 한도는 우리가 조정할 수 없습니다.

그래서 저장소에 직접 올리는 쪽으로 갑니다. 다만 이 전환은 **최적화가 아니라 신뢰 경계를 옮기는 일**입니다.

## 프리사인이 옮기는 것은 권한이다

프리사인 URL은 "이 작업을 이 조건으로 해도 된다"는 서명입니다. 서버는 자기 권한으로 서명만 해주고, 실제 바이트 전송은 클라이언트와 S3 사이에서 일어납니다.

핵심은 이렇습니다. **서명에 조건으로 박아넣지 않은 것은 강제되지 않습니다.**
서명한 다음에 "업로드된 파일이 10MB 이하인지" 확인하려면 이미 올라간 객체를 보는 수밖에 없습니다. 그때는 이미 스토리지 비용이 발생했고, 악의적인 클라이언트라면 그걸 반복할 수 있습니다.

그래서 서명 시점에 무엇을 묶을 수 있는지가 설계의 전부가 됩니다. 그리고 여기서 PUT과 POST가 갈립니다.

## PUT과 POST가 강제할 수 있는 것이 다르다

같은 프리사인인데 방식이 두 가지고, 자주 쓰이는 쪽(PUT)이 정작 크기를 못 막습니다.

| | 프리사인 PUT | 프리사인 POST (정책) |
| --- | --- | --- |
| 요청 형태 | URL 하나에 `PUT`, 본문이 파일 | `multipart/form-data` + 서명 필드들 |
| 키 고정 | 서명에 포함 | 고정 또는 `starts-with`로 접두어 제한 |
| 크기 상한 | **실질적으로 못 막음** | `content-length-range` 조건 |
| Content-Type | 서명 헤더로 값 일치 강제 | 고정 또는 `starts-with` |
| 쓰기 편한 쪽 | 클라이언트 코드가 단순 | 필드를 순서대로 붙여야 함 |

PUT 쪽 한계가 중요합니다. SigV4 서명에 크기 조건을 넣는 통로가 없어서, **프리사인 PUT URL 하나로는 업로드 크기를 제한할 수 없습니다.**
`Content-Length`를 서명 헤더로 묶는 우회가 거론되지만, 그러려면 발급 시점에 정확한 바이트 수를 알아야 하고 SDK 헬퍼들이 이걸 지원하지 않습니다.

크기를 막는 게 요구사항이면 POST 정책을 씁니다.

```typescript
import { createPresignedPost } from "@aws-sdk/s3-presigned-post";

const key = `uploads/${userId}/${crypto.randomUUID()}`; // 서버가 정한다

const { url, fields } = await createPresignedPost(s3, {
  Bucket: BUCKET,
  Key: key,
  Expires: 300,
  Fields: { "Content-Type": "image/jpeg" },
  Conditions: [
    ["content-length-range", 1, 10 * 1024 * 1024], // 1B ~ 10MB
    ["starts-with", "$Content-Type", "image/"],
  ],
});
```

클라이언트는 받은 필드를 그대로 붙이고 **파일을 마지막에** 넣습니다. 순서가 어긋나면 S3가 거부합니다.

```typescript
const form = new FormData();
Object.entries(fields).forEach(([k, v]) => form.append(k, v as string));
form.append("file", file); // 반드시 맨 뒤

const res = await fetch(url, { method: "POST", body: form });
```

크기 상한을 넘으면 S3가 정책 위반으로 응답을 돌려줍니다. 서버는 이 판단에 관여하지 않습니다.

> 단일 요청으로 올릴 수 있는 최대 객체 크기, 멀티파트 파트의 최소 크기 같은 한도는 공식 문서에서 확인하세요.
> 애플리케이션 상한(예: 10MB)은 그와 별개로 우리가 정하는 값이고, 정책에 명시하지 않으면 존재하지 않는 값입니다.

## 키를 클라이언트가 정하게 두지 않는다

프리사인을 발급하는 API가 파일명을 받아 그대로 키로 쓰는 코드가 흔합니다.

S3 키는 디렉터리가 아니라 평평한 문자열이라 `../`로 상위로 빠져나가는 일은 없습니다. 문제는 다른 쪽입니다.
클라이언트가 키를 정하면 **아무 키나 고를 수 있습니다.** 남의 객체를 덮어쓰거나, 사용자별 접두어 규칙을 무시할 수 있습니다.

원본 파일명이 필요하면 키가 아니라 메타데이터나 DB 컬럼에 담습니다. 키는 서버가 만듭니다.

- 사용자 식별자를 접두어에 넣어 조회·권한·라이프사이클 규칙의 단위를 만든다
- 파일명은 난수로 두어 추측·열거를 막는다 (다운로드 쪽은 [서명 쿠키](/blog/cloudfront-signed-cookie/)로 따로 통제)
- 확장자를 붙일지는 선택이다. 붙이면 편하고, 붙이면 클라이언트가 준 문자열이 키에 섞인다

POST 정책이라면 접두어만 묶고 뒷부분은 클라이언트에 맡기는 중간 선택도 있습니다.

```typescript
Conditions: [["starts-with", "$key", `uploads/${userId}/`]]
```

서명 발급 API 자체에도 제한이 필요합니다. 인증 없이 열어두면 누구나 우리 버킷에 쓸 수 있는 티켓을 무한정 받아갑니다. 발급 [횟수 제한](/blog/rate-limiting-token-bucket-redis/)까지 같이 걸어두는 편이 안전합니다.

## Content-Type은 클라이언트가 말하는 것이다

`Content-Type`을 서명에 묶으면 값이 일치하지 않는 요청은 거부됩니다. 하지만 그건 **선언한 값이 일치한다는 뜻일 뿐**이고, 실제 바이트가 무엇인지는 보장하지 않습니다.
`image/jpeg`라고 말하면서 아무 파일이나 올릴 수 있습니다.

그러니 형식 검증은 업로드 이후로 옮겨갑니다. 그리고 그 사이에 객체는 이미 버킷에 있습니다.

실무에서 자주 쓰는 순서는 이렇습니다.

1. 업로드 전용 버킷(또는 접두어)에 받는다. 이 영역은 서비스에서 직접 서빙하지 않는다
2. 업로드 완료 시점에 실제 바이트 앞부분을 읽어 형식을 확인한다
3. 통과한 것만 서빙 영역으로 옮기거나 처리 결과물을 만든다

```typescript
const head = await s3.send(new HeadObjectCommand({ Bucket: BUCKET, Key: key }));
if ((head.ContentLength ?? 0) > MAX_BYTES) { /* 삭제하고 거절 */ }
// 선언된 head.ContentType은 참고용. 형식은 앞부분 바이트를 직접 본다
```

이미지를 리사이즈하는 파이프라인이 이미 있다면 그 단계가 사실상 검증 역할을 합니다. 디코딩에 실패하는 파일은 거기서 걸러집니다.

## 업로드가 끝난 것을 서버는 어떻게 아는가

직접 업로드에서 서버는 전송 과정을 보지 못합니다. 그래서 완료를 알려주는 경로가 따로 필요하고, 여기서 두 가지 선택이 생깁니다.

**클라이언트 콜백** — 업로드가 끝나면 브라우저가 서버에 알려줍니다. 구현이 간단하고 사용자 컨텍스트가 그대로 살아 있습니다.
대신 브라우저를 닫거나 네트워크가 끊기면 **콜백만 유실됩니다.** 객체는 S3에 있는데 DB에는 없는 상태가 남습니다.

**S3 이벤트 알림** — 버킷이 객체 생성 이벤트를 큐나 함수로 보냅니다. 클라이언트 사정과 무관하게 도착합니다.
대신 어느 사용자의 어떤 요청이었는지는 키와 메타데이터로 되짚어야 하고, 처리 코드가 비동기 경로로 빠집니다.

```json
{ "Events": ["s3:ObjectCreated:Put",
             "s3:ObjectCreated:Post",
             "s3:ObjectCreated:CompleteMultipartUpload"] }
```

멀티파트로 올라온 객체는 앞의 두 이벤트로 오지 않습니다. 세 가지를 같이 걸어두지 않으면 **큰 파일만 조용히 누락됩니다.**

둘 다 쓰는 구성이 실용적입니다. 콜백으로 빠른 응답을 만들고, 이벤트를 진실의 출처로 둡니다. 다만 두 경로가 같은 객체를 두 번 처리하게 되니 처리 단계는 키 기준으로 [멱등](/blog/idempotency-key-payment-api/)해야 합니다.
이벤트 알림 자체도 최소 한 번 전달이라 중복은 어차피 옵니다.

서명을 발급할 때 `pending` 레코드를 먼저 만들어두면 추적이 쉬워집니다. 완료 신호가 오면 상태를 올리고, 오래 `pending`인 것은 실패로 정리합니다.
그 레코드가 없으면 버킷에 뭐가 쓰레기인지 알 방법이 없습니다.

## 남는 것들 — 고아 객체와 미완료 파트

직접 업로드는 반드시 쓰레기를 남깁니다. 사용자가 중간에 그만두는 경로가 서버 경유 방식보다 훨씬 많기 때문입니다.

- 올라갔지만 어디서도 참조되지 않는 객체
- 시작만 하고 완료하지 않은 멀티파트 업로드의 파트들

두 번째가 특히 눈에 안 띕니다. 미완료 멀티파트의 파트는 객체 목록에 나오지 않으면서 **저장 용량은 차지합니다.**
라이프사이클 규칙으로 정리하는 게 유일하게 확실한 방법입니다.

```json
{
  "Rules": [
    {
      "ID": "abort-incomplete-mpu",
      "Status": "Enabled",
      "Filter": { "Prefix": "uploads/" },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 3 }
    },
    {
      "ID": "expire-staging",
      "Status": "Enabled",
      "Filter": { "Prefix": "uploads/" },
      "Expiration": { "Days": 7 }
    }
  ]
}
```

두 번째 규칙은 스테이징 영역을 쓰는 구조에서만 성립합니다. 검증을 통과한 객체는 다른 접두어나 버킷으로 옮기고, 스테이징에 남은 것은 버려도 되는 것으로 취급하는 설계입니다.
검증 후에도 같은 자리에 둔다면 이 규칙은 **정상 파일을 지웁니다.**

## 만료 시간과, 생각보다 빨리 죽는 서명

만료는 짧게 잡는 편이 기본입니다. 유출된 서명이 살아 있는 시간이 그만큼 줄어듭니다.

다만 너무 짧으면 느린 회선에서 실패합니다. 판단 기준은 두 가지입니다.

- 업로드 **시작**이 만료 전이면 되는지, 전송 **완료**까지 유효해야 하는지
- 실패 시 재발급이 가능한 구조인지 (가능하면 짧게 잡아도 된다)

그리고 서명 수명에는 우리가 지정하지 않은 상한이 하나 더 있습니다.

> 임시 자격 증명으로 서명하면 URL은 **그 자격 증명이 만료될 때 같이 죽습니다.** `Expires`에 더 긴 값을 넣어도 그렇습니다.
> 역할을 맡아 쓰는 환경에서는 세션 만료가 실질 상한이 됩니다. 장기 자격 증명 기준의 최대 유효 기간과 실제 상한은 공식 문서를 확인하세요.

"어제 만든 링크가 오늘 안 된다"는 대부분 여기입니다. 서명 시점이 아니라 **자격 증명의 남은 수명**을 봐야 합니다.

## CORS를 빼먹으면 로컬에서만 된다

브라우저가 다른 오리진인 S3로 직접 요청을 보내니 버킷에 CORS 설정이 필요합니다.

```json
[
  {
    "AllowedOrigins": ["https://app.example.com"],
    "AllowedMethods": ["PUT", "POST"],
    "AllowedHeaders": ["content-type"],
    "ExposeHeaders": ["ETag"]
  }
]
```

`ExposeHeaders`의 `ETag`는 멀티파트를 브라우저에서 직접 할 때 필요합니다. 파트별 `ETag`를 모아 완료 요청에 실어야 하는데, 노출하지 않으면 스크립트가 그 값을 읽지 못합니다.

## 정리하면

직접 업로드는 서버의 일을 줄이는 대신 **검증 시점을 뒤로 밀고, 정리 책임을 새로 만듭니다.**

그래서 판단은 파일 크기와 신뢰 수준으로 갈립니다.

- 작고(수 MB) 내부 사용자만 올리는 파일이면 서버 경유가 여전히 단순합니다. 검증이 한 군데 모여 있는 값이 큽니다
- 크거나 외부 사용자가 올리는 파일이면 직접 업로드로 가되, 크기 상한이 필요한 순간 PUT이 아니라 POST 정책을 고릅니다
- 어느 쪽이든 키는 서버가 만들고, 완료 감지는 이벤트를 진실로 두고, 라이프사이클 규칙은 처음부터 걸어둡니다

마지막 항목이 제일 미뤄지기 쉽습니다. 그리고 그 청구서는 몇 달 뒤 스토리지 지표에서 옵니다.
