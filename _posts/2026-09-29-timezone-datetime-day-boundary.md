일별 가입자 수를 두 군데서 뽑았는데 숫자가 다릅니다. 쿼리는 같은 문장이고 보는 테이블도 같습니다.
다른 건 그 쿼리를 어디서 돌렸는지뿐입니다.

시각 값은 저장할 때 한 번, 읽을 때 한 번, 화면에 그릴 때 또 한 번 해석됩니다.
세 지점의 기준이 같다는 보장은 어디에도 없고, **어긋나도 에러가 나지 않습니다.**

## 순간과 벽시계는 다른 값이다

먼저 갈라야 할 것이 있습니다. 시각처럼 생긴 값에는 성격이 다른 두 가지가 섞여 있습니다.

**순간(instant)** 은 지구상 어디서 보든 같은 한 점입니다. 결제가 승인된 시각, 로그가 찍힌 시각, 행이 만들어진 시각이 여기 속합니다.
표현은 지역마다 달라도 가리키는 점은 하나라, UTC로 눌러 담아도 정보가 사라지지 않습니다.

**벽시계(wall clock)** 는 "10월 3일 오전 9시" 그 자체입니다. 아직 순간이 아닙니다.
어느 지역의 9시인지가 붙어야 비로소 한 점이 됩니다. 생일, 정기 일정의 시각, 영업 시작 시간이 여기 속합니다.

이 구분이 실무에서 중요한 이유는 한쪽 방향으로만 안전하기 때문입니다.
순간을 UTC로 바꿔 저장하는 건 손해가 없습니다. 반면 벽시계를 지금의 오프셋으로 환산해 순간으로 저장하면, **원래 의미가 사라지고 규칙이 바뀌어도 되돌릴 근거가 남지 않습니다.**

## MySQL의 두 타입은 이 구분을 따라간다

`DATETIME`과 `TIMESTAMP`는 "정밀도가 다른 비슷한 타입"이 아닙니다. 저장하는 것 자체가 다릅니다.

| | DATETIME | TIMESTAMP |
| --- | --- | --- |
| 저장 형태 | 준 값 그대로 | 내부적으로 UTC |
| 읽고 쓸 때 변환 | 없음 | 세션 `time_zone` 기준으로 변환 |
| 표현 범위 | 1000-01-01 ~ 9999-12-31 | 1970-01-01 00:00:01 UTC ~ 2038-01-19 03:14:07 UTC |
| 성격 | 벽시계에 가깝다 | 순간에 가깝다 |

말로 읽으면 헷갈리니 한 번 넣어보면 분명해집니다.

```sql
CREATE TABLE tz_demo (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  dt DATETIME(6)  NOT NULL,
  ts TIMESTAMP(6) NOT NULL
);

SET time_zone = '+09:00';
INSERT INTO tz_demo (dt, ts)
VALUES ('2026-09-29 09:00:00', '2026-09-29 09:00:00');

SET time_zone = '+00:00';
SELECT dt, ts FROM tz_demo;
-- dt | 2026-09-29 09:00:00.000000
-- ts | 2026-09-29 00:00:00.000000
```

같은 리터럴을 넣었는데 다른 값이 나옵니다. 버그가 아니라 두 타입의 정의입니다.

### 세션 time_zone은 연결마다 다를 수 있다

여기서 진짜 문제는 어느 쪽이 옳으냐가 아니라, 저 `SET time_zone`을 **아무도 명시적으로 하지 않는다**는 데 있습니다.

세션 `time_zone`의 기본값은 `SYSTEM`이고, 이건 DB 서버의 OS 타임존을 따라갑니다.
그리고 접속하는 쪽이 값을 바꾸면 그 연결에서만 바뀝니다.

API 서버는 컨테이너라 UTC로 붙고, 분석하러 들어간 콘솔은 로컬 설정을 그대로 들고 들어오고, 배치 서버는 또 다르면
**같은 `TIMESTAMP` 컬럼이 접속 지점마다 다른 문자열로 보입니다.** 도입부의 "숫자가 다른 두 집계"가 대개 여기입니다.

> 이름 있는 타임존(`'Asia/Seoul'`)을 쓰려면 서버에 타임존 테이블이 적재돼 있어야 합니다.
> 적재돼 있지 않으면 `SET time_zone = 'Asia/Seoul'`은 실패하고, `CONVERT_TZ()`는 오류 대신 **NULL을 돌려줍니다.**
> 오프셋 표기(`'+09:00'`)는 적재 여부와 무관하게 동작합니다. 매니지드 DB는 대개 미리 적재해 주지만, 쓰는 제품의 문서에서 확인하세요.

`CONVERT_TZ()`가 NULL을 내는 쪽이 특히 고약합니다. 집계 쿼리 한가운데서 NULL이 나오면 그 행은 조건에서 조용히 탈락하고,
결과는 "틀린 값"이 아니라 "조금 적은 값"으로 나옵니다. 누가 세어보기 전까지는 아무도 모릅니다.

```sql
-- 타임존 테이블이 없으면 이 쿼리는 전부 NULL을 돌려준다
SELECT CONVERT_TZ(NOW(), 'UTC', 'Asia/Seoul');
```

### 2038

`TIMESTAMP`의 상한은 2038년입니다. 지금 찍는 `created_at`은 당연히 범위 안이지만,
구독 만료일이나 보증 종료일처럼 **미래를 담는 컬럼**에 `TIMESTAMP`를 쓰면 이미 오늘 문제가 됩니다.
"미래 시각은 `DATETIME`"이라는 규칙 하나만 지켜도 이 부류는 사라집니다.

### 그래서 무엇을 고르나

정답은 하나가 아니고, 어느 쪽을 골라도 대가가 있습니다.

`TIMESTAMP`는 DB가 변환을 대신 해준다는 게 장점이자 위험입니다. 세션 기준을 고정해 두면 편하고, 고정하지 않으면 위에서 본 일이 일어납니다.

`DATETIME` + "애플리케이션이 항상 UTC로 넣는다"는 규칙 쪽은 DB가 아무것도 해주지 않아서 예측이 쉽습니다.
대신 규칙을 어긴 코드가 하나 섞여 들어와도 **DB는 거부하지 않습니다.** 9시간 밀린 행이 같은 컬럼에 섞이고, 나중에는 어느 행이 어느 기준인지 가릴 방법이 없습니다.

벽시계를 저장해야 한다면 선택의 여지가 적습니다. `DATE`나 `DATETIME`으로 두고, **지역을 별도 컬럼에** 함께 남깁니다.

> MySQL 8.0.19부터 날짜·시간 리터럴에 오프셋을 붙일 수 있습니다(`'2026-09-29 09:00:00+09:00'`).
> 지원 범위와 동작은 버전마다 다르니 쓰는 버전의 문서를 확인하세요.

## 드라이버가 한 번 더 바꾼다

DB에서 값을 꺼냈다고 끝이 아닙니다. 드라이버가 문자열을 `Date`로 만드는 지점에서 해석이 또 한 번 일어납니다.

`mysql2`의 `timezone` 옵션이 그 손잡이고, **기본값은 `'local'`** 입니다. 즉 프로세스의 타임존을 따라갑니다.
같은 코드가 로컬 노트북과 UTC 컨테이너에서 다르게 동작한다는 뜻입니다.

```typescript
const pool = mysql.createPool({
  host: process.env.DB_HOST,
  timezone: 'Z',   // 드라이버가 DATETIME 문자열을 해석할 기준. 기본값은 'local'
});
```

순간을 담은 `DATETIME` 컬럼을 UTC 규칙으로 쓰고 있다면 `'Z'`로 고정하는 게 맞습니다.

벽시계를 담은 컬럼이라면 이야기가 다릅니다. 변환 자체를 하지 않는 편이 낫습니다.

```typescript
const pool = mysql.createPool({
  host: process.env.DB_HOST,
  timezone: 'Z',
  dateStrings: ['DATE', 'DATETIME'],  // 문자열 그대로 받아 애플리케이션에서 해석
});
```

`Date`는 순간을 담는 타입이라, 지역이 없는 벽시계를 `Date`로 바꾸는 순간 **없는 정보를 지어내게 됩니다.**
"2026-10-03 09:00"을 어느 지역의 9시로 볼지 드라이버가 임의로 정하는 셈입니다.

정리하면 한 값이 세 개의 손잡이를 지나갑니다.

1. DB 세션 `time_zone` — `TIMESTAMP`를 문자열로 만들 때
2. 드라이버 `timezone` — 문자열을 `Date`로 만들 때
3. 프로세스 `TZ` — 드라이버가 `'local'`일 때, 그리고 로컬 포맷팅을 할 때

셋 다 기본값이 있고, 셋 다 어긋나도 예외가 없습니다. 그래서 가장 싼 방어는 **셋을 고정하고 기동할 때 로그에 찍는 것**입니다.

```typescript
const [rows] = await pool.query<any[]>(`
  SELECT @@session.time_zone AS session_tz,
         @@global.time_zone  AS global_tz,
         NOW()               AS db_now,
         UTC_TIMESTAMP()     AS db_utc
`);

logger.info({
  processTZ: process.env.TZ ?? '(unset)',
  nodeResolved: Intl.DateTimeFormat().resolvedOptions().timeZone,
  ...rows[0],
}, 'timezone context');
```

`NOW()`와 `UTC_TIMESTAMP()`가 몇 시간 벌어져 있는지만 봐도 그 연결의 기준이 바로 드러납니다.
배포 환경이 바뀌어 기준이 달라졌을 때, 데이터가 틀어진 뒤가 아니라 기동 로그에서 알아차릴 수 있습니다.

## 하루의 경계는 어디인가

"9월 29일 가입자"를 세려면 KST 기준 9월 29일 00:00부터 9월 30일 00:00까지를 세야 합니다.
저장이 UTC라면 그 구간은 UTC로 **9월 28일 15:00 ~ 9월 29일 15:00** 입니다.

자주 보는 세 가지 형태가 각각 다른 방식으로 틀립니다.

```sql
-- 1) 컬럼에 함수를 씌우면 인덱스를 못 쓴다 (그리고 어느 지역의 날짜인지도 불분명하다)
SELECT COUNT(*) FROM users WHERE DATE(created_at) = '2026-09-29';

-- 2) created_at이 TIMESTAMP라면, 이 리터럴의 의미가 세션 time_zone에 따라 달라진다
SELECT COUNT(*) FROM users WHERE created_at >= '2026-09-29 00:00:00';

-- 3) 23:59:59로 닫으면 그 뒤 1초 미만의 행이 사라진다
SELECT COUNT(*) FROM users
WHERE created_at BETWEEN '2026-09-29 00:00:00' AND '2026-09-29 23:59:59';
```

세 번째는 컬럼이 `DATETIME(6)`처럼 소수점 자리를 가질 때 실제로 행을 흘립니다. 하루에 몇 건이라 눈에 잘 안 띄는 게 더 나쁩니다.

경계는 애플리케이션에서 UTC로 계산해 넘기고, 쿼리는 **반개구간**으로 씁니다.

```sql
SELECT COUNT(*) FROM users
WHERE created_at >= '2026-09-28 15:00:00'
  AND created_at <  '2026-09-29 15:00:00';
```

한국처럼 오프셋이 고정인 지역만 상대한다면 9시간 빼는 산술로 끝납니다.
서머타임이 있는 지역이 섞이는 순간 그 산술은 1년에 두 번 틀립니다. 그때는 오프셋을 그 시점에 물어봐야 합니다.

```typescript
// 어떤 UTC 시점에서 해당 지역의 오프셋(ms)을 구한다
function zoneOffsetMs(utcMs: number, timeZone: string): number {
  const parts = new Intl.DateTimeFormat('en-US', {
    timeZone, hour12: false,
    year: 'numeric', month: '2-digit', day: '2-digit',
    hour: '2-digit', minute: '2-digit', second: '2-digit',
  }).formatToParts(new Date(utcMs));

  const p = Object.fromEntries(parts.map(({ type, value }) => [type, value]));
  const asUTC = Date.UTC(
    Number(p.year), Number(p.month) - 1, Number(p.day),
    Number(p.hour) % 24, Number(p.minute), Number(p.second),
  );
  return asUTC - utcMs;
}

// 해당 지역의 'YYYY-MM-DD' 하루가 시작하는 순간
function zonedDayStart(dateISO: string, timeZone: string): Date {
  const [y, m, d] = dateISO.split('-').map(Number);
  const guess = Date.UTC(y, m - 1, d, 0, 0, 0);
  return new Date(guess - zoneOffsetMs(guess, timeZone));
}
```

`% 24`가 붙어 있는 이유는 `hour12: false`가 자정을 `24`로 포맷하는 경우가 있기 때문입니다. 안 붙이면 자정만 하루 밀립니다.

이 구현에도 한계가 있습니다. 오프셋을 "추정한 시점"에서 구하기 때문에, **서머타임이 바뀌는 그날 하루는 보정을 한 번 더 해야** 정확합니다.
그리고 전환 때문에 아예 존재하지 않는 시각(봄에 02:00이 건너뛰는 구간)과 두 번 있는 시각(가을)이 생기는데, 이걸 어떻게 처리할지는 구현마다 규칙이 다릅니다.
여러 지역을 진지하게 다뤄야 한다면 이 부분은 검증된 라이브러리에 맡기는 편이 낫습니다.

> 표준 `Temporal` API는 2026년 3월 TC39 Stage 4에 도달했습니다. 지역과 벽시계를 타입으로 구분해 다루도록 설계돼 있어 위 계산을 훨씬 단순하게 만듭니다.
> 다만 브라우저와 런타임별 지원 시점이 제각각이니, 도입 전에 쓰는 런타임의 현행 지원 상태를 확인하세요.

## 순간이 아닌 것을 순간으로 저장하면

"매주 화요일 오전 9시에 알림"을 받겠다는 설정을 생각해 봅시다.
가장 간단한 구현은 다음 발송 시각을 UTC로 계산해 한 컬럼에 넣는 것입니다. 스케줄러가 인덱스로 집어가기도 좋습니다.

문제는 **타임존 규칙이 바뀌는 날** 드러납니다. 그 지역이 서머타임을 도입하거나 폐지하거나 오프셋을 조정하면, 저장해 둔 순간은 더 이상 오전 9시가 아닙니다.
이미 8시나 10시가 되어 버렸고, 원본을 버렸으니 되돌릴 방법이 없습니다.

타임존 데이터베이스(tzdata)는 매년 여러 차례 갱신됩니다. 규칙이 기술적 사실이 아니라 정치적 결정이라, 예고 기간이 짧은 변경도 있습니다.

그래서 미래의 벽시계 약속은 벽시계로 저장하고, 순간은 **파생값으로** 둡니다.

```sql
CREATE TABLE reminder (
  id           BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  user_id      BIGINT UNSIGNED NOT NULL,
  weekday      TINYINT      NOT NULL,   -- 2 = 화요일
  local_time   TIME         NOT NULL,   -- 09:00:00
  time_zone    VARCHAR(64)  NOT NULL,   -- 'Asia/Seoul'
  next_fire_at DATETIME(6)  NOT NULL,   -- 위 셋으로 계산한 UTC 시각 (파생값)
  KEY idx_next_fire (next_fire_at)
);
```

`next_fire_at`은 스케줄러가 인덱스로 훑기 위한 캐시입니다. 원본은 위의 세 컬럼입니다.
tzdata가 갱신되면 파생값만 다시 계산하면 됩니다. 순서를 반대로 잡았다면 다시 계산할 근거 자체가 없습니다.

과거의 순간에는 이 문제가 없습니다. 이미 일어난 일이라 그때의 오프셋이 확정돼 있고, 나중에 규칙이 바뀌어도 과거 구간은 그대로입니다.
**흔들리는 건 언제나 미래뿐입니다.**

## 경계 밖으로 나갈 때

시스템 바깥으로 값을 내보내는 지점마다 규칙을 정해둬야 합니다.

**API 응답**은 오프셋을 포함한 ISO 8601 / RFC 3339로 내보냅니다. `2026-09-29T09:00:00+09:00` 또는 `2026-09-29T00:00:00Z` 형태입니다.
오프셋 없는 `"2026-09-29 09:00:00"`을 내보내면 받는 쪽이 자기 기준으로 해석하고, 그 해석은 클라이언트마다 다릅니다.
`Date`를 그냥 JSON으로 직렬화하면 `toISOString()`이 불려 `Z`가 붙으니 대개 안전합니다. 위험한 쪽은 `dateStrings`로 받은 문자열을 손대지 않고 그대로 실어 보내는 경우입니다.

**요청으로 날짜를 받을 때**는 어느 지역 기준인지를 함께 받거나, 서버 기준을 문서에 명시합니다.
`?date=2026-09-29`만 받아놓고 서버가 UTC로 해석하면, 한국 사용자가 보는 "오늘"과 9시간 어긋납니다.

**사람이 읽는 출력**(CSV, 리포트, 알림 문구)은 반대로 로컬 시각으로 변환해서 내보내되, 어느 지역 기준인지를 헤더나 각주에 적어둡니다.
`가입일시(KST)` 한 줄이 나중의 문의를 많이 줄여줍니다.

**배치와 크론**은 실행 환경의 기준을 확인합니다. 컨테이너 기본 타임존은 대개 UTC라, "매일 자정 집계"가 실제로는 KST 오전 9시에 도는 일이 생깁니다.
스케줄 표현식이 어느 타임존으로 해석되는지는 스케줄러마다 다르니 문서를 보고 명시적으로 지정하세요.

**로그**의 타임스탬프는 UTC ISO 형식으로 통일합니다. 사람이 읽기는 불편하지만, 서로 다른 시스템의 로그를 한 줄로 늘어놓고 인과를 따질 때 기댈 수 있는 유일한 공통 기준입니다.

**덤프와 이관**도 확인 대상입니다. `TIMESTAMP` 컬럼은 덤프를 뜨는 세션의 타임존으로 문자열이 되기 때문에, 기준이 다른 곳에서 뜨면 값이 달라집니다.
`mysqldump`에는 덤프 동안 세션 타임존을 UTC로 고정하는 옵션이 있고 기본으로 켜져 있지만, 도구를 바꾸거나 직접 `SELECT ... INTO OUTFILE`로 뽑을 때는 해당되지 않습니다.

## 정리

원칙만 추리면 짧습니다.

- **순간과 벽시계를 먼저 구분한다.** 컬럼 타입 선택은 그다음 문제다.
- 순간은 UTC 하나로 저장하고, 표현할 때만 변환한다.
- 미래의 벽시계 약속은 로컬 시각 + IANA 지역 이름으로 저장하고, UTC 시각은 파생값으로만 둔다.
- 세션 `time_zone`, 드라이버 `timezone`, 프로세스 `TZ` 를 모두 명시하고 기동 로그에 남긴다.
- 기간 조회는 컬럼에 함수를 씌우지 말고, 경계를 미리 계산해 반개구간(`>=`, `<`)으로 쓴다.
- 시스템 밖으로 나가는 값에는 오프셋이나 지역 표기를 붙인다.

어느 것도 어렵지 않은데, 전부 **어겨도 당장은 아무 일이 일어나지 않는다**는 공통점이 있습니다.
이 부류의 버그가 리포트되는 시점은 대개 분기 마감이나 이벤트 첫날입니다. 그때는 이미 어긋난 데이터가 쌓여 있습니다.
