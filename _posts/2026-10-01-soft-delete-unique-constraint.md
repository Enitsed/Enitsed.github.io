탈퇴 처리를 했는데 같은 이메일로 다시 가입하면 "이미 사용 중인 이메일"이 뜹니다.
유니크 키에 `deleted_at`을 끼워 넣어 그걸 풀었더니, 이번에는 살아 있는 계정이 같은 이메일로 두 개 생깁니다.

두 증상은 서로 반대 방향인데 원인은 하나입니다. `DELETE` 대신 컬럼 하나를 쓰기 시작하는 순간,
DB가 대신 지켜주던 약속이 조용히 우리 쪽으로 넘어옵니다.

## DELETE를 안 하면 무엇이 달라지는가

`DELETE`는 행을 없앱니다. 그 행이 차지하던 유니크 제약의 자리, 인덱스 엔트리, 외래키 참조 대상, `COUNT(*)`의 1이 같이 없어집니다.
DB가 강제하던 규칙이라 코드가 신경 쓸 일이 없었습니다.

`deleted_at`을 채우는 것은 삭제가 아니라 **상태 변경**입니다. 행은 그대로 있고, 위의 것들도 전부 그대로 남습니다.
"이 행은 없는 것으로 친다"는 약속을 이제 DB가 아니라 **모든 쿼리와 모든 제약이 각자** 지켜야 합니다.

그래서 소프트 삭제의 비용은 "컬럼 하나 추가"가 아닙니다. 그 테이블을 읽는 모든 경로에 조건 하나를 빠뜨리지 않고 붙이는 일이고,
빠뜨렸을 때 아무 에러도 나지 않는다는 게 핵심적인 문제입니다.

## 유니크 제약은 삭제 여부를 모른다

가장 먼저 부딪히는 곳입니다.

```sql
CREATE TABLE users (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  email      VARCHAR(255)    NOT NULL,
  deleted_at DATETIME(6)     NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_users_email (email)
) ENGINE=InnoDB;
```

`deleted_at`을 채워 탈퇴시킨 행도 `uk_users_email`에는 그대로 들어 있습니다.
같은 이메일로 다시 가입하는 `INSERT`는 중복 키 오류를 받습니다. 사용자 눈에는 "없는 계정이 자리를 차지하고 있는" 상태입니다.

여기서 흔한 첫 시도는 유니크 키에 `deleted_at`을 같이 넣는 것입니다.

```sql
ALTER TABLE users
  DROP KEY uk_users_email,
  ADD UNIQUE KEY uk_users_email_deleted (email, deleted_at);
```

재가입은 통과합니다. 그리고 **더 나쁜 문제가 생깁니다.**

> 표준 SQL에서 유니크 제약은 `NULL`을 서로 다른 값으로 취급합니다.
> MySQL과 PostgreSQL 모두 유니크 인덱스 안에 `NULL`이 포함된 조합은 몇 개든 허용합니다.

살아 있는 행은 `deleted_at`이 `NULL`입니다. 즉 `('a@b.com', NULL)`은 몇 번을 넣어도 충돌하지 않습니다.
**중복을 막으려고 만든 제약이 정확히 막아야 할 경우에만 작동을 멈춥니다.**

```sql
INSERT INTO users (email, deleted_at) VALUES ('a@b.com', NULL);
INSERT INTO users (email, deleted_at) VALUES ('a@b.com', NULL);  -- 통과한다
```

애플리케이션에서 `SELECT`로 먼저 확인하면 되지 않냐는 답은 이 블로그에서 반복해서 나오는 그 함정입니다.
확인과 삽입 사이에 다른 요청이 끼어들면 둘 다 통과합니다. 동시 요청을 막는 건 결국 유니크 인덱스뿐입니다.

## 부분 인덱스가 있는 쪽과 없는 쪽

PostgreSQL에서는 이게 문제가 되지 않습니다. 조건이 붙은 유니크 인덱스를 만들 수 있습니다.

```sql
-- PostgreSQL
CREATE UNIQUE INDEX uk_users_email_alive
  ON users (email)
  WHERE deleted_at IS NULL;
```

살아 있는 행만 인덱스에 들어가므로, 탈퇴한 행은 몇 개가 쌓여도 자리를 차지하지 않습니다. 의도를 그대로 적은 형태입니다.

**MySQL에는 부분 인덱스가 없습니다.** 그래서 우회가 필요하고, 실무에서 쓰이는 방법은 대략 둘입니다.

### 센티넬 값으로 NULL을 없앤다

`NULL`이 문제의 원인이니, `NULL`을 쓰지 않습니다.

```sql
ALTER TABLE users
  MODIFY deleted_at DATETIME(6) NOT NULL DEFAULT '1970-01-01 00:00:00.000000',
  ADD UNIQUE KEY uk_users_email_deleted (email, deleted_at);
```

살아 있는 행은 모두 같은 센티넬 값을 가지므로 `('a@b.com', '1970-01-01 ...')`이 중복되면 제대로 막힙니다.
탈퇴한 행은 각자 다른 시각을 가지니 서로 충돌하지 않습니다.

대가가 몇 가지 있습니다.

- 모든 쿼리 조건이 `deleted_at IS NULL`에서 `deleted_at = '1970-01-01 00:00:00'`으로 바뀝니다. 읽는 사람이 의도를 바로 알아보기 어렵습니다.
- 같은 계정을 같은 시각에 두 번 탈퇴시키면 충돌합니다. 정밀도를 `DATETIME(6)`으로 두면 실질적으로는 거의 안 나지만, 초 단위 컬럼이면 일어날 수 있습니다.
- **`TIMESTAMP`에는 이 값을 쓸 수 없습니다.** `TIMESTAMP`의 표현 범위는 1970-01-01 00:00:01 UTC부터 시작해서 에포크 0이 범위 밖입니다. 이 방식을 쓰려면 `DATETIME`이어야 합니다.

`DATETIME`과 `TIMESTAMP`가 서로 다른 것을 저장한다는 이야기는 [타임존 글](/blog/timezone-datetime-day-boundary/)에 적어뒀습니다. 센티넬을 고를 때도 같은 구분이 걸립니다.

### 생성 컬럼으로 조건을 옮긴다

`NULL`이 무시된다는 성질을 문제가 아니라 도구로 쓰는 방법입니다.

```sql
ALTER TABLE users
  ADD COLUMN email_alive VARCHAR(255)
    GENERATED ALWAYS AS (IF(deleted_at IS NULL, email, NULL)) VIRTUAL,
  ADD UNIQUE KEY uk_users_email_alive (email_alive);
```

살아 있는 행은 `email_alive`에 이메일이 들어가 서로 충돌합니다.
탈퇴한 행은 `NULL`이 되어 인덱스에서 사실상 빠집니다. PostgreSQL의 부분 유니크 인덱스와 같은 결과입니다.

`deleted_at`은 `NULL`을 유지할 수 있어서 쿼리 조건도 그대로 `deleted_at IS NULL`로 읽힙니다.
생성 컬럼 값은 DB가 계산하므로 애플리케이션이 따로 채울 일도 없습니다.

> 가상 생성 컬럼과 그 컬럼에 대한 보조 인덱스는 MySQL 5.7에서 도입됐고, 표현식에 쓸 수 있는 함수에는 제약이 있습니다.
> 가상과 저장(`STORED`) 중 무엇을 고를지, 생성 컬럼 추가가 어떤 알고리즘으로 수행되는지는 쓰는 버전의 공식 문서에서 확인하세요.
> 큰 테이블이라면 이 `ALTER`부터 [온라인 DDL 문제](/blog/mysql-online-schema-change/)가 됩니다.

정리하면 이렇습니다.

| | 센티넬 값 | 생성 컬럼 | 부분 인덱스 |
| --- | --- | --- | --- |
| MySQL | 가능 | 가능 (8.x 권장) | 없음 |
| PostgreSQL | 가능하지만 불필요 | 가능하지만 불필요 | 이게 정답 |
| 쿼리 조건 가독성 | 나빠짐 | 그대로 | 그대로 |
| 컬럼 타입 제약 | `DATETIME` 필요 | 없음 | 없음 |

## 그런데 재가입을 허용할 것인가

기술적인 우회를 고르기 전에 정해야 하는 게 있습니다. **같은 이메일의 재가입이 새 사용자인지 같은 사용자인지**입니다.

- 새 계정으로 본다면 위의 방법으로 유니크 제약을 살아 있는 행에만 걸면 됩니다. 이전 계정의 데이터는 새 계정과 이어지지 않습니다.
- 같은 사용자로 본다면 행을 새로 만들지 않고 **기존 행을 복구**하는 게 맞습니다. `deleted_at`을 비우고 필요한 필드를 초기화합니다.

두 번째를 고르면 유니크 제약을 건드릴 필요가 아예 없어집니다. 원래의 `UNIQUE KEY uk_users_email`을 그대로 두고, 가입 처리에서 탈퇴 행을 찾아 되살립니다.

```sql
UPDATE users
   SET deleted_at = NULL,
       password_hash = ?,
       restored_at = NOW(6)
 WHERE email = ?
   AND deleted_at IS NOT NULL;
```

대신 **이전 계정의 데이터가 그대로 딸려 옵니다.** 탈퇴 전 결제 내역이나 작성 글이 새로 가입한 사람에게 보이게 되고,
그 사이 이메일 주소의 주인이 바뀌었다면 남의 데이터를 넘겨주는 사고가 됩니다.

정답이 있는 문제가 아니라 제품이 정해야 하는 문제입니다. 다만 **정하지 않으면 코드가 아무 쪽으로나 정해버린다**는 것만 확실합니다.

## 조건을 빠뜨리면 조용히 틀린다

유니크 제약은 그래도 에러를 냅니다. 읽기 경로는 아무 소리도 내지 않습니다.

```sql
-- 조건이 빠졌다. 문법도 실행도 정상이고, 결과만 틀렸다
SELECT COUNT(*) FROM users WHERE created_at >= '2026-09-01';
```

특히 위험한 쪽은 조인입니다. 부모와 자식 양쪽에 `deleted_at`이 있으면 조건이 두 개 필요하고, 한쪽만 붙이기 쉽습니다.

```sql
SELECT u.id, COUNT(p.id) AS posts
  FROM users u
  LEFT JOIN posts p ON p.user_id = u.id
   AND p.deleted_at IS NULL      -- ON 절에 있어야 한다
 WHERE u.deleted_at IS NULL
 GROUP BY u.id;
```

`LEFT JOIN`에서 자식 조건을 `WHERE`로 옮기면 조인 자체가 `INNER JOIN`처럼 동작해서, 글이 하나도 없는 사용자가 결과에서 사라집니다.
조건 위치 하나로 집계가 달라지고, 이건 실행해봐도 눈에 잘 안 띕니다.

ORM의 전역 스코프는 이걸 자동으로 붙여줍니다. 편하지만 **조건이 코드에서 사라지는** 대가가 있습니다.

- 스코프를 우회해야 하는 경우(관리자 화면, 복구 기능)에 무엇이 붙고 안 붙는지 추적이 어려워집니다.
- ORM을 거치지 않는 경로 — 손으로 쓴 SQL, 리포트 쿼리, BI 도구, 배치, 마이그레이션 스크립트 — 에는 아무것도 붙지 않습니다.
- 집계를 DB에서 직접 뽑는 대시보드가 탈퇴 회원을 포함해서 세는 사고가 여기서 나옵니다.

그래서 ORM 설정보다 **DB 레벨에서 기본 경로를 만드는 쪽**이 안전합니다. 뷰를 하나 두고, 원본 테이블 접근을 예외로 만듭니다.

```sql
CREATE VIEW users_alive AS
SELECT * FROM users WHERE deleted_at IS NULL;
```

이름을 뒤집는 방법도 있습니다. 테이블을 `users_all`로 두고 뷰를 `users`로 만들면, 아무 생각 없이 쓴 쿼리가 안전한 쪽으로 떨어집니다.
`SELECT *` 뷰는 컬럼이 추가될 때 다시 만들어야 하고 갱신에도 제약이 있으니, 읽기 전용 경로에만 쓰는 편이 낫습니다.

## 인덱스와 통계에 남는 비용

지워지지 않은 행은 인덱스에도 계속 남습니다. 삭제 비율이 낮으면 신경 쓸 게 없지만, 높아지면 성능 문제로 나타납니다.

```sql
SELECT COUNT(*) AS total,
       SUM(deleted_at IS NOT NULL) AS deleted,
       ROUND(100 * SUM(deleted_at IS NOT NULL) / COUNT(*), 1) AS pct
  FROM users;
```

이 비율을 재보는 게 먼저입니다. 회원 테이블에서 탈퇴가 몇 퍼센트라면 문제가 안 됩니다.
장바구니, 임시 저장, 알림처럼 **만들어지고 지워지는 주기가 짧은 테이블**은 금방 대부분이 삭제된 행이 됩니다. 이런 테이블에 소프트 삭제를 붙이면 인덱스 대부분이 안 쓰는 데이터가 됩니다.

인덱스를 만들 때는 `deleted_at`을 어디에 둘지도 봐야 합니다.

```sql
-- 살아 있는 행을 최신순으로 뽑는 목록 쿼리라면
ALTER TABLE posts
  ADD KEY idx_posts_alive_created (deleted_at, created_at DESC);
```

카디널리티가 낮은 컬럼을 선두에 두는 게 보통은 나쁜 선택인데, 이 경우는 조건이 항상 등치 비교(`IS NULL` 또는 센티넬)로 고정되기 때문에 뒤따르는 컬럼의 정렬을 그대로 쓸 수 있습니다.
반대로 `(created_at, deleted_at)` 순서면 범위 조건 뒤에 붙은 컬럼이라 필터링에만 쓰입니다.

어느 쪽이 맞는지는 쿼리마다 다르니, 실제 쿼리로 `EXPLAIN`을 떠서 확인하세요.

## 외래키는 지켜주지 않는다

`orders.user_id`에 외래키가 걸려 있으면 DB는 참조되는 사용자가 사라지는 걸 막아줍니다.
소프트 삭제에서는 **행이 사라지지 않으니 외래키가 아무 일도 하지 않습니다.**

탈퇴한 사용자에게 새 주문이 들어가도 제약 위반이 아닙니다. 막아야 한다면 애플리케이션이 막아야 합니다.

자식 행까지 같이 지우는 것도 직접 해야 합니다. `ON DELETE CASCADE`는 `DELETE`에만 걸리니까요.

```sql
START TRANSACTION;
UPDATE users SET deleted_at = NOW(6) WHERE id = ? AND deleted_at IS NULL;
UPDATE posts SET deleted_at = NOW(6) WHERE user_id = ? AND deleted_at IS NULL;
UPDATE comments SET deleted_at = NOW(6) WHERE user_id = ? AND deleted_at IS NULL;
COMMIT;
```

이 목록은 테이블이 추가될 때마다 늘어나고, 늘어난 걸 빠뜨려도 에러가 안 납니다.
`deleted_at IS NULL` 조건을 각 문장에 넣어둔 이유는 **이미 지워진 행의 삭제 시각을 덮어쓰지 않기** 위해서입니다. 이걸 빼면 재실행할 때마다 시각이 밀립니다.

캐스케이드가 깊어진다면 그건 소프트 삭제가 안 맞는다는 신호로 읽는 편이 낫습니다.
많은 경우 자식까지 표시할 필요 없이 **조회 시점에 부모를 확인**하면 충분합니다. 상태를 한 군데만 두면 불일치가 생길 자리도 없어집니다.

## "삭제해달라"는 세 가지 다른 요구다

소프트 삭제를 택하는 이유를 뜯어보면 보통 셋 중 하나입니다. 그리고 셋 다 더 잘 맞는 답이 따로 있습니다.

**실수를 되돌리고 싶다.** 그렇다면 필요한 것은 휴지통이고, 휴지통에는 **기한이 있습니다.**
30일 뒤에 진짜 지우는 배치를 같이 만들면 소프트 삭제는 영구 상태가 아니라 유예 기간이 됩니다. 테이블이 계속 커지는 문제도 여기서 끝납니다.

```sql
DELETE FROM posts
 WHERE deleted_at < NOW() - INTERVAL 30 DAY
 ORDER BY deleted_at
 LIMIT 1000;
```

한 번에 다 지우지 않고 끊어서 도는 이유는 언두 로그와 복제 지연 때문입니다. 큰 삭제를 한 문장으로 돌리면 그 자체가 장애가 됩니다.

**누가 언제 무엇을 지웠는지 알고 싶다.** 소프트 삭제는 이걸 거의 알려주지 않습니다. 시각 하나만 남고 행위자도 이유도 없습니다.
감사 기록이 목적이라면 별도의 이력 테이블이나 감사 로그가 맞습니다.

**참조를 유지하고 싶다.** 주문 기록에서 사용자 이름이 사라지면 안 된다는 요구입니다.
이건 사용자 행을 남기는 것보다 **주문 시점의 값을 주문에 복사해두는 것**이 더 정확한 해법입니다. 어차피 이름은 바뀔 수 있고, 주문서에 필요한 건 그때의 이름입니다.

## 지우는 대신 익명화하기

법적으로 개인정보 삭제 요구를 받았을 때, 소프트 삭제는 **삭제가 아닙니다.** 데이터가 그대로 있고 조건 하나만 붙어 있는 상태입니다.

동시에 정산·통계 목적으로 행 자체는 남겨야 하는 경우가 있습니다. 두 요구가 부딪히는 자리에서 쓰는 방법이 식별 정보만 파기하는 것입니다.

```sql
UPDATE users
   SET email          = CONCAT('deleted-', id, '@invalid'),
       name           = '탈퇴한 사용자',
       phone          = NULL,
       password_hash  = NULL,
       birth_date     = NULL,
       anonymized_at  = NOW(6)
 WHERE id = ?;
```

`@invalid`를 쓰는 건 그 TLD가 실제로 존재하지 않도록 예약돼 있어서입니다. 실수로 메일이 발송되더라도 실존 주소로 가지 않습니다.
`id`를 붙여 유니크 제약을 만족시키면서, 이메일 자체는 복원 불가능하게 사라집니다.

여기서 놓치기 쉬운 것은 **사본**입니다. 원본 행을 지워도 다른 곳에 남아 있으면 지운 게 아닙니다.

- 검색 인덱스와 캐시
- 데이터 웨어하우스와 지표 테이블 (증분 적재 파이프라인은 삭제·수정을 따라오지 않는 경우가 많습니다)
- 애플리케이션 로그와 요청 로그
- 백업과 스냅샷
- 외부 SaaS로 넘긴 데이터

> 보존 의무 기간이나 삭제 요구에 응해야 하는 범위는 서비스가 받는 규제와 수집 항목에 따라 다릅니다.
> 기술적인 방법과 별개로, 무엇을 얼마나 보관해야 하는지는 반드시 관련 법령과 회사의 개인정보 처리방침을 기준으로 확인하세요.

## 선택지 비교

| 방식 | 복구 | 유니크·외래키 | 테이블 증가 | 조회 복잡도 |
| --- | --- | --- | --- | --- |
| 하드 삭제 | 불가 (백업 제외) | DB가 강제 | 없음 | 없음 |
| 소프트 삭제 컬럼 | 쉬움 | 직접 지켜야 함 | 계속 누적 | 모든 쿼리에 조건 |
| 아카이브 테이블로 이동 | 가능 (수작업) | 원본은 DB가 강제 | 원본은 안 커짐 | 평소 쿼리는 깨끗 |
| 상태 컬럼 (`status`) | 해당 없음 | 직접 지켜야 함 | 누적 | 모든 쿼리에 조건 |
| 익명화 | 불가 (의도한 것) | 유지됨 | 누적 | 없음 |

아카이브 테이블은 과소평가되는 선택지입니다. 운영 테이블은 작게 유지되고, 평소 쿼리에는 조건이 아예 필요 없습니다.

```sql
START TRANSACTION;
INSERT INTO users_archive (id, email, name, created_at, archived_at, archived_by)
SELECT id, email, name, created_at, NOW(6), ?
  FROM users WHERE id = ?;
DELETE FROM users WHERE id = ?;
COMMIT;
```

컬럼을 하나씩 적는 게 번거롭지만 `SELECT *`로 쓰면 안 됩니다. 나중에 원본에 컬럼이 추가되는 순간 컬럼 개수가 어긋나 깨집니다.
아카이브 테이블에 외래키를 걸지 않는 것도 의도적입니다. 참조 대상이 이미 없을 수 있으니까요.

대가는 복구와 조회가 번거로워지는 것입니다. 되살리려면 역방향 `INSERT`가 필요하고, 전체를 보려면 `UNION ALL`을 써야 합니다.
**복구와 조회가 일상적인 기능이면 소프트 삭제, 예외적인 운영 작업이면 아카이브**로 갈리는 지점입니다.

`status` 컬럼과 소프트 삭제를 같이 두는 것도 피하는 편이 좋습니다.
`status = 'deleted'`와 `deleted_at IS NOT NULL`이 둘 다 있으면 반드시 어긋나는 행이 생기고, 그때 어느 쪽이 진실인지 아무도 모릅니다.

## 정리

- 소프트 삭제는 DB가 강제하던 제약을 애플리케이션 규칙으로 옮기는 선택입니다. 컬럼 하나를 추가하는 비용이 아닙니다.
- 유니크 키에 `deleted_at`을 그냥 넣으면 `NULL`이 서로 다르게 취급돼 **살아 있는 행의 중복이 허용됩니다.**
- MySQL에는 부분 인덱스가 없으니 센티넬 값이나 생성 컬럼으로 우회합니다. 센티넬은 `TIMESTAMP`에 쓸 수 없습니다.
- 재가입을 새 계정으로 볼지 기존 계정 복구로 볼지는 제품 결정입니다. 정하지 않으면 코드가 아무 쪽으로나 정합니다.
- 조인에서는 자식 조건을 `ON`에 둡니다. `WHERE`로 내리면 `LEFT JOIN`이 `INNER JOIN`이 됩니다.
- ORM 전역 스코프는 조건을 숨깁니다. ORM을 거치지 않는 경로가 반드시 생기니 뷰로 기본 경로를 만드는 쪽이 안전합니다.
- 삭제 비율이 높은 테이블에는 쓰지 않습니다. 인덱스 대부분이 안 쓰는 데이터가 됩니다.
- 휴지통이 목적이면 기한과 정리 배치를 같이 만듭니다. 그러면 소프트 삭제는 영구 상태가 아니라 유예가 됩니다.
- 감사 기록이 목적이면 이력 테이블이, 개인정보 삭제 요구라면 익명화가 맞습니다. 소프트 삭제는 둘 다 아닙니다.
