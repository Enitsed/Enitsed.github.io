저장 버튼을 누르면 성공 토스트가 뜨는데, 목록으로 돌아오면 방금 만든 항목이 없습니다.
새로고침하면 보입니다. 에러 로그는 깨끗하고, 로컬에서는 백 번을 해도 재현되지 않습니다.

이 증상은 "가끔 저장이 안 돼요"라는 문장으로 들어오고, 그 문장만 들고는 아무 데도 갈 수 없습니다.

## 읽기를 나눈 순간 보장 하나를 포기했다

쓰기는 프라이머리, 읽기는 리플리카. 읽기 부하를 떼어내는 가장 흔한 구조입니다.

그런데 커밋 응답이 돌아왔다는 건 **프라이머리 기준으로 끝났다**는 뜻이지, 리플리카가 그 변경을 적용했다는 뜻이 아닙니다.
비동기 복제에서 프라이머리는 바이너리 로그에 쓰고 응답을 돌려주고, 리플리카는 그걸 받아 자기 속도로 재생합니다.

세미싱크 복제를 켜도 이 구멍은 안 메워집니다. 리플리카가 로그를 **받았다**는 확인까지만 기다리고, 적용했는지는 보장하지 않기 때문입니다.

Aurora처럼 스토리지를 공유하는 구조는 지연이 밀리초 단위로 작지만 0은 아닙니다. 리더 인스턴스가 변경된 페이지를 자기 버퍼 캐시에 반영하는 시간이 남아 있습니다.
작다는 건 **덜 자주 터진다**는 뜻이고, 안 터진다는 뜻은 아닙니다. 오히려 재현이 어려워져서 원인을 찾는 데 더 오래 걸립니다.

그러니 문제를 "지연을 없애자"로 세우면 답이 없습니다. **어떤 읽기가 지연을 견딜 수 있는가**로 세워야 합니다.

## 깨지는 건 두 가지다

### 내가 쓴 것 읽기

사용자가 방금 만든 것을 자기 화면에서 못 보는 경우입니다.

전형적인 경로는 생성 후 리다이렉트입니다. `POST /posts`로 만들고 응답의 ID로 `GET /posts/:id`를 부르는데, 그 GET이 리플리카로 가서 404가 납니다.
애플리케이션은 정직하게 "없다"고 답한 것이고, 프런트는 삭제된 글로 처리합니다.

### 단조 읽기

리플리카가 두 대 이상이면 같은 사용자의 연속된 요청이 서로 다른 리플리카로 갈 수 있습니다.
첫 요청이 더 앞선 리플리카를, 다음 요청이 더 뒤처진 리플리카를 보면 **화면의 데이터가 과거로 돌아갑니다.**

목록을 주기적으로 폴링하는 화면에서 항목이 나타났다 사라졌다 하거나, 커서 페이지네이션에서 같은 항목이 두 번 보이는 식으로 드러납니다.

두 증상은 원인이 같지만 대응이 다릅니다. 앞의 것은 "이 요청은 프라이머리로"로 풀리고, 뒤의 것은 "이 세션은 같은 리플리카로"가 필요합니다.

## 지연을 먼저 믿을 수 있게 재기

대응을 정하기 전에 지금 지연이 얼마인지 알아야 하는데, 가장 흔히 보는 값이 가장 믿을 수 없습니다.

```sql
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source: 0
```

> MySQL 8.0 중간 버전에서 `SHOW SLAVE STATUS`와 `Seconds_Behind_Master`가 각각 `SHOW REPLICA STATUS`, `Seconds_Behind_Source`로 바뀌었습니다. 어느 이름이 쓰이는지는 엔진 버전에 달려 있으니 공식 문서의 해당 버전 페이지를 확인하세요.

이 값이 0이라고 안심하면 안 되는 경우가 있습니다.

- 네트워크가 끊겨 I/O 스레드가 멈추면 적용할 이벤트 자체가 없어서 `NULL`이거나 0으로 보입니다. 밀린 게 없는 게 아니라 **받지를 못하고 있는** 상태입니다.
- 이 값은 적용 중인 이벤트의 타임스탬프 차이에 기반합니다. 큰 트랜잭션 하나를 붙들고 있으면 적용이 시작된 시점 기준이라 실제 체감 지연보다 작게 보일 수 있습니다.

그래서 운영에서는 프라이머리에 심장박동 행을 하나 두고 그걸 읽는 방식을 같이 씁니다. 복제 경로 전체를 한 번에 통과하는 값이라 해석이 단순합니다.

```sql
-- 프라이머리에서 1초마다 갱신
UPDATE heartbeat SET ts = NOW(6) WHERE id = 1;

-- 리플리카에서 읽는다. 이 차이가 실제 end-to-end 지연이다
SELECT TIMESTAMPDIFF(MICROSECOND, ts, NOW(6)) / 1000 AS lag_ms FROM heartbeat WHERE id = 1;
```

Aurora MySQL은 복제 구조가 다르므로 전용 뷰를 봅니다.

```sql
SELECT server_id,
       IF(session_id = 'MASTER_SESSION_ID', 'writer', 'reader') AS role,
       replica_lag_in_milliseconds
FROM information_schema.replica_host_status;
```

> 뒤처진 리더에서 이 뷰를 조회하면 그 안의 값 자체가 낡아 있을 수 있습니다. AWS 문서도 라이터에서 조회할 것을 권합니다. 지연을 재는 쿼리를 지연된 노드로 보내는 건 흔한 실수입니다.

## 라우팅 결정을 호출부에서 빼내기

가장 먼저 손이 가는 방식은 조회 함수마다 분기를 넣는 것입니다.

```typescript
const rows = await (useReplica ? replica : primary).query(sql, params);
```

이 방식은 한두 군데에서는 멀쩡해 보이지만, `useReplica`를 정할 책임이 모든 호출부로 퍼집니다.
새로 들어온 사람이 조회 함수를 하나 추가할 때 이 인자를 안 넘기면 조용히 기본값을 따르고, 그게 리플리카라면 위에서 본 404가 다시 생깁니다.

판단 근거는 호출부가 아니라 **요청 전체**에 있습니다. "이 요청이 이미 쓰기를 했는가"는 함수 하나가 아니라 요청 단위의 사실입니다.
그러니 요청 컨텍스트에 담고, 커넥션을 고르는 한 지점에서만 읽습니다.

```typescript
import { AsyncLocalStorage } from "node:async_hooks";

type RequestState = { wrote: boolean; inTransaction: boolean };

const store = new AsyncLocalStorage<RequestState>();

export const withRequestState = <T>(fn: () => Promise<T>) =>
  store.run({ wrote: false, inTransaction: false }, fn);

export function markWritten() {
  const s = store.getStore();
  if (s) s.wrote = true;
}

// 커넥션을 고르는 유일한 지점
export function pickReader() {
  const s = store.getStore();
  if (!s) return primary;              // 컨텍스트 밖이면 안전한 쪽
  if (s.inTransaction) return primary; // 트랜잭션 안의 읽기는 예외 없이 프라이머리
  if (s.wrote) return primary;         // 이 요청이 쓴 적이 있으면 프라이머리
  return replica;
}
```

컨텍스트가 없을 때 프라이머리로 떨어뜨리는 기본값이 중요합니다.
배치나 워커처럼 미들웨어를 안 거치는 실행 경로가 반드시 생기는데, 그때 기본값이 리플리카면 가장 디버깅하기 어려운 자리에서 낡은 데이터를 읽습니다.

트랜잭션 안의 읽기를 무조건 프라이머리로 보내는 것도 선택이 아니라 필수입니다. 트랜잭션은 커넥션에 묶여 있어서, 중간에 다른 노드로 읽으러 가면 그 트랜잭션이 아직 커밋도 안 한 자기 변경을 못 봅니다.

## 요청 하나를 넘어가면

위 구조는 한 요청 안에서만 유효합니다. 생성과 조회가 **다른 HTTP 요청**이면 플래그가 남아 있지 않습니다.

그래서 쓰기를 한 사용자(또는 세션)를 일정 시간 동안 프라이머리에 고정하는 방식을 얹습니다.

```typescript
const STICKY_MS = 3_000;

export async function markWrittenSticky(sessionKey: string) {
  markWritten();
  await redis.set(`rw:${sessionKey}`, "1", "PX", STICKY_MS);
}

export async function pickReaderFor(sessionKey: string) {
  const local = pickReader();
  if (local === primary) return primary;
  return (await redis.exists(`rw:${sessionKey}`)) ? primary : replica;
}
```

이 상태를 **프로세스 메모리에 두면 안 됩니다.** 인스턴스가 여러 대면 다음 요청이 다른 인스턴스로 가고, 거기엔 플래그가 없습니다.
인스턴스가 한 대일 때 잘 돌다가 스케일 아웃하는 순간 재현되는 종류의 버그입니다.

고정 시간을 정하는 기준도 애매합니다. 평소 지연의 p99에 맞춰 잡아도, 지연이 튀는 순간에는 그 숫자가 아무것도 보장하지 않습니다.
**시간 기반 고정은 보장이 아니라 확률을 올리는 장치**라고 이해하는 편이 정확합니다.

## 추측 대신 기다리기 — GTID

확실히 하려면 "N초쯤 지났으니 됐겠지"가 아니라 "그 트랜잭션이 적용됐는지 물어보는" 쪽으로 가야 합니다.
GTID를 켜 두었다면 리플리카에 직접 물어볼 수 있습니다.

```sql
-- 리플리카에서. 해당 GTID 집합이 적용될 때까지 최대 0.5초 기다린다
SELECT WAIT_FOR_EXECUTED_GTID_SET('3e11fa47-71ca-11e1-9e33-c80aa9429562:1-42', 0.5);
```

반환값은 **0이면 적용 완료, 1이면 타임아웃**입니다. 타임아웃을 생략하면 무한정 기다리므로, 요청 경로에서 쓸 때는 반드시 값을 주어야 합니다.

기다릴 GTID는 쓰기 직후에 확보해 둡니다. 가장 정확한 방법은 `session_track_gtids`를 `OWN_GTID`로 두고 커밋 응답에 실려 오는 세션 상태를 읽는 것인데, 이건 **드라이버가 세션 추적 정보를 노출해야** 쓸 수 있습니다. 쓰는 드라이버가 지원하는지 먼저 확인하세요.

지원하지 않는다면 커밋 직후 프라이머리에서 실행된 집합을 통째로 받아두는 타협이 있습니다.

```typescript
async function commitAndCapture(conn: Connection): Promise<string> {
  await conn.query("COMMIT");
  const [rows] = await conn.query<{ gtid: string }[]>(
    "SELECT @@global.gtid_executed AS gtid",
  );
  return rows[0].gtid;
}

async function readAfterWrite<T>(gtid: string, run: (c: Pool) => Promise<T>) {
  const [rows] = await replica.query<{ ok: number }[]>(
    "SELECT WAIT_FOR_EXECUTED_GTID_SET(?, 0.3) AS ok",
    [gtid],
  );
  // 1이면 아직 못 따라왔다. 기다리는 대신 프라이머리로 넘긴다
  return run(rows[0].ok === 0 ? replica : primary);
}
```

내 트랜잭션뿐 아니라 그 시점까지 커밋된 **다른 트랜잭션까지 같이 기다린다**는 게 이 타협의 비용입니다. 쓰기가 많은 시스템일수록 더 오래 기다립니다.

위치 기반으로 기다리는 `SOURCE_POS_WAIT()`도 있습니다. GTID를 안 쓰는 구성에서 쓰는 수단인데, 복제 채널과 위치를 직접 관리해야 해서 손이 더 갑니다. 함수 이름도 버전에 따라 과거 이름이 쓰이니 문서를 확인하세요.

> 기다리는 쪽을 택하면 읽기마다 왕복이 한 번 늘어납니다. 모든 읽기에 거는 게 아니라 **쓰기 직후의 읽기에만** 걸어야 하고, 타임아웃은 짧게 잡고 초과하면 프라이머리로 넘기는 폴백이 반드시 있어야 합니다. 폴백이 없으면 복제가 밀리는 순간 모든 요청이 거기서 같이 멈춥니다.

GTID 문자열을 응답 헤더나 쿠키로 클라이언트에 내보내는 설계는 피하는 편이 낫습니다. 서버 ID와 트랜잭션 수가 그대로 드러나고, 클라이언트가 임의의 값을 넣어 보내면 서버가 그걸 기다리게 됩니다.

## 지연이 터졌을 때

복제가 수십 초씩 밀리면 리플리카로 가는 읽기는 전부 과거를 봅니다. 이때 자동으로 프라이머리로 되돌리는 장치를 두는데, 여기에 함정이 하나 있습니다.

**전부 되돌리면 프라이머리가 죽습니다.** 리플리카로 뺀 이유가 프라이머리가 그 부하를 감당 못 해서였다면, 지연이 커졌다고 그걸 통째로 돌려보내는 건 장애를 옮기는 것에 가깝습니다.

그래서 읽기를 미리 등급으로 나눠두고, 승격 대상을 제한합니다.

```typescript
type ReadClass = "fresh" | "normal" | "stale-ok";

function routeRead(cls: ReadClass, lagMs: number) {
  if (cls === "fresh") return primary;           // 신선도가 정확성인 읽기
  if (cls === "stale-ok") return replica;        // 지연이 커도 리플리카 유지
  return lagMs > 5_000 ? primary : replica;      // 평소엔 리플리카, 밀리면 승격
}
```

`lagMs`는 요청마다 재지 않습니다. 백그라운드에서 주기적으로 측정해 캐시해 두고 그 값을 읽습니다. 지연을 재겠다고 요청마다 쿼리를 하나씩 더 쏘면 그 자체가 부하가 됩니다.

등급을 어디에 붙일지는 대체로 이렇게 갈립니다.

| 읽기 | 등급 | 이유 |
| --- | --- | --- |
| 쓰기 직후 재조회, 결제·재고 검증 | fresh | 틀리면 사고가 나는 읽기 |
| 상세·목록 조회, 검색 | normal | 몇 초 과거는 사용자가 모른다 |
| 통계·대시보드, 리포트 | stale-ok | 애초에 과거를 보는 화면 |
| 권한·소유권 확인 | fresh | 방금 바뀐 권한이 안 먹으면 보안 문제 |

권한 확인을 리플리카로 보내면 지연 구간 동안 **방금 회수한 권한이 아직 통합니다.** 리프레시 토큰 무효화와 같은 성질의 문제이고, 비용을 아낄 자리가 아닙니다.

## 애초에 다시 읽지 않는 선택

여기까지는 전부 "쓴 다음 다시 읽어야 한다"를 전제로 합니다. 그 전제를 치울 수 있으면 문제 자체가 사라집니다.

생성 응답에 만들어진 리소스를 통째로 담아 돌려주면, 클라이언트는 리다이렉트 후 다시 조회할 이유가 없습니다.
목록 화면도 마찬가지로, 서버를 다시 부르는 대신 응답으로 받은 객체를 기존 목록 앞에 끼워 넣으면 됩니다.

```typescript
// 201에 생성 결과를 담는다. 클라이언트는 재조회하지 않는다
res.status(201).json(await createPost(input));
```

이게 통하지 않는 경우도 분명히 있습니다. 목록이 서버에서 정렬·필터링되거나, 다른 사용자의 변경까지 같이 보여야 하는 화면이 그렇습니다.
다만 적지 않은 "읽기 직후 안 보임" 사례는 **굳이 안 해도 될 재조회** 때문에 생깁니다. 라우팅 구조를 손대기 전에 여기부터 보는 쪽이 싸게 끝납니다.

## 로컬에서는 절대 안 잡힌다

이 버그가 운영에서만 나타나는 이유는 단순합니다. 개발 환경의 복제 지연이 사실상 0이거나, 아예 리플리카가 없기 때문입니다.

재현하려면 지연을 **의도적으로** 넣어야 합니다. MySQL은 복제 적용을 늦추는 설정을 제공합니다.

```sql
STOP REPLICA SQL_THREAD;
CHANGE REPLICATION SOURCE TO SOURCE_DELAY = 5;
START REPLICA SQL_THREAD;
```

> `CHANGE REPLICATION SOURCE TO`는 MySQL 8.0.23부터 쓸 수 있고, 그 이전에는 `CHANGE MASTER TO ... MASTER_DELAY = N`을 씁니다. 설정된 지연과 남은 시간은 복제 상태의 `SQL_Delay`, `SQL_Remaining_Delay`에서 확인합니다.

5초 지연을 걸어두고 평소 쓰던 화면을 눌러보면, 라우팅이 잘못된 지점이 한 번에 드러납니다.
통합 테스트 환경에 이 설정을 상시로 켜두는 선택도 있습니다. 테스트가 느려지는 대신, 리플리카로 가면 안 되는 읽기가 CI에서 걸립니다.

## 정리

- 커밋 응답은 프라이머리의 사실이지 리플리카의 사실이 아닙니다. 읽기를 나눈 순간 "내가 쓴 것 읽기"는 공짜가 아닙니다.
- `Seconds_Behind_Source` 하나만 보지 말고, 심장박동 행이나 엔진이 제공하는 전용 지표로 end-to-end 지연을 따로 재세요.
- 읽기 대상 선택은 호출부가 아니라 요청 컨텍스트와 커넥션 선택 지점 한 곳에 모읍니다. 컨텍스트가 없을 때의 기본값은 프라이머리입니다.
- 정확성이 필요하면 시간 기반 고정 대신 GTID로 기다리되, 타임아웃과 프라이머리 폴백을 반드시 같이 두세요.
- 지연 폭증 시 모든 읽기를 프라이머리로 되돌리면 장애를 옮기는 것입니다. 읽기를 미리 등급으로 나눠두세요.
- 재조회를 없앨 수 있으면 그게 가장 싼 해법입니다.
