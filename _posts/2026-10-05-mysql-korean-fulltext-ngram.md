검색 기능은 보통 `LIKE '%키워드%'` 한 줄로 시작합니다. 결과도 꽤 맞고, 수만 건까지는 느린 줄도 모릅니다.

그러다 테이블이 커지면 그 한 줄이 매번 전부 읽는다는 걸 알게 되고, FULLTEXT 인덱스를 붙입니다.
빨라지긴 합니다. 그런데 이번에는 **본문에 분명히 있는 단어로 검색해도 결과가 0건**입니다.

느린 쪽과 안 맞는 쪽은 원인이 다르고, 둘을 동시에 만족시키려면 어디까지가 DB의 몫인지를 먼저 정해야 합니다.

## 느린 쪽: 앞에 와일드카드가 붙는 순간

B-tree 인덱스는 정렬된 값에서 시작 지점을 특정하고 거기서부터 범위를 좁힙니다.
문자열의 앞부분이 고정돼 있으면 그게 가능하고, 앞부분이 비어 있으면 불가능합니다.

```sql
-- 시작 지점을 특정할 수 있다 → 인덱스 범위 스캔
SELECT id FROM posts WHERE title LIKE '유치원%';

-- 특정할 수 없다 → 전부 읽고 하나씩 비교
SELECT id FROM posts WHERE title LIKE '%유치원%';
```

두 번째 쿼리에 `EXPLAIN`을 떠보면 `type`이 `ALL`로 나옵니다. 인덱스가 있어도 쓰지 못합니다.

여기서 흔한 착각이 하나 있습니다. 커버링 인덱스를 만들어두면 `type`이 `index`로 바뀌는 경우가 있는데, 이건 **인덱스 전체를 훑는다**는 뜻이지 범위를 좁혔다는 뜻이 아닙니다.
테이블 대신 인덱스를 읽으니 I/O는 줄지만, 비교 횟수는 행 수에 그대로 비례합니다. 행이 열 배가 되면 열 배 걸립니다.

그리고 LIKE의 성능 문제는 **정확도가 나쁘지 않다는 점 때문에 더 오래 방치됩니다.** 부분 문자열 매칭이라 "유치원에서"도 "유치원"으로 잡히고, 그래서 사용자 불만이 늦게 들어옵니다.

## 안 맞는 쪽: 기본 파서는 공백으로 자른다

그래서 FULLTEXT 인덱스로 넘어갑니다. 전치 색인(inverted index)은 토큰에서 문서로 바로 가므로 행 수에 비례하지 않습니다.

문제는 **무엇을 토큰으로 보는가**입니다. MySQL의 기본 전문 검색 파서는 공백과 구두점을 기준으로 단어를 자릅니다.

```text
원문:  "원장님이 유치원에서 쓰실 수 있게"
토큰:  원장님이 / 유치원에서 / 쓰실 / 수 / 있게
```

"유치원"은 이 목록에 없습니다. 그러니 결과는 0건이고, 애플리케이션은 정직하게 "없다"고 답한 것입니다.

영어에서 공백 분리가 대체로 통하는 건 굴절이 단어 바깥으로 거의 안 붙기 때문입니다.
한국어는 교착어라 조사와 어미가 붙어서 하나의 어절이 되고, 그 어절 전체가 하나의 토큰이 됩니다.
"유치원", "유치원이", "유치원에서", "유치원에는"이 서로 다른 토큰이 되니 **검색어와 색인이 거의 겹치지 않습니다.**

LIKE에서 FULLTEXT로 옮기면서 속도를 얻고 정확도를 잃는 교환이 일어난 것이고, 이게 제일 흔하게 밟는 지점입니다.

## ngram 파서

MySQL에는 공백 대신 **고정 길이로 자르는** 파서가 내장돼 있습니다. 글자 n개씩 겹치게 잘라 토큰을 만듭니다.

```text
ngram_token_size = 2
"유치원"  →  유치 / 치원
"알림장"  →  알림 / 림장
```

색인도 검색도 같은 규칙으로 잘리니, "유치원에서"를 색인한 문서는 "유치", "치원" 토큰을 갖고 있고 "유치원"으로 검색하면 걸립니다.
조사 문제가 사라지는 이유는 **단어를 이해해서가 아니라 글자 단위로 쪼개서** 부분 문자열 매칭에 가까워졌기 때문입니다.

인덱스를 만들 때 파서를 지정합니다.

```sql
ALTER TABLE posts
  ADD FULLTEXT INDEX ft_posts_search (title, body) WITH PARSER ngram;
```

토큰 길이는 서버 변수로 정합니다. 기본값은 2입니다.

```ini
[mysqld]
ngram_token_size = 2
```

> `ngram_token_size`는 읽기 전용 변수라서 **시작 옵션이나 설정 파일로만** 지정할 수 있고, 런타임에 바꿀 수 없습니다. RDS라면 파라미터 그룹을 수정한 뒤 재부팅이 필요하다는 뜻입니다. 그리고 이 값을 바꾸면 이미 만들어둔 ngram 인덱스의 토큰 구성이 달라지므로 인덱스를 다시 만들어야 합니다. 값을 정하는 건 나중에 미루기 어려운 결정입니다.

함께 알아둘 것이 하나 더 있습니다. 기본 파서에서 쓰던 최소·최대 단어 길이 설정(`innodb_ft_min_token_size`, `innodb_ft_max_token_size`)은 **ngram 인덱스에는 적용되지 않습니다.** 토큰 길이는 `ngram_token_size`가 전부 결정합니다.
스톱워드는 적용되지만, `ngram_token_size`보다 긴 스톱워드는 토큰으로 만들어질 수 없으므로 무시됩니다.

실제로 어떻게 잘렸는지는 직접 들여다볼 수 있습니다.

```sql
SET GLOBAL innodb_ft_aux_table = 'mydb/posts';

SELECT WORD, DOC_COUNT, DOC_ID
FROM information_schema.INNODB_FT_INDEX_TABLE
ORDER BY DOC_COUNT DESC
LIMIT 20;
```

검색이 안 맞을 때 추측으로 쿼리를 고치는 대신 여기를 먼저 보면 대부분 한 번에 끝납니다. 검색어가 어떤 토큰으로 변환되는지와 색인에 그 토큰이 있는지를 바로 대조할 수 있습니다.

## 두 가지 검색 모드

자연어 모드는 입력을 토큰으로 쪼개서 관련도 점수를 매깁니다.

```sql
SELECT id, title,
       MATCH(title, body) AGAINST('유치원 알림장' IN NATURAL LANGUAGE MODE) AS score
FROM posts
WHERE MATCH(title, body) AGAINST('유치원 알림장' IN NATURAL LANGUAGE MODE)
ORDER BY score DESC
LIMIT 20;
```

`MATCH()`에 적는 컬럼 목록은 **FULLTEXT 인덱스 정의와 정확히 같아야** 합니다. 순서나 개수가 다르면 인덱스를 못 쓰고 오류가 납니다.
컬럼을 하나만 검색하고 싶다면 그 컬럼만 가진 별도 인덱스가 필요합니다.

불리언 모드는 연산자로 필수·제외·구문을 지정합니다.

```sql
SELECT id, title
FROM posts
WHERE MATCH(title, body) AGAINST('+유치원 -폐원' IN BOOLEAN MODE)
LIMIT 20;
```

여기서 ngram 파서가 끼면 변환이 한 겹 더 일어납니다. 검색어는 **ngram 구문 검색으로 바뀝니다.**
토큰 크기가 2일 때 `abc`는 `"ab bc"`라는 구문 검색이 됩니다. 즉 두 토큰이 그 순서로 인접해 있어야 매치됩니다.

이 변환을 모르면 왜 어떤 검색어는 되고 어떤 건 안 되는지가 설명되지 않습니다.

### 사용자 입력을 그대로 넣으면 안 된다

불리언 모드에서 `+ - > < ( ) ~ * " @`는 전부 연산자입니다. 검색창에 입력된 문자열을 그대로 넘기면 사용자가 문법을 쓰게 됩니다.

"C++"를 검색하면 `+`가 필수 조건 연산자로 해석되고, 괄호가 짝이 안 맞으면 쿼리 자체가 오류가 됩니다.
사용자가 의도한 적 없는 검색 결과가 나오거나, 검색창에 특정 문자를 넣으면 500이 나는 상태가 됩니다.

```typescript
// 불리언 모드 연산자를 제거하고, 각 어절을 필수 구문으로 묶는다
const OPERATORS = /[+\-><()~*"@]/g;

export function toBooleanQuery(input: string, tokenSize = 2): string | null {
  const terms = input
    .replace(OPERATORS, " ")
    .split(/\s+/)
    .map((t) => t.trim())
    .filter((t) => t.length >= tokenSize);

  if (terms.length === 0) return null; // 검색 자체를 하지 않는다
  return terms.map((t) => `+"${t}"`).join(" ");
}
```

따옴표로 묶는 건 의도적입니다. 구문 검색으로 만들면 쪼개진 ngram 토큰들이 그 순서로 붙어 있어야 하니, **글자 순서가 보존된 부분 문자열 매칭**에 가까워집니다.
묶지 않으면 토큰들이 따로 흩어져 매치돼서 전혀 다른 문맥이 걸립니다.

토큰 크기보다 짧은 어절을 버리는 것도 의도적입니다. 이유는 바로 다음입니다.

## ngram이 구조적으로 못 하는 것

### 토큰 크기보다 짧은 검색어

와일드카드 검색에서 접두어가 토큰 크기보다 **짧으면**, 그 접두어로 시작하는 ngram 토큰을 가진 행이 전부 반환됩니다.
한 글자로 검색하면 거의 걸러지지 않는다는 뜻입니다.

반대로 접두어가 토큰 크기보다 **길면** 접두어가 ngram 구문으로 변환되고 **와일드카드 연산자는 무시됩니다.**
`+유치원*`이라고 쓴 의도가 조용히 사라집니다. ngram에서는 와일드카드를 붙이는 것이 대체로 의미가 없습니다.

그리고 색인된 값 자체가 토큰 크기보다 짧으면 그 행은 찾을 수 없습니다. 한 글자짜리 태그나 코드값을 ngram 인덱스로 찾으려는 시도는 성립하지 않습니다.

실무적인 결론은 단순합니다. **검색창에 최소 글자 수를 강제하고**, 그보다 짧은 입력은 검색을 아예 보내지 않거나 다른 경로(접두어 LIKE, 정확 일치 인덱스)로 처리합니다.

### 의미 단위가 아니라 글자 쌍이다

2-gram 토큰은 단어가 아닙니다. 그래서 의도하지 않은 매치가 생깁니다.

```text
"지원장비" → 지원 / 원장 / 장비
```

"원장"으로 검색하면 이 문서가 걸립니다. 글자 쌍이 실제로 들어 있으니 틀린 동작도 아닙니다.
같은 성질이 좋게 작동하는 경우도 많습니다. "자동"으로 "자동화", "자동이체"가 같이 걸리는 건 대개 원하는 결과입니다.

문제는 **이 둘을 구분할 방법이 색인 쪽에 없다**는 점입니다. 검색어가 짧을수록 노이즈 비율이 올라가고, 관련도 점수도 글자 쌍의 빈도에 기반하니 변별력이 떨어집니다.

### 언어 지식이 전혀 없다

ngram은 글자 수준 부분 문자열 색인입니다. 그 위에 올라가는 것들이 전부 없습니다.

- 동의어 확장 — "선생님"과 "교사"를 같게 보지 않습니다
- 오타 교정 — 한 글자만 틀려도 토큰이 달라집니다
- 어간·품사 — "쓰실", "쓰는", "쓴"을 묶지 않습니다
- 복합어 분해 — "어린이집"을 "어린이"와 "집"으로 나눌지 결정하는 지식이 없습니다

이것들을 애플리케이션에서 흉내 낼 수는 있습니다. 동의어 사전을 두고 검색어를 확장해 `OR`로 붙이는 식입니다.
다만 사전 관리와 쿼리 길이가 같이 늘고, 그쯤 되면 이미 검색엔진이 기본으로 주는 걸 손으로 만들고 있는 상태입니다.

## 인덱스를 붙일 때 치르는 비용

### 첫 FULLTEXT 인덱스는 테이블을 다시 만든다

InnoDB의 전문 검색은 문서를 식별하기 위해 `FTS_DOC_ID` 컬럼을 요구합니다. 테이블에 그 컬럼이 없으면 인덱스를 만들 때 숨겨진 컬럼으로 추가되는데, 이 과정에서 **테이블이 한 번 재생성됩니다.**

운영 중인 큰 테이블이라면 컬럼 추가 ALTER와 같은 성질의 작업이 된다는 뜻입니다. 메타데이터 락과 소요 시간을 그대로 계산해야 합니다.
두 번째 인덱스부터는 재생성 없이 추가됩니다. 비싼 건 첫 번째 한 번입니다.

피하는 방법은 테이블을 만들 때 컬럼을 미리 정의해두는 것입니다.

```sql
CREATE TABLE posts (
  FTS_DOC_ID  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  id          BIGINT UNSIGNED NOT NULL,
  title       VARCHAR(255) NOT NULL,
  body        MEDIUMTEXT   NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY FTS_DOC_ID_INDEX (FTS_DOC_ID)
) ENGINE=InnoDB;
```

> 컬럼 이름·타입과 유니크 인덱스 이름까지 규칙이 정해져 있고, 이 값은 애플리케이션이 임의로 쓰면 안 되는 내부 식별자입니다. 정확한 제약은 엔진 문서의 InnoDB 전문 인덱스 항목을 확인하세요. 데이터가 쌓인 뒤에 추가하는 것보다 **적재 전에 정의해두는 쪽이 훨씬 쌉니다.**

### DELETE가 인덱스를 줄이지 않는다

행을 지우면 전치 색인에서 토큰이 바로 빠지지 않습니다. 삭제된 문서 ID가 별도 보조 테이블에 기록되고, 쿼리 결과를 돌려주기 전에 그 목록으로 걸러냅니다.

결과는 정확하지만 **인덱스는 단조 증가하고, 걸러낼 ID가 쌓이는 만큼 조회가 조금씩 느려집니다.**
삭제와 갱신이 잦은 테이블이라면 시간이 지나면서 조용히 나빠지는 종류의 문제입니다.

정리는 `OPTIMIZE TABLE`로 합니다. 전문 인덱스만 재구성하도록 범위를 좁혀서 돌립니다.

```sql
SET GLOBAL innodb_optimize_fulltext_only = ON;
SET GLOBAL innodb_ft_num_word_optimize  = 2000;   -- 한 번에 병합할 단어 수를 제한

OPTIMIZE TABLE posts;

SET GLOBAL innodb_optimize_fulltext_only = OFF;   -- 반드시 되돌린다
```

> 마지막 줄을 빠뜨리면 이후 다른 테이블에 돌린 `OPTIMIZE TABLE`도 전문 인덱스만 처리하고 지나갑니다. 테이블을 정리했다고 생각했는데 아무 일도 안 일어난 상태가 되니, 전역 변수를 켜는 작업은 되돌리는 것까지 한 묶음으로 두세요.

### 인덱스 크기

2-gram은 글자 위치마다 토큰을 만듭니다. 원문 길이에 거의 비례해서 전치 색인이 커지고, 토큰 크기를 1로 줄이면 더 커집니다.

긴 본문 컬럼을 전부 색인 대상에 넣기 전에 **무엇을 검색 대상으로 볼지 먼저 줄이는 쪽**이 낫습니다.
제목과 요약만으로 충분한 화면인데 본문 전체를 색인하고 있는 경우가 생각보다 많습니다.

## 다른 조건과 같이 쓸 때

실제 쿼리는 검색어 하나로 끝나지 않습니다. 테넌트, 상태, 기간 같은 조건이 늘 붙습니다.

```sql
SELECT id, title
FROM posts
WHERE tenant_id = ?
  AND deleted_at IS NULL
  AND MATCH(title, body) AGAINST (? IN BOOLEAN MODE)
ORDER BY MATCH(title, body) AGAINST (? IN BOOLEAN MODE) DESC
LIMIT 20;
```

여기서 일이 벌어지는 순서가 중요합니다. 전문 인덱스로 매치되는 문서를 찾고, **그 다음에** 나머지 조건으로 걸러냅니다.
테넌트가 많고 각 테넌트의 데이터가 작으면, 전역에서 매치한 결과를 거의 다 버리는 구조가 됩니다. 검색어가 흔할수록 버리는 양이 늘어납니다.

선택지는 대체로 셋입니다.

첫째, 검색 대상을 좁힌 별도 테이블을 두는 것. 검색에 필요한 컬럼만 모은 테이블을 만들면 색인이 작아지고 버리는 비율도 줄어듭니다. 원본과 동기화할 책임이 생기는 대신입니다.

둘째, 테넌트 식별자를 색인되는 텍스트에 토큰으로 끼워 넣고 검색어에 필수 조건으로 붙이는 방식. 전문 검색 단계에서 테넌트가 걸러지니 효과는 확실하지만, 색인 텍스트에 데이터가 아닌 값이 섞이고 그 규칙을 모르는 사람이 보면 이해할 수 없는 구조가 됩니다. 쓰더라도 색인을 만드는 지점 한 곳에만 두세요.

셋째, 검색을 별도 엔진으로 분리하는 것.

> 파티셔닝으로 테넌트를 나누는 방법은 쓸 수 없습니다. 파티션된 테이블에는 FULLTEXT 인덱스를 만들 수 없습니다.

점수 기반 정렬은 페이지네이션과도 잘 맞지 않습니다. 관련도 점수는 고유하지 않아서 커서(keyset) 페이지네이션의 기준으로 쓰기 어렵고, `OFFSET`으로 넘기면 깊은 페이지에서 다시 느려집니다.

## 어디서 멈추고 검색엔진으로 갈지

| | LIKE '%...%' | FULLTEXT + ngram | 검색엔진(형태소 분석) |
| --- | --- | --- | --- |
| 색인 단위 | 없음 | 고정 길이 글자 | 형태소 |
| 속도 | 행 수에 비례 | 전치 색인 | 전치 색인 |
| 조사·어미 | 영향 없음 | 영향 없음 | 분석해서 제거 |
| 동의어·오타 | 없음 | 없음 | 사전·퍼지 매칭 |
| 노이즈 | 적음 | 글자 쌍 우연 매치 | 적음 |
| 운영 비용 | 없음 | 인덱스 재구성·OPTIMIZE | 클러스터 + 동기화 파이프라인 |

형태소 분석 쪽을 보면, 한국어는 Lucene 계열의 nori 분석기가 사실상 표준 선택입니다.
`nori_tokenizer`가 어절을 형태소로 쪼개고, `decompound_mode`로 복합어를 분해할지(`discard`) 원형까지 같이 남길지(`mixed`) 고를 수 있습니다.
`nori_part_of_speech` 필터로 조사·어미 같은 품사를 걸러내고, 사용자 사전으로 서비스 고유 명사를 추가합니다.

> Amazon OpenSearch Service에서는 nori가 도메인에 연결하는 선택 플러그인으로 제공됩니다. 지원 버전과 연결 방법은 바뀔 수 있으니 콘솔의 플러그인 목록과 서비스 문서를 확인하세요.

판단 기준은 기능 목록이 아니라 **요구사항이 어디까지 왔는가**로 잡는 편이 깔끔합니다.

- 검색이 부가 기능이고 "이 단어가 들어 있는 글 찾기" 수준이면 ngram으로 충분합니다. 클러스터 하나를 더 운영하는 비용이 기능보다 큽니다.
- 동의어, 오타 교정, 필드별 가중치, 하이라이팅, 패싯 중 **둘 이상이 요구사항에 들어오면** DB로 버티는 구간은 지난 것입니다. 하나씩 흉내 내다 보면 사전과 쿼리 조립 코드가 검색엔진 설정보다 복잡해집니다.
- 넘어갈 때 실제로 비싼 건 엔진 운영이 아니라 **색인과 원본의 동기화**입니다. 쓰기 트랜잭션과 색인 갱신은 한 묶음이 아니니, 아웃박스나 CDC 같은 장치가 같이 필요합니다. 이걸 "나중에"로 미루면 검색 결과가 조용히 원본과 어긋나는 상태가 됩니다.

> PostgreSQL이라면 선택지가 조금 다릅니다. `pg_trgm` 확장과 GIN 인덱스로 `LIKE '%...%'`를 가속할 수 있고 유사도 검색도 되지만, 기본 전문 검색(`tsvector`)에 한국어 형태소 사전이 들어 있지는 않습니다. 어느 DB든 형태소 분석은 별도 확장이나 외부 엔진의 몫이라는 점은 같습니다.

## 정리

- `LIKE '%...%'`는 정확도가 나쁘지 않아서 느린 게 늦게 발견됩니다. 앞에 와일드카드가 붙으면 B-tree로 범위를 좁힐 수 없습니다.
- 기본 전문 검색 파서는 공백으로 자르므로 조사·어미가 붙는 한국어에서는 검색어와 색인이 겹치지 않습니다.
- ngram 파서는 글자 단위로 쪼개 이 문제를 피합니다. 단어를 이해해서가 아니라 부분 문자열에 가까워졌기 때문입니다.
- `ngram_token_size`는 재시작으로만 바꿀 수 있고 바꾸면 인덱스를 다시 만들어야 합니다. 먼저 정해야 하는 값입니다.
- 불리언 모드에 사용자 입력을 그대로 넘기지 마세요. 연산자를 제거하고 어절을 구문으로 묶고, 토큰 크기보다 짧은 입력은 아예 보내지 않습니다.
- 첫 FULLTEXT 인덱스는 테이블을 재생성합니다. 가능하면 테이블 생성 시점에 `FTS_DOC_ID`를 정의해두세요.
- 삭제는 색인을 줄이지 않습니다. `innodb_optimize_fulltext_only`를 켠 `OPTIMIZE TABLE`을 주기 작업으로 두고, 끝나면 변수를 되돌리세요.
- 동의어·오타·가중치가 요구사항에 들어오는 순간이 경계입니다. 넘어갈 때의 진짜 비용은 엔진이 아니라 색인 동기화입니다.
