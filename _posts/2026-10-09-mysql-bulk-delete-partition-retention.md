디스크 사용률 알람을 보고 오래된 로그 행 수천만 건을 지웁니다. `COUNT(*)`는 줄었는데 디스크 사용률은 그대로입니다.

그리고 삭제가 도는 동안 사용률이 **오히려 올라갑니다.**

공간을 비우려는 작업이 공간을 쓰기 때문입니다. 삭제는 공짜가 아니고, 디스크를 돌려받는 일은 삭제와 별개의 작업입니다.

## 지운 공간은 테이블 안에 남는다

InnoDB는 테이블마다 별도 파일(`.ibd`)을 씁니다. `DELETE`는 그 파일 안의 레코드에 삭제 표시를 하고, 백그라운드 purge 스레드가 뒤따라오며 실제로 레코드를 치웁니다.

치운 자리는 **빈 페이지로 남아 그 테이블스페이스에 그대로 귀속됩니다.** 파일은 줄지 않습니다. OS 입장에서는 아무 일도 없었습니다.

```sql
SELECT TABLE_NAME,
       ROUND(DATA_LENGTH  / 1024 / 1024) AS data_mb,
       ROUND(INDEX_LENGTH / 1024 / 1024) AS index_mb,
       ROUND(DATA_FREE    / 1024 / 1024) AS free_mb
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE()
ORDER BY DATA_LENGTH + INDEX_LENGTH DESC
LIMIT 10;
```

삭제 후 `free_mb`만 커지고 `data_mb`는 그대로라면 지운 공간이 테이블 안에 고여 있다는 뜻입니다.

이게 항상 문제는 아닙니다. 그 공간은 **같은 테이블이 재사용합니다.** 매일 쌓이고 매일 오래된 것을 지우는 로그 테이블이라면, 파일 크기가 어느 수준에서 평평해지고 그대로 유지됩니다. 이 경우 파일을 줄일 이유가 없습니다.

문제가 되는 건 **다시는 그만큼 쓰지 않을 때**입니다. 보관 기간을 1년에서 3개월로 줄였거나, 쓰지 않게 된 테이블을 비운 경우입니다. 이때 고인 공간은 영구히 노는 공간이 됩니다.

> 매니지드 데이터베이스에서는 이 구분이 비용으로 직결됩니다. 할당된 스토리지는 자동으로 늘어나지만 줄이는 건 제한적이라, 과금 기준이 최고점에 머무를 수 있습니다.
> 엔진과 서비스에 따라 축소 가능 여부가 다르니 공식 문서에서 확인하세요.

## 한 번에 지우면 더 많은 공간을 쓴다

`DELETE FROM access_logs WHERE created_at < '2026-07-01'` 한 줄은 트랜잭션 하나입니다. 중간에 실패하면 전부 되돌아가야 하고, 되돌릴 수 있어야 한다는 말은 **지운 행의 이전 이미지를 전부 어딘가에 들고 있다는 뜻**입니다.

그래서 한 번에 지울 때 자리를 차지하는 것이 셋 늘어납니다.

- **undo 로그** — 삭제 대상 전체의 이전 이미지. 트랜잭션이 끝날 때까지 쌓입니다.
- **바이너리 로그** — `ROW` 포맷에서는 지운 행마다 이벤트가 기록됩니다. 테이블 크기에 비례한 로그가 새로 생깁니다.
- **purge 지체** — 긴 트랜잭션이 떠 있는 동안 purge는 그 이전 버전을 치울 수 없습니다. 쌓인 양은 history list로 드러납니다.

```sql
SHOW ENGINE INNODB STATUS\G
-- TRANSACTIONS 절의 "History list length" 를 본다. 삭제 중에 치솟고,
-- 트랜잭션이 끝난 뒤에도 한참 동안 떨어지지 않으면 purge가 못 따라오는 것이다.
```

여기서 순서가 거꾸로 돌아갑니다. 디스크가 이미 90%여서 지우려는 상황인데, **그 삭제가 디스크를 채워서 서비스를 멈춥니다.** 바이너리 로그가 같은 볼륨에 있으면 특히 빠르게 닿습니다.

락도 같이 번집니다. 범위 조건으로 지우면 스캔한 인덱스 구간 전체에 넥스트키 락이 걸려서, 그 구간에 끼어드는 `INSERT`가 대기합니다. 어떤 범위가 잠기는지는 [InnoDB 락 글](/blog/innodb-deadlock-gap-lock/)에서 다뤘습니다.

그리고 리플리카에서는 이 트랜잭션이 **한 덩어리로 적용됩니다.** 원본에서 10분 걸린 삭제는 리플리카에서도 10분이고, 그 10분 동안 복제 지연이 쌓입니다.

## PK 범위로 쪼개서 지운다

가장 흔한 쪼개기는 이것입니다.

```sql
-- 반복 실행
DELETE FROM access_logs WHERE created_at < '2026-07-01' LIMIT 1000;
```

트랜잭션은 작아졌지만 문제가 남습니다. `created_at`에 인덱스가 없으면 매 회차가 풀 스캔입니다. 인덱스가 있어도 매번 같은 범위의 **앞쪽부터 다시 훑고**, purge가 따라오기 전의 삭제 표시 레코드는 스캔 비용으로 남아 있습니다. 뒤로 갈수록 느려지는 구조는 [OFFSET 페이지네이션](/blog/cursor-pagination-keyset/)과 같습니다.

삭제 범위를 **기본키 하나로 환산**하면 이 문제가 사라집니다. `id`가 `AUTO_INCREMENT`이고 `created_at`이 삽입 시각이라면 둘은 같은 방향으로 증가하므로, 날짜 경계를 PK 경계로 바꿀 수 있습니다.

```sql
-- 경계를 한 번만 구한다. created_at 인덱스를 역방향으로 한 건만 읽는다.
SELECT id
FROM access_logs
WHERE created_at < '2026-07-01'
ORDER BY created_at DESC
LIMIT 1;
```

이제 PK 범위를 전진하면서 지웁니다.

```typescript
const CHUNK = 1_000;

async function purgeUpTo(maxId: number, startId: number): Promise<number> {
  let cursor = startId;          // 워터마크를 저장해두면 중단 후 이어서 돌릴 수 있다
  let removed = 0;

  while (cursor < maxId) {
    const upper = Math.min(cursor + CHUNK, maxId);

    const [res] = await pool.execute<ResultSetHeader>(
      `DELETE FROM access_logs WHERE id > ? AND id <= ?`,
      [cursor, upper],
    );

    removed += res.affectedRows;
    cursor = upper;              // 0건이 지워져도 커서는 전진한다

    await throttle();            // 아래에서 설명
  }

  return removed;
}
```

이 모양이 가진 성질이 몇 개 있습니다.

**이미 지운 구간을 다시 보지 않습니다.** 커서가 단조 증가하므로 회차마다 비용이 일정합니다. 해당 구간에 남은 행이 없으면 `affectedRows`가 0이고, 그 회차는 거의 공짜입니다.

**잠기는 범위가 예측 가능합니다.** PK의 닫힌 구간만 잠그니, 테이블 뒤쪽에 들어오는 새 `INSERT`는 영향을 받지 않습니다. 로그처럼 꼬리에만 쓰는 테이블에서는 사실상 간섭이 없습니다.

**중단해도 손해가 없습니다.** 커서를 어딘가에 적어두면 다음 실행이 거기서 이어집니다. 전체를 하나의 트랜잭션으로 묶지 않았으니 롤백할 것도 없습니다.

전제는 하나입니다. **`id`와 `created_at`의 상관관계.** 과거 데이터를 나중에 백필했거나 PK가 랜덤 UUID라면 이 환산이 성립하지 않습니다. 후자라면 [정렬 가능한 ID](/blog/uuid-primary-key-innodb-clustered-index/) 쪽 이야기가 먼저입니다. 상관관계를 믿을 수 없을 때는 지울 PK 목록을 먼저 `SELECT`로 뽑고 그 목록으로만 `DELETE`하는 2단계가 안전합니다.

### 쉬는 구간이 필요한 이유

청크 사이에 쉬지 않으면 쪼갠 효과가 절반만 남습니다. purge 스레드와 리플리카가 따라올 시간을 주지 않기 때문입니다.

```typescript
async function throttle(): Promise<void> {
  for (;;) {
    const lag = await replicaLagSeconds();
    if (lag < 5) break;
    await sleep(1_000);
  }
  await sleep(200);              // purge가 숨 쉴 틈
}
```

복제 지연을 믿을 수 있게 재는 방법은 [복제 지연 글](/blog/read-your-writes-replica-lag/)에서 다뤘습니다. 지연을 보고 멈추는 이 루프가 야간 배치를 몇 시간으로 늘리지만, 늘어난 시간은 서비스 영향과 맞바꾼 것입니다.

청크 크기는 **한 회차가 수백 밀리초 안에 끝나는 선**에서 정합니다. 키우면 undo와 바이너리 로그와 락 범위가 다시 커져서, 쪼갠 이유가 희미해집니다.

> 운영 콘솔에서 손으로 돌릴 때는 `SET sql_safe_updates = 1`을 켜두면 키 조건 없는 `DELETE`를 거부합니다.
> 조건 한 줄을 빼먹은 `DELETE`의 비용은 되돌릴 수 없습니다.

## 파일 크기를 줄이려면 재구성해야 한다

고인 공간을 OS에 돌려받는 방법은 **테이블을 다시 만드는 것**뿐입니다. InnoDB에서 `OPTIMIZE TABLE`은 사실상 테이블 재구성이고, `ALTER TABLE ... FORCE`와 같은 일을 합니다.

```sql
ALTER TABLE access_logs FORCE;
-- 또는
OPTIMIZE TABLE access_logs;
```

여기에 함정이 있습니다. 재구성은 **새 파일을 만들고 다 옮긴 뒤 바꿔치기**합니다. 즉 작업 중 피크 디스크 사용량이 테이블 크기만큼 더 필요합니다.

디스크가 꽉 차서 공간을 회수하려는데, 회수 작업이 테이블 크기만큼의 여유를 요구합니다. **순서가 반대입니다.** 여유가 있을 때 해두는 작업이고, 꽉 찬 다음에 꺼낼 수 있는 카드가 아닙니다.

온라인 DDL이라 동시 DML은 대체로 허용되지만, 그동안의 변경을 담는 로그가 `innodb_online_alter_log_max_size`를 넘으면 작업이 실패합니다. 쓰기가 많은 테이블에서 몇 시간 걸리는 재구성이라면 이 값과 작업 시간대를 같이 봐야 합니다. 큰 테이블이라면 `gh-ost`나 `pt-online-schema-change`로 재구성하는 쪽이 통제하기 쉽습니다. [온라인 스키마 변경 글](/blog/mysql-online-schema-change/)의 판단 기준이 그대로 적용됩니다.

재구성이 끝나면 통계도 다시 만듭니다.

```sql
ANALYZE TABLE access_logs;
```

### 전부 비운다면, 대부분을 지운다면

남길 행이 **하나도 없다면** `DELETE`를 쓸 이유가 없습니다.

```sql
TRUNCATE TABLE access_logs;
```

`TRUNCATE`는 테이블스페이스를 버리고 새로 만듭니다. undo도 행 단위 바이너리 로그도 없고, 디스크는 즉시 반환됩니다. 대가는 명확합니다. `WHERE`를 붙일 수 없고, 암묵적 커밋이라 롤백할 수 없고, `AUTO_INCREMENT`가 초기화됩니다.

**대부분을 지우고 소수만 남긴다면** 방향을 뒤집는 게 더 쌉니다. 남길 행만 새 테이블에 복사하고 이름을 바꿔 끼웁니다.

```sql
CREATE TABLE access_logs_new LIKE access_logs;

INSERT INTO access_logs_new
SELECT * FROM access_logs WHERE created_at >= '2026-07-01';

RENAME TABLE access_logs     TO access_logs_old,
             access_logs_new TO access_logs;
```

`RENAME TABLE`은 두 교체를 원자적으로 처리하니, 테이블이 사라져 보이는 구간은 없습니다. 복사하는 동안 들어온 쓰기는 새 테이블에 없으므로, 교체 전에 그 구간을 한 번 더 옮기거나 쓰기를 짧게 멈출 계획이 필요합니다. 그리고 `access_logs_old`는 **문제가 없다는 걸 확인한 뒤에** 지웁니다.

## 삭제를 파일 삭제로 바꾸기 — RANGE 파티션

여기까지는 전부 "이미 쌓인 것을 어떻게 치울까"입니다. 보관 기간이 정해진 테이블이라면 애초에 치우는 일이 싸지도록 만들 수 있습니다.

날짜로 RANGE 파티션을 걸면, 오래된 데이터를 지우는 일이 **파티션 하나를 떼어내는 일**이 됩니다.

```sql
CREATE TABLE access_logs (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id    BIGINT UNSIGNED NOT NULL,
  path       VARCHAR(255)    NOT NULL,
  created_at DATETIME        NOT NULL,
  PRIMARY KEY (id, created_at),
  KEY idx_user_created (user_id, created_at)
) ENGINE = InnoDB
PARTITION BY RANGE COLUMNS (created_at) (
  PARTITION p202608 VALUES LESS THAN ('2026-09-01'),
  PARTITION p202609 VALUES LESS THAN ('2026-10-01'),
  PARTITION p202610 VALUES LESS THAN ('2026-11-01')
);
```

```sql
ALTER TABLE access_logs DROP PARTITION p202608;
```

이 한 줄은 행을 하나씩 지우지 않습니다. 해당 파티션의 데이터를 통째로 버리므로 undo도, 행 단위 바이너리 로그도, purge 부담도 없고 **디스크가 즉시 돌아옵니다.** 앞에서 본 비용 대부분이 사라집니다.

공짜는 아닙니다. DDL이라 짧게 메타데이터 락을 잡고, 그 순간 해당 테이블 쿼리는 대기합니다. 그리고 지운 데이터는 돌아오지 않습니다.

### 파티션이 요구하는 것

파티션을 고르면 스키마 설계에 제약이 따라옵니다. 이게 실제 판단 지점입니다.

**모든 유니크 키가 파티션 표현식의 컬럼을 포함해야 합니다.** 위 예시에서 기본키가 `(id)`가 아니라 `(id, created_at)`인 이유입니다. MySQL이 파티션 사이를 넘나들며 유일성을 검사하지 않기 때문에 생기는 제약입니다.

따라오는 결과가 둘입니다. `id` 단독 유니크 제약을 DB가 보장해주지 않고, **파티션된 InnoDB 테이블에는 외래 키를 쓸 수 없습니다.** 다른 테이블이 이 테이블을 참조하는 구조라면 여기서 멈춰야 합니다.

**파티션 프루닝은 쿼리가 파티션 컬럼으로 필터할 때만 동작합니다.** `created_at` 없이 `id`나 `user_id`만으로 조회하면 모든 파티션을 뒤집니다. 파티션 수만큼 검색이 늘어나니, 프루닝이 안 되는 조회 패턴이 주력이라면 파티션은 이득이 아니라 손해입니다.

```sql
EXPLAIN SELECT COUNT(*) FROM access_logs
WHERE created_at >= '2026-10-01' AND created_at < '2026-10-08';
-- partitions 컬럼에 p202610 하나만 나와야 한다
```

`EXPLAIN`의 `partitions` 컬럼을 확인하는 습관이 필요합니다. 여기에 전체 파티션 목록이 찍히면 프루닝이 안 되는 쿼리입니다.

**파티션을 미리 만들어둬야 합니다.** 범위에 해당하는 파티션이 없는 행은 `INSERT`가 실패합니다. 다음 달 파티션을 추가하는 작업을 스케줄로 돌려야 하고, 그 스케줄이 멈추면 어느 날 갑자기 쓰기가 전부 거부됩니다.

```sql
ALTER TABLE access_logs
  ADD PARTITION (PARTITION p202611 VALUES LESS THAN ('2026-12-01'));
```

> `VALUES LESS THAN (MAXVALUE)` 파티션을 두면 `INSERT` 실패는 막힙니다. 대신 그 뒤의 모든 데이터가 거기 쌓이고, 나중에 날짜별로 떼어내려면 `REORGANIZE PARTITION`으로 쪼개야 합니다.
> 그 작업은 해당 파티션의 데이터를 다시 쓰는 일이라, 앞에서 피하려던 비용이 돌아옵니다.

마지막으로, **기존 큰 테이블을 파티션 테이블로 바꾸는 것 자체가 전체 재구성**입니다. `ALTER TABLE ... PARTITION BY`는 테이블을 다시 만들므로 앞 절의 디스크 여유와 작업 시간 문제를 똑같이 안고 갑니다. 처음 만들 때 거는 것이 가장 쉽고, 이미 커진 테이블이라면 새 테이블로 옮기는 계획이 필요합니다.

정리하면 파티션이 맞는 테이블은 이렇습니다. **한 번 쓰고 수정하지 않으며, 조회가 날짜 조건을 포함하고, 보관 기간이 정해져 있고, 다른 테이블이 외래 키로 참조하지 않는 테이블.** 접근 로그, 이벤트 기록, 알림 발송 이력, 감사 로그가 여기에 들어갑니다. 수정되고 참조되는 업무 테이블에는 비용이 큽니다.

## "지워도 되나"는 기술 질문이 아니다

여기까지의 모든 선택은 보관 기간이 정해져 있다는 전제에서 출발합니다. 그런데 그 숫자를 개발자가 정하고 있는 경우가 많습니다.

보관 기간을 결정하는 건 법정 보관 의무, 분쟁 대응에 필요한 범위, 분석팀의 요구입니다. 전부 코드 밖에 있습니다. "90일이면 충분하겠지"로 지운 데이터는 반년 뒤 감사나 분쟁에서 필요해집니다.

그래서 할 일은 두 가지입니다. **숫자는 법무·사업과 합의하고, 코드에는 한 군데에만 적습니다.** 테이블별 보관 기간을 설정으로 모아두면 나중에 근거를 찾을 수 있고, 배치 스크립트마다 흩어진 상수를 추적하지 않아도 됩니다.

보관이 필요한데 운영 DB에서는 치우고 싶다면, 삭제가 아니라 **이동**입니다.

- **콜드 테이블로 옮기기** — 같은 DB의 별도 테이블이나 별도 인스턴스. 조회 경로가 살아 있는 게 장점이고, 스토리지 비용은 그대로인 게 단점입니다.
- **객체 스토리지로 내보내기** — 가장 싸고, 되살리는 비용이 가장 비쌉니다. 매니지드 DB는 서버 로컬 파일 쓰기가 막혀 있어 클라이언트로 스트리밍해 받거나 엔진이 제공하는 내보내기 기능을 써야 합니다. 쓸 수 있는 방식은 엔진·서비스마다 다르니 공식 문서에서 확인하세요.

어느 쪽이든 순서를 지켜야 합니다. **내보내고, 검증하고, 지웁니다.** 내보내기와 삭제는 한 트랜잭션으로 묶이지 않으니, 중간에 끊겨도 다시 돌릴 수 있게 워터마크를 남기고 행 수나 체크섬을 맞춰본 뒤 삭제를 실행합니다. 이 구조는 [아웃박스](/blog/transactional-outbox-pattern/)나 ETL 파이프라인에서 쓰는 것과 같습니다.

청크 삭제와 아카이빙을 직접 구현하지 않고 `pt-archiver` 같은 도구를 쓰는 선택도 있습니다. 청크 단위 이동·삭제와 복제 지연에 따른 조절을 옵션으로 제공하니, 일회성 정리라면 스크립트를 쓰는 것보다 빠릅니다.

## 무엇을 고를까

| 상황 | 방법 | 대가 |
| --- | --- | --- |
| 보관 기간이 정해진 append-only 테이블 | RANGE 파티션 + `DROP PARTITION` | 유니크 키에 날짜 포함, 외래 키 불가, 프루닝 조건, 파티션 관리 작업 |
| 주기적으로 일부를 지우고 공간은 테이블이 재사용 | PK 범위 청크 `DELETE` | 파일 크기는 줄지 않는다 |
| 파일 크기를 꼭 줄여야 함 | 청크 삭제 후 테이블 재구성 | 작업 중 테이블 크기만큼 추가 디스크 |
| 대부분 지우고 소수만 남김 | 새 테이블에 복사 후 `RENAME TABLE` | 복사 구간의 쓰기 처리, 추가 디스크 |
| 전부 비움 | `TRUNCATE TABLE` | `WHERE` 불가, 롤백 불가, `AUTO_INCREMENT` 초기화 |

두 줄로 줄이면 이렇습니다.

**디스크를 돌려받는 일과 행을 지우는 일은 다른 작업입니다.** 한쪽만 해놓고 다른 쪽을 기대하면 알람은 그대로 남습니다.

그리고 **보관 기간이 정해진 테이블이라면 삭제를 설계 단계에서 싸게 만들 수 있습니다.** 파티션의 제약을 미리 받아들이는 비용이, 커진 뒤에 치우는 비용보다 거의 항상 작습니다.
