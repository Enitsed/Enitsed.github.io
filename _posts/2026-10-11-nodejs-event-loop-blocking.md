평소 50ms로 끝나던 API들이 어느 순간 전부 2초씩 걸립니다.
DB는 한가하고, 외부 API도 정상이고, 느린 쿼리 로그에는 아무것도 안 찍혀 있습니다.

지표를 보면 컨테이너 CPU가 100%인데 코어는 하나만 쓰고 있습니다.
이건 어느 한 엔드포인트가 느린 문제가 아니라, **모든 요청이 한 줄로 서 있는** 문제입니다.

## 느려지는 방식이 다르다

요청 처리가 느린 것과 이벤트 루프가 막힌 것은 지표에서 구분됩니다.

| | 특정 작업이 느릴 때 | 루프가 막혔을 때 |
| --- | --- | --- |
| 영향 범위 | 그 엔드포인트만 | **전부**, 헬스체크까지 |
| CPU | 대개 낮음 (대기 중) | 한 코어가 100% |
| DB 지표 | 느린 쿼리·커넥션 대기가 보임 | 깨끗함 |
| p99 모양 | 특정 경로만 상승 | 모든 경로가 같은 시각에 계단식 |

세 번째 줄이 핵심입니다. 응답은 느린데 **아래쪽 어디에도 원인이 없으면** 런타임 안에서 순서를 기다리고 있는 겁니다.

Node.js는 자바스크립트를 한 스레드에서 실행합니다. 동기 코드가 300ms 도는 동안 그 프로세스는 새 요청을 받지도, 끝난 쿼리의 콜백을 실행하지도 못합니다.
동시 요청이 20개면 마지막 요청은 앞의 19개가 끝나기를 기다립니다. **블로킹 시간이 요청 수만큼 곱해집니다.**

## await는 루프를 막지 않는다

가장 자주 보는 오해부터 정리합니다. `await`가 붙어 있으면 "기다리니까 느리다"고 읽히지만, 루프를 막는 것과는 무관합니다.

```typescript
// 루프를 막지 않는다. 기다리는 동안 다른 요청이 처리된다
const rows = await pool.query('SELECT ...');

// 루프를 막는다. 이 줄이 끝날 때까지 프로세스가 아무것도 못 한다
const parsed = JSON.parse(hugeString);
```

`await`는 제어권을 루프에 돌려주고 콜백을 등록합니다. 그 사이 다른 요청의 코드가 돕니다.
막는 건 **중간에 양보하지 않는 동기 코드**입니다.

| 코드 | 루프를 막는가 |
| --- | --- |
| `await pool.query(...)`, `await fetch(...)` | 아니다 |
| `JSON.parse` / `JSON.stringify` (큰 입력) | 막는다 |
| `fs.readFileSync`, `execSync` | 막는다 |
| `bcrypt.hashSync`, `crypto.pbkdf2Sync` | 막는다 |
| `bcrypt.hash` (비동기), `crypto.pbkdf2` | 루프는 안 막고 스레드풀을 점유 |
| 큰 배열의 `sort`·`map`·`filter` 체인 | 막는다 |
| 백트래킹이 폭주하는 정규식 | 막는다 |
| 문자열 수만 건을 이어붙이는 템플릿 렌더링 | 막는다 |

실무에서 제일 많이 걸리는 건 맨 아래 세 줄이 아니라 **`JSON.parse`** 입니다.
외부 API 응답, 큐 메시지, 캐시에서 꺼낸 값 — 어디서든 입력 크기가 사용자 데이터에 비례해 커지고, 파싱은 그 크기에 비례해 루프를 잡습니다.
개발 환경에서 10KB였던 응답이 운영에서 10MB가 되는 순간 증상이 나타납니다.

정규식도 한 번 정리해둘 만합니다. 입력 길이에 지수적으로 시간이 늘어나는 패턴은 `(a+)+b` 같은 교과서 예제뿐 아니라, 중첩 수량자가 들어간 검증 정규식에서 흔히 나옵니다.
사용자 입력을 그런 정규식에 넣으면 **요청 하나로 프로세스를 멈출 수** 있습니다. 검증은 가능하면 정규식 대신 길이 제한과 문자 집합 검사로 쪼개는 쪽이 안전합니다.

## 지연을 숫자로 재기

"루프가 막힌 것 같다"를 지표로 바꿔야 합니다. `perf_hooks`의 히스토그램이 가장 가볍습니다.

```typescript
import { monitorEventLoopDelay } from 'node:perf_hooks';

const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();

const toMs = (ns: number) => Math.round(ns / 1e6);

setInterval(() => {
  logger.info({
    msg: 'event_loop_delay',
    mean_ms: toMs(histogram.mean),
    p99_ms: toMs(histogram.percentile(99)),
    max_ms: toMs(histogram.max),
  });
  histogram.reset();
}, 10_000).unref();
```

이 히스토그램은 `resolution` 간격으로 루프를 찔러보고 실제로 돌아온 시각과의 차이를 기록합니다.
유휴 상태에서도 `resolution` 근처의 기본값이 깔리니 **절대값보다 변화를 봅니다.** 평소 수십 ms에 머물던 p99가 수백 ms로 뛰면 그게 신호입니다.

`unref()`를 붙여야 이 타이머 때문에 프로세스가 종료되지 못하는 일이 없습니다. 종료 절차를 다루는 서비스라면 특히 챙기세요.

의존성을 추가하기 어려운 환경이라면 타이머 지연으로도 비슷하게 잡힙니다.

```typescript
let last = Date.now();
setInterval(() => {
  const now = Date.now();
  const drift = now - last - 1000;   // 1초마다 돌기로 했는데 얼마나 늦었나
  last = now;
  if (drift > 200) logger.warn({ msg: 'loop_blocked', drift_ms: drift });
}, 1000).unref();
```

`setInterval`은 "정확히 1초 뒤"가 아니라 "1초 뒤에 가능해지면"입니다. 그 차이가 곧 루프가 다른 일에 잡혀 있던 시간입니다.

지연은 떴는데 어디가 범인인지 모를 때는 CPU 프로파일을 받습니다.

```bash
# 프로세스를 --cpu-prof 로 띄우면 종료 시 .cpuprofile 파일이 떨어진다
node --cpu-prof --cpu-prof-dir=/tmp/prof dist/main.js
```

받은 파일은 크롬 개발자도구의 성능 탭에 그대로 올려 볼 수 있습니다. 한 함수가 넓게 자리를 차지하고 있으면 그게 막는 코드입니다.
운영 프로세스에 바로 걸기 부담스러우면, 운영과 같은 크기의 입력을 재생하는 스테이징에서 받는 편이 낫습니다.

## 고치는 방향 네 개

범인을 찾았다면 선택지는 넷입니다. 순서대로 비용이 커집니다.

### 1. 일을 줄인다

가장 먼저 볼 것은 "이 작업을 요청 처리 중에 꼭 해야 하는가"입니다.

전체를 파싱해서 필드 두 개만 쓰고 버리는 코드, 1만 행을 메모리에 올려 애플리케이션에서 집계하는 코드, 매 요청마다 같은 설정을 다시 계산하는 코드는 흔합니다.
집계는 DB가 훨씬 잘하고, 큰 응답은 필요한 필드만 받도록 요청을 바꾸면 됩니다.

파싱 자체를 피할 수 없다면 스트리밍 파서로 바꾸는 선택도 있습니다. 조각마다 루프에 양보할 기회가 생기니까요.
다만 코드가 복잡해지므로, 아래 2번으로 해결되는 크기라면 거기서 멈추는 편이 낫습니다.

### 2. 쪼개서 양보한다

순수하게 자바스크립트로 도는 반복 작업이라면, 중간중간 루프에 제어권을 넘기는 것만으로 "전부 느려짐"이 사라집니다.

```typescript
const yieldToLoop = () => new Promise<void>((resolve) => setImmediate(resolve));

export async function summarize(rows: Row[]): Promise<Totals> {
  const totals = emptyTotals();

  for (let i = 0; i < rows.length; i++) {
    accumulate(totals, rows[i]);

    // 1024건마다 한 번 숨을 돌린다
    if ((i & 0x3ff) === 0x3ff) await yieldToLoop();
  }

  return totals;
}
```

`setImmediate`여야 합니다. `process.nextTick`은 **루프의 다음 단계로 넘어가기 전에** 큐를 다 비우기 때문에, 그걸로 쪼개면 양보가 일어나지 않습니다.

이 방법은 전체 작업 시간을 조금 늘리는 대신 **그 시간을 다른 요청과 나눕니다.** 작업 하나의 완료는 늦어지고 전체 p99는 좋아집니다.
그 교환이 맞는지는 작업의 성격에 달렸습니다. 사용자가 응답을 기다리는 작업이면 조금 손해고, 백그라운드 집계라면 거의 공짜입니다.

양보 간격은 측정해서 정합니다. 1건마다 양보하면 `setImmediate` 왕복 비용이 작업 시간을 몇 배로 불립니다.
한 덩어리가 수 ms 정도 걸리게 묶는 선에서 시작하면 대개 적당합니다.

### 3. 스레드풀로 내린다

CPU를 쓰는 작업 중 일부는 Node.js가 이미 별도 스레드에서 처리할 준비를 해뒀습니다. 동기 버전을 비동기 버전으로 바꾸는 것만으로 루프에서 빠집니다.

```typescript
import { pbkdf2, randomBytes } from 'node:crypto';
import { promisify } from 'node:util';

const pbkdf2Async = promisify(pbkdf2);
const randomBytesAsync = promisify(randomBytes);

// 동기 버전이었다면 해싱 시간 전체가 루프를 막았다
const salt = await randomBytesAsync(16);
const key = await pbkdf2Async(password, salt, 210_000, 32, 'sha512');
```

비밀번호 해싱은 **의도적으로 느리게 설계된** 연산입니다. 동기 API로 쓰면 로그인 요청 하나가 그 시간 동안 서버 전체를 세웁니다.
`bcrypt` 계열 라이브러리도 동기·비동기 함수를 둘 다 제공하니, 어느 쪽을 쓰고 있는지 확인해볼 만합니다.

> 반복 횟수나 비용 계수 같은 파라미터의 권장값은 시간이 지나면 올라갑니다. 숫자는 OWASP나 사용 중인 라이브러리의 현재 문서를 기준으로 정하세요.

이미지 변환이나 압축처럼 네이티브 모듈이 처리하는 작업도 대부분 비동기 API가 스레드풀을 씁니다. 동기 API만 있는 라이브러리라면 4번으로 가야 합니다.

### 4. 프로세스 밖으로 낸다

순수 자바스크립트 CPU 작업이 무겁고 쪼갤 수도 없다면 `worker_threads`입니다.

```typescript
// worker.ts
import { parentPort, workerData } from 'node:worker_threads';
import { renderReport } from './render';

parentPort!.postMessage(renderReport(workerData));
```

```typescript
// 호출하는 쪽
import { Worker } from 'node:worker_threads';

function runInWorker<T>(data: unknown): Promise<T> {
  return new Promise((resolve, reject) => {
    const worker = new Worker(new URL('./worker.js', import.meta.url), {
      workerData: data,
    });
    worker.once('message', resolve);
    worker.once('error', reject);
    worker.once('exit', (code) => {
      if (code !== 0) reject(new Error(`worker exited with ${code}`));
    });
  });
}
```

주의할 점이 둘 있습니다.

첫째, **워커 생성은 공짜가 아닙니다.** 새 V8 인스턴스를 띄우는 비용과 메모리가 들어서, 요청마다 하나씩 만들면 블로킹 대신 다른 종류의 과부하를 얻습니다.
미리 몇 개 띄워 재사용하는 풀로 만들거나, 그런 풀을 제공하는 라이브러리를 쓰세요.

둘째, **데이터를 넘기는 비용**이 있습니다. 워커로 보내는 값은 기본적으로 복사되므로, 큰 객체를 넘기면 그 직렬화가 다시 루프를 잡습니다.
이진 데이터는 `ArrayBuffer`를 소유권째로 넘겨 복사를 피할 수 있지만, 일반 객체라면 **넘기는 양이 작고 계산이 무거울 때** 이득이 남습니다.

작업이 몇 초 단위로 길거나 실패하면 다시 돌려야 하는 성격이면, 워커보다 큐로 떼어내는 편이 맞습니다.
그쪽이 재시도·가시성·실패 격리를 전부 가져다주니까요. 응답을 즉시 줄 수 없다는 제약은 [대용량 내보내기](/blog/large-export-streaming-memory/)에서 작업 ID를 돌려주는 방식과 같습니다.

### 고르는 기준

| 상황 | 선택 |
| --- | --- |
| 입력을 줄일 수 있다 | 1번. 다른 걸 보기 전에 여기부터 |
| 순수 JS 반복, 수십~수백 ms | 2번 `setImmediate` 쪼개기 |
| 해싱·압축·이미지 등 네이티브 작업 | 3번 비동기 API로 교체 |
| 쪼갤 수 없는 무거운 JS 계산 | 4번 워커 풀 |
| 수 초 이상, 재시도가 필요 | 큐로 분리 |

프로세스를 늘리는 것(클러스터, 태스크 수 증가)은 이 목록에 없습니다.
인스턴스가 4개면 블로킹에 걸리는 요청 비율이 줄어들긴 하지만, **걸린 요청이 겪는 지연은 그대로**입니다. 원인을 고치는 대신 확률을 낮추는 선택이라, 임시 완화로만 쓰는 게 맞습니다.

## 두 번째 범인: 스레드풀이 마르는 경우

증상이 조금 다른 경우가 있습니다. 루프 지연은 정상인데 **외부 호출만 느려지는** 상황입니다.

Node.js는 파일 입출력, 일부 암호 연산, 압축, 그리고 **DNS 이름 조회**를 libuv 스레드풀에 넘깁니다. 이 풀의 기본 크기는 작습니다(기본값 4).
비동기 해싱을 동시에 여러 개 돌리면 풀이 가득 차고, 그 뒤에 들어온 **DNS 조회가 큐에서 대기**합니다.

그래서 이런 그림이 됩니다. 애플리케이션 지표에는 "외부 API 호출 2초"로 찍히는데, 상대 서버 로그에는 10ms로 끝난 요청만 있습니다.
차이는 **연결을 맺기 전 이름을 푸는 단계**에서 생긴 것이고, 범인은 같은 프로세스 안의 해싱입니다.

대응은 두 갈래입니다.

```bash
# 풀 크기를 늘린다. 프로세스 시작 전에 설정해야 적용된다
UV_THREADPOOL_SIZE=16
```

올릴 수 있는 상한과 기본값은 사용 중인 Node.js 버전의 문서를 확인하세요. 코어 수보다 크게 잡아도 의미가 있는 종류의 작업(대기가 섞인 I/O)과 그렇지 않은 작업이 섞여 있어서, 늘려놓고 CPU를 같이 봐야 합니다.

더 효과적인 건 **조회 자체를 줄이는 쪽**입니다. HTTP 클라이언트에 keep-alive 에이전트를 붙이면 연결을 재사용하니 이름 조회가 매 요청마다 일어나지 않습니다.

```typescript
import { Agent } from 'node:https';

export const httpsAgent = new Agent({
  keepAlive: true,
  maxSockets: 50,
});
```

커넥션 재사용은 [커넥션 풀이 마르는 문제](/blog/db-connection-pool-exhaustion/)와 같은 구조입니다. 한정된 자원을 짧게 잡고 빨리 돌려주는 것.

## 헬스체크가 같이 막힌다

루프 블로킹이 성능 문제에서 장애로 번지는 지점이 여기입니다.

헬스체크 엔드포인트가 아무리 가벼워도, 루프가 막혀 있으면 **그 요청도 줄 뒤에 섭니다.**
로드밸런서 타임아웃이 블로킹 시간보다 짧으면 정상 동작 중인 태스크가 실패 판정을 받습니다.

그다음은 이렇게 굴러갑니다.

1. 블로킹으로 헬스체크가 몇 번 연속 실패한다
2. 로드밸런서가 그 태스크를 내리고 오케스트레이터가 교체한다
3. 남은 태스크가 같은 트래픽을 나눠 받으니 블로킹이 더 자주 걸린다
4. 다음 태스크가 같은 이유로 실패한다

CPU를 많이 쓰는 작업이 있는 서비스라면 헬스체크 타임아웃과 실패 임계치를 **최악의 블로킹 시간보다 여유 있게** 잡아두는 게 안전합니다.
다만 이건 완화책입니다. 임계치를 늘리면 진짜로 죽은 태스크를 늦게 걸러내니, 블로킹 자체를 줄이는 작업과 같이 가야 합니다.

종료 신호를 받은 뒤의 동작도 같은 영향을 받습니다. 루프가 막혀 있으면 종료 핸들러도 늦게 실행되니, [배포 중 5xx](/blog/graceful-shutdown-deploy-5xx/)를 다룰 때 잡은 타임아웃 부등식이 블로킹 구간에서 깨질 수 있습니다.

## 먼저 넣어둘 것

블로킹은 트래픽이 늘거나 데이터가 커진 뒤에 드러납니다. 그때 원인을 빠르게 찾으려면 두 가지가 미리 있어야 합니다.

**루프 지연 지표.** 위의 히스토그램을 지표로 내보내고 p99에 알람을 걸어둡니다. 응답 지연이 아니라 루프 지연을 봐야 "전부 느려짐"의 원인을 바로 지목할 수 있습니다.

**입력 크기 로그.** 파싱하거나 순회하는 데이터의 크기를 요청 로그에 같이 남깁니다.
`rows`, `bytes`, `items` 같은 필드 하나가 "어제까지 괜찮았는데 오늘부터 느리다"의 답인 경우가 많습니다.

그리고 코드 리뷰에서 걸러낼 수 있는 것들이 있습니다.

- 이름이 `Sync`로 끝나는 함수가 요청 경로에 있는가 (초기화 코드에서는 대개 무해합니다)
- 크기 상한이 없는 입력을 `JSON.parse`에 넣고 있는가
- 사용자 입력이 중첩 수량자가 있는 정규식에 들어가는가
- 반복 횟수가 데이터 양에 비례하는데 양보 지점이 없는 루프가 있는가

마지막 항목이 제일 자주 통과됩니다. 개발 DB에서 100행이던 루프는 운영에서 100만 행이 되고, 그때는 코드가 아니라 데이터가 바뀐 것이라서 배포 이력으로는 원인이 안 잡힙니다.
