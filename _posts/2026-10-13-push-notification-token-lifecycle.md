"푸시가 안 와요"라는 제보는 서버 로그에 아무 흔적을 남기지 않습니다.
전송 요청은 200을 받았고, 실패 건수도 0입니다.

그 둘이 동시에 참일 수 있습니다. 그리고 그러는 동안 토큰 테이블은 조용히 썩습니다.

## 200이 보장하는 범위

전송이 성공했다는 건 푸시 서비스가 메시지를 **접수했다**는 뜻입니다. 단말 화면에 떴다는 뜻이 아닙니다.

요청과 사용자 사이에 낀 주체가 넷입니다.

```text
우리 서버 → FCM → APNs / 단말 OS → 앱 → 사용자 화면
                ↑
            여기까지가 200
```

각 구간이 메시지를 버릴 수 있고, 버리는 이유가 서로 다릅니다.

| 구간 | 여기서 사라지는 이유 | 우리 쪽에 남는 흔적 |
| --- | --- | --- |
| 서버 → FCM | 토큰 무효, 페이로드 오류, 인증 실패 | 응답에 에러 코드 |
| FCM → OS | 단말이 오래 오프라인, TTL 만료, 같은 키로 대체됨 | 없음 |
| OS → 앱 | 알림 권한 거부, 채널 차단, 절전 모드 | 없음 |
| 앱 → 화면 | 데이터 메시지를 앱이 안 띄움 | 없음 |

첫 줄만 우리가 볼 수 있습니다. 아래 세 줄에서 사라진 메시지는 **전송 성공으로 집계됩니다.**

푸시는 요청-응답이 아니라 **맡겨두고 잊는** 전달입니다. 푸시 서비스는 단말이 꺼져 있으면 일정 기간 들고 있다가 포기하는데, 그 보관 기간(TTL)의 기본값과 상한은 플랫폼 문서에서 확인하세요. 중요한 건 숫자가 아니라, 그 기간이 지나면 **아무 통보 없이 버려진다**는 성질입니다.

## 토큰은 사용자의 속성이 아니다

여기서 모델링이 한 번 꼬이면 나머지가 전부 어긋납니다.

토큰이 가리키는 것은 사람이 아니라 **특정 단말에 설치된 앱 하나**입니다. `users` 테이블에 `fcm_token` 컬럼을 하나 두는 설계는 이 사실과 정면으로 충돌합니다.

충돌이 드러나는 경우가 넷입니다.

- 한 사용자가 휴대폰과 태블릿을 같이 쓴다 — 컬럼이 하나면 나중에 로그인한 쪽만 살아남습니다.
- 한 단말에 여러 사용자가 번갈아 로그인한다 — 공용 태블릿을 쓰는 환경에서 흔합니다.
- 앱을 재설치하면 토큰이 새로 발급된다 — 옛 토큰은 한동안 더 유효합니다.
- 같은 토큰이 두 사용자 행에 동시에 달린다 — 위 두 번째 경우를 정리하지 않으면 그대로 남습니다.

두 번째가 가장 위험합니다. 로그아웃할 때 토큰을 떼어내지 않으면, 같은 단말로 로그인한 **다음 사람에게 앞사람 알림이 갑니다.** 기능 버그가 아니라 개인정보 사고입니다.

그래서 토큰은 별도 테이블로 분리하고, 토큰 자체에 유니크를 걸어야 합니다.

```sql
CREATE TABLE device_tokens (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id      BIGINT UNSIGNED NOT NULL,
  token        VARCHAR(255)    NOT NULL,
  platform     ENUM('ios','android') NOT NULL,
  app_version  VARCHAR(32)     NULL,
  last_seen_at DATETIME        NOT NULL,
  created_at   DATETIME        NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_token (token),
  KEY idx_user (user_id, last_seen_at)
) ENGINE=InnoDB;
```

`uk_token`을 `(user_id, token)`이 아니라 **토큰 단독**으로 잡은 게 핵심입니다.

토큰은 전역에서 유일한 값입니다. 같은 토큰이 다른 사용자로 올라왔다는 건 "그 단말에서 사람이 바뀌었다"는 뜻이고, 행을 하나 더 만들 일이 아니라 **소유권을 옮겨야** 하는 상황입니다. 유니크를 복합키로 걸면 한 단말이 두 사용자에게 동시에 매달린 행이 그대로 쌓입니다.

등록은 업서트로 처리합니다.

```sql
INSERT INTO device_tokens (user_id, token, platform, last_seen_at, created_at)
VALUES (?, ?, ?, NOW(), NOW())
ON DUPLICATE KEY UPDATE
  user_id      = VALUES(user_id),   -- 소유권 이동
  platform     = VALUES(platform),
  last_seen_at = NOW();
```

> MySQL 8.0의 최근 버전은 `ON DUPLICATE KEY UPDATE` 안의 `VALUES()` 대신 행 별칭(`AS new ...`)을 권고합니다.
> 쓰는 버전의 문서를 확인하세요.

로그아웃은 방향이 반대입니다.

```typescript
// 이 "사용자의 토큰 전부"가 아니라 이 "단말의 토큰"을 지운다
await db.query('DELETE FROM device_tokens WHERE token = ?', [token]);
```

`WHERE user_id = ?`로 지우면 휴대폰에서 로그아웃한 사용자의 태블릿 알림까지 같이 끊깁니다. 제보로 올라오지 않고 조용히 안 오는 쪽이라 발견이 늦습니다.

## 토큰 테이블은 조용히 썩는다

무효 토큰을 알려주는 신호는 **전송을 시도할 때만** 옵니다. 자주 보내지 않는 종류의 알림만 쓰는 사용자의 죽은 토큰은 계속 남습니다.

플랫폼별로 수명 규칙이 다르다는 점도 걸립니다.

> 안드로이드 쪽 등록은 일정 기간 비활성 상태가 이어지면 만료 처리되고, 그 뒤 전송은 거부됩니다. 공식 문서는 이 기준을 270일로 설명합니다.
> iOS는 FCM이 APNs에 얹혀 동작해서 **같은 비활성 만료 규칙이 적용되지 않습니다.** 오래된 토큰은 우리가 직접 정리해야 합니다.
> 문서는 한 달 넘게 접속하지 않은 단말의 등록을 stale로 보고, 여기에 계속 보내면 전달률 지표가 왜곡된다고 안내합니다.

즉 **삭제 신호를 기다리는 것만으로는 부족합니다.** 앱이 포그라운드로 올라올 때마다 토큰을 서버에 다시 올리고, 서버는 `last_seen_at`을 갱신합니다. 토큰 값이 바뀌지 않아도 갱신해야 합니다 — 우리가 알고 싶은 건 토큰의 변경이 아니라 그 단말이 아직 살아 있다는 사실입니다.

그러면 정리 기준이 생깁니다.

```sql
-- 한참 소식 없는 단말은 발송 대상에서 뺀다
DELETE FROM device_tokens
WHERE last_seen_at < NOW() - INTERVAL 180 DAY
LIMIT 1000;
```

기간은 서비스 성격에 따라 정할 값입니다. 짧게 잡으면 복귀한 사용자가 재로그인 전까지 알림을 못 받고, 길게 잡으면 전달률 지표가 흐려집니다. 기간을 고르는 대신 대상을 지우지 않고 `disabled_at`만 표시해두는 선택도 있는데, 그러면 되살리기는 쉬워지고 테이블은 계속 커집니다.

## 부분 실패는 예외로 오지 않는다

다건 발송에서 가장 많이 놓치는 지점입니다.

여러 토큰에 보내는 호출은 **일부가 실패해도 예외를 던지지 않습니다.** 결과는 반환값 안에 토큰별로 들어 있습니다. `try/catch`만 둘러놓은 코드는 실패를 한 건도 보지 못하면서 정상 동작합니다. "실패 카운트 0"의 정체가 대개 이것입니다.

Node 환경에서 확인해야 할 성질이 셋입니다.

- 한 번에 보낼 수 있는 토큰 수에 상한이 있습니다. 공식 문서 기준 **500개**입니다.
- 결과 배열은 **입력 토큰과 같은 순서**입니다. 인덱스로 짝을 맞춰야 어떤 토큰이 실패했는지 알 수 있습니다.
- 부분 실패는 반환값으로만 드러납니다. 예외가 던져졌다면 그건 호출 전체가 실패한 경우입니다.

```typescript
import { getMessaging } from 'firebase-admin/messaging';

const CHUNK = 500;   // 한 호출당 토큰 수 상한

type Verdict = { dead: string[]; retry: string[] };

async function sendToTokens(tokens: string[], notification: { title: string; body: string }): Promise<Verdict> {
  const dead: string[] = [];
  const retry: string[] = [];

  for (let i = 0; i < tokens.length; i += CHUNK) {
    const slice = tokens.slice(i, i + CHUNK);
    const res = await getMessaging().sendEachForMulticast({ tokens: slice, notification });

    // responses는 slice와 같은 순서다 — 인덱스로만 짝이 맞는다
    res.responses.forEach((r, idx) => {
      if (r.success) return;

      const token = slice[idx];
      const code = r.error?.code;

      switch (classify(code)) {
        case 'delete':
          dead.push(token);
          break;
        case 'retry':
          retry.push(token);
          break;
        default:
          // 우리 코드나 설정 문제 — 토큰은 건드리지 않고 로그만 남긴다
          logger.error({ code, tokenId: hash(token) }, 'push send failed');
      }
    });
  }

  return { dead, retry };
}
```

로그에 토큰 원문을 찍지 않은 것도 의도입니다. 토큰은 그 단말에 알림을 보낼 수 있는 자격이고, 로그 수집 경로로 흘려보낼 값이 아닙니다.

## 지울 토큰과 재시도할 토큰

에러 코드를 세 갈래로만 나눠도 대부분 처리됩니다.

```typescript
function classify(code: string | undefined): 'delete' | 'retry' | 'bug' {
  switch (code) {
    // 이 토큰은 다시 유효해지지 않는다
    case 'messaging/registration-token-not-registered':
      return 'delete';

    // 일시적 — 백오프 후 다시
    case 'messaging/unavailable':
    case 'messaging/internal-error':
    case 'messaging/quota-exceeded':
      return 'retry';

    default:
      return 'bug';
  }
}
```

삭제 조건을 **하나로만** 둔 게 중요합니다. 앱 삭제나 등록 해제로 토큰이 죽은 경우가 이 코드로 오고, 문서도 이때는 저장소에서 지워도 된다고 안내합니다.

문제는 토큰 오류와 페이로드 오류가 같은 코드로 겹쳐 오는 경우입니다.

> 잘못된 인자를 뜻하는 코드는 **토큰 형식이 틀렸을 때도, 메시지 페이로드가 틀렸을 때도** 돌아옵니다.
> 공식 문서도 "페이로드가 유효하다고 확신할 때" 토큰을 지우라는 단서를 붙입니다.
> 이 코드를 삭제 조건에 넣으면, 페이로드 버그를 배포한 날 **발송 대상 토큰이 전부 지워집니다.**

지워진 토큰은 되살릴 방법이 없습니다. 사용자가 앱을 다시 열어 재등록하기를 기다리는 것 외에는 없고, 그 사이 알림은 한 건도 가지 않습니다. 코드 한 줄의 실수가 복구 불가능한 데이터 손실이 되는 드문 경우입니다.

그래서 삭제에는 비율 상한을 둡니다.

```typescript
const { dead, retry } = await sendToTokens(tokens, notification);

// 한 번에 지우는 비율에 상한 — 페이로드 버그로 전체가 날아가는 것을 막는다
if (dead.length > Math.max(20, tokens.length * 0.3)) {
  logger.error({ dead: dead.length, total: tokens.length }, 'mass token deletion blocked');
  await alert('푸시 토큰 대량 삭제 조건 감지 — 삭제를 보류했습니다');
} else if (dead.length > 0) {
  await db.query('DELETE FROM device_tokens WHERE token IN (?)', [dead]);
}
```

정상 상태에서 한 발송의 무효 토큰 비율은 서서히 움직입니다. 그 비율이 갑자기 튀었다면 사용자가 한꺼번에 앱을 지운 게 아니라 **우리가 뭔가 잘못 보낸 것**일 확률이 훨씬 높습니다.

## 하나의 이벤트가 몇 건의 발송인가

푸시는 발송 수가 곱셈으로 늘어납니다.

공지 한 건이 한 반의 보호자 전원에게 가고, 보호자마다 단말이 여러 대라면, 발송 건수는 `대상자 × 단말 수`입니다. 전체 공지라면 여기에 반 수가 또 곱해집니다.

그래서 **알림 발송은 API 요청 안에서 끝낼 작업이 아닙니다.** 500개씩 묶어도 수십, 수백 번의 외부 호출이 되고, 그 시간 동안 요청 하나가 커넥션과 스레드를 잡고 있습니다. 이벤트만 큐에 넣고 워커가 처리하는 구조로 떼어내야 합니다.

떼어내면 재시도가 생기고, 재시도는 중복 발송을 만듭니다. 워커가 500건 중 300건을 보낸 뒤 죽으면, 다시 받은 메시지는 앞의 300건을 또 보냅니다.

중복을 줄이는 수단이 둘입니다.

**발송 단위를 쪼갭니다.** 큐 메시지 하나가 `(이벤트, 토큰 묶음)`을 가리키게 하면 재시도 범위가 그 묶음으로 제한됩니다.

**같은 알림을 대체하게 만듭니다.** 대기 중인 메시지를 새 메시지로 덮어쓰는 키를 지정할 수 있습니다.

```typescript
await getMessaging().send({
  token,
  notification: { title, body },
  android: {
    priority: 'high',
    collapseKey: `notice-${noticeId}`,          // 대기 중인 같은 키 메시지를 대체
    notification: { channelId: 'notice' },      // 존재하는 채널이어야 한다
  },
  apns: {
    headers: {
      'apns-collapse-id': `notice-${noticeId}`,
      'apns-priority': '10',
    },
    payload: { aps: { 'thread-id': `notice-${noticeId}` } },
  },
});
```

이건 **이미 표시된 알림을 회수하지는 못합니다.** 단말이 아직 못 받은 메시지에만 효과가 있습니다. 중복의 진짜 해법은 발송 단위를 작게 쪼개는 쪽이고, 대체 키는 그 위에 얹는 보조 수단입니다.

## 도착했는데 안 보이는 경우

여기서부터는 우리 로그에 성공으로 남는 실패들입니다.

**데이터 메시지와 알림 메시지가 다릅니다.** 페이로드에 알림 필드가 있으면 OS가 대신 띄워주고, 데이터만 보내면 앱이 직접 띄워야 합니다. 앱이 꺼져 있을 때의 동작이 플랫폼마다 다르므로, 화면에 떠야 하는 알림이라면 알림 필드를 넣는 쪽이 안전합니다.

**안드로이드는 채널이 필수입니다.** Android 8.0부터 알림은 채널에 속해야 하고, 사용자가 그 채널을 끄면 메시지는 도착해도 표시되지 않습니다. 앱이 만들지 않은 `channelId`를 서버가 보내면 의도한 설정이 적용되지 않습니다. 서버가 보내는 채널 아이디와 앱이 생성하는 채널은 **같이 관리되어야 하는 한 쌍**인데, 서버와 앱이 따로 배포되면 쉽게 어긋납니다.

**권한은 토큰과 별개입니다.** 사용자가 알림 권한을 거부해도 토큰은 발급되고 전송도 성공합니다. 표시만 안 됩니다.

**절전 기능이 지연시킵니다.** 우선순위를 낮게 보낸 메시지는 단말이 절전 상태일 때 묶여 있다가 나중에 전달될 수 있습니다. 시간이 중요한 알림은 우선순위를 높게 주되, 모든 알림을 높게 주면 그 구분이 의미를 잃습니다.

네 경우 모두 **전송 결과는 성공입니다.** 실패 카운트가 0이라는 사실이 "모두 도착했다"를 뜻하지 않는 이유입니다.

## 끝단을 보려면 앱이 말해줘야 한다

서버 로그로 알 수 있는 건 접수까지입니다. 그래서 두 가지를 따로 남깁니다.

발송 시도를 토큰 단위로 기록합니다. "안 왔어요" 제보가 들어오면 이 기록으로 접수까지 갔는지, 에러 코드가 있었는지, 아예 대상에서 빠졌는지를 가릴 수 있습니다. 대상에서 빠졌다면 발송 로직이 아니라 토큰 테이블 쪽 문제입니다.

그리고 앱에서 수신·열람 이벤트를 올려받습니다. 이게 없으면 위에서 적은 네 가지 조용한 실패를 영원히 구분할 수 없습니다. 플랫폼이 제공하는 전달 데이터 리포트도 있으니 어디까지 집계되는지는 공식 문서에서 확인하세요.

## 정리

지금까지의 판단들을 모으면 이렇게 됩니다.

| 결정 | 선택 | 이유 |
| --- | --- | --- |
| 토큰 소유 단위 | 사용자가 아니라 단말 | 한 사람이 여러 단말, 한 단말에 여러 사람 |
| 유니크 제약 | 토큰 단독 | 재로그인은 행 추가가 아니라 소유권 이동 |
| 로그아웃 | 해당 토큰만 삭제 | 다른 단말 알림을 끊지 않기 위해 |
| 토큰 삭제 조건 | 등록 해제 코드 하나만 | 페이로드 오류와 겹치는 코드를 믿으면 전체가 날아간다 |
| 삭제 안전장치 | 비율 상한 + 알림 | 되살릴 방법이 없는 손실이라서 |
| 발송 위치 | 요청이 아니라 워커 | 발송 수가 곱셈으로 늘어난다 |

푸시에서 가장 비싼 착각은 "전송 성공"을 "전달 완료"로 읽는 것입니다. 성공 응답은 우리가 할 일을 끝냈다는 뜻일 뿐, 사용자가 봤다는 증거가 아닙니다.
