엑셀 업로드 기능은 만들기 쉬운 쪽에 속합니다. 파싱 라이브러리를 붙이고 행을 돌면서 `INSERT`하면 일단 동작합니다.

어려운 건 그다음입니다. 1000행 중 세 줄이 제약에 걸렸을 때 응답은 200이고 화면에는 "업로드 완료"가 뜨는데, **사용자는 무엇이 들어가지 않았는지 모릅니다.**
그리고 며칠 뒤 "명단에 세 명이 없다"는 문의로 돌아옵니다.

임포트에서 품질을 결정하는 건 파서가 아니라, 실패를 어떻게 돌려주고 어디까지 되돌리는지입니다.

## 정책을 코드보다 먼저 정한다

한 행이 틀렸을 때 나머지를 어떻게 할지에는 정답이 없습니다. 데이터 성격에 따라 갈립니다.

| 정책 | 맞는 경우 | 대가 |
| --- | --- | --- |
| 전부 아니면 아무것도 | 정산·회계처럼 부분 반영이 의미 없는 데이터 | 한 줄 때문에 999줄을 다시 올려야 한다 |
| 되는 것만 넣기 | 명단 등록처럼 행이 서로 독립적일 때 | 무엇이 빠졌는지 추적하는 책임이 사용자에게 간다 |
| 검증 먼저, 전부 통과하면 적용 | 대부분의 업무 데이터 | 파일을 두 번 읽고, 두 단계 사이에 상태가 바뀔 수 있다 |

세 번째가 기본값으로 무난합니다. 사용자 입장에서 "고칠 목록을 한 번에 받고, 고쳐서 다시 올리면 전부 들어간다"가 가장 예측 가능하기 때문입니다.

이 선택을 먼저 하는 이유는 **트랜잭션 경계가 여기서 결정되기** 때문입니다. 나중에 바꾸려면 파싱부터 응답 형식까지 같이 손대야 합니다.

## 파일은 도착하기 전에 이미 깨져 있다

먼저 확장자에 따라 문제의 종류가 다릅니다.

`.xlsx`는 XML을 담은 zip 아카이브이고 내부 인코딩이 UTF-8로 정해져 있습니다. 그래서 글자가 깨지는 문제는 사실상 없습니다.
`.csv`는 그냥 바이트 뭉치입니다. 어떤 인코딩인지 파일 안에 적혀 있지 않아서, 받는 쪽이 **추측해야 합니다.**

한국어 환경에서 이게 매번 걸리는 이유는 구체적입니다. 윈도우 엑셀에서 "CSV(쉼표로 분리)"로 저장하면 UTF-8이 아닌 CP949로 떨어집니다.
이걸 UTF-8로 읽으면 한글이 전부 깨지고, 깨진 문자열이 그대로 DB에 들어갑니다.

반대 방향으로는 BOM이 있습니다. UTF-8 BOM이 붙은 파일을 그냥 읽으면 첫 번째 헤더 이름이 `이름`이 아니라 `\uFEFF이름`이 됩니다.

> 증상이 특이해서 기억해둘 만합니다. **첫 번째 컬럼만 전부 `undefined`가 되고 나머지 컬럼은 정상**이면 BOM입니다.

디코딩은 추측이지만, 추측을 좁힐 수는 있습니다.

```typescript
import iconv from 'iconv-lite';

const UTF8_BOM = Buffer.from([0xef, 0xbb, 0xbf]);

function detectCsvEncoding(head: Buffer): 'utf-8' | 'cp949' {
  if (head.subarray(0, 3).equals(UTF8_BOM)) return 'utf-8';

  // UTF-8로 디코딩했을 때 복원 불가 문자(U+FFFD)가 나오면 UTF-8이 아니다
  if (head.toString('utf8').includes('\uFFFD')) return 'cp949';
  return 'utf-8';
}
```

`'cp949'`로 떨어뜨리는 마지막 줄이 이 함수의 전부이자 한계입니다. UTF-8이 아니라는 것만 알아낸 뒤 **지역적 가정**으로 메우고 있습니다.
한국 사용자만 쓰는 기능이면 맞는 베팅이고, 그렇지 않으면 틀립니다.

스트림으로 읽을 때는 디코딩을 파이프 중간에 끼웁니다.

```typescript
import fs from 'node:fs';
import iconv from 'iconv-lite';
import { parse } from 'csv-parse';

const rows = fs.createReadStream(filePath)
  .pipe(iconv.decodeStream(encoding))     // 바이트 → 문자열
  .pipe(parse({ columns: true, bom: true, trim: true }));

for await (const row of rows) {
  // row는 헤더 이름을 키로 갖는 객체
}
```

`columns: true`로 헤더를 키로 쓰고, `bom: true`로 남은 BOM을 한 번 더 걷어냅니다.
구분자가 쉼표가 아닐 수도 있다는 점은 따로 생각해야 합니다. 로케일에 따라 엑셀이 세미콜론으로 저장하는 경우가 있고, 그때 전체가 한 컬럼으로 들어옵니다.

그래서 가장 싸게 끝내는 방법은 디코딩을 잘하는 게 아닙니다. **임포트 템플릿을 `.xlsx`로 배포하는 것**입니다.
인코딩 추측과 구분자 문제가 동시에 사라지고, 열 서식을 미리 지정해둘 수 있다는 이득이 하나 더 붙습니다.

## 셀 값은 문자열이 아니다

CSV든 xlsx든, 셀에 보이는 것과 파일에 저장된 것은 다릅니다. 그리고 **이 손실은 대부분 서버에 도착하기 전에 이미 끝나 있습니다.**

**선행 0.** `01012345678`을 셀에 넣으면 엑셀이 숫자로 판단해 `1012345678`로 저장합니다. 전화번호, 학번, 우편번호가 전부 여기에 걸립니다.

**15자리 초과 정밀도.** 엑셀은 숫자를 배정밀도 부동소수점으로 다룹니다. 유효숫자 15자리를 넘는 긴 숫자는 뒷자리가 0으로 바뀝니다.

**자동 서식 변환.** `3-1`처럼 적은 반·조 표기가 날짜로 바뀝니다. 입력한 사람은 모르고, 파일에는 이미 날짜가 들어 있습니다.

**날짜.** 엑셀의 날짜는 1900년 1월 1일을 1로 두는 일련번호입니다. 1900년을 윤년으로 취급하는 과거 호환 동작 때문에, 보통 1899-12-30을 기준으로 환산합니다.
여기에 1904 체계로 저장된 파일이 섞이면 4년이 어긋납니다.

파싱 라이브러리가 날짜 셀을 `Date` 객체로 돌려주는 경우가 많은데, 여기서 한 번 더 어긋납니다.
엑셀 셀에는 "2026년 3월 2일"이라는 날짜만 있고 시각도 타임존도 없습니다. 그걸 특정 순간으로 바꾸는 순간 해석이 끼어들고, 하루가 밀립니다.
같은 종류의 문제를 [타임존 글](/blog/timezone-datetime-day-boundary/)에 적어뒀습니다. 날짜만 의미 있는 값은 순간이 아니라 `YYYY-MM-DD` 문자열로 받아 저장하는 쪽이 안전합니다.

**보이지 않는 공백.** 웹 페이지에서 복사해 붙인 값에는 비분리 공백(U+00A0)이 섞여 들어옵니다.
`trim()`은 양 끝의 U+00A0을 지우지만 문자열 중간에 있는 것은 남고, 그 값은 눈으로 봐서는 정상입니다. 이름 조회가 안 되는 원인으로 꽤 오래 숨어 있습니다.

```typescript
function normalizeCell(v: unknown): string {
  if (v === null || v === undefined) return '';
  if (v instanceof Date) return toDateStringKst(v);   // 시각을 붙이지 않는다
  return String(v).replace(/\u00a0/g, ' ').trim();
}
```

여기서 선을 하나 그어야 합니다. **서버가 할 수 있는 것은 복구가 아니라 거절입니다.**
10자리로 도착한 휴대폰 번호 앞에 `0`을 붙여주는 보정은 그럴듯하지만, 원래 값이 무엇이었는지에 대한 추측입니다. 틀리면 존재하는 다른 번호를 만들어냅니다.
형식이 안 맞으면 떨어뜨리고, 어느 행의 어느 칸인지 알려주는 편이 낫습니다. 템플릿의 해당 열을 텍스트 서식으로 지정해두면 애초에 덜 생깁니다.

## 행 번호는 사용자가 보는 번호여야 한다

에러 리포트의 품질은 거의 행 번호에서 결정됩니다. 그리고 코드의 인덱스와 사용자가 엑셀에서 보는 행 번호는 다릅니다.

헤더가 1행이면 데이터 첫 행은 2행이고, 배열 인덱스로는 0입니다. 이걸 그대로 내보내면 사용자는 매번 두 줄 아래를 보게 됩니다.

```typescript
type RowError = {
  excelRow: number;   // 엑셀에서 보이는 행 번호
  column: string;     // 헤더 이름 ("생년월일")
  value: string;      // 실제로 받은 값
  reason: string;     // 왜 거절했는지
};

function toRowErrors(index: number, parsed: z.SafeParseReturnType<unknown, Row>, raw: Record<string, string>): RowError[] {
  if (parsed.success) return [];
  return parsed.error.issues.map((issue) => {
    const column = String(issue.path[0] ?? '');
    return {
      excelRow: index + 2,          // 헤더 1행 + 1-base
      column,
      value: raw[column] ?? '',
      reason: issue.message,
    };
  });
}
```

`value`를 같이 넣는 게 생각보다 중요합니다. 사용자 화면에 보이는 값과 서버가 받은 값이 다른 경우가 바로 위에서 본 것들이라, 받은 값을 그대로 보여주면 원인이 한 번에 드러납니다.

DB 제약 위반도 같은 모양으로 변환해야 합니다. `ER_DUP_ENTRY`를 그대로 노출하면 사용자는 아무것도 할 수 없습니다.

다만 여기에 구조적인 제약이 하나 있습니다. **벌크 `INSERT`는 어느 행이 걸렸는지 알려주지 않습니다.**
1000행을 한 문장으로 넣다가 중복으로 실패하면 실패한 건 문장 전체입니다. 이게 검증 단계를 따로 두는 또 하나의 이유입니다.

에러 개수에도 상한을 둡니다. 500개를 전부 JSON으로 돌려주면 화면이 못 그리고, 사용자도 읽지 않습니다.
앞쪽 몇십 개와 전체 개수를 주고, 전체 목록은 파일로 내려주는 쪽이 낫습니다. 그 파일을 엑셀로 열 사람을 위해 **BOM을 붙여서** 내보내야 한다는 점만 기억하면 됩니다.

## 같은 파일을 두 번 올린다

임포트가 느릴 때 사용자는 반드시 다시 누릅니다. 응답이 없으면 실패로 보이기 때문입니다.

처리 중이던 요청은 서버에서 계속 돌고 있고, 두 번째 요청이 겹치면 명단이 두 벌 들어갑니다.
그래서 임포트는 작업 레코드를 남기는 쪽이 안전합니다.

```sql
CREATE TABLE import_jobs (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id    BIGINT UNSIGNED NOT NULL,
  kind         VARCHAR(40)     NOT NULL,
  file_sha256  CHAR(64)        NOT NULL,
  status       ENUM('validating','applying','done','failed') NOT NULL,
  total_rows   INT UNSIGNED    NOT NULL DEFAULT 0,
  applied_rows INT UNSIGNED    NOT NULL DEFAULT 0,
  created_at   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_import_file (tenant_id, kind, file_sha256)
) ENGINE=InnoDB;
```

유니크 제약이 중복 접수를 막습니다. 같은 파일을 다시 올리면 `INSERT`가 거부되고, 그때 진행 중인 작업의 상태를 돌려주면 됩니다.
[멱등키](/blog/idempotency-key-payment-api/)와 같은 발상이고, 키를 요청 헤더가 아니라 파일 내용에서 얻는다는 점만 다릅니다.

해시로 막는 것에는 한계가 있습니다. 같은 내용을 **의도적으로** 두 번 올리는 경우가 있고, 반대로 한 글자만 고친 파일은 다른 해시가 됩니다.
그래서 해시는 "방금 올린 것과 같은 파일"을 막는 짧은 창의 보호 장치로 보고, 기간을 두고 판단하는 편이 맞습니다.

더 튼튼한 쪽은 행 단위입니다. 자연키가 있으면 적용 자체를 멱등하게 만들 수 있습니다.

```sql
INSERT INTO children (tenant_id, class_id, name, birth_date)
VALUES (?, ?, ?, ?)
ON DUPLICATE KEY UPDATE
  class_id = VALUES(class_id),
  birth_date = VALUES(birth_date);
```

이러면 두 번 적용해도 결과가 같습니다. 대신 이건 조용한 제품 결정을 하나 포함합니다.
**재업로드가 덮어쓰기가 됩니다.** 누군가 화면에서 고쳐둔 값이 예전 파일을 다시 올리는 순간 되돌아갑니다.
덮어쓸지, 건너뛸지, 충돌로 보고할지는 코드에서 정할 게 아니라 사용자에게 물어볼 일입니다.

## 메모리와 트랜잭션 길이

파일 크기 제한만으로는 메모리를 막을 수 없습니다. xlsx가 zip이기 때문입니다. 몇 MB 파일이 펼쳐지면 수백 MB가 될 수 있습니다.

그래서 두 가지를 같이 둡니다. 업로드 크기 상한과 **행 수 상한**입니다. 행 수 상한이 없는 서비스는 상한이 OOM인 서비스입니다.

파서도 전체를 메모리에 올리는 것과 스트리밍하는 것이 갈립니다. xlsx를 스트리밍으로 읽으면 행을 하나씩 흘려보낼 수 있습니다.

```typescript
import ExcelJS from 'exceljs';

const reader = new ExcelJS.stream.xlsx.WorkbookReader(filePath, {});

for await (const sheet of reader) {
  for await (const row of sheet) {
    // row.values 로 셀 배열 접근
  }
}
```

> 스트리밍 리더의 옵션 이름과 기본값은 버전에 따라 다릅니다. 공유 문자열 캐싱이나 스타일 처리 옵션은 공식 문서에서 확인하세요.

쓰기 쪽에서는 왕복 횟수가 문제가 됩니다. 행마다 `INSERT`를 보내면 네트워크 왕복이 행 수만큼 생기고, 5000행이면 그 자체로 느립니다.
500~1000행씩 묶어 넣으면 대체로 충분합니다.

그런데 "전부 아니면 아무것도"를 지키려고 전체를 **하나의 트랜잭션으로 감싸면** 다른 비용이 생깁니다. 언두 로그가 커지고, 잡은 락이 끝까지 유지되고, 복제도 밀립니다.
[대량 삭제 글](/blog/mysql-bulk-delete-partition-retention/)에서 본 것과 같은 구조입니다.

이 둘을 분리하는 방법이 있습니다. 스테이징 테이블을 하나 두는 것입니다.

```sql
-- 1단계: 파싱한 행을 그대로 쌓는다. 중간에 커밋해도 본 테이블에 영향이 없다
INSERT INTO children_staging (job_id, excel_row, name, birth_date) VALUES ...;

-- 2단계: 전부 쌓인 뒤 검증 쿼리로 한 번에 확인한다
SELECT s.excel_row, s.name
FROM children_staging s
JOIN children c
  ON c.tenant_id = ? AND c.name = s.name AND c.birth_date = s.birth_date
WHERE s.job_id = ?;

-- 3단계: 통과하면 한 문장으로 옮긴다
INSERT INTO children (tenant_id, class_id, name, birth_date)
SELECT ?, s.class_id, s.name, s.birth_date
FROM children_staging s
WHERE s.job_id = ?;
```

적재는 여러 번 커밋해서 길게 끌지 않고, 본 테이블에 들어가는 순간만 짧은 트랜잭션으로 원자적이 됩니다.
검증을 쿼리로 할 수 있다는 것도 덤입니다. 중복 검사를 애플리케이션에서 행마다 `SELECT`로 돌리는 것보다 훨씬 빠릅니다.

물론 2단계와 3단계 사이에 다른 사람이 같은 이름을 등록할 수 있습니다. 검증이 경쟁을 없애주지는 않아서, 3단계에서도 유니크 제약이 최종 방어선으로 남아 있어야 합니다.

응답 시간도 정책에 넣어야 합니다. 수 초 안에 끝나지 않는 임포트는 동기 응답으로 돌려주기 어렵습니다.
접수만 하고 `import_jobs` 레코드를 돌려준 뒤 진행률을 따로 조회하게 하는 편이 낫습니다. [대용량 내보내기](/blog/large-export-streaming-memory/)에서 같은 결론에 도달했던 것과 같은 이유입니다.

## 업로드된 파일은 신뢰 경계 밖이다

마지막으로 파일 자체를 입력으로 다루는 관점입니다.

확장자와 `Content-Type`은 사용자가 정하는 값입니다. zip 매직 바이트(`50 4b 03 04`)로 xlsx 여부를 확인하는 정도는 해두는 편이 낫습니다.
압축 해제 크기에도 상한을 둡니다. 압축률이 비정상적으로 높은 파일은 거절하는 것으로 충분합니다.

시트 구조도 믿을 수 없습니다. 헤더가 없는 파일, 컬럼 순서가 바뀐 파일, 병합된 셀이 섞인 파일이 옵니다.
**컬럼 인덱스가 아니라 헤더 이름으로 매핑**하고, 필요한 헤더가 없으면 파싱을 시작하기 전에 거절하는 쪽이 에러 메시지가 훨씬 친절해집니다.

파일 안의 식별자 컬럼은 특히 조심해야 합니다. 템플릿에 `원 ID` 같은 칸이 있다고 그 값으로 쓰면, 남의 데이터에 쓰는 경로가 열립니다.
테넌트는 항상 세션에서 가져옵니다. [멀티테넌시 격리](/blog/multi-tenant-data-isolation/)와 같은 규칙입니다.

그리고 임포트에서는 안전하지만 내보내기에서 돌아오는 문제가 하나 있습니다. `=`, `+`, `-`, `@`로 시작하는 셀 값입니다.
DB에는 그냥 문자열로 들어가지만, 그 값을 나중에 CSV로 내보내면 받는 사람의 엑셀이 **수식으로 해석합니다.**
저장 시점에 거절하거나, 내보낼 때 접두사를 붙여 무력화해야 합니다. 임포트와 내보내기를 같이 만드는 경우에 한 번쯤 점검할 지점입니다.

## 체크리스트

- [ ] 실패 정책(원자적 / 부분 / 2패스)을 코드 전에 정했는가
- [ ] 템플릿을 `.xlsx`로 배포하고 있는가 (인코딩·구분자 문제가 통째로 사라진다)
- [ ] CSV에서 BOM과 CP949를 모두 처리하는가
- [ ] 날짜를 순간이 아니라 날짜 문자열로 받는가
- [ ] 에러 리포트에 엑셀 행 번호·헤더 이름·받은 값이 있는가
- [ ] 같은 파일 재업로드를 막거나 멱등하게 적용하는가
- [ ] 행 수 상한과 압축 해제 크기 상한이 있는가
- [ ] 테넌트를 파일이 아니라 세션에서 가져오는가

임포트 기능에서 사용자가 체감하는 품질은 성공했을 때가 아니라 실패했을 때 결정됩니다.
"3행의 생년월일이 `2026-02-30`이라 등록하지 못했습니다"까지 돌려주면 사용자가 스스로 끝낼 수 있고, "업로드에 실패했습니다"로 끝나면 문의가 옵니다.
