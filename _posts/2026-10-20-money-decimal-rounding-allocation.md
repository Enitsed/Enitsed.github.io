정산서를 뽑았는데 항목 합계와 총액이 1원 차이 납니다. 코드에는 틀린 데가 없어 보이고, 어제 뽑은 건 맞았습니다.

금액 버그는 크게 틀리지 않습니다. 1원씩 틀리고, 그래서 "원래 그런 것"으로 넘어가다가 세금계산서나 PG 대사에서 한꺼번에 돌려받습니다.

어긋남이 들어오는 자리는 셋입니다. **어떤 타입에 담았는가, 어디서 반올림했는가, 나눠떨어지지 않은 나머지를 누구에게 줬는가.**

## 부동소수점은 10진 소수를 담는 타입이 아니다

`FLOAT`과 `DOUBLE`, 그리고 자바스크립트의 `number`는 전부 2진 부동소수점입니다. 0.1은 2진 분수로 유한하게 적을 수 없으니, 저장되는 건 0.1에 가장 가까운 다른 수입니다.

```javascript
0.1 + 0.2;                                  // 0.30000000000000004
Array(10).fill(0.1).reduce((a, b) => a + b); // 0.9999999999999999
```

금액에서 이게 무서운 건 틀린 값이 눈에 안 띄기 때문입니다. 화면에는 반올림해서 뿌리니 멀쩡해 보이고, 합계를 낼 때만 끝자리가 어긋납니다.

데이터베이스도 같습니다. `DOUBLE` 컬럼에 담은 금액은 **등호 비교가 안 맞는 경우**가 생기고, `SUM()` 결과가 돌린 순서에 따라 달라질 수 있습니다.

> `FLOAT`·`DOUBLE`은 금액 컬럼으로 쓰지 않습니다. 이미 쓰고 있다면 타입 변경이 이 글에서 가장 먼저 할 일입니다.

선택지는 둘입니다.

| | `DECIMAL(p, s)` | 최소 단위 정수 (`BIGINT`) |
| --- | --- | --- |
| 저장하는 값 | 10진수 그대로 | 통화의 최소 단위 개수 |
| 소수 단가·환율 | 스케일 안에서 가능 | 별도 스케일 규칙이 필요 |
| 언어 경계 | 드라이버가 `number`로 바꾸면 깨짐 | 정수라 안전한 편 |
| 연산 | DB가 정확하게 처리 | 애플리케이션에서 `BigInt` |
| 읽기 | 쿼리 결과가 바로 읽힌다 | 사람이 보려면 변환 필요 |

원화만 다루고 소수 단가가 없다면 `BIGINT`에 원 단위로 담는 쪽이 단순합니다. 단가에 소수가 끼거나(1개당 1,666.67원), 환율·수수료율을 같이 저장해야 한다면 `DECIMAL`이 맞습니다.

어느 쪽이든 **한 서비스 안에서 섞지 않는 것**이 실제로 더 중요합니다. 테이블마다 표현이 다르면 조인과 집계에서 변환이 끼고, 변환이 끼는 자리마다 반올림이 하나씩 생깁니다.

## DECIMAL을 골랐다면 스케일을 먼저 정한다

`DECIMAL(19, 4)` 같은 선언에서 두 번째 숫자가 소수 자릿수(scale)입니다. 원화 금액만 담을 거면 `DECIMAL(19, 0)`이지만, 중간 계산값을 같은 테이블에 담는다면 자리를 남겨둬야 합니다.

주의할 점은 **연산 결과의 스케일이 피연산자와 다르다**는 것입니다. MySQL 기준으로 대략 이렇습니다.

- 덧셈·뺄셈: 두 스케일 중 큰 쪽
- 곱셈: 두 스케일의 **합**
- 나눗셈: 왼쪽 스케일 + `div_precision_increment` (기본값 4)

```sql
SELECT 10.00 * 1.1,        -- 11.000   (2 + 1 = 3자리)
       10.00 / 3;          -- 3.333333 (2 + 4 = 6자리)
```

곱셈이 반복되면 스케일이 계속 늘어나고, 어딘가에서 잘립니다. 잘리는 자리를 DB에 맡기지 말고 **의도한 지점에서 `ROUND()`로 끊어야** 합니다.

집계도 같은 눈으로 봅니다. `SUM()`은 덧셈이라 정확하지만 `AVG()`는 나눗셈이라 스케일이 늘어납니다. 평균 객단가를 그대로 금액 컬럼에 넣으면 거기서 또 한 번 잘립니다.

`ROUND()`의 동작도 타입에 따라 다릅니다. `DECIMAL` 같은 정확한 값은 **0에서 멀어지는 쪽으로 반올림**하고, `DOUBLE` 같은 근사값은 C 라이브러리 구현을 따릅니다. 금액에서 `ROUND()`를 믿으려면 그 전에 타입이 `DECIMAL`이어야 한다는 뜻입니다.

## 경계를 넘을 때마다 타입이 바뀐다

타입을 잘 골라놔도 값이 애플리케이션까지 오는 길에 바뀝니다.

첫 번째 경계는 드라이버입니다. `DECIMAL`을 문자열로 줄지 `number`로 줄지는 드라이버 설정에 달려 있습니다. `number`로 받는 순간 지금까지의 노력이 전부 무효가 됩니다.

```typescript
const [rows] = await pool.query('SELECT amount FROM payments LIMIT 1');
console.log(typeof rows[0].amount);   // 'string' 이어야 한다
```

기본값을 외우지 말고 한 번 찍어보세요. mysql2에는 `decimalNumbers`, `supportBigNumbers` 같은 옵션이 있고, Prisma는 `Decimal` 타입을 decimal.js 인스턴스로 돌려줍니다. 어느 쪽이든 **코드에서 `Number()`로 감싸는 순간** 같은 문제가 돌아옵니다.

두 번째 경계는 JSON입니다. JSON의 숫자에는 정밀도 규정이 없고, `JSON.parse`는 전부 `number`로 만듭니다.

```javascript
JSON.parse('{"a":9007199254740993}').a;   // 9007199254740992
```

원 단위 정수라면 2^53은 현실적으로 넘지 않습니다. 문제는 거기가 아니라, 응답을 숫자로 내보내는 순간 **클라이언트에서 곱셈·나눗셈이 가능해진다**는 점입니다. 프런트에서 부가세를 다시 계산하고 서버와 1원이 어긋나는 사고가 여기서 납니다.

그래서 API 응답은 금액을 문자열로, 단위를 명시해서 내보내는 편이 안전합니다.

```typescript
type Money = { amount: string; currency: 'KRW' };

// { "total": { "amount": "25300", "currency": "KRW" } }
```

표시 형식은 클라이언트가 만듭니다. 서버가 `"25,300원"`을 내려보내면 그 문자열로 다시 계산하려는 코드가 반드시 생깁니다.

```javascript
new Intl.NumberFormat('ko-KR', { style: 'currency', currency: 'KRW' }).format(25300);
// '₩25,300'
```

## 반올림은 한 번만, 정해진 자리에서

언어가 주는 반올림 함수는 금액 기준과 미묘하게 다릅니다.

```javascript
(1.005).toFixed(2);   // '1.00'  — 1.005가 실제로는 1.00499...이기 때문
(2.675).toFixed(2);   // '2.67'
Math.round(-0.5);     // -0      — 음수는 0 쪽으로 올라간다
Math.round(-1.5);     // -1
```

`toFixed`는 입력이 이미 부동소수점이라 손쓸 수 없고, `Math.round`는 **항상 +∞ 방향**으로 올립니다. 환불이나 차감처럼 음수 금액이 섞이면 절댓값이 같은데 반올림 방향이 달라집니다.

금액 반올림은 정수 연산으로 직접 적습니다. 원 단위로 끊는다면 이렇습니다.

```typescript
/** 0에서 멀어지는 방향으로 반올림 (half away from zero) */
export function roundDiv(numerator: bigint, denominator: bigint): bigint {
  if (denominator <= 0n) throw new Error('denominator must be positive');
  const sign = numerator < 0n ? -1n : 1n;
  const abs = numerator < 0n ? -numerator : numerator;
  return (sign * (abs * 2n + denominator)) / (denominator * 2n);
}

roundDiv(1005n, 2n);    // 503n
roundDiv(-1005n, 2n);   // -503n
```

규칙 자체보다 중요한 건 **횟수**입니다. 반올림은 계산 경로에서 딱 한 번, 저장 직전에 합니다.

중간 단계마다 끊으면 오차가 누적되고, 같은 값을 다른 경로로 계산했을 때 결과가 달라집니다. 단가 × 수량 × (1 - 할인율) 같은 식에서 각 단계를 원 단위로 끊어보면 금방 벌어집니다.

> 반올림 기준(올림·버림·반올림)은 서비스 정책이지 기술 선택이 아닙니다. 코드에 흩어두지 말고 한 함수에 모으고, 그 함수를 쓰는 것을 규칙으로 두세요.

## 부가세는 더하기와 빼기가 다르다

공급가액에서 세액을 구하는 건 쉽습니다. 10%를 곱하면 됩니다.

문제는 반대 방향입니다. 세금 포함 가격으로 파는 서비스에서는 총액이 먼저 정해지고, 거기서 공급가액을 역산합니다.

```text
공급가액 = 총액 / 1.1
세액     = 총액 - 공급가액
```

여기서 두 값을 **각각 반올림하면 합이 총액과 달라집니다.** 그래서 한쪽은 반드시 뺄셈으로 정해야 합니다.

```typescript
const VAT_RATE = 10n;   // 퍼센트

export function splitVatIncluded(total: bigint) {
  const supply = roundDiv(total * 100n, 100n + VAT_RATE);
  return { supply, vat: total - supply };   // 합은 항상 total
}

splitVatIncluded(10000n);   // { supply: 9091n, vat: 909n }
```

더 자주 걸리는 건 **항목별로 나눠서 계산했을 때**입니다. 1,000원 + 1,000원 + 1,700원짜리 주문을 보겠습니다.

| 계산 방식 | 공급가액 |
| --- | --- |
| 항목별 역산 후 합산 | 909 + 909 + 1,545 = **3,363** |
| 총액(3,700원) 기준 역산 | **3,364** |

둘 다 틀리지 않았습니다. 반올림을 어디서 했느냐가 다를 뿐입니다.

중요한 건 어느 쪽이 맞느냐가 아니라 **한 서비스 안에서 한쪽으로 통일하는 것**입니다. 주문서는 항목별로 계산하고 정산 배치는 총액으로 계산하면, 매번 설명할 수 없는 1원이 남습니다.

영수증에 항목별 세액을 표시해야 한다면 항목 기준으로 가야 하고, 그 경우 총액의 세액은 **항목 세액의 합으로 정의**합니다. 역산한 값과 비교해서 맞추려 들면 끝나지 않습니다.

> 원 단위 절사·반올림 기준은 제도와 거래 조건에 따라 다릅니다. 적용할 기준은 회계 쪽과 확인하고, 코드에서는 그 기준을 한 곳에만 두세요.

## 나눠떨어지지 않는 돈을 누구에게 줄 것인가

주문 전체에 3,000원 쿠폰이 붙었습니다. 이걸 항목별로 쪼개야 하는 이유는 부분 환불 때문입니다. 항목 하나만 취소될 때 얼마를 돌려줄지 정하려면 할인액도 항목에 배분돼 있어야 합니다.

비례 배분을 소박하게 적으면 합이 맞지 않습니다.

```typescript
// 합계가 2,999원이나 3,001원이 될 수 있다
const share = items.map((it) => Math.round(discount * (it.price / totalPrice)));
```

해결은 간단합니다. **먼저 내림으로 나눈 다음, 남은 1원들을 나머지가 큰 순서로 하나씩 나눠줍니다.** 최대 잔여법이라고 부르는 방식입니다.

```typescript
/** total(>= 0)을 weights 비율로 쪼갠다. 반환값의 합은 항상 total. */
export function allocate(total: bigint, weights: bigint[]): bigint[] {
  const sum = weights.reduce((a, b) => a + b, 0n);
  if (sum <= 0n) throw new Error('weights must sum to a positive value');

  const base = weights.map((w) => (total * w) / sum);          // 내림

  // 나머지가 큰 쪽부터, 같으면 인덱스가 앞선 쪽부터
  const order = weights
    .map((w, i) => ({ i, rem: total * w - base[i] * sum }))
    .sort((a, b) => (a.rem === b.rem ? a.i - b.i : a.rem < b.rem ? 1 : -1));

  const out = [...base];
  let rest = total - base.reduce((a, b) => a + b, 0n);
  for (let k = 0; rest > 0n; k++, rest--) out[order[k].i] += 1n;
  return out;
}

allocate(1000n, [3300n, 3300n, 3400n]);   // [330n, 330n, 340n]
allocate(100n, [1n, 1n, 1n]);             // [34n, 33n, 33n]
allocate(1n, [1n, 1n, 1n]);               // [1n, 0n, 0n]
```

남는 1원의 개수는 항상 항목 수보다 적으니 한 바퀴 안에 끝납니다. 동률일 때 인덱스 순으로 고정한 것은 **같은 입력이 항상 같은 결과를 내도록** 하기 위해서입니다. 이게 없으면 재계산할 때마다 배분이 흔들려 환불 금액이 달라집니다.

음수는 이 함수가 다루지 않습니다. 환불처럼 음수 금액을 배분해야 한다면 절댓값으로 배분한 뒤 부호를 되돌리는 편이 안전합니다. 그래야 "100원을 쪼갠 결과"와 "-100원을 쪼갠 결과"가 부호만 다른 같은 모양이 됩니다.

쿠폰·포인트·카드사 할인이 겹치면 **적용 순서도 정책**입니다. 순서가 바뀌면 각 항목에 배분되는 금액이 달라지고, 부분 환불 금액도 달라집니다. 코드가 아니라 문서에 먼저 적혀 있어야 하는 종류의 결정입니다.

## 통화가 둘 이상이면

원화만 다룰 때는 "소수점이 없다"는 전제가 코드 곳곳에 깔립니다. 통화가 하나 늘어나는 순간 그 전제가 전부 무너집니다.

최소 단위 자릿수는 통화마다 다릅니다.

```javascript
for (const c of ['KRW', 'USD', 'JPY', 'KWD']) {
  const d = new Intl.NumberFormat('en', { style: 'currency', currency: c })
    .resolvedOptions().maximumFractionDigits;
  console.log(c, d);
}
// KRW 0, USD 2, JPY 0, KWD 3
```

그래서 금액은 **숫자 하나가 아니라 (금액, 통화) 쌍**으로 다뤄야 합니다. 통화가 다른 두 금액은 더할 수 없고, 더하려는 코드는 타입 단계에서 막는 게 낫습니다.

환산도 결과를 저장합니다. 환율은 시점마다 달라서, 나중에 다시 계산하면 그때의 금액이 나오지 않습니다.

- 원 통화 금액과 통화 코드
- 적용 환율과 그 환율의 기준 시각
- 환산된 금액

세 가지를 같이 적어두면 나중에 재현할 수 있습니다. 하나라도 빠지면 "이 숫자가 왜 이렇게 나왔는지" 설명할 방법이 없어집니다.

## 안 맞는 것을 빨리 찾기

금액 버그는 조용해서, 찾는 장치를 따로 둬야 합니다.

DB에서 막을 수 있는 건 DB에 맡깁니다.

```sql
ALTER TABLE order_items
  MODIFY amount BIGINT NOT NULL,
  ADD CONSTRAINT ck_amount_nonneg CHECK (amount >= 0);
```

`CHECK` 제약은 MySQL 8.0.16 이상에서 실제로 강제됩니다. 그 전 버전에서는 문법만 통과하고 검사하지 않으니, 버전부터 확인하세요.

그다음은 합계 불변식입니다. 주문 테이블의 총액과 항목 합계가 맞는지는 쿼리 한 줄로 상시 확인할 수 있습니다.

```sql
SELECT o.id, o.total_amount, SUM(i.amount) AS items_sum
  FROM orders o
  JOIN order_items i ON i.order_id = o.id
 WHERE o.created_at >= CURRENT_DATE - INTERVAL 7 DAY
 GROUP BY o.id, o.total_amount
HAVING o.total_amount <> SUM(i.amount);
```

결과가 0건이어야 정상입니다. 배치로 돌려 건수를 지표로 올려두면, 어긋남이 생긴 날을 바로 알 수 있습니다.

배분 함수처럼 규칙이 분명한 코드는 **불변식으로 테스트**하는 편이 예제 몇 개보다 촘촘합니다.

```typescript
import fc from 'fast-check';

test('배분 결과의 합은 언제나 원래 금액과 같다', () => {
  fc.assert(
    fc.property(
      fc.bigInt({ min: 0n, max: 10_000_000n }),
      fc.array(fc.bigInt({ min: 1n, max: 1_000_000n }), { minLength: 1, maxLength: 20 }),
      (total, weights) => {
        const parts = allocate(total, weights);
        return parts.reduce((a, b) => a + b, 0n) === total;
      },
    ),
  );
});
```

"합이 보존된다", "같은 입력은 같은 결과를 낸다", "공급가액 + 세액 = 총액" 같은 성질은 전부 이렇게 적을 수 있습니다. 예제 테스트는 내가 생각한 경우만 막지만, 불변식은 생각 못 한 경우에서 깨집니다.

## 체크리스트

- [ ] 금액 컬럼에 `FLOAT`·`DOUBLE`이 남아 있지 않은가
- [ ] `DECIMAL`을 쓴다면 스케일을 정했고, 곱셈·나눗셈 결과를 어디서 끊는지 정해져 있는가
- [ ] 드라이버가 금액을 어떤 타입으로 돌려주는지 직접 확인했는가
- [ ] API 응답에서 금액을 숫자로 내보내 클라이언트가 재계산할 여지를 주고 있지 않은가
- [ ] 반올림 함수가 한 곳에 모여 있고, 음수에서도 의도대로 도는가
- [ ] 반올림이 계산 경로에서 한 번만 일어나는가
- [ ] 부가세를 항목 기준으로 계산하는지 총액 기준으로 계산하는지 전 구간에서 같은가
- [ ] 세액과 공급가액 중 한쪽을 뺄셈으로 정해 합이 총액과 일치하는가
- [ ] 할인 배분의 합이 할인 총액과 같고, 재계산해도 결과가 같은가
- [ ] 할인 적용 순서가 코드 밖에 문서로 정해져 있는가
- [ ] 통화가 둘 이상이라면 금액과 통화를 한 쌍으로 다루고, 환산 결과와 환율을 저장하는가
- [ ] 합계 불변식을 확인하는 쿼리나 테스트가 있는가

금액 계산에 "대략 맞는 값"은 없습니다. 1원 차이는 정확도의 문제가 아니라 **규칙이 한 곳에 없다는 신호**입니다.

타입을 하나로 정하고, 반올림 지점을 하나로 모으고, 나머지를 누구에게 줄지 정해두면 대부분 사라집니다. 남는 건 정책이고, 그건 코드로 풀 문제가 아닙니다.
