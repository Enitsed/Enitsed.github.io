백업 성공 알림은 매일 옵니다. 그 백업으로 복구를 해본 사람은 팀에 없습니다.

백업이 성공했다는 건 **파일이 생겼다**는 뜻이지, 그걸로 서비스를 되돌릴 수 있다는 뜻이 아닙니다. 둘 사이에는 아직 아무도 확인하지 않은 단계가 여러 개 있습니다.

그 단계들을 사고가 난 날 처음 밟게 되면, 복구 시간은 예상의 몇 배가 됩니다.

## 복제는 백업이 아니다

가장 흔한 착각부터 짚고 갑니다. 리드 리플리카가 있으니 데이터는 안전하다는 생각입니다.

복제는 **원본에서 일어난 일을 그대로 따라 합니다.** 누군가 `DELETE FROM orders`를 조건 없이 날리면, 그 문장은 몇 밀리초 뒤 리플리카에도 똑같이 적용됩니다.

| 사고 | 복제가 막아주는가 | 백업이 막아주는가 |
| --- | --- | --- |
| 인스턴스·AZ 장애 | 막힘 (페일오버) | 막히지만 느림 |
| 스토리지 손상 | 대체로 막힘 | 막힘 |
| 사람이 잘못된 DML·DDL 실행 | **그대로 전파** | 막힘 |
| 애플리케이션 버그로 인한 대량 변경 | **그대로 전파** | 막힘 |
| 계정 탈취 후 삭제 | **그대로 전파** | 백업까지 지워지면 못 막음 |

복제는 **가용성**을 위한 장치이고 백업은 **되돌리기**를 위한 장치입니다. 겹치는 영역이 좁아서 서로를 대신하지 못합니다.

표의 마지막 줄이 중요합니다. 운영 DB를 지우는 권한과 백업을 지우는 권한이 같은 계정에 있으면, 그 계정 하나가 뚫렸을 때 두 겹이 동시에 사라집니다.

## 무엇을 몇 분까지 잃어도 되는가

복구 설계는 도구를 고르는 일이 아니라 **숫자 두 개를 정하는 일**에서 시작합니다.

- **RPO**(Recovery Point Objective) — 되돌아갈 수 있는 가장 최근 시점과 사고 시점 사이의 간격. "몇 분치 데이터를 잃어도 되는가".
- **RTO**(Recovery Time Objective) — 복구를 시작해서 서비스가 다시 뜰 때까지 걸리는 시간. "몇 시간 동안 멈춰도 되는가".

이 둘은 기술 지표가 아니라 **사업 결정**입니다. 그런데 정해두지 않으면 사고가 난 자리에서 즉석으로 정하게 되고, 그때는 아무도 "한 시간치는 버리자"고 말하지 못합니다.

적어두는 방식은 데이터 종류별로 나누는 게 현실적입니다. 전부를 같은 기준으로 지키려면 비용이 감당되지 않습니다.

| 데이터 | RPO | RTO | 수단 |
| --- | --- | --- | --- |
| 결제·주문 | 분 단위 | 1시간 이내 | 자동 백업 + PITR, 리전 간 복사 |
| 사용자 생성 콘텐츠 | 시간 단위 | 반나절 | 자동 백업 |
| 집계·캐시 테이블 | 복구 안 함 | — | 원본에서 재생성 |

세 번째 줄이 의외로 효과가 큽니다. **다시 만들 수 있는 데이터를 복구 대상에서 빼면** 복원해야 할 크기가 줄고, 그만큼 RTO가 짧아집니다.

> RPO를 "0"으로 적고 싶은 유혹이 있는데, 그건 동기 복제와 그에 따르는 쓰기 지연을 받아들이겠다는 뜻입니다. 숫자를 적기 전에 그 대가를 같이 적으세요.

## PITR이 실제로 하는 일

RDS의 특정 시점 복구(PITR)는 마법이 아닙니다. 두 단계를 붙여놓은 것입니다.

1. 목표 시각 **이전의 가장 가까운 스냅샷**을 복원한다.
2. 거기서부터 목표 시각까지의 **트랜잭션 로그를 재생**한다.

그래서 특성이 전부 여기서 나옵니다. 스냅샷 복원은 데이터 크기에 비례하고, 로그 재생은 그 구간의 쓰기량에 비례합니다. **데이터가 크고 쓰기가 많을수록 RTO가 길어집니다.**

되돌릴 수 있는 가장 최근 시점도 "지금"이 아닙니다. 로그가 주기적으로 업로드되기 때문에, 보통 몇 분 전이 한계입니다.

```bash
aws rds describe-db-instances \
  --db-instance-identifier prod-mysql \
  --query 'DBInstances[0].{Latest:LatestRestorableTime,Earliest:EarliestRestorableTime}'
```

이 두 값 사이가 되돌릴 수 있는 구간 전부입니다. 복구 계획을 세우기 전에 **지금 이 값이 얼마인지** 먼저 확인하세요. 자동 백업이 꺼져 있으면 이 구간 자체가 없습니다.

복원은 원본을 덮어쓰지 않습니다. **새 인스턴스를 만듭니다.**

```bash
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier prod-mysql \
  --target-db-instance-identifier prod-mysql-restored \
  --restore-time "2026-10-21T02:15:00Z" \
  --db-subnet-group-name prod-private \
  --vpc-security-group-ids sg-0123456789abcdef0 \
  --db-parameter-group-name prod-mysql80 \
  --no-publicly-accessible
```

`--restore-time`은 UTC로 줍니다. 한국 시간으로 기억한 사고 시각을 그대로 넣으면 9시간 어긋난 지점으로 복구됩니다. 가장 최근 시점으로 갈 거라면 `--use-latest-restorable-time`으로 대신합니다.

서브넷 그룹·보안 그룹·파라미터 그룹을 **명시한 것**에 주목하세요. 이걸 생략하면 원본과 다른 설정이 붙을 수 있고, 복구된 인스턴스에 애플리케이션이 붙지 못하거나 운영과 다른 파라미터로 뜹니다. 사고 한가운데서 보안 그룹을 디버깅하는 상황은 피하는 게 좋습니다.

> 복원된 인스턴스에 따라오지 않거나 다시 구성해야 하는 것들이 있습니다. 리드 리플리카, 백업 보존 설정, 이벤트 구독, 태그 같은 것들입니다. 엔진과 배포 형태(단일 인스턴스·Multi-AZ·Aurora)에 따라 명령과 따라오는 범위가 다르니, 실제 절차는 운영 중인 구성의 공식 문서로 한 번 맞춰보세요. Aurora는 클러스터 단위의 별도 명령을 씁니다.

그리고 **이름이 다른 인스턴스가 생겼다는 사실**이 복구의 마지막 단계를 만듭니다. 애플리케이션이 보는 엔드포인트를 이쪽으로 돌려야 복구가 끝납니다.

접속 문자열을 환경변수에 직접 박아두었다면 전 서비스 재배포가 필요하고, 그 시간이 전부 RTO에 더해집니다. DNS CNAME이나 파라미터 스토어를 한 겹 두면 이 단계가 몇 분으로 줄어듭니다.

```text
app → db.internal.example.com (CNAME) → prod-mysql.xxxx.rds.amazonaws.com
                                      → prod-mysql-restored.xxxx.rds.amazonaws.com
```

이 한 겹은 사고가 나기 전에 넣어둬야 의미가 있습니다. 복구 도중에 DNS 레코드를 새로 만들면 TTL이 끝나기를 기다리는 시간이 또 붙습니다.

## 바이너리 로그 보존은 PITR과 다른 이야기다

RDS MySQL에서 자주 섞이는 두 가지를 구분해둡니다.

PITR이 재생하는 로그는 RDS가 **자체적으로 관리하는** 것이고, 되돌릴 수 있는 범위는 **자동 백업 보존 기간**이 결정합니다. 자동 백업을 끄면 PITR도 같이 사라집니다.

반면 `binlog retention hours`는 **외부에서 바이너리 로그를 읽어가는 쪽**을 위한 설정입니다. 외부 복제나 CDC가 붙어 있을 때, RDS가 로그를 너무 빨리 지우지 않도록 붙잡아두는 값입니다.

```sql
CALL mysql.rds_set_configuration('binlog retention hours', 24);
CALL mysql.rds_show_configuration();
```

이 값을 늘린다고 PITR 가능 구간이 늘어나지 않습니다. 반대로 PITR을 켜두었다고 외부 복제가 안전해지지도 않습니다. 둘을 혼동하면 "분명히 로그를 보관하게 해뒀는데 그 시점으로 못 돌아간다"는 상황이 생깁니다.

> 보존 시간에는 상한이 있고, 늘린 만큼 스토리지를 먹습니다. 현재 허용되는 값과 기본 동작은 엔진 버전별로 다르니 공식 문서에서 확인하세요.

## 테이블 하나만 날렸을 때

실제로 더 자주 일어나는 사고는 인스턴스 소실이 아니라 **마이그레이션 스크립트가 엉뚱한 테이블을 비우는 것**입니다.

이때 전체 PITR로 운영 DB를 통째로 되돌리면, 사고 이후에 들어온 **정상 데이터까지 같이 버립니다.** 한 테이블을 살리려고 나머지 전부를 몇 시간 전으로 돌리는 셈입니다.

그래서 순서를 바꿉니다.

1. **쓰기를 멈출지 먼저 정한다.** 망가진 테이블에 계속 쓰기가 들어오고 있으면 복구 목표가 움직입니다. 해당 기능만 차단할 수 있으면 그게 최선입니다.
2. 사고 시점을 특정한다. 배포 로그, 감사 로그, 슬로우 쿼리 로그에서 문제의 문장이 실행된 시각을 찾습니다.
3. **그 직전 시점으로 별도 인스턴스를 복원한다.** 운영은 건드리지 않습니다.
4. 복원본에서 필요한 테이블만 뽑는다.
5. 운영으로 옮기고 검수한다.

4번은 논리 덤프로 합니다.

```bash
mysqldump \
  --host prod-mysql-restored.xxxx.rds.amazonaws.com \
  --single-transaction --no-create-info --set-gtid-purged=OFF \
  --where="created_at >= '2026-10-21 10:00:00'" \
  appdb orders > orders_recovered.sql
```

`--single-transaction`은 일관된 시점의 스냅샷을 읽기 위한 것이고, InnoDB에서만 의미가 있습니다. 덤프 도중에 DDL이 끼어들면 이 보장이 깨지지만, 복원본은 아무도 안 건드리니 여기서는 안전합니다.

5번이 진짜 어려운 부분입니다. 사고 이후에 같은 테이블에 들어온 새 행이 있고, 자동 증가 기본키라면 **복구하려는 행과 ID가 겹칠 수 있습니다.**

그래서 덤프를 운영에 바로 밀어 넣지 않습니다. 임시 테이블로 올려놓고 비교부터 합니다.

```sql
-- 복구분을 별도 테이블로 적재한 뒤
SELECT COUNT(*) FROM orders_recovered r
  JOIN orders o ON o.id = r.id;        -- 0이어야 안전하다

-- 겹치지 않는 것만 넣는다
INSERT INTO orders (id, user_id, amount, created_at)
SELECT r.id, r.user_id, r.amount, r.created_at
  FROM orders_recovered r
  LEFT JOIN orders o ON o.id = r.id
 WHERE o.id IS NULL;
```

겹치는 ID가 나온다면 그건 **다른 행이 같은 번호를 이미 차지했다**는 뜻이고, 기계적으로 넣으면 안 됩니다. 어느 쪽이 진짜인지는 사람이 판단해야 합니다.

외래키로 엮인 테이블이라면 부모부터 넣습니다. 자식 행만 먼저 복구하면 제약에 걸려 실패하거나, 제약이 없는 설계라면 **부모 없는 행이 조용히 생깁니다.**

## 스냅샷과 논리 덤프는 역할이 다르다

관리형 스냅샷이 있는데 `mysqldump`를 따로 돌려야 하냐는 질문이 자주 나옵니다. 쓰임이 다릅니다.

| | 스냅샷·PITR | 논리 덤프 |
| --- | --- | --- |
| 단위 | 인스턴스 전체 | 테이블·행 단위로 가능 |
| 복원 속도 | 크기에 비례, 대체로 빠름 | 느림 (INSERT 재실행) |
| 다른 엔진·버전으로 | 어려움 | 가능 |
| 사람이 내용 확인 | 복원해야 가능 | 파일을 바로 읽을 수 있음 |
| 보관처 | 관리형 서비스 안 | 원하는 곳 (S3 등) |

스냅샷은 **인프라 사고**에, 논리 덤프는 **데이터 사고**와 **이동**에 강합니다. 둘 다 두되 빈도와 보존 기간을 다르게 가져가는 편이 현실적입니다.

논리 덤프를 돌린다면 운영 인스턴스가 아니라 **리플리카나 복원본에서** 뽑으세요. 큰 테이블을 통째로 읽는 작업이라 버퍼 풀을 밀어내고, 그 영향은 서비스 쪽에 나타납니다.

## 복구해본 적 없는 백업은 백업이 아니다

여기가 이 글에서 하고 싶은 말의 전부입니다. 백업 파이프라인이 조용히 망가지는 경우는 흔합니다.

- 스냅샷은 도는데 중요한 테이블이 다른 인스턴스로 옮겨가 있다
- 암호화 키 권한이 바뀌어 복원 계정이 스냅샷을 못 읽는다
- 덤프 스크립트가 에러를 삼켜서 0바이트 파일을 매일 올리고 있다
- 복원은 되는데 애플리케이션이 붙지 못한다

전부 **복원을 시도해야만** 드러납니다. 그래서 리허설을 사람 기억이 아니라 작업으로 돌립니다.

```bash
#!/usr/bin/env bash
# 최신 자동 스냅샷에서 복원 → 검증 → 정리. 실패하면 즉시 종료한다.
set -euo pipefail

SRC="prod-mysql"
TARGET="restore-drill-$(date -u +%Y%m%d)"

SNAPSHOT=$(aws rds describe-db-snapshots \
  --db-instance-identifier "$SRC" --snapshot-type automated \
  --query 'sort_by(DBSnapshots,&SnapshotCreateTime)[-1].DBSnapshotIdentifier' \
  --output text)

aws rds restore-db-snapshot-to-db-instance \
  --db-snapshot-identifier "$SNAPSHOT" \
  --db-instance-identifier "$TARGET" \
  --db-subnet-group-name prod-private \
  --vpc-security-group-ids sg-0123456789abcdef0 \
  --no-publicly-accessible

aws rds wait db-instance-available --db-instance-identifier "$TARGET"

HOST=$(aws rds describe-db-instances --db-instance-identifier "$TARGET" \
  --query 'DBInstances[0].Endpoint.Address' --output text)

mysql -h "$HOST" -u "$DRILL_USER" -p"$DRILL_PASSWORD" appdb \
  -e "SELECT COUNT(*) FROM orders; SELECT MAX(created_at) FROM orders;"

aws rds delete-db-instance --db-instance-identifier "$TARGET" --skip-final-snapshot
```

`set -euo pipefail`이 중요합니다. 중간 단계가 실패했는데 스크립트가 계속 진행하면, **리허설이 성공했다고 보고하는 가짜 초록불**이 생깁니다.

검증은 "인스턴스가 떴다"에서 멈추지 말고 한 걸음 더 갑니다. 핵심 테이블의 행 수와 가장 최근 레코드의 시각을 찍어보면, 스냅샷이 실제로 어느 시점의 것인지가 드러납니다.

측정해서 기록할 값은 세 가지입니다.

- 복원 시작부터 접속 가능까지 걸린 시간 → **이게 RTO의 하한**입니다
- 가장 최근 레코드 시각과 스냅샷 시각의 차이 → **실제 RPO**
- 복원본의 행 수가 기대 범위 안인지

이 숫자들이 분기마다 어떻게 변하는지 보는 게 핵심입니다. 데이터가 늘면 RTO는 조용히 길어지고, 어느 순간 목표치를 넘깁니다. 사고 때 알게 되는 것보다 낫습니다.

리허설은 비용이 듭니다. 인스턴스를 잠깐 띄웠다 지우는 값인데, 복구가 안 되는 걸 사고 당일에 아는 비용보다는 쌉니다.

## 백업 자체를 지키기

마지막으로, 앞의 표에서 복제도 백업도 못 막는다고 한 줄입니다.

삭제 사고를 어렵게 만드는 장치들을 걸어둡니다.

```bash
# 인스턴스 삭제 방지
aws rds modify-db-instance \
  --db-instance-identifier prod-mysql \
  --deletion-protection --apply-immediately

# 다른 리전으로 스냅샷 복사
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier "arn:aws:rds:ap-northeast-2:<account-id>:snapshot:<name>" \
  --target-db-snapshot-identifier "<name>-dr" \
  --source-region ap-northeast-2 --region ap-northeast-1 \
  --kms-key-id "<target-region-kms-key>"
```

리전 간 복사에서 KMS 키를 빼먹는 실수가 잦습니다. 암호화된 스냅샷은 **대상 리전의 키**로 다시 암호화되어야 하고, 복구 담당 역할에 그 키 사용 권한이 없으면 정작 복원할 때 막힙니다. 권한까지가 백업의 일부입니다.

더 중요한 건 **권한 분리**입니다. 운영 DB를 다루는 역할과 백업을 지우는 역할을 같은 자격 증명에 두지 않습니다. 계정이 하나 뚫렸을 때 두 겹이 같이 사라지는 걸 막는 유일한 방법입니다.

S3에 덤프를 보관한다면 버전 관리와 객체 수준의 보존 설정을 같이 켭니다. 덮어쓰기로 망가진 백업이 조용히 정상 백업을 대체하는 경우를 막아줍니다.

## 런북에 미리 적어둘 것

사고 중에 하면 안 되는 일이 **결정**입니다. 미리 적어두면 그 자리에서는 실행만 하면 됩니다.

- 누가 복구 개시를 선언하는가, 그 사람이 없으면 누구인가
- 어느 시점으로 되돌릴지 정하는 기준과, 그 판단에 필요한 로그가 어디 있는가
- 복구 중 쓰기를 막을 것인가. 막는다면 어떻게 (기능 플래그, 읽기 전용 전환)
- 복원 명령 전문 — 서브넷 그룹, 보안 그룹, 파라미터 그룹 이름까지 채워진 상태로
- 엔드포인트를 어떻게 전환하는가
- 복구 완료를 무엇으로 확인하는가 (확인할 쿼리와 기대값)
- 고객 공지를 언제 누가 보내는가

마지막 줄을 빼먹기 쉬운데, 복구가 길어질 때 가장 먼저 필요해지는 항목입니다.

## 체크리스트

- [ ] 자동 백업이 켜져 있고, `EarliestRestorableTime`과 `LatestRestorableTime`을 실제로 확인해봤는가
- [ ] 데이터 종류별 RPO·RTO가 숫자로 적혀 있는가
- [ ] 다시 만들 수 있는 데이터를 복구 대상에서 빼두었는가
- [ ] 복원 명령에 서브넷·보안 그룹·파라미터 그룹이 명시돼 있는가
- [ ] 엔드포인트를 바꾸지 않고 복구본으로 전환할 방법이 있는가
- [ ] PITR 보존 기간과 `binlog retention hours`를 구분하고 있는가
- [ ] 테이블 단위 복구 경로가 전체 복구와 따로 정리돼 있는가
- [ ] 복원 리허설이 자동으로 돌고, 실패하면 알림이 오는가
- [ ] 리허설에서 복원 소요 시간과 실제 RPO를 기록하고 추이를 보고 있는가
- [ ] 스냅샷이 다른 리전이나 계정에 복사되고, 그 키 권한이 확인돼 있는가
- [ ] 운영 권한과 백업 삭제 권한이 분리돼 있는가
- [ ] 런북에 복원 명령이 값까지 채워진 상태로 적혀 있는가

백업 설정은 한 번 켜두면 끝나는 일처럼 보입니다. 실제로는 데이터가 늘고 구성이 바뀌는 만큼 **복구 가능성이 조용히 줄어드는** 일에 가깝습니다.

그 감소를 알아차리는 방법은 하나뿐입니다. 주기적으로 한 번씩 되돌려보고, 걸린 시간을 적어두는 것.
