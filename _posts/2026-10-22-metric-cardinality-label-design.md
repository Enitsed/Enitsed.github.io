"어떤 사용자가 느린지 보고 싶다"는 요구는 자연스럽고, 라벨을 하나 추가하는 작업은 한 줄입니다.
그 한 줄이 배포되고 며칠 뒤 모니터링 서버의 메모리가 차고, 대시보드가 타임아웃으로 비어 있습니다.

장애는 서비스가 아니라 **서비스를 보는 장치**에서 먼저 났습니다.
문제는 라벨을 추가한 판단이 아니라, 라벨 하나가 시계열 수에 어떻게 곱해지는지를 모르고 추가했다는 쪽입니다.

## 시계열이 생기는 단위

Prometheus 계열 저장소에서 데이터가 쌓이는 단위는 메트릭 이름이 아니라 **메트릭 이름 + 라벨 집합의 조합**입니다.
라벨 값이 하나 다르면 완전히 다른 시계열이고, 저장소는 그 각각에 대해 인덱스와 메모리 블록을 따로 잡습니다.

```text
http_requests_total{method="GET", route="/v1/users", status="200"}   → 시계열 1
http_requests_total{method="GET", route="/v1/users", status="500"}   → 시계열 2
http_requests_total{method="POST", route="/v1/users", status="200"}  → 시계열 3
```

그래서 비용은 덧셈이 아니라 **곱셈**으로 늘어납니다. 라벨별 값의 개수를 곱한 것이 그 메트릭의 상한입니다.

| 라벨 구성 | 값의 개수 | 시계열 수 |
| --- | --- | --- |
| `method`, `route`, `status` | 5 × 40 × 6 | 1,200 |
| + `pod` (인스턴스 10개) | × 10 | 12,000 |
| + `user_id` (사용자 5만) | × 50,000 | 6억 |

마지막 줄은 과장이 아니고 산수입니다. 실제로는 모든 조합이 등장하지 않으니 저만큼 생기지는 않지만, **등장하는 조합만큼은 반드시 생깁니다.**
그리고 사용자 수는 서비스가 잘될수록 늘어나는 값이라, 이 라벨은 성공할 때 터지는 설계입니다.

여기서 중요한 성질 하나. 시계열은 값이 더 들어오지 않아도 **바로 사라지지 않습니다.**
어제 한 번 요청한 사용자의 시계열은 그 뒤로 비어 있어도 당장 메모리와 인덱스를 차지하고, 일정 기간이 지나야 정리됩니다.
짧게 살다 사라지는 라벨 값(요청 ID, 배포마다 바뀌는 해시)이 특히 고약한 이유입니다. 이걸 보통 **처닝(churn)** 이라고 부릅니다.

## 히스토그램은 한 줄이 아니다

지연 시간을 재려고 히스토그램을 쓰면, 라벨 조합 하나가 시계열 하나가 아닙니다.
버킷 경계마다 `_bucket` 시계열이 하나씩 생기고 여기에 `_sum`과 `_count`가 더 붙습니다.

```text
http_request_duration_seconds_bucket{le="0.1", route="/v1/users"}
http_request_duration_seconds_bucket{le="0.3", route="/v1/users"}
...
http_request_duration_seconds_bucket{le="+Inf", route="/v1/users"}
http_request_duration_seconds_sum{route="/v1/users"}
http_request_duration_seconds_count{route="/v1/users"}
```

버킷을 12개 잡으면 `+Inf`를 포함해 13개, 거기에 `_sum`·`_count`로 **라벨 조합당 15개**입니다.
카운터에서는 신경 쓰지 않던 라벨 하나가 히스토그램에서는 15배로 들어옵니다.

> 카디널리티 조사에서 상위에 올라오는 메트릭은 거의 항상 히스토그램의 `_bucket`입니다.
> 범인을 찾을 때 여기부터 보면 대개 빠릅니다.

그래서 라벨 추가를 검토할 때는 메트릭 종류를 같이 봐야 합니다.
카운터에는 붙여도 괜찮은 라벨이 히스토그램에는 안 되는 경우가 생기고, 그럴 때는 **상세 분해는 카운터로, 분포는 묶어서 히스토그램으로** 가는 분리가 답이 됩니다.

## 폭발은 이런 모습으로 온다

카디널리티 문제는 "시계열이 너무 많습니다"라는 알림으로 오지 않습니다. 대개 이런 순서로 드러납니다.

- 수집기의 메모리 사용량이 트래픽과 무관하게 **단조 증가**한다
- 대시보드 중 범위가 긴 패널(최근 7일 등)만 먼저 타임아웃난다
- 스크레이프 주기 안에 수집이 안 끝나고 간격이 들쭉날쭉해진다
- 재시작 후 복구가 눈에 띄게 느려진다

마지막 항목이 특히 무섭습니다. 평소에는 버티고 있다가, **정작 장애로 재시작하는 순간 모니터링이 가장 늦게 돌아옵니다.**
지표를 봐야 하는 시점에 지표가 없는 상태가 되는 것이고, 이건 [트레이싱을 붙였는데 장애 때 못 쓰는 문제](/blog/opentelemetry-trace-context-sampling/)와 같은 결의 실패입니다.
평상시에 잘 돌아가는 것과 장애 때 쓸 수 있는 것은 다른 조건입니다.

## 지금 몇 개인지 재는 법

추측하지 말고 셉니다. 전체 규모부터 봅니다.

```promql
# 헤드 블록(최근 구간)에 들어 있는 시계열 수
prometheus_tsdb_head_series

# 스크레이프 대상별로 몇 개를 긁어오고 있는가
sum by (job) (scrape_samples_scraped)
```

어느 메트릭이 범인인지는 메트릭 이름별로 묶어서 셉니다.

```promql
topk(10, count by (__name__) ({__name__=~".+"}))
```

> 이 쿼리는 모든 시계열을 훑기 때문에 **이미 힘든 서버에 더 부하를 줍니다.**
> 운영 중인 수집기에서 돌릴 때는 짧은 시간 범위로, 한가한 시간대에 한 번만 돌리세요.

Prometheus는 카디널리티 통계를 돌려주는 상태 엔드포인트도 제공합니다. 쿼리보다 훨씬 가볍게 상위 목록을 볼 수 있습니다.

```bash
curl -s "$PROM/api/v1/status/tsdb" | jq '.data.seriesCountByMetricName[:10]'
```

여기에는 메트릭 이름별 시계열 수, 라벨 이름별 메모리 사용량, 라벨 값 개수 같은 항목이 함께 들어 있습니다.
다만 응답 필드 이름과 `limit` 같은 파라미터 지원 여부는 **버전에 따라 다르니 쓰는 버전의 공식 문서에서 확인**하세요. 이 통계가 보여주는 범위도 현재 헤드 블록 기준이라, 과거의 처닝은 여기서 안 보입니다.

한도를 넘겼을 때 조용히 넘어가지 않게 하는 설정도 있습니다. 스크레이프 설정의 `sample_limit`은 한 대상에서 받는 샘플 수에 상한을 두고, 넘으면 그 스크레이프를 실패로 처리합니다.

```yaml
scrape_configs:
  - job_name: api
    sample_limit: 20000
    static_configs:
      - targets: ["api:9090"]
```

```promql
# 상한에 걸려 버려진 스크레이프가 있는지
increase(prometheus_target_scrapes_exceeded_sample_limit_total[1h]) > 0
```

라벨 개수나 라벨 값 길이에 상한을 두는 옵션도 있는데 지원 버전이 갈리므로 문서를 확인하고 쓰세요.
상한을 걸면 사고가 **메트릭 일부 유실**로 끝납니다. 걸지 않으면 수집기 전체가 느려지는 쪽으로 번집니다. 어느 쪽이 나은지는 명확합니다.

## 라벨에 넣어도 되는 값의 기준

규칙은 하나로 줄어듭니다. **값의 집합이 유계(bounded)이고, 그 상한을 코드를 읽고 말할 수 있는가.**

넣어도 되는 것들입니다.

- HTTP 메서드, 상태 코드 계열, 환경 이름, 리전
- 라우트 **템플릿** (`/v1/users/:id`)
- 큐 이름, 작업 종류, 결과(`success` / `failure`)처럼 코드에 상수로 박혀 있는 값

넣으면 안 되는 것들입니다.

- 사용자 ID, 테넌트 ID(테넌트가 늘어나는 구조라면), 주문 번호, 세션 ID, 요청 ID
- 이메일·전화번호 같은 개인정보 — 카디널리티 전에 **유출 문제**입니다
- 경로 파라미터가 박힌 전체 URL, 쿼리스트링
- 예외 메시지, SQL 문장, 외부 API 응답 본문
- 타임스탬프, 커밋 해시, 배포 ID

판단이 애매할 때 쓰는 질문이 있습니다. **"이 라벨 값의 종류가 트래픽이나 데이터가 늘어나면 같이 늘어나는가?"**
같이 늘어난다면 라벨이 아닙니다. 지금 10개뿐이어도, 늘어나는 성질이면 라벨로 두는 순간 폭탄을 심은 것입니다.

테넌트 ID는 이 기준에서 가장 자주 걸리는 경계입니다. 수십 개 수준으로 고정돼 있고 테넌트별 지표가 실제로 운영에 쓰인다면 라벨로 둘 수 있습니다.
셀프 서비스로 가입이 열려 있다면 라벨이 아니고, [멀티테넌시](/blog/multi-tenant-data-isolation/)에서 격리를 쿼리 조건으로 강제하듯 지표도 상위 소수만 따로 보는 쪽으로 가야 합니다.

## 경로를 템플릿으로 묶기

고카디널리티가 가장 자주 들어오는 경로는 의외로 사용자 ID가 아니라 **URL 경로**입니다.
`req.path`를 그대로 라벨에 넣으면 `/v1/users/8f3a...`가 사용자 수만큼 생깁니다.

라우터가 알고 있는 템플릿을 씁니다. Express라면 라우팅이 끝난 뒤 `req.route`에 패턴이 들어옵니다.

```typescript
import express from 'express';
import { Histogram, Registry, collectDefaultMetrics } from 'prom-client';

const register = new Registry();
collectDefaultMetrics({ register });

const httpDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP 요청 처리 시간',
  labelNames: ['method', 'route', 'status'] as const,
  buckets: [0.05, 0.1, 0.3, 0.5, 1, 2, 5],
  registers: [register],
});

export function metricsMiddleware() {
  return (req: express.Request, res: express.Response, next: express.NextFunction) => {
    const end = httpDuration.startTimer({ method: req.method });

    res.on('finish', () => {
      // 라우팅된 패턴을 쓴다. 매칭 실패(404)는 한 버킷으로 모은다.
      const route = req.route?.path
        ? `${req.baseUrl}${req.route.path}`
        : 'unmatched';

      end({ route, status: String(res.statusCode) });
    });

    next();
  };
}
```

두 군데가 핵심입니다.

`req.route?.path`는 미들웨어 진입 시점에는 아직 비어 있어서 **응답이 끝난 뒤에 읽어야** 값이 들어옵니다. 진입 시점에 읽으면 전부 `undefined`가 됩니다.

매칭되지 않은 요청을 `unmatched` 하나로 모으는 부분은 생략하면 안 됩니다.
존재하지 않는 경로로 들어오는 스캐너 트래픽은 경로가 매번 다르고, 이걸 그대로 라벨에 넣으면 **외부에서 카디널리티를 주입**할 수 있게 됩니다. 라벨 값이 외부 입력에서 오는 경로는 전부 이 검토를 거쳐야 합니다.

`status`도 생각해볼 여지가 있습니다. 코드별로 다 봐야 한다면 그대로 두고, 계열만 필요하다면 `2xx`/`4xx`/`5xx`로 묶어 6개 이하로 줄입니다. 히스토그램이라면 이 선택이 15배로 들어옵니다.

## 에러 라벨이 새는 자리

에러를 세는 메트릭에서 사고가 자주 납니다. 디버깅에 도움이 될 것 같아서 메시지를 넣기 때문입니다.

```typescript
// 하지 말 것: 메시지에 ID·주소·타임스탬프가 섞여 들어온다
errorCounter.inc({ reason: err.message });

// 분류된 상수로 좁힌다
type ErrorKind = 'timeout' | 'conflict' | 'validation' | 'upstream_5xx' | 'unknown';

function classify(err: unknown): ErrorKind {
  if (isTimeout(err)) return 'timeout';
  if (isDuplicateKey(err)) return 'conflict';
  if (isValidationError(err)) return 'validation';
  if (isUpstreamServerError(err)) return 'upstream_5xx';
  return 'unknown';
}

errorCounter.inc({ kind: classify(err) });
```

`classify`의 반환 타입이 유니온이라는 점이 라벨의 상한을 코드로 고정해줍니다. 값이 늘어나려면 타입을 고쳐야 하고, 그건 리뷰에 걸립니다.

그리고 `unknown`을 버리지 마세요. **`unknown` 비율이 올라가는 것 자체가 분류가 현실을 못 따라간다는 신호**입니다.
원래 메시지는 메트릭이 아니라 로그로 보냅니다. 거기서는 전체 문자열을 남겨도 되고, 그게 로그의 역할입니다.

## 이미 들어간 라벨을 수집 단계에서 떼기

계측 코드를 고치고 배포하면 끝이지만, 당장 수집기가 힘들어하는 상황이라면 배포를 기다릴 수 없습니다.
`metric_relabel_configs`는 스크레이프한 뒤 저장 전에 적용되므로, 들어오는 것을 그 자리에서 버릴 수 있습니다.

```yaml
scrape_configs:
  - job_name: api
    static_configs:
      - targets: ["api:9090"]
    metric_relabel_configs:
      # 메트릭 하나를 통째로 버린다
      - source_labels: [__name__]
        regex: 'myapp_debug_.*'
        action: drop

      # 라벨 하나만 떼어낸다 (regex는 라벨 '이름'에 매칭)
      - regex: 'user_id|request_id|session_id'
        action: labeldrop

      # 특정 메트릭의 히스토그램만 버린다
      - source_labels: [__name__]
        regex: 'myapp_internal_duration_seconds_bucket'
        action: drop
```

> `labeldrop`에는 함정이 있습니다. 라벨을 떼면 서로 달랐던 시계열이 **같은 식별자로 합쳐지고**,
> 같은 타임스탬프에 값이 둘 들어와 `duplicate sample for timestamp` 오류가 납니다.
> 카운터에서 이게 생기면 값은 둘 중 하나만 남아 **조용히 틀린 수치**가 됩니다. 떼려는 라벨이 유일성에 기여하지 않는지 먼저 확인하세요.

그래서 relabel은 응급 처치입니다. 라벨을 떼는 것이 아니라 **애초에 안 붙이는 것**이 정답이고, relabel은 그 배포가 나갈 때까지 버티는 수단입니다.
다만 서드파티 익스포터처럼 계측을 우리가 못 고치는 경우에는 이게 유일한 수단이기도 합니다.

## 버킷은 거꾸로 정한다

버킷 개수가 히스토그램 비용을 직접 결정하는데, 기본값을 그대로 쓰면 필요 없는 구간에 버킷을 낭비하기 쉽습니다.

판단 기준을 질문으로 바꾸면 쉬워집니다. **"어떤 지연 시간을 넘으면 문제라고 말할 것인가?"**

`p99 300ms`를 목표로 보기로 했다면 그 근처가 촘촘해야 합니다. `0.2 / 0.3 / 0.5` 같은 경계가 있어야 "지금 목표를 넘겼는가"를 답할 수 있고, `10초 / 30초` 구간은 "느리다"는 사실 외에 알려주는 게 없으니 하나로 묶어도 됩니다.

반대로 백그라운드 작업처럼 초 단위가 정상인 메트릭에 웹 요청용 기본 버킷을 쓰면 대부분이 `+Inf`에 몰려서, 분포를 전혀 못 봅니다.

버킷을 바꾸면 그 전 데이터와 비교가 깨진다는 점도 같이 알아두세요. 경계가 달라지면 `histogram_quantile`의 보간 결과가 달라서, 바꾼 시점을 전후로 그래프에 계단이 생깁니다.

버킷 개수와 정확도의 교환을 자동으로 처리하는 네이티브 히스토그램 쪽 기능도 있는데, 지원 상태와 설정 방법이 버전에 따라 다르니 **공식 문서를 먼저 확인**하고 도입 여부를 판단하세요.

## 고유 식별자는 로그와 트레이스의 몫

카디널리티 논의의 결론은 "그 정보를 보지 말자"가 아닙니다. **보는 장치를 바꾸자**입니다.

| 알고 싶은 것 | 맞는 도구 | 이유 |
| --- | --- | --- |
| 5xx 비율이 올랐는가 | 메트릭 | 집계값, 라벨 소수 |
| 어떤 라우트가 느려졌는가 | 메트릭 | 라벨이 유계 |
| 특정 사용자의 그 요청이 왜 느렸는가 | 트레이스 | 요청 단위, 샘플링 전제 |
| 그때 무슨 에러 메시지가 났는가 | 로그 | 전문 보존, 검색 |

메트릭은 "무언가 이상하다"를 싸게 알려주고, 로그와 트레이스는 "무엇이 왜"를 비싸게 알려줍니다.
사용자 ID를 라벨에 넣으려는 충동은 대개 **메트릭에게 트레이스의 일을 시키려는 것**입니다.

둘을 잇는 장치로 exemplar가 있습니다. 히스토그램 샘플에 trace ID를 매달아 그래프의 튀는 점에서 해당 트레이스로 넘어가는 방식인데,
수집기와 대시보드 양쪽의 지원·설정이 필요하니 쓰려면 문서를 확인하세요. 개념만 알아둬도 "이 정보를 라벨로 넣을 필요가 없다"는 판단에는 충분합니다.

트레이스 쪽에서 느린 요청을 버리지 않으려면 샘플링 전략이 먼저 맞아야 합니다. 그 이야기는 [꼬리 샘플링](/blog/opentelemetry-trace-context-sampling/)에 적어뒀습니다.

## 쿼리 쪽에도 비용이 있다

시계열이 많아지면 저장만 무거워지는 게 아니라 쿼리가 같이 느려집니다. 대시보드가 띄우는 쿼리가 매번 수십만 시계열을 훑기 때문입니다.

자주 쓰는 집계는 레코딩 룰로 미리 계산해둡니다.

```yaml
groups:
  - name: api
    interval: 30s
    rules:
      - record: job:http_request_errors:rate5m
        expr: |
          sum by (job, route) (
            rate(http_requests_total{status=~"5.."}[5m])
          )
```

대시보드와 알림이 원본 대신 이 결과를 보게 되면, 같은 계산을 매 새로고침마다 반복하지 않습니다.
알림 쪽에서는 효과가 더 큽니다. 평가 주기마다 도는 쿼리라서, 무거운 표현식 하나가 상시 부하가 됩니다.

주의할 점은 레코딩 룰이 **집계 결과도 시계열로 저장한다**는 것입니다. `by` 절에 고카디널리티 라벨을 남기면 룰 자체가 새로운 폭발의 원인이 됩니다.
룰을 쓸 때는 라벨을 더하는 게 아니라 줄이는 방향으로만 씁니다.

## 체크리스트

- [ ] 새 라벨을 추가할 때 **값의 상한을 숫자로 말할 수 있는가**
- [ ] 그 값의 종류가 트래픽·사용자·데이터가 늘면 같이 늘어나는 성질인가
- [ ] 대상 메트릭이 히스토그램인가 (버킷 수만큼 곱해진다)
- [ ] 라벨 값이 외부 입력(URL, 헤더, 요청 본문)에서 오는 경로가 있는가
- [ ] 경로를 라우트 템플릿으로 묶고, 매칭 실패는 한 값으로 모으는가
- [ ] 에러 분류가 코드상의 유한한 상수 집합인가
- [ ] 개인정보가 라벨로 들어가는 자리가 없는가
- [ ] `sample_limit` 같은 상한을 걸어 사고를 국소화했는가
- [ ] `seriesCountByMetricName` 상위 목록을 주기적으로 확인하는가
- [ ] 무거운 집계를 레코딩 룰로 내렸고, 룰이 라벨을 늘리지 않는가
