에러율이 올라갔는데 최신 앱으로는 아무리 눌러도 재현되지 않습니다.
로그를 보면 전부 2주 전 버전, 그리고 그보다 오래된 버전입니다.

서버는 롤백하면 되지만 **앱은 내가 롤백할 수 없습니다.**
한 번 깨진 클라이언트는 사용자가 업데이트할 때까지 깨진 채로 남고, 그 시점은 내가 정하지 못합니다.

## 깨지는 변경인지는 서버가 정하지 않는다

문서에 "필드 추가는 하위 호환"이라고 적어두어도, 실제로 깨지는지는 클라이언트의 역직렬화 코드가 정합니다.
같은 변경이 어떤 클라이언트에서는 무해하고 어떤 클라이언트에서는 응답 전체 파싱 실패가 됩니다.

| 변경 | 깨지지 않는 조건 | 깨지는 조건 |
| --- | --- | --- |
| 응답에 필드 추가 | 모르는 키를 버리는 파서 | 모르는 키를 거부하도록 설정된 검증 |
| enum 값 추가 | 모르는 값을 기타로 떨어뜨림 | 모르는 값에서 디코딩 실패 |
| non-null → nullable | 거의 없음 | 비어 있을 수 없다고 가정한 모든 코드 |
| 숫자 → 문자열 | 없음 | 전부 |
| 필드 이름 변경 | 없음 | 전부 |
| 기본 정렬·페이지 크기 변경 | 순서에 의존하지 않는 화면 | 중복·누락으로 보이는 목록 |
| 성공 상태코드 변경 | `2xx` 안의 변경 | 코드로 분기하던 클라이언트 |
| 에러 바디 구조 변경 | 메시지만 쓰는 클라이언트 | `code`로 분기하던 클라이언트 |

위쪽 두 줄이 가장 자주 사고를 냅니다. 서버 입장에서는 둘 다 **"추가"**고, 추가는 안전하다고 배우기 때문입니다.

## enum 값 하나가 화면을 비운다

원아 상태에 값을 하나 더한다고 해봅시다. 서버 코드에서는 한 줄입니다.

```typescript
type EnrollmentStatus =
  | 'ENROLLED'
  | 'GRADUATED'
  | 'WITHDRAWN'
  | 'ON_LEAVE';   // 추가
```

정적 타입 언어 클라이언트에서 열거형 디코딩은 기본적으로 **아는 값만** 받습니다.
모르는 값을 만나면 그 필드 하나가 비는 게 아니라 디코딩이 예외로 끝나고, 그 예외는 보통 응답 전체로 번집니다.

목록 API라면 수십 개 중 한 항목 때문에 화면이 통째로 비고, 사용자에게는 "원아 목록이 안 보인다"로 도착합니다.
서버 로그에는 `200`이 찍혀 있습니다.

> enum에 값을 추가하는 건 서버 쪽에서 가장 싸게 느껴지지만 클라이언트 쪽에서는 가장 비싼 변경입니다.
> 값이 늘어날 수 있는 필드라면 처음부터 닫힌 집합으로 내보내지 않는 편이 낫습니다.

서버가 할 수 있는 건 두 가지입니다.

첫째, **분기용 값과 표시용 값을 나눕니다.** 분기에 쓰는 쪽은 늘어나지 않는 소수의 값으로 고정하고, 세분화된 상태는 표시용 문자열로 내려줍니다.

```json
{
  "status": "ON_LEAVE",
  "statusGroup": "INACTIVE",
  "statusLabel": "휴원"
}
```

클라이언트는 `statusGroup`으로 분기하고 `statusLabel`을 그대로 그립니다.
상태가 다섯 개 더 늘어도 `statusGroup`은 그대로이니 구버전이 깨지지 않습니다. 대신 **문구를 서버가 쥐게 되므로** 클라이언트에서 다국어나 서식을 다루기 어려워집니다.

둘째, 구버전에는 **아는 값으로 접어서** 내려줍니다. 뒤에 나오는 클라이언트 버전 식별이 전제입니다.
다만 접을 수 있는 값이 있을 때만 성립합니다. 휴원을 퇴원으로 접어 보여주면 깨지지는 않지만 **틀린 정보**가 나가고, 그건 파싱 실패보다 나쁩니다.

## 모르는 키는 방향에 따라 반대로 다룬다

같은 "모르는 키"인데 응답을 읽을 때와 요청을 받을 때 맞는 전략이 다릅니다.

**응답을 읽을 때는 버립니다.** 클라이언트가, 그리고 외부 API를 호출하는 서버가 모르는 키에서 실패하면 상대는 필드를 영원히 추가할 수 없습니다.

**요청을 받을 때는 선택입니다.** 모르는 키를 `400`으로 거부하면 클라이언트의 오타를 즉시 잡아줍니다.
대신 신버전 클라이언트가 새 필드를 보내기 시작한 순간, 아직 교체되지 않은 구버전 서버 인스턴스가 그 요청을 거부합니다.
[롤링 배포 중에 두 버전이 동시에 떠 있는 구간](/blog/graceful-shutdown-deploy-5xx/)은 가정이 아니라 매 배포마다 지나가는 구간입니다.

실용적인 선은 **무시하되 세는 것**입니다.

```typescript
function takeKnown<T extends object>(
  body: Record<string, unknown>,
  keys: readonly (keyof T & string)[],
): { value: Partial<T>; unknownKeys: string[] } {
  const known = new Set<string>(keys);
  const value: Record<string, unknown> = {};
  const unknownKeys: string[] = [];

  for (const [k, v] of Object.entries(body)) {
    if (known.has(k)) value[k] = v;
    else unknownKeys.push(k);
  }

  return { value: value as Partial<T>, unknownKeys };
}
```

모르는 키 이름을 로그에 남겨두면 두 가지가 보입니다. 클라이언트의 오타와, **아직 배포되지 않은 필드를 보내고 있는 신버전**입니다.
후자가 보이기 시작하면 서버 배포가 뒤쳐졌다는 신호입니다.

스키마 검증 라이브러리를 쓴다면 모르는 키의 기본 동작이 무엇인지(버린다 / 거부한다 / 그대로 통과시킨다) 쓰는 버전의 문서에서 확인하세요.
이 기본값은 메이저 버전에서 바뀔 수 있고, 바뀌면 **내 코드를 한 줄도 안 고쳐도 API 동작이 달라집니다.**

## 버저닝 방식과 그 비용

| 방식 | 예 | 장점 | 단점 |
| --- | --- | --- | --- |
| URL 경로 | `/v2/children` | 눈에 보이고 라우팅·캐시·로그가 단순하다 | 리소스마다 버전이 다르면 경로가 어긋난다 |
| 커스텀 헤더 | `X-API-Version: 2` | URL이 하나로 유지된다 | 브라우저에서 눌러볼 수 없고 캐시 키에 넣어야 한다 |
| 미디어 타입 | `Accept: application/vnd.app.v2+json` | HTTP 협상 체계에 맞는다 | 클라이언트·게이트웨이 설정이 번거롭다 |

세 방식의 차이는 대개 취향 수준이고, **진짜 비용은 라우팅이 아니라 두 개의 동작을 유지하는 일**에 있습니다.

그래서 먼저 정할 것은 표기법이 아니라 **버전의 단위**입니다.
API 전체 버전을 올리면 바뀐 건 두 엔드포인트인데 나머지 수십 개의 `v1`·`v2`를 같은 코드로 두 번 등록하게 됩니다.
그 상태가 몇 달 지나면 어느 쪽이 쓰이는지 아무도 모르게 됩니다.

엔드포인트 단위로, 더 좁히면 필드 단위로 끊는 쪽이 유지 비용이 작습니다.

## 분기를 표현 계층 밖으로 내보내지 않는다

버전 분기가 도메인 로직까지 내려가면 쓰기 경로가 둘이 됩니다. 그때부터 버그 수정을 두 번 해야 하고, 한쪽을 빼먹습니다.

규칙은 하나입니다. **계산은 한 번, 직렬화는 버전마다.**

```typescript
// 도메인은 버전을 모른다
const child = await childService.get(childId);

// 표현만 버전별로 나눈다
export function toChildV1(c: Child) {
  return {
    id: c.id,
    name: c.name,
    status: foldStatusForV1(c.status),   // 구버전이 아는 값으로 접는다
  };
}

export function toChildV2(c: Child) {
  return {
    id: c.id,
    name: c.name,
    status: c.status,
    statusGroup: groupOf(c.status),
    statusLabel: labelOf(c.status),
  };
}
```

응답 조립 함수가 한 자리에 모여 있으면, 구버전에 무엇이 나가는지를 코드에서 바로 읽을 수 있습니다.
반대로 컨트롤러 곳곳에 `if (version >= 2)`가 흩어지면 **지금 구버전에 무엇이 나가는지를 아무도 말할 수 없는 상태**가 됩니다. 그 상태에서는 폐기 판단도 못 합니다.

쓰기 쪽은 더 엄격하게 봅니다. 구버전 요청은 **새 모델로 변환해 같은 핸들러에 넘기는 형태**가 안전합니다.

```typescript
// v1 바디를 v2 모델로 올려 보낸 뒤, 핸들러는 하나만 둔다
function upgradeCreateBody(v1: CreateChildV1): CreateChildV2 {
  return {
    name: v1.name,
    guardians: v1.parentName
      ? [{ name: v1.parentName, relation: 'UNKNOWN' }]
      : [],
  };
}
```

변환 함수는 순수 함수라 테스트하기 쉽고, **구버전을 지울 때 지울 대상이 함수 하나로 명확합니다.**

## 클라이언트 버전을 재지 않으면 아무것도 못 지운다

구버전 지원을 끊는 결정에는 숫자가 필요합니다. "아직 쓰는 사람이 있을 것 같다"로는 영원히 못 끊습니다.

모든 요청에 클라이언트 식별 정보를 받습니다.

```typescript
app.use((req, _res, next) => {
  // 예: "kinderboard-ios/3.4.1"
  const raw = req.header('x-client-version') ?? '';
  const m = /^([a-z-]+)\/(\d+)\.(\d+)\.(\d+)$/.exec(raw);

  req.client = m
    ? { app: m[1], major: Number(m[2]), minor: Number(m[3]) }
    : { app: 'unknown', major: 0, minor: 0 };

  next();
});
```

패치 번호를 버린 것은 의도입니다. 이 값을 메트릭 라벨로 쓸 거라서, 전체 버전 문자열을 그대로 넣으면 [시계열 수가 버전 수만큼 늘어납니다](/blog/metric-cardinality-label-design/).
`major.minor`까지면 "구버전이 아직 몇 %인가"를 보는 데 충분합니다. 정확한 패치 버전이 필요한 조사는 로그에서 합니다.

> 응답을 클라이언트 버전에 따라 분기한다면 캐시 쪽을 반드시 같이 보세요.
> 버전 헤더가 캐시 키에 들어가지 않으면 CDN이나 프록시가 **구버전용 응답을 신버전 클라이언트에 그대로 줍니다.** 헤더로 분기할 때는 `Vary`에 그 헤더를 넣어야 합니다.

## 폐기는 날짜를 적는 순간부터 시작된다

HTTP에는 "이 URI가 언제까지 살아 있는가"를 알리는 응답 헤더가 있습니다. `Sunset`이고, [RFC 8594](https://www.rfc-editor.org/rfc/rfc8594)로 정의된 정보성 RFC입니다.

```typescript
res.set('Sunset', 'Sat, 31 Jan 2026 00:00:00 GMT');
res.set('Link', '<https://docs.example.com/api/v1-sunset>; rel="sunset"');
```

함께 쓰이는 `Deprecation` 헤더는 아직 IETF에서 표준화가 진행 중이라, 쓰기 전에 [현재 상태](https://datatracker.ietf.org/doc/draft-ietf-httpapi-deprecation-header/)를 확인하세요.
어느 쪽이든 **사람이 읽는 공지를 대체하지는 않습니다.** 헤더는 기록이고, 실제로 클라이언트를 고치게 만드는 건 공지와 기한입니다.

순서는 이렇게 됩니다.

1. 새 버전을 올리고 문서에 폐기 예정일을 적는다.
2. 구버전 응답에 `Sunset` 헤더를 붙인다.
3. 구버전 호출량을 버전·클라이언트별로 센다.
4. 호출량이 미리 정한 임계 아래로 떨어질 때까지 기다린다.
5. 제거하고, 그 경로는 명확한 응답으로 막는다.

4번의 임계를 **미리 숫자로 적어두는 게 중요합니다.** 그때 가서 정하면 "아직 0.3%가 쓰는데요"에서 매번 멈춥니다.

제거 후에는 조용히 `404`를 주지 말고 의도를 담아 돌려줍니다. 지원이 끝났음을 알리는 응답은 바디에 코드를 함께 넣어야 클라이언트가 분기할 수 있습니다.

```json
{
  "code": "CLIENT_VERSION_UNSUPPORTED",
  "message": "앱을 업데이트해 주세요.",
  "minSupportedVersion": "3.2.0",
  "storeUrl": "https://..."
}
```

`426 Upgrade Required`를 쓰는 사례가 있는데, 원래는 프로토콜 업그레이드를 요구하는 코드라 앱 버전 강제는 **재해석**입니다.
상태코드만으로는 클라이언트가 무엇을 해야 할지 알 수 없으니, 어느 코드를 고르든 위처럼 구조화된 바디를 같이 내려주는 쪽이 실용적입니다.

그리고 모바일에서는 **최소 지원 버전을 올리는 데 리드 타임이 필요합니다.** 새 버전을 내려면 스토어 심사를 거쳐야 하고, 사용자가 업데이트하는 데는 그보다 더 걸립니다.
"오늘부터 구버전 차단"은 선택지가 아닙니다. 최소 지원 버전은 코드에 박지 말고 설정으로 빼두는 편이 낫습니다. 기한을 미루는 결정이 배포 없이 가능해집니다.

## 계약을 CI에서 고정한다

필드 이름 변경과 삭제는 리뷰에서 눈으로 잡는 게 아니라 테스트로 막습니다.
값이 아니라 **키 집합을 단정**하면 됩니다.

```typescript
it('children 응답의 공개 필드 집합은 변하지 않는다', async () => {
  const res = await request(app).get('/v2/children/1').expect(200);

  expect(Object.keys(res.body).sort()).toEqual([
    'id', 'name', 'status', 'statusGroup', 'statusLabel',
  ]);
});
```

필드를 추가하면 이 테스트가 깨집니다. 그게 목적입니다. **추가도 의식적인 결정이 되게** 만드는 장치고, 깨진 테스트를 고치는 커밋이 곧 계약 변경의 기록입니다.

OpenAPI 스펙을 관리한다면 스펙 diff로 깨지는 변경을 CI에서 검출할 수 있습니다.
도구마다 "깨지는 변경"의 정의가 다르니, 쓰기 전에 어떤 변경을 차단하는지 목록을 확인하세요. 응답 필드 **추가**를 깨지는 변경으로 볼지 여부부터 갈립니다.

스펙에서 클라이언트 타입을 생성해 쓰고 있다면 그게 가장 강한 장치입니다. 서버가 필드를 지우면 클라이언트 빌드가 깨지니까요.
다만 이건 클라이언트를 **다시 빌드할 때만** 작동합니다. 이미 사용자 손에 있는 앱에는 아무 효과가 없고, 이 글의 문제는 전부 거기서 생깁니다.

## 그래도 깨야 할 때

깨지 않는 게 늘 정답은 아닙니다. 보안 문제가 있거나, 법적으로 내려줄 수 없는 값이거나, 모델 자체가 틀렸으면 깨야 합니다.

그때 최악의 선택은 **같은 URL의 동작을 조용히 바꾸는 것**입니다. 깨지는 변경을 "버그 수정"이라고 부르면 아무도 대비하지 못합니다.
새 경로나 새 필드를 만들고, 구 경로는 위의 폐기 절차를 밟게 하세요. 느리지만 예측 가능합니다.

예외는 하나입니다. 보안 사고로 지금 당장 값을 가려야 하는 경우에는 먼저 막고, 깨진 클라이언트를 찾는 일은 그다음입니다. 순서가 바뀌면 안 됩니다.

## 체크리스트

- [ ] 응답 필드 **추가**가 클라이언트에서 안전한지 실제 파서 설정으로 확인했는가
- [ ] 값이 늘어날 수 있는 필드를 닫힌 enum으로 내려주고 있지 않은가
- [ ] 분기용 값과 표시용 값이 분리되어 있는가
- [ ] 요청의 모르는 키를 무시하면서 **로그로 세고** 있는가
- [ ] 버전 분기가 도메인 로직이 아니라 직렬화·변환 함수에만 있는가
- [ ] 구버전에 무엇이 나가는지 한 파일에서 읽을 수 있는가
- [ ] 모든 요청에서 클라이언트 버전·플랫폼을 식별할 수 있는가
- [ ] 버전 라벨의 카디널리티를 제한했는가
- [ ] 버전 헤더로 응답을 분기하면서 `Vary`를 설정했는가
- [ ] 구버전 제거 임계를 **숫자로** 적어두었는가
- [ ] 최소 지원 버전이 배포 없이 바꿀 수 있는 설정인가
- [ ] 응답 키 집합을 단정하는 테스트가 있는가
