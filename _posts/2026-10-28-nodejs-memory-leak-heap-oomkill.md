메모리 그래프가 톱니 모양으로 올라갑니다. 떨어지긴 하는데 떨어진 자리가 매번 조금씩 높습니다.

며칠 뒤 컨테이너가 재시작되고, 애플리케이션 로그에는 아무것도 없습니다. 에러도 스택트레이스도 없이 그냥 끊깁니다.

이 조합이 제일 다루기 어렵습니다. **범인이 남긴 흔적이 애플리케이션 밖에 있기 때문**입니다.

## 두 가지 죽음을 먼저 가른다

메모리 때문에 프로세스가 끝나는 경로는 둘이고, 대응이 완전히 다릅니다.

하나는 **V8이 스스로 포기하는 경우**입니다. 힙이 자기 한도에 닿으면 치명적 오류를 내고 죽습니다.

```text
FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
```

이건 좋은 죽음입니다. 메시지가 남고, 스택트레이스가 따라오고, 운이 좋으면 어떤 할당에서 터졌는지까지 보입니다.

다른 하나는 **커널이 죽이는 경우**입니다. 컨테이너가 cgroup 메모리 한도를 넘으면 OOM 킬러가 `SIGKILL`을 보냅니다.

프로세스에게 정리할 틈이 없으니 애플리케이션 로그에는 아무것도 남지 않습니다. 종료 코드만 남습니다.

```bash
# 쿠버네티스: 직전 종료 이유를 본다
kubectl get pod "$POD" -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}{"\t"}{.status.containerStatuses[0].lastState.terminated.exitCode}{"\n"}'
# OOMKilled  137
```

`137`은 `128 + 9`, 즉 `SIGKILL`로 끝났다는 뜻입니다. ECS라면 중단된 태스크의 중단 이유에 메모리 때문에 컨테이너가 종료됐다는 문장이 남습니다.

| | V8 힙 OOM | 커널 OOMKill |
| --- | --- | --- |
| 흔적 | 치명적 오류 메시지 + 스택 | 종료 코드 137 (앱 로그 없음) |
| 원인 범위 | JS 힙 안 | 프로세스 전체 RSS |
| 보는 숫자 | `heapUsed` / `heap_size_limit` | 컨테이너 RSS / cgroup 한도 |
| 먼저 할 일 | 힙 스냅샷 | 힙 바깥까지 포함해 측정 |

그래서 증상만 듣고 "메모리 누수"로 넘어가면 안 됩니다. **어느 한도에 먼저 닿았는지**가 다음 행동을 정합니다.

## 늘어나는 것과 새는 것은 다르다

메모리가 오르는 그래프는 정상적인 서비스에서도 나옵니다. V8은 필요할 때까지 반납하지 않고, 캐시는 채워지는 게 정상입니다.

누수의 정의는 "메모리가 는다"가 아니라 **"풀 GC가 돈 뒤에도 기준선이 계속 오른다"** 입니다.

그래서 봐야 하는 건 그래프의 고점이 아니라 **골짜기**입니다. 골짜기가 평평하면 누수가 아니고, 골짜기가 우상향이면 누수입니다.

GC 로그로 직접 확인할 수 있습니다.

```bash
node --trace-gc dist/server.js
```

출력에서 `Scavenge`는 신생 객체를 치우는 가벼운 수집이고, `Mark-Compact`가 구세대까지 훑는 무거운 수집입니다.

`Mark-Compact` 줄의 **직후 값**만 추려서 시간순으로 보면 됩니다. 이 값이 계단처럼 올라가면 살아남는 객체가 계속 쌓이고 있다는 뜻입니다.

> `--trace-gc`는 운영에서도 켤 수 있을 만큼 가볍지만, 수집마다 한 줄이 나오므로 로그 양이 늘어납니다. 로그 비용이 수집량에 비례한다는 점만 계산해두세요.

## 숫자를 어디서 꺼내는가

추측을 줄이는 가장 빠른 방법은 프로세스가 자기 상태를 주기적으로 기록하게 만드는 것입니다.

```typescript
import v8 from 'node:v8';

const mb = (n: number) => Math.round(n / 1024 / 1024);

setInterval(() => {
  const m = process.memoryUsage();
  const h = v8.getHeapStatistics();

  console.log(
    JSON.stringify({
      evt: 'mem',
      rss: mb(m.rss),                   // 프로세스 전체 (커널이 보는 값에 가깝다)
      heapUsed: mb(m.heapUsed),         // JS 힙에서 실제로 쓰는 양
      heapTotal: mb(m.heapTotal),       // V8이 확보해둔 힙
      external: mb(m.external),         // 힙 밖 네이티브 할당 (Buffer 등)
      arrayBuffers: mb(m.arrayBuffers), // 그중 ArrayBuffer 몫
      heapLimit: mb(h.heap_size_limit), // V8이 생각하는 상한
      detached: h.number_of_detached_contexts,
    }),
  );
}, 30_000).unref();
```

여기서 필드 네 개의 관계가 진단의 뼈대입니다.

- `heapUsed`가 오르고 `heapLimit`에 접근한다 → JS 객체 누수. 스냅샷으로 갑니다.
- `heapUsed`는 평평한데 `rss`만 오른다 → 힙 바깥입니다. 스냅샷을 떠도 아무것도 안 보입니다.
- `external` / `arrayBuffers`가 오른다 → `Buffer`나 스트림 쪽입니다.
- `number_of_detached_contexts`가 0이 아니고 늘어난다 → 떼어낸 컨텍스트가 회수되지 않고 있습니다.

컨테이너 쪽 숫자는 cgroup에서 직접 읽습니다. 애플리케이션이 보는 값과 커널이 판단하는 값이 다르기 때문입니다.

```bash
# cgroup v2
cat /sys/fs/cgroup/memory.max        # 한도
cat /sys/fs/cgroup/memory.current    # 현재 사용량 (파일 캐시 포함)
cat /sys/fs/cgroup/memory.events     # oom, oom_kill 횟수
grep -E '^(anon|file) ' /sys/fs/cgroup/memory.stat

# cgroup v1
cat /sys/fs/cgroup/memory/memory.limit_in_bytes
cat /sys/fs/cgroup/memory/memory.max_usage_in_bytes   # 고점이 남아 있다
cat /sys/fs/cgroup/memory/memory.failcnt
```

`memory.current`에는 **파일 캐시가 같이 들어갑니다.** 그래서 이 값이 `rss`보다 훨씬 클 수 있고, 그걸 누수로 읽으면 엉뚱한 곳을 파게 됩니다.

파일 캐시는 대체로 압력이 오면 회수되므로 그 자체가 OOM의 원인은 아닙니다. 비교할 때는 `memory.stat`의 `anon`과 프로세스 `rss`를 맞춰 보세요.

v1에서 `max_usage_in_bytes`는 특히 유용합니다. **이미 지나간 고점**을 들고 있으니, 재시작된 컨테이너에서 사후에 "얼마까지 올라갔었나"를 알 수 있습니다.

## 런타임의 한도와 컨테이너의 한도

로그가 없는 재시작의 가장 흔한 원인은 누수 자체가 아니라 **두 한도의 순서**입니다.

V8의 힙 상한은 명시하지 않으면 런타임이 보는 메모리 총량에서 유도됩니다. 그런데 컨테이너 안에서 런타임이 보는 총량이 cgroup 한도가 아닐 수 있습니다.

그러면 이런 상태가 됩니다. 컨테이너 한도는 512MB인데 V8은 자기 힙을 몇 GB까지 써도 된다고 믿습니다.

힙이 자랄 때 V8은 한도가 멀다고 보고 **전면 수집을 서두르지 않습니다.** 그 사이 RSS가 512MB를 넘고, 커널이 먼저 손을 씁니다. 그래서 V8의 OOM 메시지를 볼 기회가 아예 없습니다.

실제 값은 추측하지 말고 컨테이너 안에서 직접 확인하세요.

```bash
# 컨테이너 안에서
node -e 'console.log(require("v8").getHeapStatistics().heap_size_limit / 1024 / 1024, "MB")'
cat /sys/fs/cgroup/memory.max
```

두 값을 본 뒤에 할 일은 **힙 한도를 컨테이너 한도보다 낮게 못 박는 것**입니다.

```yaml
# 컨테이너 한도 512Mi, 힙은 그보다 낮게
env:
  - name: NODE_OPTIONS
    value: "--max-old-space-size=384"
resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "512Mi"
```

이렇게 하면 죽는 방식이 바뀝니다. V8이 먼저 한도에 닿아 **오류 메시지를 남기고** 죽으므로, 다음 조사가 로그에서 시작됩니다.

여유를 얼마나 둘지는 힙 바깥이 얼마나 되는지에 달려 있습니다. 힙 외에 코드·스택·네이티브 할당·`Buffer`가 다 RSS에 들어가므로, 한도 전부를 힙에 주면 그만큼 다시 커널 쪽에서 터집니다.

> 최근 런타임에는 상한을 비율로 지정하는 옵션도 있습니다. 다만 그 비율의 기준이 되는 "사용 가능한 메모리"를 런타임이 어떻게 계산하는지가 버전과 환경에 따라 다릅니다. 쓰려면 반드시 컨테이너 안에서 결과 값을 찍어 확인하세요.

메모리 리퀘스트와 리밋을 같게 두는 것도 같은 이유입니다. 메모리는 압축할 수 없는 자원이라, 리밋만 크게 열어두면 노드가 압박을 받는 순간 축출 대상이 됩니다.

## 힙 바깥에서 새는 경우

`heapUsed`는 평평한데 `rss`만 오른다면 스냅샷은 시간 낭비입니다. 힙에 없는 걸 힙에서 찾는 셈이니까요.

후보는 대체로 셋입니다.

첫째, **`Buffer`와 스트림**입니다. `external`과 `arrayBuffers`가 같이 오르면 여기입니다. 응답을 통째로 버퍼에 담거나, 스트림을 소비하지 않은 채로 붙들고 있으면 이렇게 됩니다.

둘째, **네이티브 애드온**입니다. 이미지 처리, 압축, 암호화 라이브러리가 자기 메모리를 직접 잡으면 JS 힙에는 작은 핸들만 남습니다.

셋째, **할당기 단편화**입니다. 큰 버퍼를 잡았다 놨다 반복하면 프로세스가 반납하지 않고 들고 있는 영역이 생깁니다. 이건 누수가 아니라 고점이 유지되는 현상인데, cgroup 한도 앞에서는 결과가 같습니다.

진단 순서는 간단합니다. `external`이 같이 오르면 애플리케이션 코드의 버퍼 경로를, `external`도 평평한데 `rss`만 오르면 네이티브 쪽을 봅니다.

```typescript
// 흔한 자리: 외부 응답을 전부 메모리에 담는다
const res = await fetch(url);
const buf = Buffer.from(await res.arrayBuffer());   // 크기에 상한이 없다
await s3.send(new PutObjectCommand({ Bucket, Key, Body: buf }));
```

여기서 문제는 한 건의 크기가 아니라 **동시에 몇 건이 이 코드를 지나는지**입니다. 100MB 응답 하나는 괜찮고, 동시에 열 건이면 1GB입니다.

스트림으로 바꿔 흘려보내거나, 동시 실행 수를 세마포어로 묶는 게 답입니다. 둘 중 하나는 반드시 해야 합니다.

## 운영에서 스냅샷을 뜨고 비교하기

JS 힙 쪽이 확실해졌다면 힙 스냅샷이 가장 확실한 도구입니다. 다만 공짜가 아닙니다.

스냅샷을 뜨는 동안 **프로세스는 멈춥니다.** 그리고 결과 파일은 힙 크기에 비례해서, 수 MB 힙에서도 수 MB짜리 파일이 나옵니다.

그래서 운영에서는 "필요할 때만" 뜰 수 있게 신호로 묶어둡니다.

```bash
# SIGUSR2 를 받으면 현재 작업 디렉터리에 스냅샷을 쓴다
node --heapsnapshot-signal=SIGUSR2 dist/server.js
```

`SIGUSR1`은 런타임이 인스펙터용으로 예약하고 있으니 `SIGUSR2`를 씁니다. 코드에서 직접 제어하고 싶다면 API를 써도 됩니다.

```typescript
import v8 from 'node:v8';

process.on('SIGUSR2', () => {
  const path = v8.writeHeapSnapshot(`/tmp/heap-${Date.now()}.heapsnapshot`);
  console.log(JSON.stringify({ evt: 'heapsnapshot', path }));
});
```

> 스냅샷 파일에는 힙에 살아 있는 **문자열이 그대로** 들어갑니다. 토큰, 개인정보, 요청 본문이 포함될 수 있으니 저장 위치와 반출 경로를 로그와 같은 수준으로 다뤄야 합니다.

죽기 직전 상태가 필요하면 힙 한도에 근접할 때 자동으로 뜨게 하는 옵션도 있습니다.

```bash
node --heapsnapshot-near-heap-limit=2 dist/server.js
```

횟수를 제한하는 인자가 붙어 있는 이유가 있습니다. 한도 근처에서는 같은 상황이 반복되기 쉽고, 그때마다 멈추면서 큰 파일을 쓰면 **스냅샷 자체가 장애를 길게 만듭니다.** 1~2로 두세요.

### 두 장을 비교한다

한 장만 보면 "무엇이 많다"까지만 알 수 있고, 많은 것이 원래 많은 것인지 알 수 없습니다.

그래서 **간격을 두고 두 장**을 뜹니다. 기동 후 안정화된 시점에 한 장, 메모리가 눈에 띄게 오른 뒤에 한 장.

두 파일을 브라우저 개발자 도구의 메모리 탭에 올리고 비교 보기로 전환하면, 그 사이에 생겨서 **아직 살아 있는 객체**만 남습니다. 여기서 볼 건 두 가지입니다.

하나는 얕은 크기가 아니라 **유지 크기(retained size)** 입니다. 객체 자신은 작아도 그것 때문에 회수되지 못하는 양이 크면 그게 범인입니다.

다른 하나는 **유지 경로(retainer)** 입니다. "누가 이걸 붙들고 있는가"를 따라가면 대개 모듈 스코프의 전역 객체나 이벤트 이미터에 닿습니다. 거기가 고칠 자리입니다.

## 새는 코드 패턴

스냅샷에서 찾게 되는 유지 경로는 결국 몇 가지로 수렴합니다.

### 상한 없는 캐시

제일 흔합니다. 요청 단위 키로 결과를 저장하면서 꺼내는 쪽이 없으면, 그 `Map`은 캐시가 아니라 로그입니다.

```typescript
// 새는 쪽: 키 종류가 사용자 수만큼 늘어난다
const cache = new Map<string, Profile>();

export async function getProfile(id: string) {
  const hit = cache.get(id);
  if (hit) return hit;
  const row = await repo.findProfile(id);
  cache.set(id, row);     // 지우는 코드가 없다
  return row;
}
```

캐시는 **개수나 바이트 상한, 그리고 TTL** 중 적어도 하나를 가져야 합니다. 직접 구현하기보다 LRU 구현체를 쓰는 편이 안전합니다.

`WeakMap`으로 해결되는 경우는 생각보다 좁습니다. 키가 객체일 때만 쓸 수 있고, 위 예시처럼 키가 문자열이면 아예 선택지가 아닙니다.

### 쌓이는 리스너

요청을 처리하는 경로에서 모듈 스코프 이미터에 리스너를 붙이면, 요청 수만큼 리스너가 쌓입니다.

리스너는 클로저로 요청 컨텍스트를 붙들고 있으니, 리스너 하나가 붙드는 양이 작지 않습니다.

런타임이 경고를 띄워주는 게 이 경우입니다.

```text
MaxListenersExceededWarning: Possible EventEmitter memory leak detected.
11 x listeners added to [EventEmitter]. MaxListeners is 10.
```

이 경고를 `setMaxListeners`로 올려서 끄는 건 대개 틀린 대응입니다. 정당하게 리스너가 많이 필요한 구조가 아니라면, **떼는 코드가 없는 것**이 원인입니다.

```typescript
export function withProgress(job: Job, res: Response) {
  const onTick = (p: number) => res.write(`data: ${p}\n\n`);
  bus.on(`job:${job.id}`, onTick);

  // 성공·실패·중도 이탈 모두에서 떼야 한다
  res.on('close', () => bus.off(`job:${job.id}`, onTick));
}
```

`AbortSignal`을 받는 API라면 `{ signal }` 옵션으로 해제를 신호에 맡기는 쪽이 빠뜨릴 여지가 적습니다.

### 정리되지 않는 타이머

`setInterval`은 돌려놓은 쪽이 명시적으로 멈추지 않으면 영원히 살아 있고, 콜백이 참조하는 모든 것을 같이 살립니다.

요청이나 연결 단위로 타이머를 만드는 코드라면 해제 경로가 **모든 종료 분기**에 있어야 합니다.

```typescript
const timer = setInterval(() => ping(conn), 10_000);
try {
  await handle(conn);
} finally {
  clearInterval(timer);   // 예외로 빠져나가도 멈춘다
}
```

프로세스 수준 타이머에는 `unref()`를 붙여둡니다. 종료를 막지 않게 하는 것이고, 종료가 막히면 배포 때 강제 종료로 이어집니다.

### 끝나지 않는 프로미스

`await` 중인 프로미스는 그 호출 프레임의 지역 변수를 전부 붙들고 있습니다. 타임아웃이 없는 외부 호출이 섞여 있으면, 응답을 영원히 기다리는 요청들이 메모리에 그대로 남습니다.

이건 메모리 문제로 보이지만 뿌리는 타임아웃 문제입니다. 모든 외부 호출에 상한을 두는 게 선행 조건입니다.

## 누수가 아닌 경우

마지막으로, 고치려 들면 안 되는 경우를 가려야 합니다. 여기서 오진하면 코드만 복잡해지고 재시작은 계속됩니다.

**동시성 고점.** 요청 하나가 쓰는 메모리 × 동시 처리 수가 한도를 넘는 구조입니다. 누수가 없어도 트래픽이 몰리면 죽습니다. 고칠 자리는 코드가 아니라 동시 실행 수와 한도입니다.

**원래 그만큼 필요한 작업.** 큰 파일 파싱이나 집계처럼 고점이 높은 작업이 있으면, 그 작업을 요청 경로에서 떼어내 별도 워커로 보내는 게 맞습니다. 리밋을 그 작업 기준으로 잡으면 평시 자원이 전부 낭비됩니다.

**한도를 올리는 게 답인 경우.** 기준선이 평평한데 고점이 한도에 닿는다면, 한도가 작은 겁니다. 이때 코드를 뜯는 건 시간 낭비입니다.

구분 기준은 앞에서 본 것과 같습니다. **GC 후 기준선이 평평하면 누수가 아닙니다.** 기준선과 고점 중 무엇이 한도에 닿는지를 먼저 보세요.

## 체크리스트

- [ ] 재시작이 V8 힙 OOM인지 커널 OOMKill인지 **종료 코드로 확인**했는가
- [ ] 고점이 아니라 **풀 GC 직후 기준선**을 보고 누수 여부를 판단했는가
- [ ] `rss`·`heapUsed`·`external`을 같이 기록해, 힙 안인지 밖인지 갈랐는가
- [ ] 컨테이너 안에서 `heap_size_limit`과 cgroup 한도를 **둘 다 찍어** 비교했는가
- [ ] 힙 상한을 컨테이너 한도보다 낮게 명시해, 죽을 때 로그가 남게 했는가
- [ ] 메모리 리퀘스트와 리밋을 같게 두었는가
- [ ] 스냅샷을 신호로 뜰 수 있게 해두고, 저장 위치를 민감정보 기준으로 다루는가
- [ ] 캐시마다 개수·바이트 상한이나 TTL 중 하나가 있는가
- [ ] 리스너·타이머 해제가 예외·중도 이탈 분기에도 있는가
- [ ] 외부 호출 전부에 타임아웃이 있는가
- [ ] 동시 처리 수 × 요청당 메모리가 한도 안에 들어오는가

순서 하나만 덧붙입니다. **측정 지점을 붙이는 게 코드를 고치는 것보다 먼저입니다.**

메모리 누수는 추측으로 고쳐도 한동안 고쳐진 것처럼 보입니다. 재현에 며칠이 걸리니까요. 기준선 그래프와 종료 코드가 남아 있지 않으면, 다음에 같은 증상이 왔을 때 또 처음부터 시작하게 됩니다.
