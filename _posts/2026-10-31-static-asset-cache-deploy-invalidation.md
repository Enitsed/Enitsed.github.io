파이프라인은 초록불이고 헬스체크도 통과했습니다. 그런데 제보가 두 갈래로 옵니다.

한쪽은 "바뀐 게 하나도 안 보인다"고 하고, 다른 한쪽은 "새로고침했더니 화면이 하얗게 떴다"고 합니다.
정반대로 들리지만 원인은 같습니다. 성격이 다른 두 종류의 파일을 한 가지 캐시 규칙으로 내보내고 있는 것입니다.

## 두 파일은 수명이 다르다

번들러가 만드는 산출물은 파일명에 내용 해시가 붙습니다. 내용이 바뀌면 이름이 같이 바뀝니다.
그래서 이 파일은 **한 번 받으면 다시 확인할 이유가 없습니다.** 같은 이름이면 같은 내용이니까요.

반면 엔트리 HTML은 이름이 고정입니다. 하는 일은 "지금 쓸 자산의 이름 목록"을 알려주는 것뿐입니다.
이 파일을 캐시하면 **옛 목록을 들고 있는 상태**가 됩니다. 새 자산이 서버에 올라와 있어도 그 이름을 모르니 요청하지 않습니다.

두 파일에 같은 `Cache-Control`을 주면 어느 쪽을 택해도 하나는 틀립니다.

| | HTML + 자산 모두 짧게 | 모두 길게 | 계층을 나눠서 |
| --- | --- | --- | --- |
| 배포 반영 | 빠름 | 안 됨 | 빠름 |
| 재방문 요청 수 | 매번 전부 재검증 | 거의 없음 | HTML 한 건만 |
| 오리진 부하 | 높음 | 낮음 | 낮음 |
| 설정 복잡도 | 낮음 | 낮음 | 경로별 규칙 필요 |

세 번째 칸만 양쪽을 동시에 만족합니다. 그래서 규칙은 하나가 아니라 두 개여야 합니다.

- 해시가 붙은 자산: 아주 길게, 재검증 없이
- 엔트리 HTML: 저장은 하되 **쓸 때마다 검증**

## no-cache는 캐시하지 말라는 뜻이 아니다

이름 때문에 가장 많이 틀리는 지점입니다. HTML에 `no-store`를 걸어놓고 "캐시를 껐다"고 생각하는 설정을 자주 봅니다.

- `no-cache`: **저장해도 된다.** 다만 재사용하기 전에 오리진에 물어봐야 한다.
- `no-store`: 저장 자체를 금지한다. 디스크에도 메모리에도 남기지 않는다.

둘의 차이는 조건부 요청에서 드러납니다. `no-cache`면 브라우저가 가진 사본의 `ETag`를 `If-None-Match`에 담아 보내고,
내용이 같으면 서버는 **본문 없이 `304`만** 돌려줍니다. 왕복 한 번은 남지만 바이트는 거의 들지 않습니다.

`no-store`는 이 최적화를 통째로 버립니다. 매번 전체 본문을 다시 받습니다.
HTML을 항상 최신으로 유지하고 싶은 것이지, 매번 전부 다시 받고 싶은 건 아니라면 `no-cache`가 맞습니다.

> `no-store`가 필요한 자리는 따로 있습니다. 토큰이 담긴 응답이나 개인정보가 들어간 문서처럼 **디스크에 남는 것 자체가 문제**인 경우입니다. 배포 반영을 빠르게 하려는 목적이라면 `no-store`는 과한 선택입니다.

```nginx
# 엔트리 HTML: 저장은 허용, 사용 전 검증
location = /index.html {
  add_header Cache-Control "no-cache";
}

# 해시가 붙은 자산: 길게, 재검증 생략
location /assets/ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}
```

## immutable은 전제가 깨지면 되돌릴 수 없다

`max-age`만 길게 주면 한 가지가 남습니다. 사용자가 새로고침을 누르면 브라우저는 유효기간이 남은 사본에도 재검증 요청을 보냅니다.
`immutable`은 "이 응답은 유효기간 안에 바뀌지 않는다"는 선언이라, 그 재검증까지 생략하게 하는 신호입니다.

전제는 하나입니다. **같은 URL이면 영원히 같은 내용.** 해시 파일명이 이 전제를 만들어줍니다.

전제가 성립하지 않는 파일에 붙이면 사고가 됩니다. `app.js`나 `logo.png`처럼 이름이 고정된 파일에 `immutable`과 1년을 같이 걸면,
그 파일을 한 번 받아간 브라우저는 **1년 동안 다시 묻지 않습니다.** 서버 설정을 고쳐도 이미 나간 응답은 회수할 방법이 없습니다.

> 경로 단위로 규칙을 거세요. 파일 확장자가 아니라 **해시가 붙는 디렉터리**를 기준으로 삼아야 안전합니다. `*.js`에 1년을 주는 규칙은 해시 없는 스크립트 하나가 추가되는 순간 깨집니다.

## 흰 화면은 자산을 지워서 생긴다

이쪽이 더 곤란한 쪽입니다.

사용자가 탭을 열어둔 채 배포가 나갑니다. 그 탭은 구 버전 HTML을 들고 있고, 거기 적힌 자산 이름도 구 버전입니다.
그 사용자가 아직 안 가본 화면으로 이동하면, 지연 로딩된 청크를 **그 시점에** 요청합니다.

배포가 이전 빌드 자산을 지웠다면 그 요청은 `404`입니다. 모듈 로드가 실패하고, 라우팅이 멈추고, 화면은 비어 버립니다.
서버 로그에는 애플리케이션 에러가 없습니다. 정적 파일 `404` 몇 건만 남습니다.

핵심은 **배포가 자산을 지운다는 것 자체**입니다. 해시 파일명은 공존할 수 있게 설계된 이름인데, 배포 스크립트가 그 전제를 깹니다.

### 지우지 말고 겹쳐 쌓는다

가장 효과가 큰 조치입니다. 자산은 이름이 겹치지 않으니 이전 빌드와 같이 두어도 충돌하지 않습니다.

```bash
# 자산: 기존 파일을 지우지 않고 더한다 (--delete 를 쓰지 않는다)
aws s3 sync ./dist/assets "s3://$BUCKET/assets" \
  --cache-control "public, max-age=31536000, immutable"
```

`--delete`를 빼는 것만으로 열어둔 탭이 깨지는 경로가 사라집니다.
롤백할 때도 같은 이유로 필요합니다. HTML을 이전 버전으로 되돌려도 그 HTML이 가리키는 자산이 아직 남아 있어야 합니다.

누적되는 용량은 스토리지 수명주기 규칙으로 정리합니다. 바로 지우지 않고, 사용자의 탭이 살아 있을 만한 기간을 지나고 나서 지우는 쪽입니다.
며칠치 정적 파일 용량과 배포 때마다 일부 사용자가 흰 화면을 보는 것 중 어느 쪽이 싼지는 계산해볼 필요도 없습니다.

### 그래도 실패하면 한 번만 새로고침

겹쳐 쌓아도 구멍은 남습니다. 수명주기로 지워진 아주 오래된 탭, 캐시가 꼬인 중간 프록시, 단순 네트워크 실패까지.
동적 `import()`는 실패하면 거부되는 프로미스이므로, 거기서 잡을 수 있습니다.

```typescript
const RELOAD_FLAG = "chunk-reload-once";

export async function loadRoute<T>(load: () => Promise<T>): Promise<T> {
  try {
    const mod = await load();
    sessionStorage.removeItem(RELOAD_FLAG);   // 성공했으면 표식을 거둔다
    return mod;
  } catch (err) {
    // 이미 한 번 새로고침해봤다면 더 하지 않는다
    if (sessionStorage.getItem(RELOAD_FLAG)) throw err;

    sessionStorage.setItem(RELOAD_FLAG, "1");
    location.reload();

    // reload 는 비동기라 아래로 흐르는 것을 막아야 한다
    return new Promise<T>(() => {});
  }
}
```

가드가 없으면 **무한 새로고침**이 됩니다. 자산이 정말로 없는 상황에서는 새로고침해도 또 실패하고, 또 새로고침합니다.
사용자 입장에서는 화면이 깜빡이기만 하고 아무것도 안 되는 상태라, 흰 화면보다 나쁩니다.

번들러에 따라 프리로드 실패를 알리는 전용 이벤트를 제공하는 경우가 있습니다. 있으면 그걸 쓰는 편이 더 정확하니 쓰는 도구의 문서를 확인하세요.

> 서비스 워커를 등록해 두었다면 여기를 먼저 보세요. 엔트리 문서를 캐시 우선으로 응답하는 워커는 서버 설정과 무관하게 옛 HTML을 계속 내놓습니다. `Cache-Control`을 아무리 고쳐도 반영되지 않는다면 원인이 이쪽일 수 있습니다.

## 올리는 순서가 정해져 있다

자산을 먼저, HTML을 나중에 올립니다.

반대로 하면 새 HTML이 **아직 존재하지 않는 자산**을 가리키는 창이 생깁니다. 그 사이에 들어온 사용자는 전부 흰 화면입니다.
창이 몇 초라도 배포마다 반복되면 결국 누군가는 겪습니다.

```bash
set -euo pipefail

# 1) 자산 먼저. 길게 캐시하고, 기존 것은 남긴다
aws s3 sync ./dist/assets "s3://$BUCKET/assets" \
  --cache-control "public, max-age=31536000, immutable"

# 2) HTML 나중. 매번 검증하게 한다
aws s3 sync ./dist "s3://$BUCKET" \
  --exclude "assets/*" \
  --cache-control "no-cache"
```

`--exclude "assets/*"`를 빼먹으면 두 번째 명령이 자산까지 다시 올리면서 `no-cache`로 덮어씁니다.
한 번 덮이면 그 뒤로 자산마다 재검증 요청이 붙기 시작하는데, 기능은 멀쩡하니 눈치채기 어렵습니다.

## 무효화는 HTML만

CDN을 끼우면 캐시 계층이 하나 더 생깁니다. 브라우저 캐시를 잡아놨어도 CDN 엣지가 옛 HTML을 들고 있으면 결과는 같습니다.

흔한 실수는 배포 끝에 `/*`를 무효화하는 것입니다. 편하지만 두 가지를 같이 버립니다.

- 해시 자산까지 전부 날아갑니다. **바뀌지도 않은 파일**을 다시 받게 만듭니다.
- 엣지 캐시가 비면서 그 직후 요청이 오리진으로 몰립니다. 배포 직후에 오리진 부하가 튀는 원인이 여기일 때가 많습니다.

무효화가 필요한 건 이름이 고정된 파일뿐입니다.

```bash
aws cloudfront create-invalidation \
  --distribution-id "$DISTRIBUTION_ID" \
  --paths "/" "/index.html"
```

무효화는 요청 경로 수를 기준으로 과금되는 항목이 있으니, 배포마다 전체를 날리는 습관은 비용으로도 돌아옵니다. 현재 기준은 공식 요금 문서를 확인하세요.

더 나은 방향은 무효화에 의존하지 않는 것입니다. HTML에 대해 엣지 TTL을 짧게 두고 오리진 검증을 거치게 설정하면,
배포 때 별도 조작 없이도 다음 요청에서 새 HTML이 내려갑니다. 무효화는 사고 대응 수단으로 남겨두는 쪽이 운영하기 편합니다.

## API 응답은 전제가 다르다

여기서부터는 틀렸을 때의 결과가 성격이 다릅니다. 화면이 안 바뀌는 것과 **남의 데이터가 보이는 것**은 같은 급의 문제가 아닙니다.

CDN은 공유 캐시입니다. 사용자 A의 응답을 저장해두고 사용자 B에게 줄 수 있다는 뜻입니다.
그래서 로그인한 사용자별로 달라지는 응답에 `public`을 붙이면 안 됩니다.

```typescript
// 개인화·인증된 응답
res.setHeader("Cache-Control", "private, no-store");

// 모두에게 같은 공개 데이터 (공지, 약관, 코드 테이블 등)
res.setHeader("Cache-Control", "public, max-age=60");
```

`private`은 "최종 사용자 캐시에만 저장하라"는 지시입니다. 중간 공유 캐시는 저장하지 않아야 합니다.

"`Vary: Authorization`을 붙이면 되지 않나"는 생각이 들 수 있는데, 거기 기대는 건 위험합니다.
`Vary` 처리는 CDN마다 다르고, 어떤 값까지 실제로 반영되는지도 제품과 시점에 따라 갈립니다.

믿을 수 있는 방법은 **CDN의 캐시 키 설정에 그 헤더를 명시적으로 포함시키는 것**입니다. CloudFront라면 캐시 정책에서 캐시 키에 넣을 헤더·쿠키·쿼리 문자열을 직접 지정합니다.
쓰는 CDN의 캐시 키 문서를 보고 설정으로 못 박아두세요. 응답 헤더 하나로 해결된 것처럼 보이는 상태가 가장 위험합니다.

> 더 단순한 방어선도 있습니다. 인증이 필요한 경로는 CDN 캐시 동작에서 아예 제외하는 것입니다. 성능을 조금 포기하고 사고 가능성을 지우는 거래인데, 대개 이쪽이 맞습니다.

## 지금 무엇이 나가고 있는지 보는 법

설정은 고쳤다고 끝나지 않습니다. 실제로 그 헤더가 나가는지는 확인해야 아는 일입니다.

```bash
# HTML: no-cache 가 붙었는지
curl -sI "https://$HOST/" | grep -iE 'cache-control|etag|x-cache|age'

# 자산: immutable 과 긴 max-age 가 붙었는지
curl -sI "https://$HOST/assets/index-abc123.js" | grep -iE 'cache-control|x-cache|age'
```

`x-cache`는 엣지에서 적중했는지, `Age`는 엣지가 그 응답을 들고 있던 시간입니다.
HTML의 `Age`가 계속 커진다면 엣지가 옛 HTML을 붙들고 있다는 뜻이고, 배포 반영이 안 보이는 이유가 거기입니다.

조건부 요청이 실제로 `304`로 끝나는지도 한 번 봐둘 만합니다.

```bash
ETAG=$(curl -sI "https://$HOST/" | awk -F': ' 'tolower($1)=="etag"{print $2}' | tr -d '\r')
curl -s -o /dev/null -w '%{http_code}\n' -H "If-None-Match: $ETAG" "https://$HOST/"
```

`304`가 나오면 HTML 재검증이 바이트를 거의 쓰지 않고 돌아가는 상태입니다. `200`이 계속 나오면 매번 전체를 다시 받고 있다는 뜻이니,
`no-store`가 걸려 있거나 응답마다 `ETag`가 달라지고 있는지 확인해보세요.

이전 빌드 자산이 아직 살아 있는지도 배포 후에 확인해두면 좋습니다. 수명주기 규칙이 생각보다 공격적으로 돌고 있는 경우가 있습니다.

## 체크리스트

- 해시 자산과 엔트리 HTML에 서로 다른 `Cache-Control`이 나가는가
- `immutable`이 붙은 경로에 해시 없는 파일이 섞여 있지 않은가
- 배포가 이전 빌드 자산을 지우고 있지 않은가 (`--delete` 여부)
- 자산을 HTML보다 먼저 올리는가
- 동적 import 실패에 새로고침 가드가 있는가
- 무효화 대상이 이름 고정 파일로 좁혀져 있는가
- 개인화 응답이 공유 캐시에 저장될 수 있는 설정은 아닌가
- 인증 관련 헤더가 CDN 캐시 키에 설정으로 포함돼 있는가
