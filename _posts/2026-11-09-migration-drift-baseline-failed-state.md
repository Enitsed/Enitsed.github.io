로컬에서 수십 번 돌린 마이그레이션이 운영에서 한 번 멈추면, 그때부터는 도구가 도와주지 않습니다.
다음 배포는 "이력이 깨졌다"며 아무것도 적용하지 않고, 되돌리는 명령도 없습니다.

손으로 고친 뒤 도구에게 "이건 됐다고 쳐라"라고 알려주는 게 유일한 복구 경로입니다.
그 한 줄을 잘못 고르면 다음 배포가 같은 DDL을 한 번 더 돌립니다.

## 도구가 믿고 있는 한 가지

마이그레이션 도구는 두 개를 들고 있습니다. 저장소의 **이력 파일**과, DB 안의 **적용 기록 테이블**입니다.

```text
repo                        database
────────────────────        ──────────────────────────
migrations/
  20260801_init/            _prisma_migrations
  20260903_add_column/        ├ 20260801_init     (완료)
  20260914_add_index/         ├ 20260903_add_col  (완료)
                              └ 20260914_add_idx  (완료)
                            실제 스키마  ← 여기가 일치한다는 전제
```

도구의 추론은 단순합니다. *기록에 남은 파일을 순서대로 다 돌렸으니, 실제 스키마는 이력의 마지막 상태와 같다.*

**드리프트(drift)는 이 전제가 깨진 상태입니다.** 기록은 전부 완료인데 실제 스키마가 다릅니다.

| 상태 | 기록 테이블 | 실제 스키마 | 도구가 보는 것 |
| --- | --- | --- | --- |
| 정상 | 이력 전부 완료 | 이력의 마지막 상태 | 적용할 게 없다 |
| 미적용 | 일부만 완료 | 완료된 것까지 | 남은 것을 적용 |
| 드리프트 | 전부 완료 | 이력과 다름 | **적용할 게 없다** (문제를 모름) |
| 실패 | 완료 표시가 없는 행 | 반쯤 적용 | **멈춤** (앞으로 못 감) |

세 번째 줄이 조용히 위험합니다. 도구는 할 일이 없다고 판단하고, 다음에 추가하는 마이그레이션이 없는 컬럼을 참조하거나 이미 있는 인덱스를 또 만들다가 거기서 터집니다.
**드리프트는 발생한 시점이 아니라, 그 위에 뭔가를 더 쌓는 시점에 드러납니다.**

## dev 명령과 deploy 명령은 같은 일을 하지 않는다

이름이 비슷해서 섞어 쓰기 쉬운데, 사실 용도가 반대입니다.

| | 개발용 (`migrate dev`) | 운영용 (`migrate deploy`) |
| --- | --- | --- |
| 하는 일 | 스키마 차이로 파일 생성 + 적용 | 기록에 없는 파일만 적용 |
| 섀도 DB | 사용 | 사용하지 않음 |
| 드리프트 감지 | 감지함 | **감지하지 않음** |
| 리셋 | 상황에 따라 제안 | 하지 않음 |

**섀도 DB**는 개발용 명령이 쓰는 임시 데이터베이스입니다. 이력 파일을 빈 DB에 처음부터 다시 돌려서 "이력대로라면 이런 스키마가 나온다"를 만들고, 그걸 지금 붙어 있는 DB와 비교합니다.
그래서 개발용 명령은 드리프트를 잡아낼 수 있습니다. 비교 대상을 직접 만들어 보기 때문입니다.

운영용 명령은 섀도 DB를 쓰지 않습니다. 운영 DB 옆에 임시 DB를 만들 권한도 보통 없고, 운영 중에 전체 이력을 재생할 여유도 없습니다.
대신 **기록 테이블만 보고 미적용분을 적용합니다.** 그래서 드리프트가 있어도 그냥 통과합니다.

> 운영 DB를 대상으로 개발용 명령을 돌리지 마세요. 드리프트나 이력 불일치를 발견하면 **리셋을 제안하는 경로**가 있고, 그건 데이터를 지우겠다는 뜻입니다.
> 접속 정보가 환경변수로 들어가는 구조라면, 로컬 셸에 운영 자격 증명이 남아 있는 것만으로 사고가 가능합니다.

운영 자격 증명으로는 적용·상태 확인·정리 명령만 돌 수 있게 묶어두는 편이 안전합니다.

```json
{
  "scripts": {
    "db:dev":    "prisma migrate dev",
    "db:deploy": "prisma migrate deploy",
    "db:status": "prisma migrate status"
  }
}
```

> 명령 이름과 설정 파일의 위치는 메이저 버전에서 바뀝니다. 이 글은 구조를 설명하는 쪽이고, 플래그와 설정 형식은 쓰는 버전의 공식 문서에서 확인하세요.

## 드리프트는 어디서 생기는가

운영에서 드리프트를 만드는 경로는 대체로 정해져 있습니다.

- **급해서 손으로 고친 것.** 장애 중에 콘솔에서 인덱스를 하나 추가하고, 그 뒤 저장소에 반영하지 않은 경우.
- **도구 밖에서 돌린 스키마 변경.** 큰 테이블을 `gh-ost` 같은 외부 도구로 바꿨는데 기록을 남기지 않은 경우.
- **스냅샷 복원.** [과거 시점으로 복원](/blog/db-backup-restore-pitr-drill/)하면 스키마와 기록 테이블이 **동시에** 그 시점으로 돌아갑니다. 복원 이후에 적용했던 마이그레이션이 기록에서도 사라지므로, 이건 오히려 다시 적용하면 맞습니다. 문제는 복원 시점을 착각할 때입니다.
- **같은 이력을 여러 DB가 공유.** 스테이징에서만 손으로 고친 변경이 쌓이면, 스테이징이 운영과 다른 모양이 되어 리허설의 의미가 사라집니다.

첫 번째를 완전히 막기는 어렵습니다. 장애 중에 저장소 커밋부터 하라고 할 수는 없으니까요.
그래서 막는 대신 **남기게** 만듭니다. 손으로 DDL을 돌렸다면 그 직후 할 일은 같은 내용의 마이그레이션 파일을 만들고, 적용하지 않은 채 적용됐다고 기록하는 것입니다.

```bash
# 1. 손으로 돌린 DDL과 같은 내용의 파일을 만든다 (적용은 하지 않는다)
npx prisma migrate dev --create-only --name add_orders_paid_at_index

# 2. 운영에는 이미 적용돼 있으므로, 돌리지 않고 기록만 남긴다
npx prisma migrate resolve --applied 20261109120000_add_orders_paid_at_index
```

이걸 해두지 않으면 다음 배포에서 같은 인덱스를 또 만들다 실패하고, 그러면 아래의 "멈춘 상태"로 넘어갑니다.

## 멈춘 이력을 무엇으로 정리할 것인가

마이그레이션이 도중에 실패하면 기록 테이블에 **시작은 했지만 완료 표시가 없는 행**이 남습니다.
이 행이 있는 동안 적용 명령은 아무것도 하지 않습니다. 이력이 어디까지 진행된 상태인지 도구가 판단할 수 없기 때문입니다.

먼저 상태를 봅니다.

```bash
npx prisma migrate status
```

복구 수단은 두 개뿐이고, 둘은 **반대 방향**입니다.

| 명령 | 뜻 | 다음 배포에서 |
| --- | --- | --- |
| `resolve --rolled-back <name>` | 이 마이그레이션은 **적용되지 않았다** | 같은 파일을 **다시 돌린다** |
| `resolve --applied <name>` | 이 마이그레이션은 **적용 완료다** | 건너뛴다 |

고르는 기준은 하나입니다. **실패한 마이그레이션이 DB에 흔적을 남겼는가.**

```bash
# 흔적이 전혀 없다 → 다시 돌리면 된다
npx prisma migrate resolve --rolled-back 20261109120000_add_settled_at

# 남은 부분을 손으로 끝냈다 → 완료로 기록하고 넘어간다
npx prisma migrate resolve --applied 20261109120000_add_settled_at
```

그리고 이 질문의 답은 **DB 엔진이 DDL을 트랜잭션으로 감싸주는지**에 달려 있습니다.

PostgreSQL은 DDL이 트랜잭션 안에서 롤백됩니다. 한 파일을 트랜잭션으로 묶어 돌렸다면 실패 시 전부 되돌아가고, 그러면 `--rolled-back` 쪽이 맞습니다.

MySQL은 그렇지 않습니다. `ALTER TABLE`은 커밋 지점처럼 동작해서, **파일 안의 세 번째 문장이 실패해도 앞의 두 문장은 그대로 남습니다.**

```sql
-- 한 파일에 세 문장이 들어 있었다면
ALTER TABLE orders ADD COLUMN settled_at DATETIME(3) NULL;   -- 성공 (남는다)
ALTER TABLE orders ADD INDEX idx_settled_at (settled_at);    -- 성공 (남는다)
ALTER TABLE orders MODIFY status VARCHAR(20) NOT NULL;       -- 실패 ← 여기서 멈춤
```

여기서 `--rolled-back`을 고르면 다음 배포가 첫 문장부터 다시 돌리고, 이미 있는 컬럼을 또 추가하다 **같은 자리에서 또 멈춥니다.**
`--applied`를 고르면 세 번째 문장은 영원히 적용되지 않은 채 "완료"로 기록됩니다. 이게 드리프트의 교과서적인 발생 경로입니다.

정리하면 MySQL에서 여러 문장이 든 파일이 중간에 실패했을 때는, 둘 중 어느 쪽도 그냥 맞지 않습니다. **먼저 실제 스키마를 확인해서 어디까지 갔는지 확정해야 합니다.**

```sql
SHOW CREATE TABLE orders;

SELECT COLUMN_NAME, IS_NULLABLE, COLUMN_TYPE
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'orders';

SELECT INDEX_NAME, GROUP_CONCAT(COLUMN_NAME ORDER BY SEQ_IN_INDEX) AS cols
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'orders'
GROUP BY INDEX_NAME;
```

확인한 다음 남은 문장만 손으로 끝내고 `--applied`로 닫는 게 가장 예측 가능합니다.
도구가 파일 전체를 트랜잭션으로 감싸는지는 도구와 엔진 조합마다 다르니, 쓰는 조합의 동작을 한 번은 확인해두세요.

## 그래서 파일 하나에 문장 하나

위 문제는 복구를 잘해서 해결하는 게 아니라, **복구할 게 적게 만들어서** 피합니다.

파일 하나에 문장 하나면 실패 지점이 곧 파일 경계가 됩니다. 멈춘 파일만 보면 되고, 앞의 파일들은 완료 기록이 남아 있으니 다시 돌릴 걱정이 없습니다.

```text
migrations/
  20261109_120000_add_settled_at/      ← 완료
  20261109_120100_index_settled_at/    ← 완료
  20261109_120200_status_not_null/     ← 여기만 멈춤
```

세 문장을 한 파일에 넣어 아끼는 건 파일 두 개고, 잃는 건 실패 시의 판단 가능성입니다.

이 규칙은 **위험한 문장을 분리하는** 효과도 같이 냅니다. 위 예시에서 실제로 실패한 건 `NOT NULL` 제약이고, 기존 행에 `NULL`이 있으면 당연히 실패합니다.
그 문장이 따로 있으면 "값을 다 채운 뒤에 거는 문장"이라는 게 파일 이름에서 드러나고, 순서를 틀리기 어려워집니다.

넓힌 다음 좁히는 순서, 그리고 백필을 끊어서 돌리는 방법은 [운영 중인 큰 테이블에 컬럼 추가하기](/blog/mysql-online-schema-change/)에 적어뒀습니다.

## 기존 DB를 이력에 편입시키기

이미 돌고 있는 서비스에 마이그레이션 도구를 도입할 때는 출발점이 비어 있지 않습니다.
스키마는 있는데 기록 테이블은 없고, 그 상태로 적용 명령을 돌리면 도구가 **처음부터 다 만들려고** 합니다.

**베이스라인**은 "지금 상태를 첫 마이그레이션으로 선언하고, 그건 이미 적용된 것으로 치는" 작업입니다.

```bash
# 1. 현재 운영 스키마를 모델 정의로 가져온다
npx prisma db pull

# 2. 빈 DB → 현재 모델 차이를 첫 마이그레이션 파일로 뽑는다
mkdir -p prisma/migrations/0_init
npx prisma migrate diff \
  --from-empty \
  --to-schema-datamodel prisma/schema.prisma \
  --script > prisma/migrations/0_init/migration.sql

# 3. 돌리지 않고 적용됐다고 기록한다
npx prisma migrate resolve --applied 0_init
```

3번이 베이스라인의 핵심입니다. 파일은 생겼지만 **운영 DB에서는 실행되지 않습니다.**

여기서 두 가지를 확인해야 합니다.

첫째, 뽑아낸 파일이 실제 스키마와 같은가. 도구가 표현하지 못하는 것들 — 트리거, 저장 프로시저, 특정 제약, 생성 컬럼, 뷰 — 은 모델 정의로 역변환되지 않고 조용히 빠집니다.
운영에서는 그 자체로 문제가 되지 않지만(파일을 돌리지 않으니), **새로 만드는 환경에서는 그게 없는 DB가 생깁니다.** 로컬과 운영이 다른 모양이 되는 출발점입니다.

둘째, 베이스라인은 **모든 환경에서 같은 시점으로** 잡아야 합니다. 환경마다 다른 시점을 첫 마이그레이션으로 선언하면 그 차이가 영구적으로 남습니다.

## 큰 테이블은 도구 밖으로 보낸다

마이그레이션 도구가 생성하는 건 평범한 `ALTER TABLE`입니다. 수천만 행 테이블에서 이게 어떤 결과를 내는지는 별개의 문제고, 도구는 거기에 관여하지 않습니다.

그래서 큰 테이블의 변경은 **적용 자체를 도구 밖에서** 하는 선택지가 있습니다.

```bash
# 1. 파일만 만든다 (적용하지 않는다)
npx prisma migrate dev --create-only --name alter_orders_add_memo

# 2. 운영에서는 외부 도구로 적용한다
gh-ost \
  --database=app --table=orders \
  --alter="ADD COLUMN memo VARCHAR(255) NULL" \
  --execute

# 3. 적용됐다고 기록만 남긴다
npx prisma migrate resolve --applied 20261109130000_alter_orders_add_memo
```

대가가 있습니다. **저장소의 파일과 실제로 돌린 DDL이 같다는 보장이 사람에게 있습니다.** `--alter`에 적은 내용과 파일의 내용이 다르면 그 순간 드리프트가 생기고, 도구는 알 수 없습니다.

| | 도구가 적용 | 외부 도구로 적용 |
| --- | --- | --- |
| 락 시간 | 문장에 따름 | 짧게 유지 |
| 이력과 실제의 일치 | 도구가 보장 | 사람이 보장 |
| 절차 | 한 단계 | 세 단계, 수동 |

작은 테이블에 이걸 적용할 이유는 없습니다. **락이 실제로 문제가 되는 테이블에만** 쓰고, 그 테이블 목록을 따로 관리하는 편이 낫습니다.

## 파이프라인의 어디에서 돌리나

애플리케이션 시작 스크립트에 적용 명령을 넣는 구성을 흔히 보는데, 인스턴스가 두 대 이상이면 바로 문제가 됩니다.

여러 인스턴스가 동시에 뜨면서 같은 DB에 동시에 적용하려 하고, 도구는 보통 **DB 락으로 직렬화**합니다. 동시에 적용되지 않는다는 점에서는 안전하지만, 락을 기다리던 쪽이 타임아웃으로 죽으면 그 인스턴스는 기동에 실패합니다.
오토스케일링이 그 자리를 또 채우면서 같은 일이 반복되고, 배포 전체가 느려집니다.

마이그레이션은 **배포 전에 한 번만 도는 별도 단계**로 두는 게 맞습니다.

```yaml
# .gitlab-ci.yml
stages: [build, migrate, deploy]

migrate:
  stage: migrate
  image: node:22-alpine
  environment: production
  resource_group: production-db     # 같은 대상에 동시에 돌지 않게 한다
  script:
    - npm ci --omit=dev
    - npx prisma migrate status      # 적용 전 상태를 로그에 남긴다
    - npx prisma migrate deploy
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```

`resource_group`이 있으면 같은 그룹의 잡이 동시에 돌지 않습니다. 두 번 연달아 머지됐을 때 두 파이프라인이 같은 DB에 겹치는 걸 막아줍니다.

적용 전 상태를 로그에 남기는 것도 챙기면 좋습니다. 나중에 "어느 배포에서 꼬였나"를 추적할 때, 각 파이프라인에 그 시점의 이력 상태가 남아 있으면 범위가 금방 좁혀집니다.

그리고 이 단계가 실패하면 **배포를 멈춰야 합니다.** 스키마 변경이 안 된 상태로 새 코드가 올라가면 그 코드가 없는 컬럼을 참조합니다.
반대로 스키마만 적용되고 코드 배포가 실패하는 경우는 — 넓힌 다음 좁히는 순서를 지켰다면 — [구 버전 코드가 새 컬럼을 모른 채](/blog/api-backward-compatibility-versioning/) 계속 돌기만 하므로 문제가 되지 않습니다. **이 비대칭이 순서를 정하는 이유입니다.**

## 되돌리기는 사실상 없다

도구마다 역방향 마이그레이션을 지원하기도 하고 안 하기도 하는데, 운영에서는 어느 쪽이든 크게 다르지 않습니다.
스키마는 되돌릴 수 있지만 **데이터는 되돌아오지 않습니다.**

```sql
-- 적용: 컬럼을 지운다
ALTER TABLE orders DROP COLUMN legacy_memo;

-- 역방향: 컬럼은 돌아오지만 값은 돌아오지 않는다
ALTER TABLE orders ADD COLUMN legacy_memo VARCHAR(255) NULL;
```

그래서 운영의 기본 전략은 되돌리기가 아니라 **앞으로 고치기**입니다. 잘못 적용했으면 그걸 교정하는 마이그레이션을 새로 만들어 적용합니다.

이게 성립하려면 **데이터를 지우는 변경을 늦추는** 습관이 필요합니다.

- 컬럼을 지우기 전에, 코드가 그 컬럼을 참조하지 않는 상태로 한동안 돌려본다
- 이름을 바꿀 때는 `RENAME`이 아니라 새 컬럼 추가 → 양쪽 쓰기 → 읽기 이전 → 구 컬럼 제거
- 테이블 삭제는 이름을 바꿔두고 며칠 뒤에 지운다

파괴적인 변경을 감지해 경고하는 기능이 있는 도구라면 그 경고를 넘기는 습관부터 경계해야 합니다.
한 번 `--force` 류의 플래그로 넘기기 시작하면, 그 플래그가 스크립트에 남아 다음 사람에게는 경고가 아예 보이지 않습니다.

## 정리

- 도구는 기록 테이블과 실제 스키마가 같다고 전제한다. 드리프트는 발생 시점이 아니라 그 위에 뭘 더 쌓는 시점에 드러난다.
- 개발용 명령은 섀도 DB로 드리프트를 잡고, 운영용 명령은 잡지 않는다. 운영 DB에 개발용 명령을 돌리지 않게 스크립트로 묶어둔다.
- 손으로 DDL을 돌렸으면 같은 내용의 파일을 만들어 `--applied`로 기록을 맞춘다. 이 한 단계를 빼먹는 것이 드리프트의 주된 출처다.
- 멈춘 이력에서 `--rolled-back`과 `--applied`는 반대 방향이다. MySQL은 DDL이 롤백되지 않으므로, 고르기 전에 실제 스키마를 확인한다.
- 파일 하나에 문장 하나. 실패 지점이 파일 경계와 같아져서 판단할 게 줄어든다.
- 기존 DB는 베이스라인으로 편입시킨다. 역변환에서 빠지는 객체가 있는지, 모든 환경이 같은 시점인지 확인한다.
- 큰 테이블은 외부 도구로 적용하고 기록만 남길 수 있다. 대신 이력과 실제의 일치를 사람이 책임진다.
- 적용은 앱 기동이 아니라 배포 전 단독 단계에서. 동시 실행을 막고, 실패하면 배포를 멈춘다.
- 되돌리기는 스키마만 되돌린다. 데이터를 지우는 변경은 미루고, 앞으로 고치는 것을 기본으로 둔다.
