한 대로 돌릴 때는 완벽하게 동작했습니다. 두 대로 늘리자 같은 방에 있는 사람 중 절반만 메시지를 받습니다.

서버를 늘리면 처리량이 늘어나는 건 요청-응답에서만 참입니다.
연결을 들고 있는 서버에서는 대수를 늘리는 것 자체가 기능을 깨뜨립니다.

## 상태가 커넥션에 붙어 있다

HTTP 요청은 어느 인스턴스로 가도 상관없습니다. 상태는 DB와 캐시에 있고, 애플리케이션은 매 요청마다 그걸 다시 읽습니다.

WebSocket은 다릅니다. **"이 사용자에게 보낸다"는 행위가 특정 프로세스의 메모리에 있는 소켓 객체를 통해서만 가능합니다.**

```text
          ┌── 인스턴스 A ── 소켓: 유저1, 유저2
LB ───────┤
          └── 인스턴스 B ── 소켓: 유저3, 유저4

유저1이 글을 쓴다 → A가 처리 → A가 가진 소켓에만 전송
                                  → 유저3, 유저4는 모른다
```

로드밸런서는 연결을 나눠주지만 상태를 공유해주지는 않습니다.
그래서 수평 확장의 문제는 "부하를 어떻게 나누나"가 아니라 **"내가 들고 있지 않은 소켓에 어떻게 보내나"** 입니다.

조용히 나빠지는 쪽은 테스트 환경입니다. 로컬과 스테이징은 보통 한 대로 돌아가서 이 결함이 드러나지 않습니다.
운영에서 인스턴스가 두 대 이상일 때만 재현되고, 그마저도 "가끔 알림이 안 와요"라는 형태로 들어옵니다.

## 스티키 세션은 이 문제를 풀지 않는다

가장 먼저 떠오르는 답은 로드밸런서의 세션 고정입니다. 그런데 이게 푸는 문제는 따로 있습니다.

| | 스티키 세션 | pub/sub 팬아웃 |
| --- | --- | --- |
| 재연결 시 같은 인스턴스 | 대체로 보장 | 보장하지 않음 (필요 없음) |
| 다른 인스턴스의 사용자에게 전달 | **안 됨** | 됨 |
| 인스턴스가 빠질 때 | 그 인스턴스에 붙은 연결이 전부 끊김 | 동일 |
| 추가 구성요소 | 없음 | 메시지 버스 |

핸드셰이크는 HTTP 업그레이드 요청으로 시작하므로 쿠키 기반 고정이 걸립니다. 그래서 **재연결했을 때 같은 서버로 돌아가는 것**은 해결됩니다.

하지만 원래 문제는 그게 아닙니다. 같은 방에 있는 유저1과 유저3이 서로 다른 인스턴스에 붙어 있다는 사실은 고정으로 바뀌지 않습니다.
고정을 아무리 강하게 걸어도 **방 참여자들을 같은 인스턴스로 모아주지는 않습니다.**

스티키 세션이 실제로 필요한 경우는 연결 자체에 붙은 세션 상태(인증 후 협상 결과, 진행 중인 업로드)를 재연결 때 이어가야 할 때입니다.
그런 상태를 두지 않는 설계라면 고정 없이도 됩니다. [재연결 로직](/blog/websocket-reconnect/)이 새 인스턴스를 잡고 다시 구독하면 끝입니다.

## 인스턴스 사이로 메시지를 흘리기

구조는 단순합니다. 각 인스턴스는 **자기가 들고 있는 소켓만** 알고, 외부로 보낼 메시지는 전부 메시지 버스를 한 번 거칩니다.

```text
유저1이 글을 쓴다
   ↓
인스턴스 A ──publish(room:42)──▶ Redis
                                  │
            ┌─────────────────────┴─────────────────────┐
            ▼                                           ▼
      인스턴스 A (구독)                            인스턴스 B (구독)
      로컬 소켓에 전송                             로컬 소켓에 전송
```

중요한 건 **발행한 인스턴스도 구독자로서 받는다**는 점입니다.
"내 소켓에는 직접 보내고 나머지는 발행한다"로 나누면 분기가 두 개가 되고, 로컬 전송과 원격 전송의 순서가 어긋납니다.
전부 버스를 거치게 하면 모든 인스턴스가 같은 코드 경로를 탑니다.

로컬 구독 테이블은 메모리에 둡니다.

```typescript
import { WebSocketServer, WebSocket } from 'ws';

const wss = new WebSocketServer({ noServer: true });

// 이 프로세스가 들고 있는 소켓만 담는다
const rooms = new Map<string, Set<WebSocket>>();

function broadcastLocal(room: string, payload: string) {
  const set = rooms.get(room);
  if (!set) return;
  for (const ws of set) {
    if (ws.readyState === WebSocket.OPEN) ws.send(payload);
  }
}
```

`payload`를 문자열로 받아 그대로 넘기는 게 의도입니다.
소켓마다 `JSON.stringify`를 다시 돌리면 참여자 수에 비례해 CPU를 씁니다. **직렬화는 한 번만 합니다.**

`readyState` 검사도 빼놓지 마세요. 닫히는 중인 소켓에 쓰면 예외가 나거나 조용히 버려지는데, 루프 안에서 예외가 터지면 그 뒤 소켓들은 메시지를 못 받습니다.

### 구독 연결은 따로 둔다

Redis 클라이언트는 구독 모드에 들어가면 일반 명령을 받지 않습니다. 발행용과 구독용 연결을 분리해야 합니다.

```typescript
import Redis from 'ioredis';

const pub = new Redis(process.env.REDIS_URL!);
const sub = pub.duplicate();   // 구독 전용

sub.on('message', (channel, payload) => {
  broadcastLocal(channel.slice('room:'.length), payload);
});

export async function publishToRoom(room: string, event: unknown) {
  await pub.publish(`room:${room}`, JSON.stringify(event));
}
```

이걸 모르고 하나의 연결로 쓰면 구독을 시작한 뒤부터 캐시 조회가 전부 실패합니다.
그런데 애플리케이션 시작 직후에는 아직 구독 전이라 잘 돌고, 첫 연결이 들어온 다음부터 깨집니다. 원인을 찾기 까다로운 형태입니다.

### 채널을 무엇 단위로 나눌 것인가

전역 채널 하나에 다 흘리고 각 인스턴스가 걸러내는 방식이 구현은 가장 쉽습니다. 그리고 가장 먼저 한계에 닿습니다.

모든 인스턴스가 모든 메시지를 역직렬화하고, 자기와 무관한 것을 버립니다. 인스턴스 대수를 늘리면 **버스 트래픽이 대수에 비례해 늘어납니다.** 확장하려고 늘린 대수가 비용이 됩니다.

방 단위로 채널을 쪼개고, 로컬에 참여자가 있을 때만 구독합니다.

```typescript
async function joinRoom(room: string, ws: WebSocket) {
  let set = rooms.get(room);
  if (!set) {
    set = new Set();
    rooms.set(room, set);
    await sub.subscribe(`room:${room}`);   // 이 인스턴스의 첫 참여자
  }
  set.add(ws);
}

async function leaveRoom(room: string, ws: WebSocket) {
  const set = rooms.get(room);
  if (!set) return;
  set.delete(ws);
  if (set.size === 0) {
    rooms.delete(room);
    await sub.unsubscribe(`room:${room}`);  // 마지막 참여자가 나갔다
  }
}
```

`leaveRoom`은 명시적 퇴장뿐 아니라 `close`와 `error` 양쪽에서 불러야 합니다. 한쪽만 걸어두면 비정상 종료된 소켓이 `Set`에 남아 누수가 됩니다.

> Redis 클러스터 모드에서 `PUBLISH`는 노드 전체로 전파되므로, 채널을 쪼개도 클러스터 내부 트래픽은 줄지 않습니다.
> 샤드 단위로 전파를 제한하는 명령(`SPUBLISH`/`SSUBSCRIBE`)이 별도로 있으니, 지원 버전과 제약은 공식 문서에서 확인하세요.

채널 이름에는 반드시 테넌트나 소유자 식별자를 포함시킵니다. `room:42`처럼 전역 숫자를 쓰면 다른 조직의 방 번호와 겹칠 수 있고, 그 순간 [격리](/blog/multi-tenant-data-isolation/)가 메시지 레이어에서 뚫립니다.

## 유실을 전제로 설계하기

여기서 설계가 갈립니다. **Redis pub/sub은 전달을 보장하지 않습니다.**

구독자가 그 순간 붙어 있지 않으면 메시지는 그냥 사라집니다. 저장하지 않으니 나중에 받을 방법도 없습니다.
느린 구독자는 더 나쁩니다. 출력 버퍼 한도를 넘기면 서버가 그 클라이언트 연결을 끊어버립니다. 이 한도는 pub/sub에 대해 별도로 설정되어 있으니 쓰는 버전의 설정값을 확인해두세요.

인스턴스 재시작, 배포, 네트워크 순단 — 유실 구간은 평소에도 생깁니다.

그래서 실시간 채널을 **진실의 출처로 쓰지 않습니다.**

- 쓰기는 DB에 커밋하고, 커밋된 내용을 발행합니다.
- 클라이언트는 받은 마지막 식별자를 들고 있습니다.
- 재연결하면 그 이후를 **HTTP로 다시 조회**해서 메꿉니다.

```sql
SELECT id, room_id, body, created_at
FROM room_messages
WHERE room_id = ?
  AND id > ?            -- 클라이언트가 마지막으로 받은 id
ORDER BY id
LIMIT 200;
```

`created_at` 대신 단조 증가하는 식별자로 자르는 이유는 [커서 페이지네이션](/blog/cursor-pagination-keyset/)과 같습니다. 같은 시각에 들어온 행이 경계에서 빠지거나 겹칩니다.

이렇게 두면 WebSocket은 **"다시 조회해라"는 신호를 빠르게 전달하는 수단**이 됩니다.
유실돼도 다음 재연결이나 다음 이벤트에서 복구되고, 실시간 경로가 죽어도 서비스가 멈추지 않습니다.

DB 커밋과 발행이 같이 성공해야 한다면 그건 pub/sub으로 풀 문제가 아닙니다. [트랜잭셔널 아웃박스](/blog/transactional-outbox-pattern/) 쪽입니다.

## 죽은 연결을 걷어내기

연결이 끊긴 것을 서버가 모르는 경우가 생깁니다. 모바일에서 네트워크가 바뀌거나 중간 장비가 조용히 세션을 버리면 `close` 이벤트가 오지 않습니다.

그 소켓은 `Set`에 남아서 메모리를 잡고, 접속자 수를 부풀리고, 보내는 메시지를 전부 흘립니다. 프로토콜 레벨 핑으로 직접 걷어내야 합니다.

```typescript
const alive = new WeakSet<WebSocket>();

wss.on('connection', (ws) => {
  alive.add(ws);
  ws.on('pong', () => alive.add(ws));
});

const heartbeat = setInterval(() => {
  for (const ws of wss.clients) {
    if (!alive.has(ws)) {
      ws.terminate();   // close 핸드셰이크를 기다리지 않는다
      continue;
    }
    alive.delete(ws);
    ws.ping();
  }
}, 25_000);
```

주기는 **로드밸런서의 유휴 타임아웃보다 짧게** 잡아야 합니다. 그보다 길면 조용한 연결이 LB에서 먼저 끊기고, 클라이언트는 이유 없이 재연결을 반복합니다.
기본값은 환경마다 다르니 쓰는 로드밸런서의 설정을 확인하고 거기서 역산하세요.

> `ws`의 `permessage-deflate` 압축은 연결당 메모리를 크게 씁니다. 연결 수가 많은 서버에서는 기본적으로 끄는 편이 안전하고, 켤 거라면 메모리를 재보고 결정하세요.

접속 여부(presence)를 다른 사용자에게 보여줘야 한다면 TTL로 처리합니다.

```typescript
// 하트비트마다 갱신 — 인스턴스가 급사하면 TTL로 알아서 사라진다
await pub.set(`presence:${userId}`, instanceId, 'EX', 60);
```

인스턴스가 정상 종료하지 못할 가능성이 있는 한, 접속 목록을 명시적으로 지우는 방식은 언젠가 유령을 남깁니다. **만료로 사라지게 두는 쪽이 복구가 필요 없습니다.**
대신 TTL 길이만큼 "실제로는 나갔는데 접속 중으로 보이는" 구간이 생깁니다. 이건 피할 수 없는 트레이드오프고, TTL과 하트비트 주기로 그 폭을 정하는 겁니다.

## 배포와 스케일 지표

연결을 들고 있는 서버는 배포할 때 조건이 다릅니다. 요청-응답 서버는 "처리 중인 요청이 끝나기"를 기다리면 되는데, WebSocket은 계속 열려 있는 것이 정상이라 그 기준으로는 영원히 안 끝납니다.

종료 신호를 받으면 **서버가 먼저 닫습니다.**

```typescript
process.on('SIGTERM', async () => {
  clearInterval(heartbeat);
  for (const ws of wss.clients) {
    ws.close(1001, 'server going away');   // 1001 = Going Away
  }
  // 잔여 프레임이 나갈 시간만 주고 종료
  setTimeout(() => process.exit(0), 5_000);
});
```

닫는 순서와 LB에서 빠지는 시점의 관계는 [무중단 배포 쪽 이야기](/blog/graceful-shutdown-deploy-5xx/)와 같습니다.
다만 여기서는 **클라이언트가 전부 동시에 재연결한다**는 점이 추가됩니다. 지터 없는 재연결은 새로 뜬 인스턴스에 그대로 쏟아집니다.

스케일 지표도 다릅니다. 유휴 연결은 CPU를 거의 쓰지 않아서, CPU 기반 정책은 연결이 꽉 차는 동안 아무 반응을 하지 않습니다.
**연결 수나 인스턴스당 소켓 수를 지표로 쓰는 편이 맞습니다.** [지표 선택이 스케일 아웃을 늦추는 구조](/blog/autoscaling-scale-out-lag-metric-selection/)는 여기서 더 뚜렷하게 나타납니다.

새 인스턴스가 떠도 **기존 연결은 옮겨가지 않습니다.** 늘어난 대수는 새로 들어오는 연결만 받습니다.
그래서 이미 포화된 상태에서 늘리는 것은 효과가 느리고, 분산시키려면 기존 연결을 의도적으로 끊어 재연결시켜야 합니다.

연결당 비용의 하한도 미리 봐두세요. 프로세스의 파일 디스크립터 한도(`ulimit -n`)와 연결당 메모리가 실질적인 상한을 정합니다.
목표 연결 수에 소켓당 버퍼를 곱해보면 인스턴스 사양이 나오고, 그게 대수 계획의 출발점입니다.

## 접속 중에 권한이 바뀌면

핸드셰이크에서 토큰을 검증하고 끝내면, 그 연결은 토큰 수명과 무관하게 계속 살아 있습니다.
**접속을 끊지 않는 한 권한 변경이 반영되지 않습니다.** 방에서 내보낸 사용자가 그 방 메시지를 계속 받는 경로가 여기입니다.

토큰은 핸드셰이크에서만 검증할 수 있으면 되지만, 쿼리스트링에 담는 방식은 액세스 로그에 남습니다.
단기 티켓을 HTTP로 발급받아 그걸로 연결하는 방식이 깔끔합니다.

```text
1. POST /ws-ticket   (일반 인증)  → 짧은 수명의 1회용 티켓
2. WS  /ws?ticket=…              → 서버가 검증 후 소비
```

그리고 **구독 시점마다 권한을 다시 확인합니다.** 방 참여 요청은 연결이 이미 인증됐다는 사실과 별개로, 그 방에 대한 권한을 그때 조회해야 합니다.
[권한을 리소스 범위로 보는 관점](/blog/authorization-role-permission-resource-scope/)이 그대로 적용됩니다.

권한을 뺏었을 때 즉시 끊어야 한다면 그 사실도 버스로 흘립니다.

```typescript
// 권한 회수 → 해당 사용자의 연결을 들고 있는 인스턴스가 처리
sub.on('message', (channel, payload) => {
  if (channel === 'revoke') {
    const { userId, room } = JSON.parse(payload);
    for (const ws of rooms.get(room) ?? []) {
      if (sessionOf(ws)?.userId === userId) {
        void leaveRoom(room, ws);
        ws.close(4403, 'forbidden');   // 4000~4999는 애플리케이션 정의
      }
    }
  }
});
```

여기에도 같은 전제가 붙습니다. 이 메시지는 유실될 수 있습니다.
그래서 **접근 제어를 끊기에 의존시키지 않습니다.** 다음 구독 요청에서 막히고, 메꾸기 조회에서도 막혀야 실제로 닫힌 겁니다. 끊기는 반응 속도를 위한 최적화일 뿐입니다.

## 정리

- 수평 확장의 문제는 부하 분산이 아니라 **내가 들고 있지 않은 소켓에 보내기**입니다.
- 스티키 세션은 재연결 시 같은 인스턴스만 해결하고, 방 참여자를 모아주지는 못합니다.
- 발행한 인스턴스도 구독자로서 받게 해서 **경로를 하나로 유지**합니다.
- 채널은 방 단위로 쪼개고, 로컬 참여자가 있을 때만 구독합니다.
- pub/sub은 유실됩니다. **진실은 DB에 두고, 실시간은 "다시 조회해라"는 신호로** 씁니다.
- 핑으로 죽은 연결을 걷어내고, 주기는 LB 유휴 타임아웃에서 역산합니다.
- 배포는 서버가 먼저 닫고, 스케일 지표는 CPU가 아니라 연결 수입니다.
- 권한은 구독 시점마다 확인합니다. 강제 종료는 최적화고, 보장은 조회 경로에 있습니다.
