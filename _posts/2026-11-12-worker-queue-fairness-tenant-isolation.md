큐는 먼저 들어온 것을 먼저 처리합니다. 그래서 공정해 보입니다.

그런데 한 테넌트가 만 건을 한꺼번에 밀어넣은 직후에 다른 테넌트가 한 건을 넣으면, 그 한 건은 만 건 뒤에 섭니다.
규칙은 지켜졌는데 결과는 전혀 공정하지 않습니다.

## 숫자로 보면 선택이 아니다

워커 10개가 건당 2초를 쓴다고 하면 초당 5건을 처리합니다. 큐에 만 건이 들어 있으면 비우는 데 2000초, 33분입니다.

그 직후에 들어온 작업의 대기 시간은 **자기 작업의 처리 시간과 무관하게** 33분입니다.
0.2초면 끝나는 알림 한 건도 마찬가지입니다. 이게 선두 차단(head-of-line blocking)입니다.

여기서 중요한 건 이 지연이 장애가 아니라는 점입니다. 워커는 정상이고, 처리량도 설계한 대로 나오고, 에러율은 0입니다.
그래서 모니터링이 조용하고, 문의가 먼저 들어옵니다.

## 대기 시간을 큐 길이와 같이 보지 않는다

큐 길이(depth)만 보면 "쌓였다"는 사실은 알지만 **누가 얼마나 기다리는지**는 모릅니다.
만 건이 쌓인 상태와 열 건이 쌓인 상태가 같은 그래프 위에서 다르게 보일 뿐, 둘 다 "쌓임"입니다.

봐야 하는 값은 투입 시각과 처리 시작 시각의 차이입니다.

```typescript
interface Job {
  id: string;
  tenantId: string;
  type: string;
  enqueuedAt: number;   // epoch ms — 투입한 쪽에서 찍는다
  payload: unknown;
}

// 워커에서 처리를 시작할 때
const waitingMs = Date.now() - job.enqueuedAt;
metrics.histogram("job_waiting_ms", waitingMs, { type: job.type });
```

`enqueuedAt`은 반드시 **투입하는 쪽에서** 찍습니다. 워커에서 찍으면 그 값은 항상 0에 가깝게 나옵니다.

테넌트 ID를 라벨로 붙이고 싶은 마음이 들지만, 테넌트 수만큼 시계열이 늘어납니다.
전체 분위수는 라벨 없이 기록하고, 테넌트별로는 "대기 시간 상위 N" 같은 형태로 따로 뽑는 편이 안전합니다.

이 지표가 있으면 다음 질문에 답할 수 있습니다. 지금 느린 게 처리 능력이 부족해서인지, 아니면 능력은 충분한데 순서가 나빠서인지.
**전자는 워커를 늘려야 하고, 후자는 늘려도 거의 나아지지 않습니다.**

## 선택지는 네 가지다

| 방법 | 효과 | 비용 |
| --- | --- | --- |
| 작업 종류별 큐 분리 | 짧은 작업이 긴 작업 뒤에 서지 않음 | 큐·워커 풀이 늘어남 |
| 테넌트별 동시성 상한 | 한 테넌트가 워커를 전부 점유하지 못함 | 상한값을 정해야 함 |
| 테넌트별 공정 분배 | 대기 시간이 투입량에 비례해 분산 | 디스패처 구현 필요 |
| 큰 작업 쪼개기 | 양보 지점이 생김 | 진행 상태 관리 필요 |

하나를 고르는 게 아니라 위에서부터 차례로 적용하는 목록입니다.
첫 번째만으로 해결되는 경우가 생각보다 많고, 세 번째까지 가야 하는 경우는 테넌트 수가 많고 투입량 편차가 큰 서비스입니다.

## 먼저 종류로 쪼갠다

가장 싸고 효과가 큰 것은 작업을 **지연에 민감한 것과 처리량이 중요한 것**으로 나누는 일입니다.

- 지연 민감: 알림 발송, 사용자가 화면에서 기다리는 변환, 인증 메일
- 처리량 위주: 대량 임포트, 월간 리포트 생성, 재색인, 정산 배치

이 둘을 같은 워커 풀에 두면 두 번째가 첫 번째의 대기 시간을 결정합니다. 그리고 두 번째는 대개 한 번에 많이 들어옵니다.

큐를 나누면 워커도 나뉘고, 그만큼 유휴 워커가 생깁니다. 그게 이 방법의 비용입니다.
다만 유휴 워커 몇 개와 알림 33분 지연 중 무엇이 싼지는 대체로 명확합니다.

> 우선순위 필드 하나로 해결하려는 시도는 두 가지 이유로 잘 안 됩니다.
> 낮은 우선순위가 영구히 밀리는 기아 상태가 생기고, 시간이 지나면 모든 작업이 최고 우선순위로 들어옵니다.
> 우선순위는 큐 안의 순서를 바꾸는 장치이고, 지금 필요한 건 **자원을 나누는 장치**입니다.

## 테넌트별 동시성 상한

종류를 나눠도 같은 큐 안에서 한 테넌트가 워커를 전부 차지하는 문제는 남습니다.
워커 10개 중 한 테넌트가 최대 3개까지만 쓰게 제한하면, 나머지 7개는 항상 다른 테넌트가 쓸 수 있습니다.

구현에서 틀리기 쉬운 지점이 두 개 있습니다.

첫째, **상한에 걸린 작업을 어떻게 할 것인가.** 꺼낸 다음에 상한을 확인하고 큐에 되돌리면, 같은 작업을 계속 꺼내고 되돌리는 회전이 생깁니다.
상한에 걸린 테넌트는 **꺼내기 단계에서 건너뛰어야** 합니다.

둘째, **점유 카운터가 새는 문제.** 워커가 죽으면 감소 연산이 실행되지 않고, 그 테넌트는 영구히 상한에 걸린 것처럼 보입니다.
카운터를 숫자로 들고 있으면 이걸 복구할 방법이 없으니, 만료 시각을 가진 리스(lease) 집합으로 들고 있어야 합니다.

## 가상 시간으로 순서를 정하기

동시성 상한은 "동시에 몇 개"를 제한하지만 대기 순서는 여전히 투입 순서입니다.
대기 시간 자체를 나누려면 꺼내는 순서를 바꿔야 합니다.

방법은 각 작업에 **가상 완료 시각**을 매기고 그 순서로 처리하는 것입니다.

```text
finish(job) = max(해당 테넌트의 직전 finish, 현재 시각) + 예상비용 / 가중치
```

같은 테넌트가 연속으로 넣으면 `finish`가 뒤로 계속 밀려나고, 다른 테넌트의 새 작업은 `현재 시각` 근처 값을 받아 그 앞에 끼어듭니다.
`max(..., 현재 시각)` 이 있어서 **한동안 작업을 넣지 않은 테넌트가 과거의 투입량 때문에 벌점을 받지는 않습니다.** 이 항이 없으면 오래전에 대량 투입한 테넌트가 영원히 뒤로 밀립니다.

Redis에서는 정렬 집합의 점수로 그대로 표현됩니다.

```lua
-- enqueue.lua
-- KEYS[1] ready(zset)  KEYS[2] tenant:vfinish(hash)  KEYS[3] job:tenant(hash)  KEYS[4] job:payload(hash)
-- ARGV[1] tenantId  ARGV[2] jobId  ARGV[3] costMs  ARGV[4] weight  ARGV[5] nowMs  ARGV[6] payload
local now    = tonumber(ARGV[5])
local vfin   = tonumber(redis.call('HGET', KEYS[2], ARGV[1])) or 0
local start  = math.max(vfin, now)
local finish = start + (tonumber(ARGV[3]) / tonumber(ARGV[4]))

redis.call('HSET', KEYS[2], ARGV[1], finish)
redis.call('HSET', KEYS[3], ARGV[2], ARGV[1])
redis.call('HSET', KEYS[4], ARGV[2], ARGV[6])
redis.call('ZADD', KEYS[1], finish, ARGV[2])
return tostring(finish)
```

현재 시각을 스크립트 안에서 읽지 않고 `ARGV`로 넘깁니다. 시간을 인자로 받으면 스크립트가 같은 입력에 같은 결과를 내므로, 재현과 테스트가 쉬워집니다.

`weight`는 플랜이나 계약에 따라 다르게 줄 수 있는 자리입니다. 전부 1이면 균등 분배가 되고, 특정 테넌트에 2를 주면 같은 시간에 두 배를 처리합니다.

`costMs`는 투입 시점에 정확히 알 수 없습니다. 선택지는 두 가지입니다.

- **전부 1로 두기** — 건수 기준 공정성. 단순하지만 무거운 작업이 섞이면 틀어집니다.
- **작업 종류별 최근 평균 처리 시간** — 시간 기준 공정성에 가까워집니다. 평균을 어디에 저장하고 얼마 주기로 갱신할지는 정해야 합니다.

종류별 큐를 이미 나눴다면 한 큐 안의 작업들은 비용이 비슷하므로, 1로 두고 시작해도 대개 충분합니다.

## 꺼내는 쪽 — 상한에 걸린 테넌트는 건너뛴다

꺼낼 때는 점수가 가장 낮은 작업부터 보되, 그 테넌트가 상한에 걸려 있으면 다음 후보로 넘어갑니다.

```lua
-- dequeue.lua
-- KEYS[1] ready(zset)  KEYS[2] job:tenant(hash)  KEYS[3] tenant:cap(hash)
-- ARGV[1] scanLimit  ARGV[2] defaultCap  ARGV[3] nowMs  ARGV[4] leaseMs  ARGV[5] inflightPrefix
local now   = tonumber(ARGV[3])
local lease = tonumber(ARGV[4])
local cands = redis.call('ZRANGE', KEYS[1], 0, tonumber(ARGV[1]) - 1)

for i = 1, #cands do
  local jobId  = cands[i]
  local tenant = redis.call('HGET', KEYS[2], jobId)
  if tenant then
    local ikey = ARGV[5] .. tenant
    redis.call('ZREMRANGEBYSCORE', ikey, '-inf', now)   -- 만료된 리스 회수
    local cap = tonumber(redis.call('HGET', KEYS[3], tenant)) or tonumber(ARGV[2])
    if redis.call('ZCARD', ikey) < cap then
      redis.call('ZREM', KEYS[1], jobId)
      redis.call('ZADD', ikey, now + lease, jobId)       -- 점유를 리스로 기록
      return { jobId, tenant }
    end
  end
end
return false
```

점유를 숫자 대신 **만료 시각을 점수로 가진 정렬 집합**에 담은 것이 핵심입니다.
워커가 죽어도 `ZREMRANGEBYSCORE` 한 줄이 다음 꺼내기에서 회수하므로, 상한이 영구히 막히지 않습니다.

`scanLimit`은 공정성과 비용의 타협입니다. 앞쪽 몇 개만 보기 때문에, 상한에 걸린 테넌트의 작업이 앞을 길게 메우고 있으면 뒤에 있는 처리 가능한 작업을 그 호출에서는 못 찾습니다.
그래도 상한에 걸린 쪽이 결국 자리를 비우면 그 작업들이 가장 먼저 처리되므로, **순서가 늦어질 뿐 굶지는 않습니다.**

워커 쪽 코드는 이렇게 됩니다.

```typescript
const LEASE_MS = 30_000;

async function runOnce(): Promise<boolean> {
  const got = (await redis.eval(
    DEQUEUE_LUA, 3,
    "q:{wq}:ready", "q:{wq}:job:tenant", "q:{wq}:tenant:cap",
    "20", "3", String(Date.now()), String(LEASE_MS), "q:{wq}:inflight:",
  )) as [string, string] | null;

  if (!got) return false;              // 지금 처리할 수 있는 작업이 없다
  const [jobId, tenantId] = got;

  const timer = setInterval(() => {    // 긴 작업은 리스를 갱신한다
    redis.zadd(`q:{wq}:inflight:${tenantId}`, Date.now() + LEASE_MS, jobId)
      .catch(() => {});
  }, LEASE_MS / 3);

  try {
    await handle(jobId);
  } finally {
    clearInterval(timer);
    await redis.zrem(`q:{wq}:inflight:${tenantId}`, jobId);
  }
  return true;
}

// 꺼낼 게 없으면 짧게 쉬고 다시 본다
while (running) {
  const worked = await runOnce();
  if (!worked) await sleep(200);
}
```

리스 갱신 주기는 리스 길이보다 충분히 짧게 둡니다. 갱신이 한 번 실패해도 다음 주기에 복구되는 여유가 필요합니다.

갱신을 아예 넣지 않으면 리스보다 오래 걸리는 작업에서 점유가 먼저 회수되고, 그 테넌트가 상한을 넘겨 쓰게 됩니다.

> 키 이름의 `{wq}` 는 Redis Cluster용 해시 태그입니다.
> 하나의 스크립트에서 다루는 키들은 같은 슬롯에 있어야 하므로, 중괄호로 공통 태그를 묶어 같은 노드에 모읍니다.
> 단일 노드 환경이라면 없어도 동작하지만, 나중에 클러스터로 옮길 때 스크립트를 다시 쓰게 됩니다.

이 구조의 대가는 **블로킹 꺼내기를 잃는다**는 점입니다.
정렬 집합에서 조건부로 고르는 동작이라 `BRPOP` 같은 대기가 불가능해서, 위처럼 짧은 간격으로 폴링해야 합니다.
작업이 드문 큐에서 폴링 간격이 그대로 최소 지연이 되니, 투입 시 별도 키로 깨우는 신호를 보내는 방법을 함께 쓸 수 있습니다.

## 쌓이는 상태를 정리한다

테넌트별 가상 완료 시각 해시는 한 번 들어온 테넌트만큼 커집니다. 지워도 되는 항목은 조건이 분명합니다.

```typescript
// vfinish 가 충분히 과거인 테넌트는 다음 투입에서 max(..., now) 로 초기화되므로 지워도 동작이 같다
async function sweepIdleTenants(graceMs = 3_600_000) {
  const cutoff = Date.now() - graceMs;
  const all = await redis.hgetall("q:{wq}:tenant:vfinish");
  const stale = Object.entries(all)
    .filter(([, v]) => Number(v) < cutoff)
    .map(([k]) => k);
  if (stale.length > 0) await redis.hdel("q:{wq}:tenant:vfinish", ...stale);
}
```

`job:tenant` 와 `job:payload` 해시에서 완료된 작업을 지우는 것도 잊기 쉬운 자리입니다.
처리 성공 후 삭제가 빠지면 메모리가 단조 증가하고, Redis 메모리 상한에 닿는 순간 축출 정책에 따라 **큐 자체가 잘려나갈 수** 있습니다.

## 큰 작업은 쪼개서 넣는다

만 건 임포트를 메시지 하나로 넣으면 공정 분배가 개입할 자리가 없습니다. 이미 꺼낸 작업 하나가 워커를 길게 점유하기 때문입니다.

쪼개면 양보 지점이 생깁니다. 500건씩 20개로 넣으면 각 조각 사이에서 다른 테넌트가 끼어들 수 있습니다.

```typescript
const CHUNK = 500;
for (let offset = 0; offset < rows.length; offset += CHUNK) {
  await enqueue({
    tenantId, type: "import.chunk",
    payload: { importId, offset, limit: CHUNK },
  });
}
```

조각 크기는 두 가지 힘의 타협입니다. 작게 쪼개면 양보가 잦아 공정해지지만 투입·조회 오버헤드가 커지고, 크게 쪼개면 그 반대입니다.
한 조각의 처리 시간이 **허용하려는 최대 대기 시간보다 짧아지는 선**에서 고르면 대체로 맞습니다.

진행률과 완료 판정은 별도 레코드로 관리합니다. 조각이 순서 없이 끝나기 때문에, 마지막 조각이 끝났다는 사실만으로 전체 완료를 판단할 수 없습니다.

## 큐를 바꿀 수 없을 때

SQS 같은 매니지드 큐에는 테넌트별 공정 분배가 없습니다. 꺼내는 순서를 조건부로 바꿀 수 없으니, 선택지가 달라집니다.

**첫째, 큐를 나눕니다.** 작업 종류별로 나누는 것은 거의 항상 맞습니다. 테넌트별로 나누는 것은 테넌트가 수십 개 수준일 때나 가능하고, 큐가 늘어나면 폴링하는 쪽의 복잡도가 그만큼 올라갑니다.

**둘째, FIFO 큐의 메시지 그룹을 테넌트로 씁니다.** 같은 그룹은 순서대로 처리되고 서로 다른 그룹은 병렬로 처리되므로, 한 테넌트의 메시지가 막혀도 다른 테넌트는 진행합니다.
다만 그룹은 격리를 주지 **순서를 균등하게 섞어주지는 않습니다.** 그룹 수와 처리량에 대한 제한은 버전과 리전에 따라 다르니 공식 문서에서 확인하세요.

**셋째, 디스패처를 앞에 둡니다.** 큐에서 꺼내는 일만 하는 얇은 프로세스가 메시지를 받아 위에서 만든 Redis 구조에 넣고, 워커는 Redis에서만 꺼냅니다.
큐는 내구성과 재시도를 담당하고 순서는 디스패처가 정하는 분담입니다.
대신 상태를 들고 있는 지점이 하나 늘어나므로, 디스패처가 죽었을 때 메시지가 어디까지 넘어갔는지 판단할 수 있어야 합니다.

## 무엇을 보고 알 수 있나

공정성은 평균으로는 보이지 않습니다. 평균 대기 시간은 대량 투입 중에도 멀쩡해 보일 수 있습니다.

- 종류별 대기 시간 p50 / p95 / p99 — 투입량과 같이 그려야 해석됩니다
- 테넌트별 처리 건수 분포 — 상위 한 곳이 대부분을 차지하면 상한이 느슨한 것입니다
- 상한에 걸려 건너뛴 횟수 — 상한이 실제로 동작하는지 보여주는 유일한 지표입니다
- 리스 만료로 회수된 건수 — 0이 아니면 워커가 죽거나 리스 갱신이 밀리고 있다는 뜻입니다
- 가장 오래 기다린 작업의 나이 — 기아가 생기는지 확인하는 값입니다

마지막 값은 큐 길이와 함께 알람 조건으로 쓸 만합니다. 길이는 늘었다 줄지만, 특정 작업의 나이가 계속 자라면 그건 구조 문제입니다.

## 정리

- FIFO는 순서를 보장하지만 공정성은 보장하지 않습니다. 대량 투입 한 번이 모든 테넌트의 대기 시간을 결정합니다.
- 큐 길이 대신 **투입에서 처리 시작까지의 지연**을 봅니다. 능력 부족과 순서 문제를 구분해주는 값입니다.
- 작업 종류를 지연 민감/처리량 위주로 나누는 것이 가장 싸고 효과가 큽니다. 여기서 끝나는 경우가 많습니다.
- 테넌트별 동시성 상한은 꺼내기 단계에서 건너뛰는 방식으로 구현하고, 점유는 만료 시각이 있는 리스로 들고 있어야 워커 장애에서 회복됩니다.
- 대기 순서까지 나누려면 가상 완료 시각을 점수로 쓰고, `max(직전 finish, 현재 시각)` 으로 유휴 테넌트의 벌점을 끊습니다.
- 큰 작업은 쪼개야 양보 지점이 생깁니다. 조각 하나의 처리 시간을 허용 대기 시간보다 짧게 둡니다.
- 매니지드 큐에서는 큐 분리, FIFO 메시지 그룹, 앞단 디스패처 중에서 고릅니다. 공정성을 공짜로 주는 옵션은 없습니다.
