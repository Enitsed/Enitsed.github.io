요청에 10초 타임아웃을 걸어두면 10초 뒤에 클라이언트는 응답을 포기합니다.
그런데 그 요청이 돌리던 쿼리는 DB에서 40초째 돌고 있습니다.

아무도 기다리지 않는 결과를 만들기 위해 커넥션 하나와 CPU가 계속 묶여 있습니다.
그리고 포기한 쪽이 재시도를 하면, 같은 무거운 쿼리가 한 개 더 추가됩니다.

## 포기는 요청하는 쪽에서만 일어난다

타임아웃이라는 말이 "작업을 멈춘다"는 뜻으로 읽히는데, 대부분의 타임아웃은 **기다리기를 멈추는 것**입니다.

애플리케이션에서 `Promise.race`로 쿼리를 끊거나, `AbortController`로 핸들러를 중단하면 그 코드는 다음으로 넘어갑니다.
DB 서버 입장에서는 아무 일도 일어나지 않았습니다. 질의는 접수됐고, 실행 중이고, 결과를 쓸 준비를 하고 있습니다.

이게 가장 나쁜 순간에 복리로 불어납니다.

1. 쿼리가 느려진다 (데이터가 늘었거나 실행 계획이 바뀌었거나)
2. 요청 타임아웃에 걸려 응답이 실패한다
3. 클라이언트가 재시도한다 — 같은 쿼리가 두 번째로 접수된다
4. 첫 번째는 아직 돌고 있다. 커넥션 두 개가 묶인다
5. 커넥션 풀이 마르면서, 그 쿼리를 쓰지 않는 API까지 느려진다

5번에 도달하면 원인이 보이지 않습니다. 느려진 건 한 엔드포인트인데 전부 느려지니까요.
풀이 마르는 쪽 이야기는 [커넥션 풀이 마르는 순간](/blog/db-connection-pool-exhaustion/)에 따로 적었는데, 여기서 하려는 이야기는 **애초에 쿼리를 서버에서 끊는 것**입니다.

## 타임아웃은 한 개가 아니다

하나의 요청이 DB까지 가는 길에는 타임아웃이 여럿 있고, 각자 끊는 대상이 다릅니다.

| 계층 | 설정 | 실제로 끊기는 것 |
| --- | --- | --- |
| 로드밸런서·게이트웨이 | 유휴·요청 타임아웃 | 클라이언트 쪽 연결 |
| 애플리케이션 요청 | 요청 전체 데드라인 | 응답 생성 |
| 커넥션 풀 | 획득(acquire) 타임아웃 | 커넥션을 기다리는 중인 코드 |
| 드라이버 | 쿼리 타임아웃 | 응답 대기 (구현마다 다름) |
| **DB 서버** | **문장 타임아웃** | **쿼리 실행 자체** |
| **DB 서버** | **락 대기 타임아웃** | **락을 기다리는 문장** |

위의 네 개를 다 걸어도 서버에서 도는 쿼리는 멈추지 않습니다. 멈추는 건 아래 두 줄뿐입니다.

> 드라이버의 쿼리 타임아웃 옵션은 라이브러리와 버전마다 동작이 다릅니다.
> 어떤 것은 대기만 포기하고, 어떤 것은 소켓을 닫고, 어떤 것은 커넥션을 폐기합니다.
> 커넥션을 닫으면 서버가 그걸 감지해 문장을 중단하는 경우도 있지만, 그 시점은 보장되지 않습니다.
> **드라이버 옵션의 의미는 공식 문서에서 확인하고, 서버 측 상한은 그것과 별개로 반드시 두세요.**

## 안쪽이 바깥쪽보다 짧아야 한다

값을 고르는 규칙은 한 줄입니다. **안쪽 계층의 타임아웃은 바깥쪽보다 짧아야 합니다.**

거꾸로 되어 있으면 안쪽이 끊기기 전에 바깥쪽이 먼저 포기하고, 그러면 방금 말한 좌초된 쿼리가 생깁니다.
또 에러가 어디서 났는지도 알 수 없게 됩니다. 게이트웨이가 먼저 끊으면 애플리케이션 로그에는 아무 흔적이 없습니다.

하나의 요청을 예산으로 보면 이렇게 쪼개집니다.

```text
게이트웨이 요청 타임아웃      30s
└─ 애플리케이션 요청 데드라인  10s
   ├─ 풀 획득                  1s
   └─ 쿼리 실행                5s
      └─ 락 대기               2s
```

합이 바깥 예산보다 작아야 하고, 중간에 외부 API 호출이 끼면 그만큼 더 쪼개야 합니다.
이 쪼개기를 호출 단위로 전파하는 방법은 [타임아웃 예산과 재시도 증폭](/blog/retry-timeout-budget-circuit-breaker/) 쪽에 적어뒀습니다.

값 자체는 추측하지 말고 재서 정합니다. 기준은 "정상적으로 가장 느린 쿼리보다는 길게, 요청 예산보다는 짧게"입니다.
정상 쿼리의 p99가 800ms인 경로에 5초를 걸면 충분히 여유롭고, 40초짜리 좌초는 확실히 막힙니다.

## PostgreSQL의 서버 측 상한

PostgreSQL은 이 부분이 깔끔합니다. 세 개를 같이 보면 됩니다.

```sql
SET statement_timeout = '5s';                    -- 문장 하나의 상한
SET lock_timeout = '2s';                         -- 락 획득 대기 상한
SET idle_in_transaction_session_timeout = '30s'; -- 트랜잭션 열어둔 채 노는 세션
```

`statement_timeout`을 넘기면 문장이 취소되고 오류가 됩니다. 트랜잭션 안이면 롤백됩니다.

`lock_timeout`을 따로 두는 이유가 있습니다. 락을 기다리느라 멈춰 있는 문장은 실행 시간을 쓰고 있는 게 아니라 **남이 끝나기를 기다리는 중**이고, 이건 더 짧게 끊어도 됩니다.
특히 `ALTER TABLE` 같은 문장은 락을 기다리는 동안 자기 뒤로 다른 세션을 줄 세우기 때문에, 짧은 `lock_timeout`을 걸고 실패하면 재시도하는 편이 안전합니다.

세 번째가 조용한 범인입니다. `BEGIN`을 하고 애플리케이션 로직을 돌다가 외부 API 응답을 기다리는 코드는 트랜잭션을 열어둔 채 아무 쿼리도 보내지 않습니다.
그 세션은 CPU를 쓰지 않으면서 락과 스냅샷을 붙들고 있어서, 문장 타임아웃으로는 잡히지 않습니다.

## MySQL은 읽기와 쓰기가 다르다

MySQL에도 문장 타임아웃이 있지만 적용 범위가 좁습니다.

```sql
-- 세션 단위 (밀리초)
SET SESSION max_execution_time = 5000;

-- 쿼리 단위 힌트
SELECT /*+ MAX_EXECUTION_TIME(5000) */ id, title
FROM posts WHERE center_id = ? ORDER BY created_at DESC LIMIT 50;
```

> `max_execution_time`은 **읽기 전용 SELECT에만** 적용됩니다.
> `UPDATE`·`DELETE`·`INSERT ... SELECT`는 이 값으로 끊어지지 않고, 데이터를 바꾸는 저장 함수를 호출하는 SELECT도 대상이 아닙니다. 저장 프로그램 안의 SELECT에도 적용되지 않습니다.
> 단위는 밀리초이며, 정확히 그 시점에 끊긴다는 보장은 없습니다. 힌트에 `0`을 주면 "제한 없음"이 아니라 세션·전역 값이 적용됩니다.

그래서 MySQL에서 쓰기를 통제하는 수단은 다른 곳에 있습니다.

```sql
SET SESSION innodb_lock_wait_timeout = 3;  -- 초 단위
```

느린 쓰기는 대개 연산이 무거워서가 아니라 **락을 기다리느라** 길어집니다. 그러니 실무에서 효과가 큰 건 이쪽입니다.
기본값이 수십 초 단위로 길게 잡혀 있는 경우가 많으니 지금 값을 먼저 확인하세요. 어떤 문장이 무엇을 기다리는지는 [InnoDB 락 읽는 법](/blog/innodb-deadlock-gap-lock/)에서 다뤘습니다.

연산 자체가 무거운 쓰기는 타임아웃으로 해결할 대상이 아닙니다. 끊어도 롤백에 그만큼 시간이 들기 때문에, 애초에 **작업을 쪼개는 쪽**이 맞습니다.
대량 삭제·갱신을 나눠 돌리는 방법은 [대량 삭제와 데이터 보관](/blog/mysql-bulk-delete-partition-retention/)에 적어뒀습니다.

커넥션 수명과 관련된 `wait_timeout`, `net_read_timeout` 같은 값들은 성격이 다릅니다.
이건 "쿼리를 끊는" 설정이 아니라 "유휴 커넥션을 정리하는" 설정이고, 풀이 죽은 커넥션을 들고 있는 문제와 연결됩니다.

## 어디에 걸 것인가

같은 값이라도 거는 자리에 따라 신뢰도가 다릅니다.

| 위치 | 장점 | 문제 |
| --- | --- | --- |
| 전역 설정 | 빠뜨릴 수 없다 | 배치·리포트까지 같이 막힌다 |
| 역할(ROLE)·계정 단위 | 용도별로 다르게, 코드 변경 없음 | 역할을 나눠야 한다 |
| 커넥션 생성 시점 | 애플리케이션이 관리 | 세션이 유지된다는 가정이 필요 |
| 쿼리 단위 | 가장 정확하다 | 빠뜨리기 쉽다 |

실무에서 제일 무난한 조합은 **역할 단위로 기본값을 깔고, 예외만 쿼리 단위로 올리는 것**입니다.
전역 하나로 끝내려 하면 리포트 쿼리가 막혀서 결국 전역값을 키우게 되고, 그러면 원래 막으려던 것도 같이 열립니다.

```sql
-- PostgreSQL: 새로 접속하는 세션부터 적용된다
ALTER ROLE app_web    SET statement_timeout = '5s';
ALTER ROLE app_worker SET statement_timeout = '60s';
ALTER ROLE app_report SET statement_timeout = '600s';
```

웹 요청용 계정과 배치용 계정을 나눠두면 이 구분이 공짜로 생깁니다.
나누지 않았다면 여기가 나눌 이유가 됩니다.

애플리케이션에서 거는 경우는 커넥션이 만들어질 때 한 번 설정합니다.

```typescript
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

// 새 커넥션마다 기본 상한을 깐다
pool.on('connect', (client) => {
  client.query("SET statement_timeout = '5s'").catch(() => { /* 로깅 */ });
  client.query("SET lock_timeout = '2s'").catch(() => { /* 로깅 */ });
});
```

이 핸들러는 첫 쿼리보다 먼저 끝난다고 보장되지 않습니다. 확실하게 하려면 역할 단위로 걸거나, 드라이버가 접속 파라미터로 넘기는 방법을 지원하는지 확인하세요.

예외는 트랜잭션 안에서 올립니다.

```sql
BEGIN;
SET LOCAL statement_timeout = '120s';   -- 이 트랜잭션에만
-- 오래 걸리는 집계
COMMIT;
```

`SET LOCAL`을 쓰는 이유는 되돌릴 걱정이 없기 때문입니다. 세션 단위로 `SET`을 하고 풀에 반납하면, 그 커넥션을 받은 다음 요청이 바뀐 값을 그대로 물려받습니다.

> 커넥션 프록시를 트랜잭션 단위 풀링 모드로 쓰고 있다면, 세션 단위로 걸어둔 값이 유지된다고 가정할 수 없습니다.
> 이 환경에서는 트랜잭션 안의 `SET LOCAL`이나 역할·전역 설정 쪽이 안전합니다.

## 좌초된 쿼리 찾아 끊기

설정을 깔기 전에도, 깐 뒤에도 지금 뭐가 돌고 있는지는 봐야 합니다.

```sql
-- MySQL: 30초 넘게 실행 중인 문장
SELECT ID, USER, HOST, TIME, STATE, LEFT(INFO, 120) AS q
FROM information_schema.PROCESSLIST
WHERE COMMAND = 'Query' AND TIME > 30
ORDER BY TIME DESC;

KILL QUERY 1234;   -- 문장만 끊는다
```

`KILL QUERY`와 `KILL`(= `KILL CONNECTION`)의 차이를 구분해서 쓰세요.
커넥션을 끊으면 풀이 그 사실을 모른 채 들고 있다가 다음 요청에서 오류를 내는 경우가 있어서, 문장만 끊는 쪽이 영향이 작습니다.

```sql
-- PostgreSQL
SELECT pid, state, now() - query_start AS dur, left(query, 120) AS q
FROM pg_stat_activity
WHERE state <> 'idle'
  AND now() - query_start > interval '30 seconds'
ORDER BY dur DESC;

SELECT pg_cancel_backend(1234);     -- 쿼리 취소 (세션은 유지)
SELECT pg_terminate_backend(1234);  -- 세션 종료
```

`state`를 같이 보는 게 중요합니다. `active`는 실제로 실행 중이고, `idle in transaction`은 트랜잭션을 열어둔 채 놀고 있는 상태입니다.
후자가 많이 보이면 타임아웃을 조일 게 아니라 코드에서 트랜잭션 범위를 줄여야 합니다. 트랜잭션 안에서 외부 호출을 하고 있을 가능성이 큽니다.

## 쓰기를 끊는 것은 성격이 다르다

읽기를 끊는 건 안전합니다. 결과를 못 받는 것뿐입니다.

쓰기는 다릅니다. **타임아웃으로 끊긴 쓰기는 "실패"가 아니라 "결과를 모름"입니다.**

- 서버 측 문장 타임아웃이나 `KILL QUERY`로 끊겼다면 그 문장은 롤백됩니다. 여기까지는 명확합니다.
- 그런데 애플리케이션이나 네트워크 쪽에서만 끊겼다면, 서버에서 그 트랜잭션이 커밋을 끝냈을 수도 있습니다.

두 번째 경우에 재시도하면 같은 쓰기가 두 번 들어갑니다.
그래서 쓰기 경로의 재시도는 멱등성이 보장될 때만 해야 하고, 그 장치가 [멱등키](/blog/idempotency-key-payment-api/)입니다.

반대 방향의 함정도 있습니다. 타임아웃이 너무 짧으면 정상적인 쓰기가 주기적으로 끊깁니다.
읽기와 쓰기 경로에 같은 값을 쓰지 말고, 쓰기 쪽은 락 대기를 포함한 실제 분포를 보고 정하세요.

## 타임아웃을 걸면 에러율이 올라간다

이걸 먼저 각오하고 켜야 합니다. 전에는 40초를 기다려서 어떻게든 응답하던 요청이 이제 5초에 오류로 끝납니다. 에러율 그래프가 올라갑니다.

그래도 이쪽이 낫습니다. 그 40초 동안 그 요청은 커넥션을 묶어 다른 요청까지 느리게 만들고 있었습니다.
**실패가 한 요청 안에서 끝나는 것과 전체로 퍼지는 것의 차이**이고, 타임아웃은 그 경계를 긋는 장치입니다.

대신 켠 다음에 볼 것을 같이 준비합니다.

```typescript
// 타임아웃 오류를 다른 DB 오류와 섞지 않는다
const TIMEOUT_CODES = new Set([
  '57014',  // PostgreSQL: query_canceled
  '55P03',  // PostgreSQL: lock_not_available
]);

function isTimeout(err: unknown): boolean {
  const code = (err as { code?: string })?.code;
  return code !== undefined && TIMEOUT_CODES.has(code);
}
```

MySQL 쪽 오류 코드와 메시지는 끊긴 원인(문장 타임아웃·락 대기·강제 종료)에 따라 다르니, 쓰는 버전의 공식 오류 코드 목록을 보고 분류하세요.

분류해서 세어야 하는 건 세 가지입니다.

- **경로별 타임아웃 건수** — 어느 엔드포인트가 상한에 닿는지. 한 곳에 몰려 있으면 그 쿼리를 고칠 차례입니다.
- **N초 초과 실행 중인 문장 수** — 게이지로 둡니다. 상한을 걸어뒀는데도 이 값이 0이 아니면 그 경로가 상한을 안 쓰고 있다는 뜻입니다.
- **풀 획득 대기 시간** — 타임아웃이 제 역할을 하면 이 값이 먼저 내려갑니다.

라벨을 테넌트나 사용자 단위로 붙이고 싶어지는데, 그 전에 [메트릭 카디널리티](/blog/metric-cardinality-label-design/) 쪽을 한 번 보고 결정하는 편이 좋습니다.

## 정리

- 애플리케이션에서 끊는 타임아웃은 **기다리기를 멈추는 것**이고, 쿼리를 멈추는 건 서버 측 상한뿐입니다.
- 안쪽 계층이 바깥쪽보다 짧아야 합니다. 거꾸로면 좌초된 쿼리가 생기고 에러 발생 위치도 흐려집니다.
- PostgreSQL은 `statement_timeout`·`lock_timeout`·`idle_in_transaction_session_timeout` 세 개를 같이 봅니다.
- MySQL의 `max_execution_time`은 읽기 전용 SELECT만 막습니다. 쓰기는 `innodb_lock_wait_timeout`과 작업 쪼개기로 다룹니다.
- 역할 단위로 기본값을 깔고 예외만 트랜잭션 안에서 올립니다. 세션에 `SET`하고 풀에 반납하면 다음 요청이 물려받습니다.
- 쓰기 타임아웃은 "실패"가 아니라 "모름"입니다. 재시도하려면 멱등성이 먼저 있어야 합니다.
- 켜면 에러율은 오릅니다. 대신 한 요청의 실패가 전체로 퍼지지 않습니다.
