`LIKE '%검색어%'`로 버티다 한계가 오면 검색 전용 저장소를 붙입니다.
쿼리는 빨라지고 형태소 분석도 되니, 여기까지는 성공한 것처럼 보입니다.

문제는 그 순간부터 같은 데이터가 두 곳에 있다는 것입니다.
그리고 두 곳은 **반드시 어긋납니다.** 남은 일은 어긋남을 얼마나 짧게, 어떤 방향으로 허용할지 고르는 것뿐입니다.

## 어긋남은 세 가지 얼굴로 온다

하나로 뭉쳐서 "동기화가 안 된다"고 보면 고칠 수 없습니다. 원인이 셋이고 해법도 셋입니다.

**지연.** 색인은 쓰는 즉시 검색에 보이지 않습니다. 대부분의 검색 엔진은 주기적으로 세그먼트를 갱신하고, 그 주기 안에 들어온 문서는 아직 조회되지 않습니다.
저장 직후 목록을 다시 불러오는 화면에서 바로 드러납니다. [리플리카 지연](/blog/read-your-writes-replica-lag/)과 증상이 똑같습니다.

**누락.** DB에는 들어갔는데 색인은 안 됐거나, 그 반대입니다. 쓰기 경로가 두 개로 갈라진 데서 옵니다.
지연은 기다리면 해결되지만 누락은 영구적입니다. 다음 재색인까지 그 문서는 검색되지 않습니다.

**역전.** 같은 문서의 갱신 두 건이 뒤바뀐 순서로 색인돼, 옛 값이 새 값을 덮습니다.
워커를 여러 대로 늘리거나 재시도를 켜는 순간 생깁니다. 가장 늦게 발견되고 가장 설명하기 어려운 종류입니다.

## 동기화를 어디에 둘 것인가

| | 동시 쓰기 | 아웃박스 + 워커 | CDC (binlog) | 주기적 전체 재색인 |
| --- | --- | --- | --- | --- |
| 누락 가능성 | 있음 | 없음 | 없음 | 없음 (주기만큼 늦다) |
| 지연 | 가장 짧다 | 초 단위 | 초 단위 | 주기 단위 |
| 애플리케이션 변경 | 쓰기 경로마다 | 쓰기 경로마다 | 없음 | 없음 |
| 문서 조립 | 쉽다 | 쉽다 | **어렵다** | 쉽다 |
| 운영 구성요소 | 없음 | 큐/워커 | CDC 파이프라인 | 배치 |
| 누가 쓰기에 끼어드는가 | 전부 | 애플리케이션만 | 전부 (수동 SQL 포함) | 전부 |

마지막 줄이 생각보다 중요합니다. 운영 중에 콘솔이나 수동 SQL로 데이터를 고치는 일이 있는 서비스라면, 애플리케이션 코드에만 동기화를 심은 구조는 그 변경을 놓칩니다.

그리고 **어떤 방식을 골라도 주기적 전체 재색인은 남겨두는 편**이 낫습니다. 어긋남을 0으로 만드는 수단이 아니라, 어긋났을 때 되돌릴 수단으로요.

### 동시 쓰기는 왜 조용히 어긋나는가

가장 먼저 쓰게 되는 형태는 대개 이렇습니다.

```typescript
// 흔하지만 어긋남을 구조적으로 허용하는 코드
async function updatePost(id: string, input: PostInput) {
  const post = await db.transaction(async (tx) => {
    await tx.post.update({ where: { id }, data: input });
    return tx.post.findUniqueOrThrow({ where: { id } });
  });

  try {
    await search.index({ index: "posts", id, document: toDoc(post) });
  } catch (e) {
    logger.error({ err: e, id }, "색인 실패");   // 로그만 남고 끝난다
  }

  return post;
}
```

색인을 커밋 **뒤에** 두면, 색인이 실패하거나 그 사이 프로세스가 죽을 때 DB에만 반영됩니다.
색인을 커밋 **앞에** 두면 더 나쁩니다. 트랜잭션이 롤백돼도 색인은 남아서, **존재하지 않는 문서가 검색 결과에 나옵니다.**

두 저장소에 동시에 쓰는 일은 순서를 바꿔도 안전해지지 않습니다. 쓰기가 하나의 원자적 단위가 아니라는 사실 자체가 원인입니다.

그래도 동시 쓰기가 합리적인 경우는 있습니다. 검색이 보조 기능이고, 누락된 문서가 다음 전체 재색인까지 안 보여도 괜찮은 서비스라면 구성요소를 늘리지 않는 쪽이 낫습니다.
중요한 건 그 선택을 **의식적으로** 하는 것입니다. `catch`에 로그만 적어두고 넘어간 코드는 선택한 게 아니라 미룬 것입니다.

### 아웃박스 — 같은 트랜잭션에 적는다

색인 요청을 DB 변경과 같은 트랜잭션에 기록하면 누락이 사라집니다.
구조는 [트랜잭셔널 아웃박스](/blog/transactional-outbox-pattern/)에 적어둔 것과 같고, 여기서는 **무엇을 적을지**가 다릅니다.

```sql
CREATE TABLE search_outbox (
  id          BIGINT       NOT NULL AUTO_INCREMENT,
  entity      VARCHAR(32)  NOT NULL,   -- 'post'
  entity_id   VARCHAR(64)  NOT NULL,
  revision    BIGINT       NOT NULL,   -- 색인 버전으로 그대로 쓴다
  created_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_pending (entity, entity_id)
);
```

문서 본문(payload)을 적지 않는 게 요점입니다. **식별자와 리비전만 적고, 워커가 최신 상태를 다시 읽어 문서를 만듭니다.**

이유는 두 가지입니다. 첫째, 같은 문서에 변경이 연달아 들어오면 워커가 한 번만 읽어 **최신 상태 한 번으로 끝낼 수** 있습니다.
둘째, 역정규화한 문서는 여러 테이블을 조인해야 만들어지는데, 그 조립을 트랜잭션 안에서 하면 쓰기 경로가 무거워집니다.

대가는 워커가 DB를 다시 읽는다는 것입니다. 그래서 워커는 아웃박스 행을 모아 **문서 단위로 중복을 제거한 뒤 한 번에 조회**해야 합니다. 행마다 쿼리를 날리면 [N+1](/blog/orm-n-plus-one-batching/)이 동기화 파이프라인으로 옮겨온 셈이 됩니다.

### CDC — 애플리케이션을 안 고치는 대가

바이너리 로그를 읽어 테이블 변경을 그대로 흘려보내는 방식입니다. 애플리케이션을 전혀 고치지 않고, 수동 SQL까지 포함해 **모든 변경을 잡습니다.**

대가는 입구가 테이블 단위라는 점입니다. 검색 문서는 보통 여러 테이블을 합친 모양인데, CDC가 주는 것은 `posts` 한 행의 변경입니다.
작성자 이름이 문서에 들어가 있다면 `users` 스트림의 변경도 받아서 **어떤 문서들을 다시 만들어야 하는지 역방향으로 풀어야** 합니다. 이 조립을 CDC 소비자에 다 담으면 금방 복잡해집니다.

현실적인 타협은 CDC를 **트리거로만 쓰는 것**입니다. 변경된 식별자만 뽑아 아웃박스 워커와 같은 경로에 넣고, 문서 조립은 한 곳에서 합니다.
그러면 "모든 변경을 잡는다"는 CDC의 장점과 "조립은 한 군데"라는 아웃박스의 장점을 같이 가져갈 수 있습니다.

## 역정규화한 문서는 갱신이 번진다

검색 엔진에는 조인이 없거나 제한적이라, 필요한 값을 문서 안에 복사해 넣습니다. 그 순간 **한 행의 변경이 여러 문서의 갱신으로 번집니다.**

브랜드 이름을 상품 문서에 넣어뒀다면, 브랜드명 한 번 수정에 그 브랜드의 상품 문서 전부를 다시 써야 합니다.
상품이 수만 개면 수정 한 번이 수만 건의 색인 작업입니다.

선택은 셋입니다.

**문서에 복사하고 대량 갱신한다.** 조건에 맞는 문서를 질의로 찾아 갱신하는 API가 있지만, 이건 백그라운드에서 오래 도는 작업입니다.
동시에 여러 건이 걸리면 색인 부하가 평소의 몇 배가 됩니다. 변경 빈도가 낮은 필드에만 쓸 만합니다.

**복사하지 않고 식별자만 넣는다.** 검색은 정렬된 ID 목록만 돌려주고, 화면에 보일 값은 DB에서 읽습니다.
이게 꽤 자주 맞는 답입니다. 판단 기준은 단순합니다. **그 필드로 검색·필터·정렬을 하는가.** 표시만 한다면 문서에 넣을 이유가 없습니다.

```typescript
// 검색은 순서만 정하고, 표시용 데이터는 DB에서 채운다
async function searchPosts(q: string, size: number) {
  const hits = await search.search({
    index: "posts-search",
    size,
    _source: false,                       // 본문을 받지 않는다
    query: { match: { title: { query: q } } },
  });

  const ids = hits.hits.hits.map((h) => h._id);
  if (ids.length === 0) return [];

  const rows = await db.post.findMany({ where: { id: { in: ids } } });

  // IN 조회 결과는 검색 점수 순서가 아니다. 반드시 다시 정렬한다
  const byId = new Map(rows.map((r) => [r.id, r]));
  return ids.map((id) => byId.get(id)).filter((r) => r !== undefined);
}
```

마지막 재정렬을 빠뜨리는 실수가 잦습니다. 검색 품질을 아무리 다듬어도 DB가 돌려준 순서로 화면에 뿌리면 관련도 순서가 사라집니다.

`_source: false`로 본문을 받지 않으면 응답 크기도 줄어듭니다. 색인에는 검색에 필요한 필드만 두고 나머지는 DB에 맡기는 구성과 잘 맞습니다.

**부모-자식 관계를 엔진 기능으로 표현한다.** 갱신 전파는 사라지지만 질의 비용과 복잡도가 올라갑니다. 앞의 두 방법으로 안 되는 경우에만 꺼내는 편이 낫습니다.

## 늦게 도착한 옛 값이 새 값을 덮는다

워커가 두 대 이상이거나 재시도가 걸려 있으면, 같은 문서의 갱신이 역순으로 도착할 수 있습니다.
색인은 마지막에 쓴 쪽이 이기므로, 늦게 도착한 옛 문서가 새 문서를 덮습니다.

막는 방법은 **문서마다 단조 증가하는 버전을 들려 보내는 것**입니다. 엔진이 들고 있는 버전보다 작으면 색인을 거부합니다.

```typescript
// revision 을 외부 버전으로 넘긴다. 작은 버전은 엔진이 거부한다
const body = docs.flatMap((d) => [
  {
    index: {
      _index: "posts-search",
      _id: d.id,
      version: d.revision,
      version_type: "external",
    },
  },
  d.source,
]);

const res = await search.bulk({ refresh: false, operations: body });
```

버전으로 쓸 값은 DB가 이미 갖고 있는 경우가 많습니다. 행마다 올라가는 리비전 컬럼이 가장 깔끔하고, 없다면 `updated_at`의 epoch 밀리초도 쓸 수 있습니다.

> `updated_at`을 버전으로 쓸 때는 **같은 밀리초에 두 번 바뀌는 경우**를 생각해야 합니다. 두 번째 갱신이 "버전이 더 크지 않다"는 이유로 거부되고, 그게 영구적인 어긋남으로 남습니다.
> 배치가 같은 행을 연달아 수정하는 경로가 있다면 리비전 컬럼을 두는 쪽이 안전합니다.

> 외부 버전은 문서를 통째로 쓰는 색인·삭제에 쓰는 장치입니다. 부분 갱신 API와의 조합은 엔진과 버전에 따라 제약이 있으니,
> 부분 갱신이 필요하면 읽은 시점의 시퀀스 번호를 조건으로 거는 방식(`if_seq_no` / `if_primary_term`)을 쓰는 버전의 공식 문서에서 확인하세요.

버전을 켜면 **버전 충돌이 정상 응답이 됩니다.** 더 새로운 문서가 이미 있다는 뜻이므로, 이 실패는 재시도하면 안 되고 그냥 넘겨야 합니다.
이 구분을 안 해두면 충돌이 재시도 폭풍으로 번집니다.

## 벌크 색인은 200을 주고도 실패한다

벌크 API는 항목을 독립적으로 처리합니다. 일부가 실패해도 **HTTP 상태는 200**이고, 실패는 응답 본문의 항목별 결과에 들어 있습니다.

```typescript
type Outcome =
  | { kind: "ok" }
  | { kind: "retry"; id: string }      // 일시적 — 백오프 후 재시도
  | { kind: "skip";  id: string }      // 더 새 버전이 있다 — 정상
  | { kind: "dead";  id: string; reason: string };  // 재시도해도 같다

function classify(items: BulkItem[]): Outcome[] {
  return items.map((item) => {
    const op = item.index ?? item.delete ?? item.update;
    if (!op?.error) return { kind: "ok" };

    const { type } = op.error;
    if (type === "version_conflict_engine_exception") {
      return { kind: "skip", id: op._id };
    }
    // 큐 포화·일시적 거절 계열
    if (op.status === 429 || type === "es_rejected_execution_exception") {
      return { kind: "retry", id: op._id };
    }
    // 매핑 불일치·파싱 실패 — 같은 입력이면 영원히 실패한다
    return { kind: "dead", id: op._id, reason: type };
  });
}
```

세 갈래로 나누는 게 핵심입니다. 전부 재시도하면 매핑 오류 하나가 큐를 영원히 막고, 전부 버리면 일시적 거절에 문서가 사라집니다.

`dead`는 따로 모아둬야 합니다. 로그로만 흘리면 "검색이 안 되는 문서"가 몇 건인지 아무도 모르는 상태가 됩니다.
[DLQ](/blog/sqs-consumer-visibility-timeout-dlq/)로 보내고, 그 적재량을 지표로 띄워두세요. 어긋남은 **눈에 보이지 않으면 영원히 남습니다.**

재시도 간격은 백오프로 벌리고 총 예산을 둡니다. 색인 거절은 대개 엔진이 이미 벅찬 상태라는 신호라서, 즉시 재시도는 상황을 악화시킵니다([재시도 증폭](/blog/retry-timeout-budget-circuit-breaker/)).

벌크 요청에 `refresh: "wait_for"`를 붙이면 색인 직후 검색에 보이도록 기다릴 수 있습니다. 편하지만 **동기화 워커에서는 쓰지 마세요.**
갱신을 강제로 유발해 처리량을 크게 떨어뜨립니다. 저장 직후 결과를 바로 보여줘야 하는 화면이 있다면, 그 한 경로에서만 쓰거나 화면에서 DB 값을 먼저 보여주는 쪽으로 푸는 게 낫습니다.

## 매핑은 나중에 바꿀 수 없다

필드를 추가하는 건 됩니다. 하지만 **기존 필드의 타입이나 분석기를 바꾸는 건 기존 인덱스에서 안 됩니다.**
한국어 분석기 설정을 손보거나, 문자열로 넣었던 필드를 숫자로 바꾸려면 **인덱스를 새로 만들어 다시 채우는 수밖에 없습니다.**

그래서 처음부터 해둘 일이 하나 있습니다. **애플리케이션이 인덱스 이름을 알지 못하게 하는 것**입니다.

```bash
# 코드는 posts-search 만 안다. 실체는 posts-v1
curl -X PUT "$ES/posts-v1" -H 'Content-Type: application/json' -d '{
  "settings": { "number_of_shards": 1, "number_of_replicas": 1 },
  "mappings": { "properties": {
    "title":      { "type": "text" },
    "brand_id":   { "type": "keyword" },
    "updated_at": { "type": "date" }
  }}
}'

curl -X POST "$ES/_aliases" -H 'Content-Type: application/json' -d '{
  "actions": [{ "add": { "index": "posts-v1", "alias": "posts-search" } }]
}'
```

이걸 안 해두면 재색인이 **배포 작업**이 됩니다. 인덱스 이름이 코드에 박혀 있으니 전환하려면 코드를 고쳐 내보내야 하고, 그 배포와 색인 완료 시점을 맞춰야 합니다.
alias 하나를 끼워두면 전환이 운영 작업으로 내려옵니다.

## 무중단 재색인 절차

새 매핑으로 인덱스를 만들고, 채우고, alias를 옮깁니다.

채우는 동안에는 색인 쪽 설정을 잠시 느슨하게 둡니다.

```bash
# 채우기 전: 갱신 주기와 복제본을 끈다
curl -X PUT "$ES/posts-v2/_settings" -H 'Content-Type: application/json' -d '{
  "index": { "refresh_interval": "-1", "number_of_replicas": 0 }
}'
```

> `refresh_interval`을 `-1`로 두는 동안 새로 넣은 문서는 **검색에 보이지 않습니다.**
> 운영 중인 인덱스에 이 설정을 걸면 그 자체로 장애입니다. 채우는 중인 새 인덱스에만 쓰세요.

다 채웠으면 설정을 되돌리고 갱신을 한 번 명시적으로 호출합니다. 이걸 빼먹고 alias를 옮기면 **문서는 다 들어 있는데 검색 결과가 비는** 상태가 됩니다.

```bash
curl -X PUT "$ES/posts-v2/_settings" -H 'Content-Type: application/json' -d '{
  "index": { "refresh_interval": "1s", "number_of_replicas": 1 }
}'
curl -X POST "$ES/posts-v2/_refresh"

# 건수와 표본 질의를 먼저 확인한다
curl -s "$ES/posts-v1/_count"; curl -s "$ES/posts-v2/_count"
```

전환은 한 번의 요청으로 합니다. alias 조작은 원자적이라, 그 사이에 alias가 양쪽을 가리키거나 아무것도 가리키지 않는 순간이 없습니다.

```bash
curl -X POST "$ES/_aliases" -H 'Content-Type: application/json' -d '{
  "actions": [
    { "remove": { "index": "posts-v1", "alias": "posts-search" } },
    { "add":    { "index": "posts-v2", "alias": "posts-search" } }
  ]
}'
```

구버전 인덱스는 바로 지우지 않습니다. 되돌릴 수단이기 때문입니다.
문제가 보이면 같은 요청을 반대로 한 번 보내면 끝나고, 그게 이 구조로 얻는 가장 큰 이득입니다. [RDS Blue/Green](/blog/rds-blue-green-upgrade/)에서 블루를 남겨두는 것과 같은 이야기입니다.

### 재색인하는 동안 들어온 변경

여기가 실제로 빠뜨리기 쉬운 지점입니다. 인덱스 간 복사든 DB 전체 조회든, 채우기는 **시작 시점의 상태**를 옮깁니다.
채우는 동안 들어온 변경은 새 인덱스에 없고, alias를 옮기는 순간 그 변경들이 함께 사라진 것처럼 보입니다.

세 가지 방법이 있습니다.

**동기화 파이프라인을 두 인덱스에 모두 흘린다.** 워커가 새 문서를 두 인덱스에 쓰도록 하고, 읽기 alias만 전환합니다.
가장 깔끔하지만 워커에 "지금 전환 중"이라는 상태가 들어갑니다. 전환이 끝나면 반드시 되돌려야 하고, 그 정리를 잊으면 삭제한 인덱스로 색인하다 실패가 쌓입니다.

**전환 후에 델타만 보정한다.** 채우기 시작 시각을 기록해두고, 전환 뒤 `updated_at`이 그 이후인 행을 다시 색인합니다.

```sql
SELECT id, revision FROM posts
WHERE updated_at >= :reindex_started_at
ORDER BY updated_at;
```

경계는 넉넉하게 잡습니다. 시작 시각보다 조금 앞에서부터 다시 긁어도 손해가 없습니다.
**외부 버전을 쓰고 있으면 이미 최신인 문서는 알아서 거부되기 때문**입니다. 앞 절에서 버전을 붙여둔 투자가 여기서 회수됩니다.

**쓰기 alias 기능을 쓴다.** alias가 여러 인덱스를 가리킬 때 어느 쪽이 쓰기 대상인지 지정하는 설정이 있습니다.
다만 alias가 여러 인덱스를 가리키는 상태에서의 쓰기 동작은 제약이 있으니, 쓰는 엔진의 공식 문서에서 확인하고 스테이징에서 한 번 돌려보세요.

어느 쪽을 고르든 **재색인은 멱등해야** 합니다. 같은 문서를 두 번 색인해도 결과가 같고, 중간에 끊겨도 처음부터 다시 돌리면 되는 상태여야 경계 계산이 틀려도 복구가 됩니다.

## 정리

- DB와 검색 엔진이 둘이 되는 순간 어긋남은 **없앨 수 없고 관리할 수만** 있다. 지연·누락·역전은 원인이 달라서 해법도 다르다.
- 두 저장소에 동시에 쓰는 건 순서를 바꿔도 안전해지지 않는다. 누락을 없애려면 쓰기 기록을 **같은 트랜잭션에** 남겨야 한다.
- 아웃박스에는 문서 본문이 아니라 **식별자와 리비전만** 적는다. 조립은 워커 한 곳에서 하고, 연달아 온 변경은 최신 한 번으로 합친다.
- CDC는 모든 변경을 잡지만 문서 조립을 어렵게 만든다. **트리거로만 쓰고 조립은 한 곳에 모으는** 타협이 실용적이다.
- 역정규화는 갱신을 전파시킨다. **검색·필터·정렬에 쓰지 않는 필드는 문서에 넣지 말고** DB에서 보강한다. 이때 검색 점수 순서를 다시 적용하는 걸 잊지 말 것.
- 문서마다 단조 증가 버전을 들려 보내 역전을 막는다. 그러면 **버전 충돌은 정상 응답**이 되고, 재색인이 멱등해진다.
- 벌크는 200을 주고도 실패한다. 항목별 실패를 **재시도 / 무시 / DLQ** 세 갈래로 나누고, DLQ 적재량을 지표로 본다.
- 매핑은 바꿀 수 없으니 처음부터 alias를 통해서만 접근한다. 그래야 재색인이 배포가 아니라 운영 작업이 된다.
- 재색인은 시작 시점의 스냅샷이다. **채우는 동안의 변경을 메우는 계획 없이 alias를 옮기면 안 된다.**
